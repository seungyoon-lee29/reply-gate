# 보안 정책

## 보호 대상과 위협 모델

이 시스템에는 **인증이 없다** — 단일 개발자 데모이고 실사용자가 없다. 그래서 보안의 축은
"누가 접근하는가"가 아니라 **"LLM 이 만든 문자열이 무엇을 할 수 있는가"** 다.

보호 대상은 셋뿐이다.

1. **합성 주문 데이터** — 특히 다른 고객의 연락처·이메일·배송지. 문의자가 자기 주문에 대해
   물었을 때 남의 데이터가 답변에 실리면 안 된다.
2. **외부 API 키와 DB 접속 정보** — 저장소에 평문으로 남으면 안 된다.
3. **DB 쓰기 권한** — text-to-SQL 경로가 절대 도달하면 안 되는 곳.

주된 공격면은 **문의 본문**이다. 문의 내용이 SQL 생성 프롬프트에 그대로 들어가므로,
프롬프트 인젝션이 곧 데이터 접근 시도가 된다.

L2 판정이 붙으면서 주입 표면이 하나 더 생겼다: **문의 본문 → 초안 claim → 판정 프롬프트**.
다만 이 경로의 **실패 방향은 권한 상승이 아니라 L2 무력화**다 — 판정을 속여도 얻는 것은
"기각되지 않는 것"뿐이고, 그건 L2 를 끈 사이클 1 수준으로의 회귀다. 판정 결과는 조회·권한·
루프 종료에 아무 영향이 없고(코드가 통제), 해석되지 않는 판정 산출은 통과가 아니라 거부다.

## text-to-SQL 안전장치 — 3층

LLM 이 만든 SQL 문자열은 **아무것도 신뢰하지 않는다.** 세 층이 각각 독립적으로 막는다.

### 1층 — read-only 계정

`reply_gate_ro` 계정은 `orders` 테이블에 **SELECT 권한만** 있다. 그 밖의 **업무 테이블**에는
권한이 없다 — 처리 기록(`inquiries`, `inquiry_attempts`, `inquiry_evidence`,
`inquiry_sql_failures`)과 `policy_chunks` 는 이 계정에서 `permission denied` 다.

**시스템 카탈로그는 예외이고, 이 층이 막지 못한다.** `pg_catalog` 은 PostgreSQL 이 PUBLIC 에
SELECT 를 주므로 `reply_gate_ro` 로도 `SELECT count(*) FROM pg_class` 가 돈다(실측했다).
카탈로그 참조 타입 변환(`cast('inquiries' AS regclass)`)도 같은 이유로 실행되어, 화이트리스트
밖 테이블의 **이름과 존재 여부**를 돌려준다. 그래서 이 두 경로를 막는 것은 권한이 아니라
2층·3층이다 — 카탈로그 테이블 참조는 스키마 화이트리스트가, 카탈로그 참조 타입 변환은
**형변환 대상 타입 허용 목록이 단독으로** 막는다. 권한을 조정해 닫을 수 있는 경로가 아니라는
것이 이 서술의 요점이다(`REVOKE ... FROM PUBLIC` 은 psql 메타명령과 드라이버 내부 조회까지
함께 깬다). 검증은 `tests/test_db_readonly.py`(업무 테이블 거부)와
`tests/test_sql_cast_allowlist.py`(카탈로그 참조 타입이 읽히는 것과 가드가 거부하는 것)에 있다.

`INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`/`CREATE`/`DROP`/`ALTER` 는 전부 `InsufficientPrivilege` 다.
권한을 넓히려면 `db/schema.sql` 의 `GRANT SELECT ... TO reply_gate_readers` 를 고쳐야 하고,
그 결정을 못박은 테스트가 함께 깨지도록 되어 있다.

이 계정에는 `statement_timeout` 이 접속 옵션(`-c statement_timeout=`)으로 걸려 있다.
`SET` 문이 아니라 접속 옵션인 이유는 `RESET ALL` 이나 롤백으로 되돌지 않게 하기 위해서다.

### 2층 — 스키마 화이트리스트

조회 가능한 테이블·컬럼 목록이 코드에 명시돼 있고, **실행 전에** AST 를 훑어 화이트리스트
밖 참조를 거부한다. 다음 우회 경로가 모두 닫혀 있다:

- CTE·서브쿼리·JOIN 안에 숨긴 화이트리스트 밖 테이블
- 시스템 컬럼(`ctid`, `xmin`, `xmax`, `tableoid`)
- **별칭을 통한 우회** — `SELECT 1 AS ctid, ctid FROM orders` 처럼 별칭으로 컬럼 검사를
  무력화하는 형태. 별칭은 화이트리스트 구성원이 아니고, 이름으로 쓸 수 있는 자리는
  `ORDER BY`/`GROUP BY` 로 한정된다(`HAVING` 은 제외 — Postgres 가 거기서 맨 이름을
  **입력 컬럼**으로 해석하므로 허용하면 우회가 되살아난다)
- `pg_catalog`·`information_schema`·크로스 데이터베이스 참조
- FROM 절의 테이블 함수(`generate_series`, `dblink`), `VALUES`, `LATERAL`
- **소스 별칭 중복** — 뒤 소스가 기저 테이블을 덮어써 검사가 통째로 스킵되던 경로

검증기가 **해석하지 못한 구문은 통과가 아니라 거부**다(fail-closed). 새 SQL 문법을 허용하려면
스코프 해석에 명시적으로 추가해야 한다.

### 3층 — 쿼리 검증

- SELECT 단일문만. DML/DDL/다중문/주석 우회(`--`, `/* */`, 중첩) 거부.
- **행 잠금 절**(`FOR UPDATE`/`FOR SHARE`/`FOR NO KEY UPDATE`/`FOR KEY SHARE`) 거부 —
  읽기 전용 SELECT 가 아니다.
- **외부 조인(LEFT/RIGHT/FULL) 거부** — 외부 조인의 ON 절은 보존측 테이블을 거르지 않아
  "주문 1건 한정"을 무력화한다. 조인 한 줄로 상한만큼의 타 고객 행이 딸려오는 경로였다.
- **주문 범위 강제** — 실행되는 쿼리가 **존재성 선검사를 통과한 그 주문 1건**으로 묶여
  있는지 AST 로 확인한다. `order_no` 동등 비교가 있어야 하고, 리터럴이 선검사된 값과
  일치해야 하며, `OR`/`IN` 다중값/부질의로 우회할 수 없다. 바인딩으로 인정하는 자리는
  WHERE 절과 INNER/CROSS 조인의 ON 절뿐이다.
- **함수 허용 목록** — 조회에 필요한 것만(집계·문자열·날짜 포맷·`CASE`·캐스트). `pg_sleep`,
  `random`, `pg_read_file`, `current_setting` 등은 거부한다. `orders` 를 끼워 넣으면 함수
  호출로 워커를 몇 분씩 묶을 수 있었던 경로다.
- **형변환 대상 타입 허용 목록** — 캐스트가 허용 함수이므로 **대상 타입도 함께 판정한다.**
  허용 범위는 SQL 생성 안내가 광고하는 용도(숫자·일자·문자열)에 맞추고, 목록 밖 타입은
  거부다(fail-closed). 시스템 카탈로그 참조 타입(`regclass`·`regtype`·`regproc`·`oid`)이
  화이트리스트 밖 테이블의 이름과 존재 여부를 결과 컬럼으로 실어 나르던 경로이고,
  1층이 막지 못하므로(위 "시스템 카탈로그는 예외이고") **막는 층이 이것 하나뿐이다.**

  **허용 타입 13종을 여기에 이름으로 적는다** — 문자열 `text`·`varchar`·`char`, 숫자
  `int`·`bigint`·`smallint`·`numeric`·`real`·`double precision`, 일자
  `date`·`timestamp`·`timestamptz`·`time`. 적어 두는 이유는 **구현이 정한 목록으로 구현을
  검증하는 자기참조를 끊기 위해서다**: 목록이 코드에만 있으면 "허용 목록의 모든 타입이
  통과한다"는 검사가 무엇을 통과시켜야 하는지를 구현이 스스로 정한다. 문서와 코드가 갈리면
  `tests/test_sql_cast_allowlist.py` 가 RED 를 낸다.

  목록의 **정의**는 여전히 가드가 단독 소유하고 SQL 생성 안내가 같은 문면을 싣는다 — 갈리면
  생성기가 목록 밖 타입을 쓸 때마다 거부 → 재시도 1회 → 인계가 되고, 그 인계가 평가 수치에
  남는다. 이 문서는 **사람이 소유한 두 번째 사본**이고, 넓히려면 여기와 가드를 함께 고쳐야
  한다(한쪽만 고치면 검사가 막는다).
- **PII allowlist 출력 provenance** — 최상위 직접 상수 projection 은 거부한다. 그 밖의 계산
  표현식은 정상 조회를 깨지 않도록 실행을 허용하되, 결과 출력명을 PII allowlist 출처로
  승인하지 않는다. 승인되는 것은 가드가 **유래를 `orders` 직접 컬럼까지 따라가 증명한**
  출력명뿐이다 — 직접 컬럼, 임시 테이블(CTE)·파생 테이블을 거친 직접 컬럼, 그리고 고정값이
  패턴형 PII 가 **아닐 때만** 빈칸 채우기 관용구(`coalesce`·`nullif`)다. 값을 이어 붙이는
  계열은 조각을 합쳐 번호를 만들 수 있으므로 고정값이 들어갈 자리를 두지 않는다. 새 SQL
  표현식을 해석하지 못하면 자동으로 불승인이므로 fail-closed 다. "패턴형 PII 인가"의 정의는
  L1 게이트가 단독 소유하고 가드가 가져다 쓴다(`gate.pii_shaped`) — 층마다 자기 정규식을
  두면 한쪽만 넓혀져 기준이 갈린다. dict 결과에서 계산값이 직접 컬럼 provenance 를 덮지
  못하도록 별표 확장 뒤 중복되는 출력명도 거부한다.
- **결과 행 수 상한** — LIMIT 이 없으면 붙이고, 상한을 넘으면 낮춘다. 정수 리터럴이 아닌
  LIMIT 만 거부한다. **실행되는 것은 모델의 원문이 아니라 검증된 AST 를 다시 렌더링한 문자열**이라,
  파서와 실행기가 다른 문장을 보는 부류의 우회가 구조적으로 닫힌다.

거부는 전부 **사유 코드 + 재시도가 고칠 수 있는 안내 문구**로 돌아가 SQL 생성 1회 재시도의
피드백이 된다. 재시도까지 실패하면 `sql_failed` 인계다.

## PII 취급

- **탐지 대상**: 초안의 답변 텍스트에 있는 패턴형 PII. 검사 대상에 `citation_ids` 는 넣지 않는다.
- **허용 기준**: 이번 문의의 수집 근거 원문에 같은 값이 있으면 허용. SQL 근거의 실행 SQL은
  표시용 `content` 에만 둔다. 비PII 계산값은 L2용 `evidence_text` 에 유지하지만 계산된 PII는
  제외하고, **유래가 `orders` 직접 컬럼으로 증명된 출력**만 PII 출처로 승인한다(위
  "PII allowlist 출력 provenance", `docs/business-rules.md` "PII 출처는 유래로 승인한다").
  없으면 기각.
- **마스킹하지 않는다**: 승인된 출력(`evidence_text`)의 연락처·이메일은 **원문 그대로** 담는다.
  요약하거나 가리면 정상 에코가 근거와 대조되지 않아 오기각된다.
- **커버리지 한계**: 이름·주소 등 비패턴형은 검사하지 않는다. 이 한계를 축소해 말하지 않는 것이
  이 프로젝트의 서술 원칙이다.

## 데이터가 나가는 곳 — 판정 프롬프트

L2 판정 프롬프트에는 **근거 원문(`evidence_text`)이 그대로 실린다.** SQL 근거의 원문은
마스킹하지 않으므로(위 "마스킹하지 않는다"), 합성 고객의 연락처·이메일·배송지가 판정
요청에 포함되어 **Anthropic 으로 전송될 수 있다.**

**전 데이터가 합성이므로 허용한다.** `db/fixtures/orders.jsonl` 은 저장소에 커밋된 생성
데이터이고 실제 개인의 정보가 아니다. 실사용자가 없다는 것이 이 결정의 전제다.

**실운영 전환 시 재결정 사안**(아래 "이 사이클에서 다루지 않는 것"과 같은 등급):

- 판정 프롬프트로 나가는 근거 원문의 범위 — 전송 전 마스킹은 PII allowlist 대조를
  깨뜨리므로 마스킹이 아니라 **판정 입력 자체를 다시 설계**해야 한다.
- 판정 provider 의 데이터 보존·학습 정책 확인과 계약.
- 근거를 외부로 보내지 않는 판정 방식(온프레미스 모델 등)과의 비용·정확도 대조.

## 비밀 관리

- API 키는 **둘**이다 — `OPENAI_API_KEY`(생성·임베딩)와 `ANTHROPIC_API_KEY`(L2 판정).
  DB 비밀번호와 함께 **환경 변수 또는 `.env` 에만** 존재한다. `.env` 는 gitignore 되고
  `.env.example` 에는 키 이름만 있다.
- 코드·문서·`docker-compose.yml`·권한 목록 어디에도 자격 증명 원문을 두지 않는다.
- 오류 메시지와 로그에 접속 정보를 실을 때 비밀번호를 제외한다(`db.describe_target`).
- 컨테이너 초기화 스크립트는 superuser 비밀번호를 명령 태그만 출력하는 방식으로 다룬다.
- 키가 없으면 `POST /inquiries` 는 **503 설정 오류**로 끝난다 — `llm_call_failed` 인계로
  집계하지 않는다. 설정 문제를 업무 판정에 섞으면 지표가 오염된다. **L2 가 켜져 있는데
  판정 키가 없는 것도 같은 503** 이고, 그 선검사는 생성 토큰을 태우기 전에 돈다.

### 설정 객체가 자격 증명을 흘리는 경로 — 표시와 덤프는 다른 경로다

자격 증명 네 종(`openai_api_key`·`anthropic_api_key`·`postgres_app_password`·
`postgres_ro_password`)은 **비밀 전용 타입**(`pydantic.SecretStr`)이고 그 위에 표시 억제
(`Field(repr=False)`)가 겹쳐 있다. 두 겹인 것은 **닫는 경로가 다르기 때문**이다.

| 경로 | 예 | 무엇이 닫는가 |
|---|---|---|
| **표시** | `repr(settings)` · `str(settings)` · f-string · 예외 트레이스백 · 실패한 단언의 pytest 출력 | `Field(repr=False)` (필드가 아예 안 실린다) |
| **덤프** | `settings.model_dump()` · `model_dump(mode="json")` · `model_dump_json()` · `dict(settings)` · `list(settings)` · `vars(settings)` · `settings.__dict__` · 이들을 중첩한 컨테이너의 `repr` | `SecretStr` (마스킹 문자열로 나간다) |

표시만 가렸을 때 **덤프 경로 전체가 열려 있었다** — 덤프는 표시 설정을 아예 보지 않는다.
실행 경로에서 부르는 곳은 없었지만, 사고가 났던 자리(pytest 실패 출력)와 같은 계열이다.
`tests/test_config_secrets.py` 가 이름이 비밀로 읽히는 필드를 **전수로** 훑어 위 표의
경로 전부에서 카나리아가 나오지 않는지 검사하고, 훑기 자체가 빈 검사가 아님을 같은 파일의
음성 대조가 증명한다.

**닫힌 것과 닫히지 않은 것을 갈라 적는다.**

- **닫혔다**: 위 표의 표시·덤프 경로.
- **닫혔다 (2026-08-25)**: `settings.database_url`·`readonly_database_url`.
  조립된 접속 문자열은 비밀번호를 **담을 수밖에 없다** — 담지 않으면 DB 에 접속할 수 없다.
  그러나 담는 것과 **평문 `str` 로 내놓는 것은 다른 문제**이고, 예전에는 뒤엣것까지 열려
  있어 이 속성을 로그·오류·설정 덤프에 그대로 실으면 비밀번호가 따라갔다. 조립 결과를
  `SecretStr` 로 감싸 표시·덤프를 필드와 같은 자격으로 닫았다. 로그·오류용 설명은 여전히
  비밀번호 없는 별도 문자열이다(`db.describe_target`).
  **닫는 순서가 규칙이었다** — 결정 0023 이 "실제로 새는지 재현하는 것이 먼저"라고 조건을
  걸었고, 사이클 5 감사가 카나리아로 그 재현을 마친 뒤에 닫았다.
- **닫히지 않았다 — 어떤 설정 클래스도 못 막는다**: `print(key.get_secret_value())` 처럼
  값을 직접 꺼내 찍는 것. 그건 리뷰가 막는다.
- **닫히지 않았다 — 가드가 그 뒤에 선다**: 에이전트 세션 기록. `.env` 를 한 번 읽히면
  그 기록이 사는 동안 평문으로 남는다. 값이 필요하면 `bool(settings.<필드>)` 로 존재만
  확인한다.

**값이 필요한 곳은 명시적으로 꺼낸다.** `.get_secret_value()` 를 부르는 자리는 애플리케이션
패키지 전체에서 **세 모듈 여섯 줄**이다 — `config.py` 2회(접속 문자열에 넣을 비밀번호),
`db.py` 1회(조립된 DSN 을 psycopg 에 넘기기 직전), `llm.py` 3회(SDK 생성자 인자).
꺼내는 자리가 코드에 드러나야 어디서 평문이 되는지 셀 수 있고, 그 수가 늘지 않는 것을 구조
검사가 지킨다. **접속 문자열을 감싸면서 자리가 하나 늘었다** — 그 대가로 평문이 되는 지점이
"속성을 읽는 모든 곳"에서 **한 줄**로 좁아졌다.

**노출을 고쳤다고 로테이션을 건너뛰지 않는다.** 타입을 바꾸는 것은 **다음 노출**을 막을
뿐 이미 새어 나간 값을 무효로 만들지 않는다.

## 감사

처리 기록이 감사 대상이다. 문의 1건마다 다음이 남는다:

- 시도별 **종합 판정 + 층별 판정**(L1·L2)과 기각 사유 목록
- L2 의 **claim 단위 판정**과 **근거쌍 모순** 기록 (미실행이면 전부 NULL — 빈 배열이 아니다)
- 채택된 SQL 근거의 **쿼리문과 결과 행 전체** 스냅샷
- 거부·실패한 쿼리의 쿼리문과 오류(근거 ID 없이)
- 지연, 생성 토큰, **판정 토큰**, 임베딩 토큰, **검색 계열 토큰**
  (`retrieval_input_tokens`·`retrieval_output_tokens` — 질의 재작성 호출의 실비용이고
  생성 계열과 분리해 센다)
- 검색 단계 **폴백 사유**(`retrieval_fallback_reason`) — 폴백은 인계가 아니지만 조용히
  지나가지도 않는다
- 초안 전 인계라도 그 시점까지 수집된 근거

이 스냅샷 위에 재현·감사·의미 검증이 모두 선다.

## 이 프로젝트가 다루지 않는 것

인증·인가·레이트 리밋·감사 로그 보존 정책·전송 구간 암호화. 실사용자와 실운영이 없어
**프로젝트 범위 밖으로** 의도적으로 두었다(어느 한 사이클의 유예가 아니다 —
`docs/problem.md` "범위"). 실운영에 올릴 때는 위 전부가 새 결정 사항이 된다.
