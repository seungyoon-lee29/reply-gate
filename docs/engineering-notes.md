# 엔지니어링 노트

코드를 읽어도 알 수 없고, 모르면 걸리는 것들.

## SQL 가드에서 실제로 뚫렸던 경로

세 번 뚫렸고 세 번 다 "막았다"가 아니라 **실제로 넣어봐서** 확인했다. 가드를 손볼 때는
같은 방식으로 확인하라 — 코드를 읽어서 안전하다고 판단하는 것으로는 부족했다.

### 1. 주문 범위가 프롬프트에만 있었다

**증상**: `SELECT order_no, customer_name, customer_phone, customer_email FROM orders LIMIT 3`
이 가드를 통과하고 실행됐다. 결과 행이 근거가 되고, L1 의 PII allowlist 가 **그 근거로부터**
만들어지므로 무관한 고객 50명(= 행 수 상한)의 연락처가 답변에 실려도 기각되지 않았다.

**원인**: "주어진 주문번호 1건만 조회한다"가 SQL 생성 프롬프트 문구로만 있었고 검증기는
`order_no` 를 받지도 않았다. 어떤 행이 나올지를 LLM 이 정하는 상태였다.

**대응**: 검증 단계에서 AST 를 훑어 `order_no` 동등 비교가 선검사된 값과 일치하는지 확인한다.
프롬프트에도 규칙을 넣되, **프롬프트는 재시도 예산을 아끼는 장치이지 안전장치가 아니다.**

### 2. 별칭이 컬럼 화이트리스트를 무력화했다

**증상**: `SELECT ctid FROM orders` 는 거부되는데
`SELECT 1 AS ctid, ctid, order_no FROM orders` 는 통과하고 실제로 `ctid` 값을 돌려줬다.
`SELECT o.ctid FROM orders AS o(ctid)` 도 같았다.

**원인**: 쿼리 어디서든 등장한 별칭 이름을 전역 허용 컬럼 집합에 더하고 있었다.

**대응**: 별칭은 화이트리스트 구성원이 아니다. 맨 이름 별칭을 받아들이는 자리는
`ORDER BY`/`GROUP BY` 로 한정한다. **`HAVING` 은 제외한다** — Postgres 는 `HAVING` 에서
맨 이름을 *입력 컬럼*으로 해석하므로 거기서 별칭을 받으면 우회가 그대로 되살아난다.

### 3. 외부 조인이 주문 1건 한정을 통째로 무력화했다 (가장 치명적)

**증상**: 1번을 고친 뒤에도 이 한 줄로 다시 50건이 샜다.

```sql
SELECT o.* FROM orders o LEFT JOIN (SELECT 1 AS x) d ON o.order_no = 'ORD-...'
```

`INNER JOIN` 으로 바꾼 대조군은 정확히 1행이 나온다.

**원인**: 검증기가 WHERE 절과 **모든 JOIN 의 ON 조건**을 한 통에 모아 바인딩으로 인정했는데,
**외부 조인의 ON 절은 보존측 테이블을 필터하지 않는다.** 조인 종류를 코드가 한 번도 읽지 않았다.

**대응**: 두 겹. (a) 외부 조인(LEFT/RIGHT/FULL)을 통째로 거부한다 — 주문 1건 조회에 외부 조인이
필요한 정당한 사례가 없고, 현실 CS 쿼리 30건 검증에서도 0건이었다. (b) 바인딩으로 인정하는
자리를 WHERE 절과 INNER/CROSS 조인의 ON 절로 한정한다. 나중에 외부 조인을 허용하게 되더라도
(b) 가 있어야 조용히 새지 않는다.

**교훈**: 조인 종류를 무시한 검증기는 "조건이 있다"와 "행이 걸러진다"를 같은 것으로 착각한다.

## L1 PII 오탐 — 근거 ID 가 검사 대상이었다

**증상**: PII 가 전혀 없는 정상 초안이 `pii_detected` 로 2회 연속 기각되어 `rejected_twice`
인계됐다. 재생성도 반드시 같이 실패했다.

**원인**: PII 검사가 원시 초안 전체를 재귀로 훑어 `citation_ids` 문자열까지 포함했다.
SQL 근거 ID 는 `sql:<문의 UUID>:<순번>` 이라 UUID 의 16진 숫자 구간이 일반전화 정규식
(`0[2-9][0-9]?[-. ]?[0-9]{3,4}[-. ]?[0-9]{4}`)에 걸린다. 근거 ID 는 `evidence_text` 에 없으니
allowlist 에도 오르지 않아 "근거에 없는 PII"가 된다. 같은 문의 ID 를 두 시도가 공유하므로
재생성이 구제할 수 없다.

**발생률**: 무작위 UUID 20,000개 중 168개(**0.84%**). SQL 근거를 인용하는 문의의 그만큼이
무조건 오기각된다.

**대응**: PII 검사 대상에서 `citation_ids` 를 제외한다. 참조 무결성은 `invalid_citation` 이
전담하므로 PII 검사가 근거 ID 를 볼 이유가 없다. 무작위 문의 ID 2,000건 무오탐 회귀 테스트로 고정.

**왜 중요한가**: 이 프로젝트의 헤드라인 지표가 "정상 초안 오탐률"이다. 오탐 버그는 곧 지표 오염이다.

## 같은 오탐이 한 겹 남아 있었다 — 답변에 실리지 않는 키

`citation_ids` 만 제외한 것은 **증상 하나를 지운 것이지 원인을 지운 것이 아니었다.** 검사는
여전히 원시 초안 전체를 훑었고, 그래서 `{"claims": [...정상...], "debug": "1588-1234"}` 처럼
스키마 밖 키에 값이 들어오면 정상 초안이 `pii_detected` 로 기각됐다. claim 안의 추가 키
(`note`)도 같다. `to_draft` 가 살리는 것은 claim 의 `text` 뿐이라 **그 값들은 답변에 아예
실리지 않는다** — 답변에 없는 값으로 답변을 기각한 것이다. 초안 JSON 은 LLM 산출이라
스키마 밖 키는 프롬프트가 바뀔 때마다 다시 생길 수 있어, 키 이름을 하나씩 빼는 방식으로는
끝나지 않는다.

**대응**: 제외 목록 대신 **포함 기준**으로 뒤집었다. PII 검사 대상 = `to_draft` 가 답변으로
내보내는 텍스트(= claim 의 `text`). 답변 후보 텍스트를 하나도 식별할 수 없을 때(원문 문자열이
통째로 넘어온 경우)만 초안 전체를 긁는 폴백으로 남긴다 — 그런 초안은 어차피
`schema_violation` 이라 답변이 나가지 않고, 게이트는 모르는 쪽에서 검사하는 방향으로 간다.
구조가 깨진 claim 옆의 멀쩡한 claim 은 여전히 답변 후보이므로 계속 검사한다.

**교훈**: 검사 범위를 "무엇을 뺄까"로 정의하면 새 키가 생길 때마다 오탐이 돌아온다.
"무엇이 실제로 사용자에게 나가는가"로 정의하면 그 목록은 코드가 이미 알고 있다.

## 실행 SQL 원문은 PII allowlist 근거가 아니다

**증상**: `SELECT status FROM orders WHERE order_no = '<선검사 주문>' AND
'010-9999-9999' <> ''`가 통과하면 결과 행에는 연락처가 없는데도, 실행 SQL 을 함께 넣은
`evidence_text` 때문에 초안의 `010-9999-9999`가 근거 유래로 인정됐다. 더 직접적인
`SELECT '010-9999-9999' AS customer_phone ...`도 가드를 통과해 리터럴을 결과 컬럼으로
위장할 수 있었다.

**원인**: 문의의 영향을 받는 LLM 산출인 SQL 문자열과 DB 결과 행을 같은 신뢰 등급의 근거로
합쳤다. allowlist 는 값이 어디에 적혔는지가 아니라 **어디에서 왔는지**를 구분해야 한다.

**대응**: 실행 SQL 은 표시용 `content` 에만 남긴다. `evidence_text` 에는 결과 행을 담되 비PII
계산값은 L2용으로 유지하고 계산된 패턴형 PII는 제외한다. 가드가 `orders` 직접 컬럼으로 증명한
값은 PII여도 마스킹하지 않아 정상 에코를 살린다. CTE·함수·CASE·CAST·문자열 연산과 새 SQL
표현식의 계산 PII는 모양과 무관하게 allowlist 출처로 승인되지 않으며 정상 계산 쿼리는 그대로
실행된다. 추가로 정확 재현인 최상위 직접 상수 projection 은
`unsupported_projection` 으로 일찍 거부한다. 직접 컬럼과 계산식이 같은 결과 이름을 쓰면
`DictRow` 를 dict 로 내릴 때 계산값이 직접 컬럼 provenance 를 덮을 수 있으므로, 별표 확장 뒤
중복되는 최상위 출력명도 같은 규칙으로 거부한다.

## PII 표기 변형은 탐지와 allowlist 에 같은 방식으로 정규화한다

기존 패턴은 국내형 전화번호·하이픈 주민등록번호·ASCII 도메인 이메일만 잡아 `+82`/`0082`,
공백·괄호 구분자, 국제화 도메인을 놓쳤다. 초안에서만 패턴을 넓히면 근거의 같은 값도 오기각되므로
양쪽에 같은 패턴과 정규화를 적용한다. 한국 국가번호는 국내 `0` 표기로 바꾸고, 숫자 경계와
완전 일치는 유지한다. 이 변경은 **L1 PII 검출률의 정의를 더 넓힌다** — 이전 수치와 비교할 때
탐지 대상 표기 범위가 달라졌음을 함께 밝혀야 한다.

## 빈 claim text 는 구조 위반이다

`claims` 배열과 citation 이 있어도 `text` 가 빈 문자열이나 공백뿐이면 L1 이 통과해 빈 답변으로
확정됐다. 문자열 타입만 보지 않고 `text.strip()` 이 비어 있는지도 스키마 검사에서 확인한다.
`citation_ids` 최소 개수는 여전히 `missing_citation` 전담이므로 이 규칙과 합치지 않는다.

## PII allowlist 는 부분 문자열 대조를 쓰면 안 된다

정규화한 숫자열을 근거 원문에 **부분 문자열로** 찾으면, 근거에 긴 숫자(주문번호 등)가 있을 때
지어낸 전화번호가 그 안에 우연히 포함되어 통과한다 — 즉 PII 유출이다.
근거 텍스트에도 **같은 패턴·같은 정규화**를 적용해 값 집합을 뽑고 **완전 일치**로 대조한다.
모든 숫자 패턴에 숫자 경계 lookaround(`(?<![0-9])`/`(?![0-9])`)를 붙여, 초안 쪽 오탐과
근거 쪽 과잉 allowlist 를 양방향으로 막는다.

## 대표번호(15xx~18xx)를 PII 패턴에 넣은 이유

개인 연락처가 아니라 넣지 않는 것이 자연스러워 보이지만, 정책 문서의 미끼 조항이 겨냥하는
값이 정확히 **고객센터 대표번호**다. 빼면 미끼가 무력해지고 기각 유발 재료가 사라진다.
`0` 으로 시작하지 않아 일반전화 패턴에 걸리지 않으므로 별도 패턴이 필요하다.

## pgvector 파라미터는 캐스트가 필요하다

`INSERT` 는 컬럼 타입이 `vector` 라 파이썬 리스트를 그대로 넘겨도 psycopg 가 추론한다.
그러나 `embedding <=> %s` 처럼 **연산자의 파라미터**로 넘기면 타입을 추론하지 못해
`UndefinedFunction: No operator matches the given name and argument types` 가 난다.
`pgvector.Vector(list)` 로 감싸서 넘긴다.

## DB 통합 테스트의 skip 은 정직해야 한다

`db` 마커 테스트가 DB 없을 때 조용히 skip 되면, 전체 녹색이 아무것도 증명하지 않는다.
skip 사유에 **접속 대상·원인·복구 명령**을 함께 담고, 게이트를 통과시킬 때는
`uv run pytest -m db` 로 **skip 0** 을 따로 확인한다. "돌았다"가 아니라 "무엇이 돌았다"가 증거다.

## 워크트리마다 compose 가 컨테이너를 재생성한다

다른 디렉터리에서 `docker compose up -d --wait` 를 실행하면 compose 프로젝트 설정 해시가 달라
같은 이름의 컨테이너를 **재생성**한다. 데이터는 named volume(`reply-gate-pgdata`)에 있어 남지만,
공유 DB 를 쓰는 다른 작업이 있을 때는 놀랄 수 있다.

## 스키마를 바꿨으면 볼륨째 지워야 한다

`db/schema.sql` 은 전부 `CREATE TABLE IF NOT EXISTS` 라 **기존 테이블의 컬럼은 바뀌지 않는다.**
마이그레이션 도구는 이 사이클 범위 밖이므로, 스키마 변경 후에는
`docker compose down -v && docker compose up -d --wait` 로 볼륨째 재생성한다.

## 목만으로는 잡히지 않는 결함이 있다

FastAPI 의존성 주입을 override 한 테스트는 클라이언트 **생성 시점**의 오류를 놓친다.
`openai.OpenAI(api_key="")` 는 생성자에서 예외를 던져, LLM 을 전혀 쓰지 않는 경로
(`GET /inquiries/{id}`, 접수 거부 422)까지 500 이 됐다. 목이 전부 녹색인 상태에서 **런타임
스모크가 잡아냈다.** 서버를 실제로 띄우고 몇 개 요청을 던지는 절차를 생략하지 마라.

## 평가 하네스의 대역 수치를 실제 수치로 읽지 마라

`--stub-llm` 은 결정론 대역으로 배관만 검증한다. 어휘 기반 임베딩 대역의 유사도는 실제
임베딩과 스케일이 달라(0.2~0.3대) 기본 임계값 0.3 에서는 대부분 걸러진다. 그래서 대역
실행은 임계값을 낮춰 돌고, 리포트에 **경고와 실행 조건**이 함께 찍힌다. 대역으로 낸
기각 재현율 100% 와 실제 6.7% 가 그 차이다.

## 정답 정책을 본 재작성문은 배포 가능한 개선폭이 아니다

처음 만든 검색 재작성 픽스처는 정답 조항 번호와 어휘를 note 에 적고, 그 어휘를 질의에도
주입했다. 구조는 재현 가능했지만 측정한 것은 일반 질의 재작성의 개선폭이 아니라 정답을 본
oracle query 의 상한이었다. 원문에 없던 결제 수단·운영시간·주문번호 필요성·본인 확인 결론도
섞여 요청 유형과 단정 강도가 바뀌었다.

기본 비교 입력은 정책·라벨을 본 적 없는 생성 모델이 문의 원문만 보고 만든
`data/rewritten_queries.jsonl` 이다(생성기는 `scripts/generate_blind_rewrites.py`).
기존 curated 세트는 `data/rewritten_queries_oracle.jsonl` 로 별도 보존하고 리포트에서
`oracle_upper_bound` 로 표시한다. 두 조건의 수치를 같은 의미로 해석하지 않는다.

검색 정답 라벨은 recall 계산을 위한 **직접 관련 조항**(정면 조항 + 상충 조항, 결정 0010)의
집합이다. 반면 L2 judge 픽스처의 citation sufficiency는 주어진 답변이 최소한으로 충분히
뒷받침되는지를 판정한다. 따라서 G18 검색 라벨에 2-6 과 상충 조항 2-4 가 모두 들어가도,
2-6 만 인용한 충분한 답변이 judge pass인 것과 모순되지 않는다. 두 계약을 합치면 검색기가
정당한 관련 조항을 찾은 결과와 답변이 불필요한 조항까지 모두 인용해야 하는지를 같은 문제로
오채점하게 된다.

## 어휘가 겹친다고 정답을 본 것은 아니다

사람이 손으로 쓴 blind 재작성이 정답 조항의 표제어를 들여온다는 지적이 리뷰 4회 중 3회
나왔다(구어체 "바꾸고" → "변경", "몇 번으로 걸면" → "고객센터"). 그럴듯한 지적이었고 정량
대조로 원문에 없고 정답 조항에 있는 문자 2-gram 이 실제로 세어졌다.

같은 자리를 **정책 문서를 입력으로 받은 적이 없는 생성 모델**에게 맡기고 같은 지표를 다시
재니 결과가 뒤집혔다 — 모델 재작성의 유입이 사람이 쓴 것의 **두 배 이상**이었다
(18건/33개 vs 7건/16개, 정답 있는 25건 기준). oracle 은 25건/144개다.

구어체를 문서체로 정규화하면 정답 조항과 같은 낱말이 나오는 것이 정상이고, 그것은 정답을
봤다는 증거가 아니다. **누출로 갈라야 하는 것은 어휘 겹침이 아니라 정답 조항에만 있는 값**
(근거 ID·조항 번호·정책 고유 수치)이다. 지금은 그것만 구조 테스트가 막는다
(`tests/test_rewritten_queries.py`).

일반화하면: **사람이 만든 평가 입력에 대해 "이건 너무 유리한 것 아닌가"를 사람이 판정하면
그 판정 자체가 측정에 실린다.** 판정 대신 조건을 실제로 재현해 재보는 편이 싸고 결론이 다르다.

## 순위 기반 점수로 채택을 판정하면 기권이 사라진다

하이브리드 단의 채택 컷을 RRF 점수로 두었더니 **어떤 조항도 걸러지지 않았다.** 벡터·BM25 두
순위가 조항 26개 전량을 덮으므로 모든 조항이 양쪽에 있고, 최소 RRF 는 `2/(60+26) = 0.023256`
이라 기본 컷 0.02 를 넘을 수 없다. 컷은 항등이었고 하이브리드는 모든 문의에서 정확히
top_k 건을 채택했다. 근거가 없어야 정답인 문의에서 벡터는 precision 1.0, 하이브리드는
구조적으로 0.0 — 검색 품질이 아니라 산술이 만든 격차였다.

교훈은 컷 값이 아니다. **순위 융합 점수에는 "관련 없음"이 없다.** 채택·기권은 절대 관련성
축(코사인)이 정하고, 순위 점수는 순서만 정한다. 컷을 새로 고를 때는 그 값이 이 코퍼스에서
실제로 걸러낼 수 있는지 코드가 검사하게 했다 — 걸러내지 못하는 컷은 걸러낸 척한다.

같은 구조적 함정이 리랭크에도 있었다. 후보가 `fused[:top_k]`(5)이고 채택 상한도 5면 리랭크
채택 집합은 하이브리드와 **항등**이라 precision·recall·recall@5 가 정의상 같은 값이 된다.
실제 모델을 태워도 그 열은 움직이지 않는다. 후보 풀을 채택 상한보다 크게 두는 것을 코드가
강제한다. 자세한 근거는 [결정 0009](tracking/decisions/0009-채택-판정을-절대-축으로-통일한다.md).

## 지표 분모를 함께 인쇄하지 않으면 비교표가 거짓말한다

"채택 0건 + 정답 있음"을 precision 평균에서 빼는 규약 자체는 맞다. 문제는 컷의 실효 강도가
전략마다 달라 제외 케이스 수가 갈리는데 markdown 표가 분모를 찍지 않은 것이었다. 대역 실측에서
vector 는 30건 중 13건의 평균 0.769, 하이브리드는 30건 평균 0.187 이었다 — 나란히 놓인 두 수가
서로 다른 표본의 평균이었고, 표를 읽는 사람은 같은 분모를 가정한다.

컷을 올릴수록 precision 이 1.0 에 수렴하는 것도 같은 함정이다. 어려운 케이스가 분모에서
사라지고 빈 정답 케이스만 남는다. 분모(`precision n`)를 값과 같은 표에 두고, 전략마다 컷을
훑어 최적점을 함께 낸다.

## 무과금이라고 안내한 플래그가 과금했다

`--bge-m3` 는 help 에 "DB·외부 API 없음"이라고 적혀 있었지만 `live=bool(args.live or
args.bge_m3)` 로 live 경로를 타고, 기본 사다리에 리랭크 단이 있어 `OpenAIGenerationClient` 를
만들어 문의마다 실제 호출을 냈다. 키가 없으면 "로컬 전용" 옵션이 실행조차 되지 않았다.

**임베딩 위치와 리랭크 과금은 다른 축이다.** 둘을 한 불리언으로 묶으면 한쪽 의도가 다른 쪽을
조용히 켠다. 지금은 `paid_rerank` 가 별개 인자이고, 미승인 상태에서 리랭크 단은 0 이 아니라
"미측정 + 사유"로 리포트에 남는다.

## 조용한 폴백은 실패한 실행과 성공한 실행을 구분하지 못하게 만든다

`llm_rerank` 가 `except Exception: return candidates` 로 모든 실패를 입력 순위 유지로 흡수했고
폴백 건수가 어디에도 남지 않았다. 리랭크 채택 집합이 하이브리드와 항등이던 것과 겹치면,
30건 전부 실패한 실행과 성공한 실행이 리포트상 **완전히 같아진다.** 리포트는 여전히
`rerank_model` 을 실행 조건으로 찍으므로 "리랭크를 돌렸다"로 읽힌다.

폴백은 유지하되 사유·건수·토큰이 호출자에게 올라가고 리포트가 집계한다. 실패한 순위를
캐시에 쓰지 않는 것도 함께 막았다 — 쓰면 다음 실행이 그것을 성공으로 재사용한다.

## 라이브 리포트를 기본 실행이 덮어썼다

`--live` 실행과 기본 실행이 같은 파일(`reports/evaluation.{md,json}`)에 썼다. 라이브
실측 뒤에 아무 생각 없이 돌린 기본 실행 한 번이 **유일한 실측 근거를 "측정 2 미실행"
리포트로 덮어썼고**, `reports/` 는 gitignore 라 되돌릴 백업이 없었다. 문서는 70.0% 를
인용하는데 그 수치를 낸 산출물은 사라진 상태였다 — 재현하려면 과금되는 재실행이
필요하고, 확률 층이라 같은 값도 나오지 않는다.

고친 방식은 이름 규칙을 **양방향 불변식**으로 만든 것이다: **라이브 이름 ⇔ 실측**
(`evaluation.resolve_report_stem`, 단위 테스트 있음). 비실측 실행은 라이브 이름을 쓸 수
없고(기본 이름도 실측 여부로 갈린다 — `--live` 여도 키·DB 문제로 미실행이면 `evaluation`),
실측 실행은 라이브 이름만 쓸 수 있으며, 이미 존재하는 라이브 리포트는 덮어쓸 수 없다.
검사는 측정 시작 전에 돌고, stem 은 경로가 아닌 파일 이름 조각만 받는다(`./`·`../`·절대경로
·대소문자 변형 우회를 막는다 — 첫 구현은 이 우회들에 전부 뚫렸고 리뷰가 잡았다).
라이브 리포트만 gitignore 예외로 추적한다.

교훈: 재생성에 돈이 드는 산출물은 재생성이 공짜인 산출물과 **같은 경로를 쓰면 안 된다.**
덮어쓰기를 막는 것은 규율이 아니라 코드여야 한다.

## 커밋된 리포트의 mismatch 문자열로 재채점하지 마라

라벨 재정렬(결정 0008)의 전후 병기 수치를 처음에는 **구 리포트의 `mismatches` 문자열에서
"기각을 기대했으나…" 항목만 빼는 방식**으로 계산했다 — 사이클 1 이 83.3% 로 나왔고 틀린
값이었다. 리포트의 mismatch 는 **그 실행 시점의 라벨**로 채점된 결과라, 사이클 1 리포트에는
사이클 2 초입의 라벨 확장(G17 에 `no_evidence` 허용) 이전 판정이 그대로 들어 있었다.
두 사이클을 이 방식으로 나란히 놓으면 **서로 다른 채점표로 채점한 값을 비교**하게 된다.
독립 리뷰(Opus 5)가 잡았고, 정답은 리포트의 `outcomes` 원시 필드(status·escalation_reason·
attempt_verdicts·reject_reasons)에 **현재 라벨 전체로 `_compare` 동등 로직을 다시 돌리는 것**
이다(사이클 1 = 86.7%).

교훈: 리포트의 판정 필드(`matched`·`mismatches`)는 당시 채점표의 산출물이다. 채점표를 바꾼
뒤의 재채점은 반드시 **원시 결과 필드 + 현재 라벨 전체**로 처음부터 다시 계산한다.

## 보안 슬라이스 적대리뷰가 제공자 필터에 죽는다 — 산출 형태를 바꿔야 통과한다

사이클 1·2 코어에 블라인드 적대리뷰 12회(4슬라이스 × 3)를 돌렸을 때 **보안·데이터 슬라이스
2회가 Codex 제공자의 사이버보안 콘텐츠 필터에 걸려 최종 작성 단계에서 죽었다.** 조사는 이미
끝난 뒤였고 로그에 요지만 남았다. 같은 프롬프트로 재시도하면 같은 자리에서 다시 죽는다.

통과시키려면 둘을 바꾼다.

1. **산출 형태에서 공격 서사를 뺀다.** 등급 라벨(`FATAL`)·"치명 N경로" 목록·우회 서술과
   payload 문장을 요구하지 말고, **"문서가 주장하는 불변식 중 코드에서 성립하지 않는 것을
   찾아 실패하는 pytest 함수로 표현하라"** 로 재구성한다. 발견 하나당 `파일:줄` / 어긋난
   불변식 / **지금 돌리면 실패하는 테스트 함수** / 고칠 방향, 그리고 등급 대신 **불변식의
   출처(문서 경로:줄)** 를 적게 한다.
2. **슬라이스를 더 잘게 나눈다.** 한 응답에 모이는 양을 줄인다(예: `sql_guard` 단독 /
   `evidence`+`records`+`db`).

이 형식으로 재실행한 2회는 둘 다 완주했고, **진행 중이던 보안 수정본 자체의 구멍(출력 별칭이
연 두 번째 세탁 경로)까지 찾아냈다.** 죽은 채로 뒀으면 수정본을 검사할 사람이 없었다.

교훈: 이건 필터를 피하려는 타협이 아니라 **더 나은 루브릭이다.** 등급과 공격 서술은 어차피
손으로 재현 코드로 옮겨 검증하게 되는 중간 산출물이고, 실패하는 테스트 함수를 직접 요구하면
그 단계가 리뷰어 쪽으로 넘어간다. 재현 불가능한 주장도 같이 걸러진다.
