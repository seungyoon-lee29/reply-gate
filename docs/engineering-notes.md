# 엔지니어링 노트

코드를 읽어도 알 수 없고, 모르면 걸리는 것들.

## SQL 가드에서 실제로 뚫렸던 경로

세 번 뚫렸고 세 번 다 "막았다"가 아니라 **실제로 넣어봐서** 확인했다. 가드를 손볼 때는
같은 방식으로 확인하라 — 코드를 읽어서 안전하다고 판단하는 것으로는 부족했다.

### 1. 주문 범위가 프롬프트에만 있었다

**증상**: `SELECT order_no, customer_name, customer_phone, customer_email FROM orders LIMIT 3`
이 가드를 통과하고 실행됐다. 결과 행이 근거가 되고, L1 의 PII allowlist 가 **그 근거로부터**
만들어지므로 무관한 고객 50명(= 행 수 상한)의 연락처가 답변에 실려도 기각되지 않았다.

**원인**: "주어진 주문번호 1건만 조회한다"가 SQL 생성 프롬프트 문구로만 있었고 검증기는
`order_no` 를 받지도 않았다. 어떤 행이 나올지를 LLM 이 정하는 상태였다.

**대응**: 검증 단계에서 AST 를 훑어 `order_no` 동등 비교가 선검사된 값과 일치하는지 확인한다.
프롬프트에도 규칙을 넣되, **프롬프트는 재시도 예산을 아끼는 장치이지 안전장치가 아니다.**

### 2. 별칭이 컬럼 화이트리스트를 무력화했다

**증상**: `SELECT ctid FROM orders` 는 거부되는데
`SELECT 1 AS ctid, ctid, order_no FROM orders` 는 통과하고 실제로 `ctid` 값을 돌려줬다.
`SELECT o.ctid FROM orders AS o(ctid)` 도 같았다.

**원인**: 쿼리 어디서든 등장한 별칭 이름을 전역 허용 컬럼 집합에 더하고 있었다.

**대응**: 별칭은 화이트리스트 구성원이 아니다. 맨 이름 별칭을 받아들이는 자리는
`ORDER BY`/`GROUP BY` 로 한정한다. **`HAVING` 은 제외한다** — Postgres 는 `HAVING` 에서
맨 이름을 *입력 컬럼*으로 해석하므로 거기서 별칭을 받으면 우회가 그대로 되살아난다.

### 3. 외부 조인이 주문 1건 한정을 통째로 무력화했다 (가장 치명적)

**증상**: 1번을 고친 뒤에도 이 한 줄로 다시 50건이 샜다.

```sql
SELECT o.* FROM orders o LEFT JOIN (SELECT 1 AS x) d ON o.order_no = 'ORD-...'
```

`INNER JOIN` 으로 바꾼 대조군은 정확히 1행이 나온다.

**원인**: 검증기가 WHERE 절과 **모든 JOIN 의 ON 조건**을 한 통에 모아 바인딩으로 인정했는데,
**외부 조인의 ON 절은 보존측 테이블을 필터하지 않는다.** 조인 종류를 코드가 한 번도 읽지 않았다.

**대응**: 두 겹. (a) 외부 조인(LEFT/RIGHT/FULL)을 통째로 거부한다 — 주문 1건 조회에 외부 조인이
필요한 정당한 사례가 없고, 현실 CS 쿼리 30건 검증에서도 0건이었다. (b) 바인딩으로 인정하는
자리를 WHERE 절과 INNER/CROSS 조인의 ON 절로 한정한다. 나중에 외부 조인을 허용하게 되더라도
(b) 가 있어야 조용히 새지 않는다.

**교훈**: 조인 종류를 무시한 검증기는 "조건이 있다"와 "행이 걸러진다"를 같은 것으로 착각한다.

## L1 PII 오탐 — 근거 ID 가 검사 대상이었다

**증상**: PII 가 전혀 없는 정상 초안이 `pii_detected` 로 2회 연속 기각되어 `rejected_twice`
인계됐다. 재생성도 반드시 같이 실패했다.

**원인**: PII 검사가 원시 초안 전체를 재귀로 훑어 `citation_ids` 문자열까지 포함했다.
SQL 근거 ID 는 `sql:<문의 UUID>:<순번>` 이라 UUID 의 16진 숫자 구간이 일반전화 정규식
(`0[2-9][0-9]?[-. ]?[0-9]{3,4}[-. ]?[0-9]{4}`)에 걸린다. 근거 ID 는 `evidence_text` 에 없으니
allowlist 에도 오르지 않아 "근거에 없는 PII"가 된다. 같은 문의 ID 를 두 시도가 공유하므로
재생성이 구제할 수 없다.

**발생률**: 무작위 UUID 20,000개 중 168개(**0.84%**). SQL 근거를 인용하는 문의의 그만큼이
무조건 오기각된다.

**대응**: PII 검사 대상에서 `citation_ids` 를 제외한다. 참조 무결성은 `invalid_citation` 이
전담하므로 PII 검사가 근거 ID 를 볼 이유가 없다. 무작위 문의 ID 2,000건 무오탐 회귀 테스트로 고정.

**왜 중요한가**: 이 프로젝트의 헤드라인 지표가 "정상 초안 오탐률"이다. 오탐 버그는 곧 지표 오염이다.

## 같은 오탐이 한 겹 남아 있었다 — 답변에 실리지 않는 키

`citation_ids` 만 제외한 것은 **증상 하나를 지운 것이지 원인을 지운 것이 아니었다.** 검사는
여전히 원시 초안 전체를 훑었고, 그래서 `{"claims": [...정상...], "debug": "1588-1234"}` 처럼
스키마 밖 키에 값이 들어오면 정상 초안이 `pii_detected` 로 기각됐다. claim 안의 추가 키
(`note`)도 같다. `to_draft` 가 살리는 것은 claim 의 `text` 뿐이라 **그 값들은 답변에 아예
실리지 않는다** — 답변에 없는 값으로 답변을 기각한 것이다. 초안 JSON 은 LLM 산출이라
스키마 밖 키는 프롬프트가 바뀔 때마다 다시 생길 수 있어, 키 이름을 하나씩 빼는 방식으로는
끝나지 않는다.

**대응**: 제외 목록 대신 **포함 기준**으로 뒤집었다. PII 검사 대상 = `to_draft` 가 답변으로
내보내는 텍스트(= claim 의 `text`). 답변 후보 텍스트를 하나도 식별할 수 없을 때(원문 문자열이
통째로 넘어온 경우)만 초안 전체를 긁는 폴백으로 남긴다 — 그런 초안은 어차피
`schema_violation` 이라 답변이 나가지 않고, 게이트는 모르는 쪽에서 검사하는 방향으로 간다.
구조가 깨진 claim 옆의 멀쩡한 claim 은 여전히 답변 후보이므로 계속 검사한다.

**교훈**: 검사 범위를 "무엇을 뺄까"로 정의하면 새 키가 생길 때마다 오탐이 돌아온다.
"무엇이 실제로 사용자에게 나가는가"로 정의하면 그 목록은 코드가 이미 알고 있다.

## 비용은 누적하면서 횟수는 누적하지 않았다

`LLMCallError.attempts` 는 "실제로 몇 번 전송했나"로 읽히는데 실은 **래퍼 루프 횟수**만
셌다. 형식 루프(판정·의도 해석·SQL 생성)를 도는 호출자가 앞선 시도의 전송을 이어 세지
않았기 때문이다. 같은 자리의 코드가 토큰은 정확히 누적한다:

```text
raise LLMCallError(
    attempts=exc.attempts,                          # ← 횟수는 덮어쓴다
    input_tokens=input_tokens + exc.input_tokens,   # ← 비용은 누적한다
)
```

앞선 시도의 **비용**은 버리면 안 된다는 것을 알면서, 그 시도가 **있었다**는 사실은 버렸다.
실측하면 판정 1차가 형식 오류(전송 1회) + 2차가 전송 오류(래퍼가 2회) = 실제 3회인데
`attempts=2` 로 신고된다. 거절 경로는 아예 `attempts=1` 하드코딩이라, 재시도 뒤에 온 거절이
1회로 신고됐다.

**대응**: `_call_with_one_retry` 가 결과와 함께 **전송 수를 세어** 돌려주고,
`JsonCompletion`·`LLMFormatError` 가 그 값을 실어 나른다. 형식 루프는 토큰과 같은 줄에서
횟수를 누적한다. 상수를 되읽으면 "몇 번 돌았나"가 아니라 "몇 번까지 돌 수 있나"를 신고하게
된다 — 두 값이 같아 보이는 것은 층이 하나일 때뿐이다.

**교훈**: 누적하는 값 옆에 누적하지 않는 값이 있으면 둘 중 하나는 버그다. 같은 예외를 다시
던지는 자리는 특히 그렇다 — 무엇을 이어받고 무엇을 덮어쓸지 한 줄씩 정하게 되어서, 하나를
빠뜨려도 코드가 자연스러워 보인다.

## claim 판정을 집합으로 대조해 옳은 산출을 거부하고 틀린 산출을 받았다

L2 판정 산출은 초안 claim 전부와 **1:1 대응**해야 한다. 검증기는 그것을 **집합** 대조로
구현했다(`draft_texts = {claim.text for claim in draft.claims}`). 초안 claim 의 text 가
유일하다는 전제였는데, **초안은 LLM 산출이라 그 전제를 아무도 강제하지 않는다.** 같은 문장이
두 번 들어오면 두 claim 의 `citation_ids` 는 다를 수 있다 — 한쪽은 뒷받침되고 한쪽은 무관한
조항을 딛는 것이 실제 시나리오다.

같은 문장 2건짜리 초안으로 재현하면 **양방향으로 다 틀렸다**:

```
① 판정 1건만 돌려줌 : 수용 — 판정 1건 (초안 claim 2건)
② 판정 2건 돌려줌   : 거부 — claim_judgments 에 같은 claim 에 대한 판정이 중복으로 있다
```

①은 판정 커버리지가 조용히 절반이 되고 판정받지 못한 문장이 답변에 실린다. ②는 **정직하게
2건을 낸 옳은 산출이 거부되는 것**이라, 모델에게는 맞게 답할 길이 아예 없었다. 프롬프트는
claim 을 2건으로 보여주면서 산출은 1건만 받는다.

**대응**: 대조를 다중집합(`Counter`)으로 바꿔 개수까지 맞춘다. 짝짓기는 계속 `claim_text` 로
한다 — 배열 위치를 계약으로 올리지 않는다(contracts.md). 검사만 조이면 모델이 계속 1건을
내고 재시도 2회를 태워 인계되므로, 시스템 프롬프트에 "같은 문장이 두 번 나오면 판정도 두 번"
을 명시했다.

**이 결함은 저장소가 이미 절반을 알고 있었다.** 판정 픽스처 로더에 "한 픽스처 안의 claim
텍스트는 유일해야 한다"는 검사가 있고, 주석이 이유를 그대로 적어 뒀다 — "판정 대조가 두 건을
한 판정으로 채점하는데 `claim_total` 은 2 로 센다". 라벨 쪽은 막았는데 **런타임 쪽은 안 막혀
있었다.**

**교훈**: 픽스처에 "이런 입력은 넣지 마라" 가드를 다는 순간, 그 입력이 런타임으로 들어오면
어떻게 되는지 확인한다. 가드는 결함을 고친 것이 아니라 결함을 피해 다닌 자국이다.

## 게이트가 안 돈 것과 게이트가 놓친 것이 같은 값이었다

L2 판정 호출이 실패하면 그 시도의 종합 verdict 는 `pass` 다 — 층 결합 정의상 "L2 미실행은
판정에서 빠진다"이고, 진실은 인계 사유(`llm_call_failed` + `l2_judge`)가 들고 있다. 계약
문서도 "종합 verdict 만 보고 통과로 읽으면 안 된다"고 적어 뒀다.

**그런데 그 규칙을 지킬 책임이 소비자에게 있었다.** 평가 하네스의 `GoldenOutcome` 은
`attempt_verdicts` 만 들고 다음 단계로 넘어가서, 미끼 재현율(`bait_reject_recall`)이 두
상태를 구분하지 못했다:

```
L2 호출 실패(판정 안 됨)   bait 0/1 = recall 0.0   attempt_verdicts=['pass']
게이트가 돌았고 놓침        bait 0/1 = recall 0.0   attempt_verdicts=['pass']
```

인프라 실패가 "게이트가 미끼를 놓쳤다"와 **같은 숫자**가 된다. `scripts/AGENTS.md` 불변식 5
("미실행 측정을 0 이나 빈 값으로 채우지 않는다")를 케이스 단위에서 위반한 것이다. 골든셋
대조의 불일치 사유 문자열도 "어떤 시도도 기각되지 않았다"라고 적혀 거짓이었다 — 게이트가
통과시킨 것이 아니라 게이트에 닿지 못했다.

**대응**: 계약이 지정한 신호(`escalation_reason` + `failed_stage`)로 판별하는
`GoldenOutcome.gate_never_ran` 을 만들어, 재현율 분모에서 빼고 `bait_unmeasured` 로 따로
센다. 전부 미측정이면 재현율은 `0.0` 이 아니라 `None`(미실행)이다. 분모에서 빼기만 하고
말하지 않으면 그냥 사라진 것이므로 리포트 문장과 JSON 에 함께 싣는다.

커밋된 라이브 6회 전부 L2 호출 실패가 0건이라 **실측 수치는 하나도 바뀌지 않았다** — 지금
막지 않으면 다음 실측에서 처음 터지고, 그때는 원인을 수치에서 읽을 수 없다.

**교훈**: "이 값을 이렇게 읽지 마라"를 문서에 적었다면, 그건 아직 안 고친 것이다. 읽는 쪽이
하나라도 있으면 코드가 대신 지켜야 한다.

## 실행 SQL 원문은 PII allowlist 근거가 아니다

**증상**: `SELECT status FROM orders WHERE order_no = '<선검사 주문>' AND
'010-9999-9999' <> ''`가 통과하면 결과 행에는 연락처가 없는데도, 실행 SQL 을 함께 넣은
`evidence_text` 때문에 초안의 `010-9999-9999`가 근거 유래로 인정됐다. 더 직접적인
`SELECT '010-9999-9999' AS customer_phone ...`도 가드를 통과해 리터럴을 결과 컬럼으로
위장할 수 있었다.

**원인**: 문의의 영향을 받는 LLM 산출인 SQL 문자열과 DB 결과 행을 같은 신뢰 등급의 근거로
합쳤다. allowlist 는 값이 어디에 적혔는지가 아니라 **어디에서 왔는지**를 구분해야 한다.

**대응**: 실행 SQL 은 표시용 `content` 에만 남긴다. `evidence_text` 에는 결과 행을 담되 비PII
계산값은 L2용으로 유지하고 계산된 패턴형 PII는 제외한다. 가드가 `orders` 직접 컬럼으로 증명한
값은 PII여도 마스킹하지 않아 정상 에코를 살린다. CTE·함수·CASE·CAST·문자열 연산과 새 SQL
표현식의 계산 PII는 모양과 무관하게 allowlist 출처로 승인되지 않으며 정상 계산 쿼리는 그대로
실행된다. 추가로 정확 재현인 최상위 직접 상수 projection 은
`unsupported_projection` 으로 일찍 거부한다. 직접 컬럼과 계산식이 같은 결과 이름을 쓰면
`DictRow` 를 dict 로 내릴 때 계산값이 직접 컬럼 provenance 를 덮을 수 있으므로, 별표 확장 뒤
중복되는 최상위 출력명도 같은 규칙으로 거부한다.

## PII 표기 변형은 탐지와 allowlist 에 같은 방식으로 정규화한다

기존 패턴은 국내형 전화번호·하이픈 주민등록번호·ASCII 도메인 이메일만 잡아 `+82`/`0082`,
공백·괄호 구분자, 국제화 도메인을 놓쳤다. 초안에서만 패턴을 넓히면 근거의 같은 값도 오기각되므로
양쪽에 같은 패턴과 정규화를 적용한다. 한국 국가번호는 국내 `0` 표기로 바꾸고, 숫자 경계와
완전 일치는 유지한다. 이 변경은 **L1 PII 검출률의 정의를 더 넓힌다** — 이전 수치와 비교할 때
탐지 대상 표기 범위가 달라졌음을 함께 밝혀야 한다.

## 접기 기준이 층마다 달라 근거 필터가 게이트보다 헐거웠다

게이트(`gate._normalized_matches`)는 초안·근거 양쪽에 `fold_for_detection`(NFKC + `Cf` 제거)을
걸고 대조하는데, 근거 렌더(`evidence._pii_shaped`)는 **접기 전 원문**으로 패턴형 PII 를 걸렀다.
그래서 **접기 전엔 PII 가 아니고 접은 뒤엔 PII 인** 값 — 전각 숫자 `０１０-…`, 숫자열 안에 끼운
제로폭 `U+200B`, 전각 하이픈 `U+FF0D` — 이 계산 컬럼인데도 `evidence_text` 로 살아남았다.
게이트가 그것을 접어 반각 `01099998888` 로 만드는 순간 **지어낸 번호가 allowlist 근거를 얻어
`pass`** 했다. 계산 컬럼 값을 버리는 방어 자체는 있었는데 그 방어가 접기 앞에서 샜다.

**두 층이 같은 값을 다르게 판정하면, 느슨한 쪽이 엄격한 쪽의 입력을 만든다.** 필터와 대조가
직렬로 이어져 있으면 기준을 공유해야 한다 — 각각 맞는 것으로는 부족하다.

수정은 `_pii_shaped` 가 `fold_for_detection` 을 거쳐 보게 하는 한 줄이고, `gate.__all__` 이
접기 함수를 연다. **접기는 판정에만 쓰고 렌더는 원문을 유지한다** — 근거 문면을 바꾸면 정상
에코 계약과 L2 근거가 함께 흔들린다. 승인된 `orders` 직접 컬럼 값은 접기와 무관하게 그대로
남는다(회귀 검사로 박아 뒀다).

**조건 보존이라 재등재 없이 넣었다.** `_pii_shaped` 판정이 접기로 뒤집히는 값을 저장소 전
데이터에서 전수로 셌고(orders 픽스처 + 실 DB `orders` 전량 + `policy_chunks`) **0 / 32,104**
였다 — 커밋된 라이브 리포트 어느 것의 조건도 흔들지 않는다. 초안 쪽 표기 우회는 별개
계열이고 아직 열려 있다(`docs/tracking/findings.md` 27-2 — `Pd`·`Mn` 은 NFKC 도 `Cf` 필터도
접지 못한다).

## 빈 claim text 는 구조 위반이다

`claims` 배열과 citation 이 있어도 `text` 가 빈 문자열이나 공백뿐이면 L1 이 통과해 빈 답변으로
확정됐다. 문자열 타입만 보지 않고 `text.strip()` 이 비어 있는지도 스키마 검사에서 확인한다.
`citation_ids` 최소 개수는 여전히 `missing_citation` 전담이므로 이 규칙과 합치지 않는다.

## PII allowlist 는 부분 문자열 대조를 쓰면 안 된다

정규화한 숫자열을 근거 원문에 **부분 문자열로** 찾으면, 근거에 긴 숫자(주문번호 등)가 있을 때
지어낸 전화번호가 그 안에 우연히 포함되어 통과한다 — 즉 PII 유출이다.
근거 텍스트에도 **같은 패턴·같은 정규화**를 적용해 값 집합을 뽑고 **완전 일치**로 대조한다.
모든 숫자 패턴에 숫자 경계 lookaround(`(?<![0-9])`/`(?![0-9])`)를 붙여, 초안 쪽 오탐과
근거 쪽 과잉 allowlist 를 양방향으로 막는다.

## 대표번호(15xx~18xx)를 PII 패턴에 넣은 이유

개인 연락처가 아니라 넣지 않는 것이 자연스러워 보이지만, 정책 문서의 미끼 조항이 겨냥하는
값이 정확히 **고객센터 대표번호**다. 빼면 미끼가 무력해지고 기각 유발 재료가 사라진다.
`0` 으로 시작하지 않아 일반전화 패턴에 걸리지 않으므로 별도 패턴이 필요하다.

## pgvector 파라미터는 캐스트가 필요하다

`INSERT` 는 컬럼 타입이 `vector` 라 파이썬 리스트를 그대로 넘겨도 psycopg 가 추론한다.
그러나 `embedding <=> %s` 처럼 **연산자의 파라미터**로 넘기면 타입을 추론하지 못해
`UndefinedFunction: No operator matches the given name and argument types` 가 난다.
`pgvector.Vector(list)` 로 감싸서 넘긴다.

## 같은 차원의 다른 모델은 아무도 막지 않는다

pgvector 는 **차원**이 다르면 거부한다 — 1536 컬럼에 3072 질의를 넣으면
`DataException: different vector dimensions 1536 and 3072` 다. 그래서 차원 오류는 시끄럽다.

**모델은 아니다.** `text-embedding-3-small` 과 `3-large` 는 둘 다 1536 을 낼 수 있고
(이 저장소의 비교 축 `DEFAULT_EMBEDDING_CANDIDATES` 에 그 두 행이 나란히 있다),
`EMBEDDING_MODEL` 만 바꾸고 `scripts.index_policies` 를 다시 돌리지 않으면 **다른 공간의
벡터를 코사인으로 비교한다.** DB 도 pgvector 도 오류를 내지 않는다.

실측한 결과는 "이상한 수치"가 아니라 **결과 0건**이었다. 다른 공간의 질의는 전 조항이
임계값 아래로 떨어지고, 파이프라인은 그것을 정상 업무 판정인 `no_evidence` 로 기록한다 —
운영 실수(재색인 누락)가 **검색 품질 지표로 위장**된다. 지표가 유일한 주장인 제품에서
가장 나쁜 실패 모양이다.

고친 방식: `policy_chunks` 가 `embedding_model`·`embedding_dimensions` 를 **NOT NULL 로**
들고, `search_policy_chunks` 가 질의 출처를 인자로 받아 유사도 계산 **전에** 대조한다.
불일치는 fail-closed 로 `PolicyIndexProvenanceError`(→ 503 설정 오류)다.

세 가지가 이 설계의 이유다:
- **확인을 호출자에게 맡기지 않는다.** 검색 함수 밖에 두면 새 호출자마다 다시 빠뜨릴 수 있고,
  빠뜨린 결과가 오류처럼 보이지 않는다.
- **전 행을 본다.** `ORDER BY … LIMIT k` 결과만 검사하면 상위 k 밖의 낡은 행을 놓친다.
  적재가 도중에 끊겨 두 출처가 섞인 상태도 같은 검사에 걸린다.
- **행 0개는 불일치가 아니다.** 적재 전과 다른 공간은 다른 상태다.

## τ 는 임베딩 모델에 묶인다 — 임베딩을 상향하면 기권 게이트가 조용히 무력해진다

기권 게이트([결정 0014](tracking/decisions/0014-기권-게이트를-1위-top_k위-산포-축으로-채택한다.md))의
τ=0.06 은 **`text-embedding-3-small` 1536차원에서만** 성립한다. 무근거 문의(G21~G24)의 통계량
최댓값과 정답이 있는 25건의 통계량 최솟값 사이에 틈이 있어야 τ 를 끼울 수 있는데, 그 틈이
모델을 바꾸면 **음수가 된다**.

손계산 산출물(`uv run python -m scripts.handcalc_adoption_axis` → `reports/adoption-axis-handcalc.md`,
입력은 커밋된 `reports/retrieval-strategies-live-*.json` 뿐이라 무과금·재현 가능)의 값이다.
**이 산출물은 gitignore 라 저장소에 없다 — 위 명령을 돌려야 생긴다.** 인용 수치 자체는
`tests/test_adoption_axis.py` 가 못박는다.
통계량은 채택된 축(1위 − `top_k`위 산포)이다.

| 조건 | 기권 쪽 최대 | 채택 쪽 최소 | 여유 |
|---|---|---|---:|
| `-3-small` d1536 blind (**현행**) | G23 0.0521 | G15 0.0668 | **+0.0147** |
| `-3-small` d1536 oracle | G23 0.0571 | G11 0.1105 | +0.0534 |
| `-3-large` d1536 blind | G22 0.0671 | G29 0.0557 | **−0.0114** |
| `-3-large` d3072 blind | G22 0.0784 | G29 0.0624 | **−0.0160** |

**`-3-large` 계열에서는 어떤 τ 도 두 군을 가르지 못한다.** 그리고 이건 이 통계량만의 문제가
아니다 — 같은 산출물에서 후보 통계량 **다섯 개 전부**가 `-3-large` 두 조건에서 음수 여유다
(표준편차 −0.0037/−0.0045 · 산포비 −0.0537/−0.0646 · 1위−2위 gap −0.0120/−0.0368 ·
꼬리비 −0.4499/−0.4724). 축을 바꿔서 피할 수 있는 문제가 아니라는 뜻이다.

**무력해지는 방식이 조용한 것이 위험이다.** `EMBEDDING_MODEL` 을 올리고 재색인까지 정상으로
마치면 provenance 검사(아래 절)는 통과한다. 게이트는 계속 돌지만 τ 가 엉뚱한 자리에 있어
**무근거 문의를 못 거르거나 정답 조항을 통째로 자른다.** 어느 쪽이든 오류가 아니라 "검색
품질"로 보인다.

막는 장치는 **셋**이다. **앞의 둘은 드러내는 장치이고, 셋째만 실제로 막는다**:

- `config.py` 의 `embedding_model` 주석이 재산출이 명시적 작업임을 그 자리에서 말한다.
- 실행 조건 지문에서 `abstention_tau` 와 `embedding_model` 이 **한 쌍**이다
  (`regression_guard.PAIRED_FINGERPRINT_FIELDS`) — 모델이 다르면 τ 가 같아도 대조 불가다.
  **사후에 "대조 불가"로 드러나는 것이지 실행을 막지는 않는다.**
- **셋째(2026-08-20 추가): 조립이 죽는다.** `Settings.abstention_gate()` 가 검증된
  `(모델, 차원)` 조합이 아니면 명시적 오류를 낸다(`AbstentionGateWiringError`) — 조용히
  게이트를 끄지도, τ 를 추정하지도 않는다. 가드가 보는 것은 **τ 값이 아니라 조건**이라
  τ 를 만져 불일치를 무마할 수 없고, 검증 조건 목록은 설정 필드가 아니라 **모듈 상수**다
  (설정 필드로 두면 `.env` 한 줄이 가드를 끄고 그 실행이 "게이트를 켜고 돌았다"로 집계된다).
  **게이트를 명시적으로 끈 실행은 통과시킨다** — 새 임베딩으로 τ 를 재산출하려면 그 조건에서
  한 번은 돌려야 하는데 등재는 실측 뒤에나 가능하고, 가드가 자기가 요구하는 명시적 경로를
  스스로 막으면 안 되기 때문이다. 그 실행은 지문에 `"꺼짐"` 으로 남는다
  ([결정 0023](tracking/decisions/0023-자격-증명을-비밀-전용-타입으로-옮기고-기권-게이트-조립을-임베딩-조건에-묶는다.md)).

**짝을 적을 때는 짝이 실제로 달라졌는지 먼저 보라.** 이 가드가 처음에는 τ 어긋남에 짝 이름을
**값 비교 없이** 붙였고, 그 결과 커밋된 리포트 18건이 *"짝인 `embedding_model` 도 함께
달라졌다"* 를 실었다 — 임베딩은 한 번도 바뀌지 않았는데 없던 사실을 적은 것이다. 짝 관계를
**설명**하는 문장과 짝이 **달라졌다고 보고**하는 문장은 다르고, 후자는 값을 봐야 한다.
코드는 고쳤고(짝만 다름·값만 다름·둘 다 다름 세 경우를 회귀 테스트가 못박는다) 산출물은
보존한 채 정정을 문서에 병기했다([findings 23](tracking/findings.md)).

**임베딩을 상향하는 사이클은 τ 재산출을 같은 작업에 넣어라.** 격자를 다시 돌리는 것 자체는
무과금이지만(커밋된 산출물 재채점) 새 모델의 검색 산출물은 새로 사야 한다.

## DB 통합 테스트의 skip 은 정직해야 한다

`db` 마커 테스트가 DB 없을 때 조용히 skip 되면, 전체 녹색이 아무것도 증명하지 않는다.
skip 사유에 **접속 대상·원인·복구 명령**을 함께 담고, 게이트를 통과시킬 때는
`uv run pytest -m db` 로 **skip 0** 을 따로 확인한다. "돌았다"가 아니라 "무엇이 돌았다"가 증거다.

## 워크트리마다 compose 가 컨테이너를 재생성한다

다른 디렉터리에서 `docker compose up -d --wait` 를 실행하면 compose 프로젝트 설정 해시가 달라
같은 이름의 컨테이너를 **재생성**한다. 데이터는 named volume(`reply-gate-pgdata`)에 있어 남지만,
공유 DB 를 쓰는 다른 작업이 있을 때는 놀랄 수 있다.

## 병렬 작업이 정책 색인을 덮어쓸 수 있다 — 라이브 실측 전에 출처를 확인하라

**DB 는 워크트리 사이에 공유된다.** 컨테이너 이름(`reply-gate-postgres`)과 볼륨
(`reply-gate-pgdata`)이 고정이고, 워크트리의 `.env` 는 보통 본체 `.env` 로의 심볼릭 링크다.
그래서 다른 워크트리에서 도는 작업이 **같은 `policy_chunks` 를 본다.**

이번 사이클에 `--stub-llm` 실행이 DB 의 임베딩을 **어휘 임베딩 대역**으로 덮어쓴 사례가 났다.
대역 임베딩은 실제 임베딩과 스케일이 달라, 그 상태로 라이브를 재면 채택 집합도 기권 게이트
통계량도 전부 다른 수가 된다 — **그리고 오류가 나지 않는다.** provenance 검사는 모델 이름과
차원만 보는데, 대역 적재도 자기 이름을 정직하게 적으므로 "다른 공간"으로 걸리는 것이 아니라
**그 이름의 인덱스가 통째로 바뀐 상태**가 된다.

확인한 것과 확인하지 못한 것을 갈라 적는다.

- **확인한 것**: `scripts/evaluate.py` 의 `--stub-llm` 경로는 대역 적재를 트랜잭션 안에서
  하고 `finally` 에서 롤백한다. `policy_index.index_policy_documents` 는 스스로 커밋하지
  않는다. DB 를 건드리는 다른 진입점은 `scripts.index_policies`(실제 임베딩) 하나이고,
  테스트는 롤백 픽스처를 쓴다. **즉 지금 코드에서 이 사고를 재현하는 경로를 찾지 못했다.**
- **확인하지 못한 것**: 실제로 덮어쓴 경로. 롤백은 **호출부마다 다시 걸어야 하는 규율**이지
  한 자리에서 강제되는 불변식이 아니므로, 새 진입점이나 임시 스크립트 하나가 같은 사고를
  다시 만들 수 있다.

**그래서 규율이 아니라 절차를 남긴다 — 라이브 실측 전에 색인 출처와 건수를 확인한다.**

```bash
uv run python -c "
from reply_gate.db import connect
with connect() as conn, conn.cursor() as cur:
    cur.execute('select embedding_model, embedding_dimensions, count(*) from policy_chunks group by 1,2')
    print(cur.fetchall())
"
# [{'embedding_model': 'text-embedding-3-small', 'embedding_dimensions': 1536, 'count': 26}]
```

기대와 다르면 `uv run python -m scripts.index_policies` 로 다시 만든다(26 청크 · 임베딩 토큰
2,577 · [pricing](tracking/pricing.md) 1절 단가로 **$0.0001 미만**). **재색인이
과금이라는 것이 이 확인을 건너뛰게 만드는 유혹이고, 잘못된 색인 위에서 산 라이브 3회가 훨씬
비싸다.**

## 스키마를 바꿨으면 볼륨째 지워야 한다 — **컬럼 추가만 예외다**

`db/schema.sql` 은 전부 `CREATE TABLE IF NOT EXISTS` 라 **기존 테이블의 컬럼은 바뀌지 않는다.**
마이그레이션 도구는 이 사이클 범위 밖이므로, 스키마 변경 후에는
`docker compose down -v && docker compose up -d --wait` 로 볼륨째 재생성한다.

**단 컬럼 추가는 볼륨을 지우지 않는다.** `ALTER TABLE … ADD COLUMN IF NOT EXISTS` 는 이 파일의
기존 성질(재실행 안전·멱등)을 유지하면서 살아 있는 볼륨에 붙고, PG11+ 에서 기본값이 있는
컬럼 추가는 테이블 재작성 없는 메타데이터 연산이다. 검색 계열 컬럼 3개가 이 방식으로 들어갔다.

이 예외를 만든 이유는 편의가 아니라 **비용**이다. 이 저장소의 `down -v` 뒤에는 두 가지가
붙는다: 보존하기로 한 처리 기록(오탐 버그 시절 기록·데모용 기각→재생성→통과)의 덤프·복원과,
**유료 정책 재색인**. 컬럼 하나 늘리자고 그 둘을 태울 이유가 없다. 대신 새 볼륨에서도 맞아야
하므로 **CREATE TABLE 쪽과 ALTER 쪽 두 자리에 같은 정의를 적는다** — 그 중복이 이 방식의
값이다. 컬럼 **변경·삭제**는 여전히 볼륨 재생성이다.

## 근사 인덱스가 검색을 조용히 잘라먹었다

`policy_chunks` 에 HNSW 인덱스(`USING hnsw (embedding vector_cosine_ops)`)가 있었다. HNSW 는
**근사** 인덱스다 — `LIMIT k` 를 요청해도 k 보다 적게, 그리고 **1위가 빠진 채** 돌려줄 수 있다.

실측한 모양이다(계측을 넣고 `pytest -m db` 를 반복해 잡았다):

```text
top_k=5  db_rows=1  table_rows=26  thr=0.0  sims=[('policy:refund:2-6', 0.1776)]
```

26행이 전부 보이는 테이블에서 5행을 요청했는데 **1행**이 돌아왔고, 그 1행은 1위
(`policy:refund:2-2`, 0.2054)가 아니라 2위였다. 같은 질의·같은 유사도인데 세션 앞부분에서는
5행이 정상으로 돌아왔다 — 세션이 진행되며 **롤백된 트랜잭션이 남긴 죽은 인덱스 항목**이
쌓이면 그래프 탐색이 방문하는 후보 중 보이는 것이 줄어들기 때문이다.

**증상이 "오류"가 아니라 "검색 품질"로 보인다는 것이 이 결함의 값이다.** 근거가 덜 잡히면
`no_evidence` 인계가 늘고, 그 숫자가 리포트에 검색 품질로 실린다. 낡은 인덱스 건(위)과 같은
계열의 실패 — **운영·인프라 사고가 업무 판정으로 위장한다.**

고친 방식은 인덱스를 **없애는 것**이다. 조항 26개에서 정확 스캔은 0.1 ms 미만이고, ANN 인덱스는
수백만 벡터를 안 훑으려고 있는 것이지 26개를 위해 recall 을 확률적으로 깎으라고 있는 것이
아니다. 규모가 커져 인덱스가 다시 필요해지면 **정확성 보장과 함께**(예: pgvector 0.8 의
`hnsw.iterative_scan`) 세우고, 그 보장을 테스트로 바꾼다.

진단에서 두 번 헛짚었으므로 방법도 적어 둔다:

- **인덱스를 `DROP` 하고 테스트를 돌려 봤는데 그대로 재현됐다** — `seed_orders()` 가 세션마다
  `apply_schema` 를 돌려 `CREATE INDEX IF NOT EXISTS` 가 인덱스를 즉시 되살렸기 때문이다.
  스키마를 손보지 않은 DB 조작은 다음 테스트 실행이 되돌린다.
- **재현 스크립트를 따로 짜서 120회 돌렸을 때는 100% 안정적이었다.** 이 결함은 세션에 쌓인
  죽은 튜플이 조건이라 깨끗한 프로세스에서는 나오지 않는다. **결국 잡은 것은 실행 경로에
  계측을 넣고 실패할 때까지 스위트를 반복한 것**이다 — 증상을 재현하는 최소 스크립트를
  만들려는 시도가 오히려 조건을 지웠다.

## 의존성으로 자원을 열면 라우트의 선검사는 이미 늦었다

이 모듈은 LLM 클라이언트에 대해 그 교훈을 이미 적어 두었다(아래 "목만으로는 잡히지 않는
결함") — 조립 시점에 만들면 키가 없는 환경에서 LLM 을 쓰지 않는 경로까지 무너진다고.
**DB 커넥션에는 그 교훈이 적용되지 않은 채 남아 있었다.** `get_service` 가 `Depends` 로
커넥션 2개를 열었고, DB 가 없으면 실측이 이랬다:

```text
POST 빈 content            → 500  (422 여야 한다)
POST 주문번호 형식 오류     → 500  (422 여야 한다)
POST 판정 키 없음          → 500  (503 여야 한다)
```

**"라우트 첫 줄에서 선검사한다"로는 못 고친다.** 의존성은 라우트 본문보다 먼저 풀리고,
요청 본문 검증도 프레임워크가 의존성을 다 푼 뒤에 한다. 선검사를 라우트 안에서 아무리
앞으로 당겨도 커넥션이 먼저 터진다.

고친 방식은 **순서를 바꾸는 것이 아니라 비용을 옮기는 것**이다: `get_service` 는 조립만
돌려주고(`ServiceOpener`), 라우트가 자기 선검사를 끝낸 뒤 `with open_service() as service`
로 연다. 해석이 공짜가 되면 프레임워크가 의존성을 어떤 차례로 풀든 결과가 같다 —
**프레임워크의 내부 순서에 기대는 수정은 업그레이드 한 번에 조용히 되돌아간다.**

DB 가 **진짜** 필요한 경로(조회·처리)는 그대로 500 이다. 그것까지 삼키면 DB 장애가 업무
판정이 된다(`docs/standards.md` "오류를 업무 판정으로 바꾸지 않는다"). 회귀 테스트가
양쪽을 함께 못박는다 — 죽은 포트로 설정을 돌려 **DB 없이** 돌리고, 422·503 과 500 을
같은 실행에서 확인한다.

## 목만으로는 잡히지 않는 결함이 있다

FastAPI 의존성 주입을 override 한 테스트는 클라이언트 **생성 시점**의 오류를 놓친다.
`openai.OpenAI(api_key="")` 는 생성자에서 예외를 던져, LLM 을 전혀 쓰지 않는 경로
(`GET /inquiries/{id}`, 접수 거부 422)까지 500 이 됐다. 목이 전부 녹색인 상태에서 **런타임
스모크가 잡아냈다.** 서버를 실제로 띄우고 몇 개 요청을 던지는 절차를 생략하지 마라.

## 평가 하네스의 대역 수치를 실제 수치로 읽지 마라

`--stub-llm` 은 결정론 대역으로 배관만 검증한다. 어휘 기반 임베딩 대역의 유사도는 실제
임베딩과 스케일이 달라(0.2~0.3대) 기본 임계값 0.3 에서는 대부분 걸러진다. 그래서 대역
실행은 임계값을 낮춰 돌고, 리포트에 **경고와 실행 조건**이 함께 찍힌다. 대역으로 낸
기각 재현율 100% 와 실제 6.7% 가 그 차이다.

## 정답 정책을 본 재작성문은 배포 가능한 개선폭이 아니다

처음 만든 검색 재작성 픽스처는 정답 조항 번호와 어휘를 note 에 적고, 그 어휘를 질의에도
주입했다. 구조는 재현 가능했지만 측정한 것은 일반 질의 재작성의 개선폭이 아니라 정답을 본
oracle query 의 상한이었다. 원문에 없던 결제 수단·운영시간·주문번호 필요성·본인 확인 결론도
섞여 요청 유형과 단정 강도가 바뀌었다.

기본 비교 입력은 정책·라벨을 본 적 없는 생성 모델이 문의 원문만 보고 만든
`data/rewritten_queries.jsonl` 이다(생성기는 `scripts/generate_blind_rewrites.py`).
기존 curated 세트는 `data/rewritten_queries_oracle.jsonl` 로 별도 보존하고 리포트에서
`oracle_upper_bound` 로 표시한다. 두 조건의 수치를 같은 의미로 해석하지 않는다.

검색 정답 라벨은 recall 계산을 위한 **직접 관련 조항**(정면 조항 + 상충 조항, 결정 0010)의
집합이다. 반면 L2 judge 픽스처의 citation sufficiency는 주어진 답변이 최소한으로 충분히
뒷받침되는지를 판정한다. 따라서 G18 검색 라벨에 2-6 과 상충 조항 2-4 가 모두 들어가도,
2-6 만 인용한 충분한 답변이 judge pass인 것과 모순되지 않는다. 두 계약을 합치면 검색기가
정당한 관련 조항을 찾은 결과와 답변이 불필요한 조항까지 모두 인용해야 하는지를 같은 문제로
오채점하게 된다.

## 어휘가 겹친다고 정답을 본 것은 아니다

사람이 손으로 쓴 blind 재작성이 정답 조항의 표제어를 들여온다는 지적이 리뷰 4회 중 3회
나왔다(구어체 "바꾸고" → "변경", "몇 번으로 걸면" → "고객센터"). 그럴듯한 지적이었고 정량
대조로 원문에 없고 정답 조항에 있는 문자 2-gram 이 실제로 세어졌다.

같은 자리를 **정책 문서를 입력으로 받은 적이 없는 생성 모델**에게 맡기고 같은 지표를 다시
재니 결과가 뒤집혔다 — 모델 재작성의 유입이 사람이 쓴 것의 **두 배 이상**이었다
(18건/33개 vs 7건/16개, 정답 있는 25건 기준). oracle 은 25건/144개다.

구어체를 문서체로 정규화하면 정답 조항과 같은 낱말이 나오는 것이 정상이고, 그것은 정답을
봤다는 증거가 아니다. **누출로 갈라야 하는 것은 어휘 겹침이 아니라 정답 조항에만 있는 값**
(근거 ID·조항 번호·정책 고유 수치)이다. 지금은 그것만 구조 테스트가 막는다
(`tests/test_rewritten_queries.py`).

일반화하면: **사람이 만든 평가 입력에 대해 "이건 너무 유리한 것 아닌가"를 사람이 판정하면
그 판정 자체가 측정에 실린다.** 판정 대신 조건을 실제로 재현해 재보는 편이 싸고 결론이 다르다.

## 순위 기반 점수로 채택을 판정하면 기권이 사라진다

하이브리드 단의 채택 컷을 RRF 점수로 두었더니 **어떤 조항도 걸러지지 않았다.** 벡터·BM25 두
순위가 조항 26개 전량을 덮으므로 모든 조항이 양쪽에 있고, 최소 RRF 는 `2/(60+26) = 0.023256`
이라 기본 컷 0.02 를 넘을 수 없다. 컷은 항등이었고 하이브리드는 모든 문의에서 정확히
top_k 건을 채택했다. 근거가 없어야 정답인 문의에서 벡터는 precision 1.0, 하이브리드는
구조적으로 0.0 — 검색 품질이 아니라 산술이 만든 격차였다.

교훈은 컷 값이 아니다. **순위 융합 점수에는 "관련 없음"이 없다.** 채택·기권은 절대 관련성
축(코사인)이 정하고, 순위 점수는 순서만 정한다. 컷을 새로 고를 때는 그 값이 이 코퍼스에서
실제로 걸러낼 수 있는지 코드가 검사하게 했다 — 걸러내지 못하는 컷은 걸러낸 척한다.

같은 구조적 함정이 리랭크에도 있었다. 후보가 `fused[:top_k]`(5)이고 채택 상한도 5면 리랭크
채택 집합은 하이브리드와 **항등**이라 precision·recall·recall@5 가 정의상 같은 값이 된다.
실제 모델을 태워도 그 열은 움직이지 않는다. 후보 풀을 채택 상한보다 크게 두는 것을 코드가
강제한다. 자세한 근거는 [결정 0009](tracking/decisions/0009-채택-판정을-절대-축으로-통일한다.md).

## 지표 분모를 함께 인쇄하지 않으면 비교표가 거짓말한다

"채택 0건 + 정답 있음"을 precision 평균에서 빼는 규약 자체는 맞다. 문제는 컷의 실효 강도가
전략마다 달라 제외 케이스 수가 갈리는데 markdown 표가 분모를 찍지 않은 것이었다. 대역 실측에서
vector 는 30건 중 13건의 평균 0.769, 하이브리드는 30건 평균 0.187 이었다 — 나란히 놓인 두 수가
서로 다른 표본의 평균이었고, 표를 읽는 사람은 같은 분모를 가정한다.

컷을 올릴수록 precision 이 1.0 에 수렴하는 것도 같은 함정이다. 어려운 케이스가 분모에서
사라지고 빈 정답 케이스만 남는다. 분모(`precision n`)를 값과 같은 표에 두고, 전략마다 컷을
훑어 최적점을 함께 낸다.

## 무과금이라고 안내한 플래그가 과금했다

`--bge-m3` 는 help 에 "DB·외부 API 없음"이라고 적혀 있었지만 `live=bool(args.live or
args.bge_m3)` 로 live 경로를 타고, 기본 사다리에 리랭크 단이 있어 `OpenAIGenerationClient` 를
만들어 문의마다 실제 호출을 냈다. 키가 없으면 "로컬 전용" 옵션이 실행조차 되지 않았다.

**임베딩 위치와 리랭크 과금은 다른 축이다.** 둘을 한 불리언으로 묶으면 한쪽 의도가 다른 쪽을
조용히 켠다. 지금은 `paid_rerank` 가 별개 인자이고, 미승인 상태에서 리랭크 단은 0 이 아니라
"미측정 + 사유"로 리포트에 남는다.

## 조용한 폴백은 실패한 실행과 성공한 실행을 구분하지 못하게 만든다

`llm_rerank` 가 `except Exception: return candidates` 로 모든 실패를 입력 순위 유지로 흡수했고
폴백 건수가 어디에도 남지 않았다. 리랭크 채택 집합이 하이브리드와 항등이던 것과 겹치면,
30건 전부 실패한 실행과 성공한 실행이 리포트상 **완전히 같아진다.** 리포트는 여전히
`rerank_model` 을 실행 조건으로 찍으므로 "리랭크를 돌렸다"로 읽힌다.

폴백은 유지하되 사유·건수·토큰이 호출자에게 올라가고 리포트가 집계한다. 실패한 순위를
캐시에 쓰지 않는 것도 함께 막았다 — 쓰면 다음 실행이 그것을 성공으로 재사용한다.

## 라이브 리포트를 기본 실행이 덮어썼다

`--live` 실행과 기본 실행이 같은 파일(`reports/evaluation.{md,json}`)에 썼다. 라이브
실측 뒤에 아무 생각 없이 돌린 기본 실행 한 번이 **유일한 실측 근거를 "측정 2 미실행"
리포트로 덮어썼고**, `reports/` 는 gitignore 라 되돌릴 백업이 없었다. 문서는 70.0% 를
인용하는데 그 수치를 낸 산출물은 사라진 상태였다 — 재현하려면 과금되는 재실행이
필요하고, 확률 층이라 같은 값도 나오지 않는다.

고친 방식은 이름 규칙을 **양방향 불변식**으로 만든 것이다: **라이브 이름 ⇔ 실측**
(`evaluation.resolve_report_stem`, 단위 테스트 있음). 비실측 실행은 라이브 이름을 쓸 수
없고(기본 이름도 실측 여부로 갈린다 — `--live` 여도 키·DB 문제로 미실행이면 `evaluation`),
실측 실행은 라이브 이름만 쓸 수 있으며, 이미 존재하는 라이브 리포트는 덮어쓸 수 없다.
검사는 측정 시작 전에 돌고, stem 은 경로가 아닌 파일 이름 조각만 받는다(`./`·`../`·절대경로
·대소문자 변형 우회를 막는다 — 첫 구현은 이 우회들에 전부 뚫렸고 리뷰가 잡았다).
라이브 리포트만 gitignore 예외로 추적한다.

교훈: 재생성에 돈이 드는 산출물은 재생성이 공짜인 산출물과 **같은 경로를 쓰면 안 된다.**
덮어쓰기를 막는 것은 규율이 아니라 코드여야 한다.

## 읽는 곳이 0인 필드는 죽은 게 아니라 **배선이 빠진 것**이었다 — 세 번 다

정의하고 생산까지 하는데 **읽는 곳이 하나도 없는** 필드를 감사가 셋 찾았다. 셋 다 지우는
것이 답이 아니었다 — 지우면 그 필드가 유일하게 들고 있던 구분이 사라지고, 그 자리를
**고정 문장이나 침묵이 대신**한다.

| 필드 | 없으면 무엇이 사라지나 | 실제로 무슨 일이 났나 |
|---|---|---|
| `RunSummary.attribution_reason` | 귀인 절이 **왜** 없는지 | 가드가 "옛 산출물이라 필드가 없다"는 **고정 문장**을 찍었다. 산출물이 사유를 들고 있는데도 그랬고, 그 거짓 문장이 커밋된 리포트 5건에 영구히 남았다 |
| `RunSummary.measurement3_executed` | **미실행**과 **미상**의 구분 | 둘 다 "한쪽이 미상이거나 세트 안에서 흔들려"로 뭉쳤다. `evaluation-live-{1,2,3}.json` 은 L2 이전 세대라 측정 3 절 자체가 없는데, 리포트는 그것을 "미상"이라 적는다 |
| `ChunkingCaseScore.ranked_unit_ids` | **컷이 무엇을 잘랐는지** | 직렬화가 `accepted_unit_ids` 만 실어, 커밋된 `retrieval-chunking-live-*.json` 에서 순위를 되짚을 수 없다. 같은 계열인 전략 리포트는 `ranked_hits` 를 함께 싣는다 |

**가려내는 질문은 "읽는 곳이 있나"가 아니라 "생산자가 이미 알고 있나"다.** 셋 다 생산 지점이
정확한 값을 손에 쥐고 있었고 소비 지점만 없었다 — 그건 **정보가 없는 게 아니라 버려지는**
것이다. 반대로 생산자도 모르는 값을 담는 필드였다면 지우는 것이 맞다.

**한 방향 더**: 같은 사안을 다루는 **자매 산출물과 필드를 맞대 보라.** 청킹 리포트의 누락은
전략 리포트가 같은 자리에 `ranked_hits` 를 싣는다는 사실 하나로 드러났다. 한 파일만 보면
"원래 이런 리포트"로 읽힌다.

## 커밋된 리포트의 mismatch 문자열로 재채점하지 마라

라벨 재정렬(결정 0008)의 전후 병기 수치를 처음에는 **구 리포트의 `mismatches` 문자열에서
"기각을 기대했으나…" 항목만 빼는 방식**으로 계산했다 — 사이클 1 이 83.3% 로 나왔고 틀린
값이었다. 리포트의 mismatch 는 **그 실행 시점의 라벨**로 채점된 결과라, 사이클 1 리포트에는
사이클 2 초입의 라벨 확장(G17 에 `no_evidence` 허용) 이전 판정이 그대로 들어 있었다.
두 사이클을 이 방식으로 나란히 놓으면 **서로 다른 채점표로 채점한 값을 비교**하게 된다.
독립 리뷰(Opus 5)가 잡았고, 정답은 리포트의 `outcomes` 원시 필드(status·escalation_reason·
attempt_verdicts·reject_reasons)에 **현재 라벨 전체로 `_compare` 동등 로직을 다시 돌리는 것**
이다(사이클 1 = 86.7%).

교훈: 리포트의 판정 필드(`matched`·`mismatches`)는 당시 채점표의 산출물이다. 채점표를 바꾼
뒤의 재채점은 반드시 **원시 결과 필드 + 현재 라벨 전체**로 처음부터 다시 계산한다.

## 커밋된 리포트의 "사람이 읽는 줄"이 틀릴 수 있다 — 정본은 조건 지문이다

`evaluation-live-l2-19` … `-24` 여섯 리포트의 `conditions.judge` 가 전부
``Anthropic `claude-sonnet-5` (effort=기본값)`` 로 적혀 있다. 실제로는 **haiku 3세트 ·
opus 3세트**로 돌았다([결정 0018](tracking/decisions/0018-판정-모델-Anthropic-3종을-비교만-하고-기본값은-바꾸지-않는다.md)).

원인은 `scripts/evaluate.py` 가 같은 자리에서 **두 개의 설정 객체**를 읽은 것이다:
사람이 읽는 설명은 `_judge_label(settings=settings)` 로 **인자가 덮기 전의 기본 설정**을,
기계가 읽는 지문은 `_condition_fingerprint(run_settings=run_settings)` 로 **덮인 설정**을
읽었다. 한 리포트 안에서 두 값이 갈렸다.

| 리포트 위치 | 값 | 맞는가 |
|---|---|---|
| `conditions.judge` (md 머리말 · 측정 3 절의 "판정 모델") | `claude-sonnet-5` | **아니다** |
| `conditions.condition_fingerprint.judge_model` (조건 지문 표) | `claude-haiku-4-5` / `claude-opus-5` | 맞다 |

**측정 결과 자체는 오염되지 않았다** — 측정 3 은 덮인 설정으로 돌았고 회귀 가드도 명시 지문을
읽는다. 세 모델의 판정 분포가 서로 다르다는 것이 그 방증이다.

**코드는 고쳤고 산출물은 그대로 뒀다.** 호출부를 `8e22897` 에서 고치고, 단위 검사로는 안
잡히는 자리라 **호출부를 구조 검사로 못박았다**
(`tests/test_evaluation.py::test_판정_모델_설명은_실행_인자가_덮은_설정을_읽는다`). 커밋된
라이브 실측은 사후 편집하지 않는 것이 이 저장소의 불변식이고, 같은 수치를 다시 사서 덮는 것도
하지 않았다 — 틀린 것은 사람이 읽는 한 줄뿐이다.

**옮겨 가는 규칙 둘:**

- **이 여섯 리포트를 인용할 때 정본은 `condition_fingerprint.judge_model` 이다.**
  `conditions.judge` 줄은 무효다.
- **같은 값을 두 경로로 렌더링하면 언젠가 갈린다.** 실행 인자가 덮는 설정이 있는 자리에서는
  "설명"과 "지문"이 **같은 객체**를 읽는지를 구조 검사로 못박아라. 단위 테스트는 두 경로가
  각각 옳게 도는 것만 확인하고 **어느 것을 넘겼는지는 보지 않는다.**

## 설정 객체가 repr 되면 자격 증명이 평문으로 따라간다

이번 사이클에 **실패한 단언 하나가 pytest 출력에 API 키 전문을 실었다.** `assert` 표현식에
`Settings` 객체가 들어 있었고, 실패 시 pytest 가 그 객체를 통째로 repr 했다. 저장소에 커밋된
적은 없지만 **CI 로그·트레이스백·공유된 실패 출력이 전부 같은 경로**다.

고친 방식은 커밋 `96abb9e`·`be1f235` 다.

- `config.Settings` 의 자격 증명 **네 필드**(`openai_api_key`·`anthropic_api_key`·
  `postgres_app_password`·`postgres_ro_password`)를 `Field(repr=False)` 로 뺐다.
  **값을 읽는 쪽은 그대로다** — 가린 것은 표시이지 값이 아니다.
- `tests/test_config_secrets.py` 가 두 겹으로 지킨다: ① 카나리아 값을 넣고 `repr`/`str`/
  f-string 셋 다에서 새지 않는 것을 확인하고, ② **이름이 비밀로 읽히는 필드 전부**
  (`api_key|password|secret`)를 훑어 `field.repr` 이 참인 것이 하나도 없음을 검사한다.
  ②가 다음에 추가될 자격 증명 필드까지 잡는다.

**그때 막은 것은 repr 경로 하나였고, 그것으로는 부족했다 — 덤프 경로가 통째로 열려 있었다.**
`repr=False` 는 **표시**만 가리는 설정이고 `model_dump()`·`model_dump_json()`·`dict(settings)`·
`vars(settings)`·`settings.__dict__` 계열은 **표시 설정을 아예 보지 않는다.** 2026-08-20 에
자격 증명 네 필드를 **비밀 전용 타입**(`SecretStr`)으로 옮겨 그 경로들도 마스킹 문자열로
나가게 했다 — 타입이 값을 들고 있으므로 어느 직렬화 경로를 타든 같은 답이 나온다.
값을 평문으로 꺼내는 자리는 **패키지 전체에서 다섯 줄**(`config.py` 2 · `llm.py` 3)로 좁히고
구조 검사가 그 개수를 못박는다 — `SecretStr | str` 로 넓히면 검사가 RED 다
([결정 0023](tracking/decisions/0023-자격-증명을-비밀-전용-타입으로-옮기고-기권-게이트-조립을-임베딩-조건에-묶는다.md)).
**그 검사도 이름·문면 기반이라 실수는 잡고 의도적 우회는 못 잡는다**([findings 28](tracking/findings.md)).

**교훈은 "표시와 직렬화는 다른 경로다"이다.** 표시를 가리는 설정으로 직렬화를 막았다고 적으면
문서가 거짓말을 한다 — 그리고 실제로 그렇게 적혀 있었다. **가린 층이 아니라 값을 든 타입이
바뀌어야 경로 전체가 닫힌다.**

**그래도 막지 못하는 것이 남는다.** `print(key.get_secret_value())` 처럼 값을 직접 꺼내 찍는
것은 어떤 설정 클래스도 막지 못한다 — 그건 리뷰가 막는다. **접속 문자열도 이 조치 밖이다**:
값을 조립한 새 문자열이라 필드 규칙이 걸리지 않고, 담지 않으면 DB 에 접속할 수 없다.
**닫히지 않았다는 것을 검사로 못박아 두었다** — 조용히 닫혔다고 믿지 못하게 하는 것이 이
자리에서 할 수 있는 최선이다. 범위를 넓혀 적으면 막지 못하는 것을 막았다고 문서가 거짓말을 한다.

**그리고 막지 못하는 경로 하나가 실제로 값을 치렀다.** 사이클 4 종료 뒤 디스크를 훑어 보니
OpenAI 키가 **에이전트 세션 기록에 평문으로** 남아 있었다 — 2026-08-06 자 서브에이전트
기록(`.jsonl`) 한 곳에 2회. `.env` 를 읽은 흔적이고 `repr` 과는 무관하다. **즉 노출 사건은
둘이었고 문서는 pytest 쪽만 적고 있었다.** 저장소·CI·셸 히스토리에는 없었다(스캔으로 확인).

옮겨 가는 규칙 둘:

- **에이전트에게 `.env` 를 읽히지 마라.** 값이 필요하면 `bool(settings.<필드>)` 로 존재만
  확인한다. 한 번 읽히면 그 세션 기록이 사는 동안 평문으로 남고, 가드는 그 뒤에 못 선다.
- **노출을 고쳤다고 로테이션을 건너뛰지 마라.** `repr=False` 는 **다음 노출**을 막을 뿐
  이미 새어 나간 값을 무효로 만들지 않는다. 이 키는 고친 뒤로도 2주 가까이 유효한 채
  기록에 남아 있었고, **폐기·재발급이 실제 조치였다**(2026-08-19 완료).

**곁가지 하나**: `96abb9e` 는 mypy 가 깨진 채로 들어갔고 바로 다음 커밋(`be1f235`)이 그것을
닫았다. 원인은 검증 명령을 체이닝으로 걸어 실패를 못 본 것이다 — **설정·검증 명령은 체이닝
없이 하나씩 돌린다.**

## 보안 슬라이스 적대리뷰가 제공자 필터에 죽는다 — 산출 형태를 바꿔야 통과한다

사이클 1·2 코어에 블라인드 적대리뷰 12회(4슬라이스 × 3)를 돌렸을 때 **보안·데이터 슬라이스
2회가 Codex 제공자의 사이버보안 콘텐츠 필터에 걸려 최종 작성 단계에서 죽었다.** 조사는 이미
끝난 뒤였고 로그에 요지만 남았다. 같은 프롬프트로 재시도하면 같은 자리에서 다시 죽는다.

통과시키려면 둘을 바꾼다.

1. **산출 형태에서 공격 서사를 뺀다.** 등급 라벨(`FATAL`)·"치명 N경로" 목록·우회 서술과
   payload 문장을 요구하지 말고, **"문서가 주장하는 불변식 중 코드에서 성립하지 않는 것을
   찾아 실패하는 pytest 함수로 표현하라"** 로 재구성한다. 발견 하나당 `파일:줄` / 어긋난
   불변식 / **지금 돌리면 실패하는 테스트 함수** / 고칠 방향, 그리고 등급 대신 **불변식의
   출처(문서 경로:줄)** 를 적게 한다.
2. **슬라이스를 더 잘게 나눈다.** 한 응답에 모이는 양을 줄인다(예: `sql_guard` 단독 /
   `evidence`+`records`+`db`).

이 형식으로 재실행한 2회는 둘 다 완주했고, **진행 중이던 보안 수정본 자체의 구멍(출력 별칭이
연 두 번째 세탁 경로)까지 찾아냈다.** 죽은 채로 뒀으면 수정본을 검사할 사람이 없었다.

교훈: 이건 필터를 피하려는 타협이 아니라 **더 나은 루브릭이다.** 등급과 공격 서술은 어차피
손으로 재현 코드로 옮겨 검증하게 되는 중간 산출물이고, 실패하는 테스트 함수를 직접 요구하면
그 단계가 리뷰어 쪽으로 넘어간다. 재현 불가능한 주장도 같이 걸러진다.

## 결함 보고서를 그대로 티켓으로 옮기지 마라 — 먼저 재현하라

사이클 1·2 코어를 적대리뷰한 일곱 건 + 사이클 3 T7 이 발견한 검색 결함 한 건에서, **여덟 번 중 일곱
번 진단이 보고서와 갈렸다.** 갈린 방향이 제각각이라는 것이 이 규칙의 값이다:

- 세 번은 결함이 **보고서보다 넓었다** — 반대 방향이 함께 있었다(판정이 접히는 것 옆에
  옳은 산출이 거부되는 것, 주입 우회 옆에 주입 없이도 활성인 `attempts` 오차).
- 한 번은 **좁았다** — 주입 우회는 운영 호출부가 0곳이라 잠재였고, 진짜 문제는 "불변식이
  문서에만 있고 그 문서가 근거로 삼은 테스트가 반쪽만 검사했다"였다.
- 한 번은 **지목한 값이 옳았다** — L2 미판정 시도의 `pass` 는 계약이 정한 값이라 그대로
  두는 것이 맞고, 결함은 그 계약을 소비자에게 맡긴 지표 경계에 있었다.
- 한 번은 **실패의 방향이 반대였다** — provenance 부재는 "다른 공간을 비교하며 정상 수치를
  낸다"가 아니라 **결과 0건 → `no_evidence`** 였다. 정상 업무 판정으로 위장되는 쪽이라 더
  조용하고, 그 차이가 곧 수정 방향(503 설정 오류)을 정했다.
- 한 번만 **보고서 문장 그대로였다**(연결 순서). 그런데 그때도 재현이 인접 결함을 하나 더
  내놨다(조회 라우트가 쓰지도 않는 RO 계정에 묶임). **진단이 맞아도 재현은 남는다.**
- 그리고 한 번은 **내 가설이 두 번 틀렸다**(HNSW 근사 인덱스 — 위 절). 자기 가설도 남의
  보고서와 같은 자격으로 재현해야 한다.

여기서 반복된 실패 모양 둘:

- **"이 값을 이렇게 읽지 마라"를 문서에 적었다면 아직 안 고친 것이다.** 읽는 쪽이 하나라도
  있으면 코드가 대신 지켜야 한다.
- **이미 적어 둔 교훈이 같은 종류의 다른 자원에는 적용되지 않은 채 남는다.** 지연 생성은
  LLM 클라이언트에만 걸려 있었고 커넥션에는 없었다. 교훈을 적을 때 **"이 규칙이 걸려야 할
  나머지 대상"을 함께 세어라.**

## 구어체 패러프레이즈는 임베딩이 잇지 못한다 — 재작성이 정면으로 고친다

같은 조항(`policy:support:4-1`)을 겨냥한 두 문의가 표현 차이만으로 갈렸다:

| 문의 | 4-1 코사인 |
|---|---|
| G16 "고객센터 전화번호 알려주세요" | 0.6289 |
| G17 "상담원과 통화하고 싶은데 몇 번으로 걸면 되나요?" | **0.2637** |

조항은 "고객센터·전화·연락"을 쓰고 G17 은 "상담원·통화·몇 번·걸다"를 쓴다.
`text-embedding-3-small` 이 이 한국어 구어체 패러프레이즈를 잇지 못한다.

**임계값을 낮추는 것은 해법이 아니었다** — G17 의 1위는 4-1 이 아니라 **4-7 회원 탈퇴**
(0.2753)였다. 컷을 내리면 맞는 조항보다 엉뚱한 조항이 먼저 올라온다. **점수 문제가 아니라
순위 문제였다는 것이 핵심이다.**

**질의 재작성이 둘 다 고쳤다.** 4-1 이 0.264 → **0.580** 으로 오르고 **순위도 1위**가 됐다.
라이브 3회에서 3회 모두 채택 근거에 실렸다(`reports/evaluation-live-l2-{4,5,6}`).
설계에서 살아남은 규율 하나: **원문과 재작성 질의를 둘 다 검색해 합집합으로 모은다.**
재작성이 주제를 옮기면 원문이 안전망이 되고, 그래서 근거 집합이 확률 층에 종속되지 않는다.

**옮겨 가는 규칙**: 검색이 "못 찾는" 케이스를 만나면 **점수를 올릴 것인지 순위를 고칠 것인지
먼저 가르라.** 컷은 점수만 움직이고 순위는 못 움직인다 — 순위 문제에 컷으로 답하면 엉뚱한
근거를 들이면서 지표는 개선된 것처럼 보인다.

## 집계가 오르는 구간에서 케이스 하나가 죽을 수 있다

사이클 3 T7 이 컷 0.50 을 고른 근거는 오프라인 격자였다. 그 격자에서 컷을 올리는 동안 **케이스가 죽은
걸음이 둘 있었고, 둘 다 macro F1 이 오른 걸음이다.**

| 컷 | P (분모) | R (분모) | macro F1 | 그 걸음에서 죽은 것 |
|---|---|---|---|---|
| 0.35 | 0.230 (30) | 1.000 (25) | 0.374 | |
| **0.40** | 0.255 (**29**) | 0.960 (25) | **0.403** | **G04 가 정답 조항을 전부 잃었다** (recall 1.00 → 0.00) |
| 0.45 | 0.322 (29) | 0.960 (25) | 0.482 | |
| **0.50** | 0.534 (29) | 0.920 (25) | **0.676** | **G18 이 상충 조항 `refund:2-4` 를 잃었다** (1.00 → 0.50) — L2 모순 기각이 사라진 지점. G01 도 함께 0.50 으로 내려갔다 |

**G04 의 전면 실패가 집계에 남긴 자국은 recall 1/25 = 0.04 하나뿐이다.** precision 에는
아무것도 남지 않았다 — "정답이 있는데 0건 검색"은 **평균에서 제외**되므로(분모 30 → 29)
벌점이 아니라 **퇴장**이다. 그 걸음에서 F1 은 0.374 → 0.403 으로 **올랐다.**

**규약이 틀린 것이 아니다.** 분모가 0 인 precision 에 0 이나 1 을 채우면 검색 실패가
precision 을 올리거나 두 번 벌한다 — 제외가 옳다. 틀린 것은 **채택 규칙이 집계만 봤다는
것**이다. 제품에서 "근거 0건"은 부분 손실이 아니라 **상태 전이**(answered → escalated)인데,
집계 단위에는 그 계단이 없다.

**옮겨 가는 규칙 둘:**

- **채택 규칙에 케이스 단위 하한을 함께 걸어라.** "라벨이 있는 케이스가 채택 근거 0건이
  되면 안 된다" 한 줄이면 이 채택은 일어나지 않았다. 평균은 계단을 못 본다.
- **회귀를 잡은 것은 지표가 아니라 귀인이었다.** 같은 실측에서 G18 의 L2 모순 기각이
  사라졌는데(3/3 기각 → 3/3 통과) 일치율·비악화 가드·측정 3 **어디에도 안 잡혔다** —
  라벨이 그 동작을 허용했고 `matched=True` 였기 때문이다. 잡은 것은 케이스별 귀인 절
  하나다(`answered_without_relevant_evidence / missing=policy:refund:2-4`).
  **"무엇이 몇 %인가" 옆에 "어느 케이스가 왜 그랬는가"를 항상 함께 산출하라.**

## 소스 주석이 아카이브될 설계 문서를 인용했다 — 가드로 바꿨더니 번호로 다시 들어왔다

사이클 문서(`.dryforge/spec.md`·`plan.md`·`handoff.md`)는 사이클이 끝나면 `.dryforge/00N/`
으로 옮겨진다. 소스에 남은 `.dryforge/spec.md §8-1` 같은 인용은 **그 순간 존재하지 않는
경로**가 된다. 사이클 3 종료(`d580275`) 뒤 실제로 14곳이 그렇게 깨져 있었다.

**세 번 같은 방식으로 재발했다.** 1차는 약 80곳을 durable 인용으로 되돌렸고(기계 치환이
만든 오귀속 20여 곳을 리뷰가 잡아 손으로 교정), 2차는 사이클 2 에서 24곳으로 재발했고,
3차가 이번 14곳이다. **두 번 다 "주석 쓸 때 durable 문서를 인용한다"는 규율로 막으려
했고 두 번 다 실패했다.** 매 사이클 새 주석이 그 사이클의 설계 문서를 자연스럽게 인용하기
때문이다 — 쓰는 시점에는 그 파일이 실제로 거기 있다.

**그래서 규율을 코드로 옮겼다**: `tests/test_durable_citations.py` 가 `src`·`scripts`·
`tests`·`db`·`docker-compose.yml` 을 훑어 `.dryforge`·`\bspec\b`·`스펙` 을 찾으면 실패한다.
단어 경계 덕분에 `_inspect_schema`·`import inspect` 는 잡히지 않고, **가드가 실제로 무언가를
잡는다는 음성 대조 테스트를 함께 둔다**(빈 검사가 초록으로 보이는 사고는 blind 구조 테스트에서
이미 한 번 겪었다).

**그리고 네 번째가 났다 — 가드가 보는 것은 "파일 이름"뿐이었다.** durable 문서 4곳과
`config.py` 주석 1곳이 `하드 게이트 10` 을 판정 기준으로 인용했는데, `docs/standards.md` 의
하드 게이트 목록은 **5번까지**였다. 10 은 `.dryforge/003/handoff.md` 의 번호였고,
같은 사이클 스펙의 "라이브가 오프라인 채택을 반증하면" 절이 원문이다. 어느 파일도 이름하지 않았으므로 `.dryforge|spec|스펙` 정규식에 걸릴
문자가 하나도 없었다. `evidence.py` 의 `하드 게이트 4` 도 같은 계열이었다 — 정본 4번은
"비밀 평문 금지"인데 그 주석이 말하는 규칙은 사이클 3 handoff 의 4번("조용한 폴백 금지")
이었다. **번호는 존재하는 번호라서 더 나쁘다: 깨진 링크가 아니라 조용히 틀린 링크가 된다.**

**막은 방법은 형태가 아니라 해결 가능성이다.** 빠진 규칙 넷(승격·리포트 무편집·라벨 격리·
실측 정당화)을 정본 목록에 6~9 로 올린 뒤, 가드가 **정본 목록을 읽어 번호 집합을 만들고**
모든 `하드 게이트 N` 인용을 그 집합으로 대조한다. 목록이 자라면 가드도 같이 자라서 상수를
손으로 맞출 일이 없다 — `§N` 인용을 "같은 파일의 절 번호"로 푸는 기존 가드와 같은 수법이다.

**여기서 옮겨 가는 것**: 가드를 세울 때 **인용의 어떤 표면을 잡는지** 적어라. 이 가드는
"경로 문자열"을 잡았고, 그래서 경로를 안 쓰는 인용은 통째로 통과했다. 같은 사고의 다음
변종은 늘 **가드가 안 보는 표면**으로 들어온다.

**인용을 옮길 때 지킬 것 셋:**

- **기계 치환 금지.** 1차에서 오귀속 20여 곳을 만들었다. 한 곳씩 읽고 그 문장이 실제로
  말하는 규칙이 어느 durable 절인지 보고 고친다.
- **인용할 절이 없으면 만든다.** 이번에 `.dryforge/spec.md §8-3`(리포트의 검색 구성 필드)은
  durable 문서에 대응이 없어서 `scripts/AGENTS.md` 불변식 15 를 신설한 뒤 인용했다.
  **없는 절을 인용하는 것이 아카이브된 절을 인용하는 것보다 낫지 않다.**
- **인용 전에 실존을 확인한다**: `grep -n '^#.*<절 제목>' docs/`.

## 존재를 보고 스스로 꺼지는 가드는, 다른 작업이 같은 이름을 들이면 조용히 죽는다

**2026-08-21 에 실제로 났다.** 판정 프롬프트 캐싱 가드는 "런타임 집계 없이 캐싱 기본값을
켤 수 없다"를 지키려고 `pipeline.py`·`records.py` 를 AST 로 훑어 **캐시 계열 이름이 보이면
"배선됐다"로 읽고 스스로 통과**하는 모양이었다. 그런데 생성 계열 캐시 토큰을 배선하는 작업이
`cache_read_input_tokens` 같은 **일반형 이름**을 그 두 파일에 들여왔고, 그 순간 가드가 조용히
꺼졌다 — **판정 캐싱은 여전히 배선되지 않았는데** 가드는 통과한다.

막은 방법은 목록을 **판정 계열 전용 이름**(`judge_cache_*`)으로 좁힌 것이다. 좁히기가 옳았음은
직접 켜서 확인했다 — 캐싱 기본값을 켜면 가드는 여전히 실패하고(fail-closed), 이름 목록을 옛
값으로 되돌리면 조용히 통과한다. **좁힘은 선택이 아니라 필수였다.**

**옮겨 가는 규칙 셋:**

- **"이름이 보이면 통과"로 가드를 짓지 마라.** 그 가드는 **자기 검사 대상이 아닌 코드**의
  이름 선택에 매달린다. 가드가 지켜야 하는 것이 A 인데 B 의 이름이 A 를 증명하게 되면,
  B 를 고치는 사람이 A 를 모른 채 가드를 끈다.
- **못 좁히면 대상 파일을 좁혀라.** 일반형 이름을 피할 수 없다면 검사 범위를 그 이름이
  의미를 갖는 파일로 제한한다.
- **음성 대조가 이것을 잡는다.** 이번에도 가드가 스스로 꺼진 것을 알려준 것은 음성 대조가
  RED 로 터진 것이었다(`tests/AGENTS.md` 불변식 3). 검사기 함수만 태우는 음성 대조는
  **검사 대상 목록이 비어도 초록**이므로, 목록 유도부까지 태워야 한다.

같은 계열을 문자열 스캔 가드에서도 한 번 더 봤다. 기권 게이트 τ 가드는 원래 **소스 문자열
스캔**이었는데, 배선을 일부러 깨는 우회를 넣어 보니 **문자열 스캔은 통과하고 AST 검사만
RED** 였다. 이름·문면을 보는 가드의 한계는 [findings 28](tracking/findings.md) 이 든다.

## 대역이 0 을 신고하는 구간은, 유료를 사기 전에 목으로 리포트 표면까지 따라가라

단계별 지연을 붙였을 때 **대역(`--stub-llm`) 실행에서 밖으로 나가는 여섯 구간이 전부 0.0**
이었다 — 대역은 실제로 나가지 않으므로 정직한 값이다. 그래서 "배선이 되어 있는가"를 무과금
end-to-end 로는 증명할 수 없는 상태가 됐다. **구현 중에 대역에 실제 시계를 붙였다가 되돌린
판단이 옳았다**: 대역 산출의 결정론은 이 저장소의 계약이고, 시계를 붙이면 `--stub-llm` 실행이
재현되지 않는다.

**여기서 멈추면 유료 3회를 사고 나서야 빈 칸을 발견한다.** 실제로 한 것은 다른 쪽이다 —
**구분 가능한 값을 목으로 주입해**(구간마다 다른 숫자) 아홉 구간이 전부 **리포트 표면까지**
도달하는지 실제 DB · 실제 파이프라인으로 확인했고, 예외 경로(형식 실패 → 전송 실패 → 예외)와
`order_not_found` 처럼 일부 구간만 도는 경로도 같은 방식으로 봤다. 유료 실측은 그 확인 뒤에
샀고, 아홉 칸이 전부 실값으로 채워졌다.

**옮겨 가는 규칙**: "대역으로는 증명할 수 없다"와 "무과금으로는 증명할 수 없다"는 **다른
문장**이다. 대역이 못 하는 것은 *밖으로 나가는 시간을 만드는 것*이지 *배선을 따라가는 것*이
아니다. **되돌릴 수 없는 구매 앞에서는, 대역이 못 하는 부분을 목이 대신할 수 있는지 먼저 묻는다.**

## `pytest -q` 를 직접 주면 요약 줄이 사라진다

`pyproject.toml` 의 `addopts` 에 이미 `-q` 가 있다. 명령줄에서 한 번 더 주면 **`-qq` 가 되어
`N passed` 요약 줄이 통째로 사라진다.** 이 저장소는 검증 건수를 문서에 적으므로 그 줄이
없으면 셀 수가 없다 — 건수를 세려면 `-q` 를 빼거나 `--collect-only` 를 쓴다.

## CHECK 제약의 음성 대조는 "거부되는가"가 아니라 "**어느 제약이** 거부하는가"다

`inquiry_attempts` 의 층별 제약은 서로 겹친다. 그래서 모순 상태 하나를 만들면 대개 **제약
둘 이상이 동시에 발화**하고, 검사가 `pytest.raises(CheckViolation)` 만 걸면 그중 아무거나
잡아 준다. 결과는 이렇다 — `inquiry_attempts_l2_reasons_match_verdict` 를 스키마에서
**통째로 지워도 스위트가 초록이었다.** 그 제약에 닿는 유일한 파라미터가 다른 제약도 함께
어기고 있었기 때문이다. 같은 이유로 L1 쪽 "pass ⟺ 사유 0건"의 cardinality 가지도 물리지
않았다(`reasons_compose_layers` 가 먼저 잡는다).

**규율 둘.**

1. **격리 케이스를 손으로 검산해서 짠다.** 제약 목록 전체를 놓고 한 줄씩 대조해, 노리는
   제약 **하나만** 거짓이 되는 조합을 찾는다. 예: `verdict='reject'` ·
   `reject_reasons=['unsupported_claim']` · `l1_verdict='pass'` · `l1_reject_reasons=[]` ·
   `l2_verdict='pass'` · `l2_reject_reasons=['unsupported_claim']` 은 종합·L1·조합·NULL 스코프
   제약을 전부 통과하고 L2 쪽 하나만 어긴다.
2. **`error.diag.constraint_name` 을 단언한다.** 이름을 안 보면 "다른 제약이 대신 잡는" 상태와
   "노린 제약이 잡는" 상태가 검사에서 같아진다. 논리적으로 단독 격리가 불가능한 조합이면
   (예: `l2_verdict='reject'` 인데 사유 0건) 억지로 만들지 말고 `in {…}` 로 두거나
   그 가지를 격리 대상에서 빼고 그 사실을 적는다.

**뮤테이션은 스크래치 DB 에서 돌린다.** 본 볼륨을 지우지 않고 확인할 수 있다 — 별도 DB 를
만들어 `db/schema.sql` 을 적용하고, `ALTER TABLE … DROP CONSTRAINT` 로 노린 제약만 지운 뒤
같은 INSERT 가 **통과하는지** 본다. 통과하면 그 제약이 유일한 방어였다는 뜻이고, 검사를 붙일
자리가 확정된다. 확인이 끝나면 `DROP DATABASE` 로 지운다(좀비 금지).
이 함정의 실물은 [findings 35번](tracking/findings.md)(닫혔다)이고, 같은 계열이 조회 가드
분기 넷에도 있었다([33번](tracking/findings.md) — **2026-08-25 에 같은 규율로 닫았다**).

**이 규율은 DB 제약만의 것이 아니다 — 겹치는 판정 분기 전부에 걸린다.** 조회 가드의 PII 유래
판정도 같은 모양이었다: 음성 파라미터 스물여섯이 전부 `_safe(sql) == ()` 를 단언했는데, 분기
넷은 뒤집어도 스위트가 초록이었다. 그 입력들이 **다른 이유로도** 불승인이라 노린 분기를
지워도 다른 분기가 대신 잡아 준 것이다. 넓은 목록에 파라미터를 더하는 것으로는 이 공백이
닫히지 않는다 — **분기 하나만 판정을 가르는 입력**을 따로 짜야 한다.

| 분기 | 그 분기에만 닿는 입력 |
|---|---|
| `_resolve_bare_pii_safe` 의 `all` | 같은 이름을 내놓는 소스가 둘이고 **한쪽만** 증명됐다 |
| `nullif` 비교 상대 검사 | `a` 는 직접 컬럼이라 통과하고 **`b` 만** 증명되지 않았다 |
| `coalesce` 전부 고정값 | 인자에 UNKNOWN 이 **없어서** 앞 가지에서 안 걸린다 |
| `o.*` projection | 별표가 `coalesce` **인자 자리**로 들어와 소스 단위 처리를 안 거친다 |

**뮤테이션은 실제로 돌려 확인한다.** DB 제약은 스크래치 DB 에서, 순수 함수 분기는 모듈
속성을 잠깐 갈아 끼우고 같은 입력의 판정이 갈리는지 본다(넷 다 `()` → `("customer_phone",)`).
"뒤집으면 갈릴 것이다"는 추측이고, 갈리는 것을 본 뒤에 검사를 붙이는 것이 규율이다.


## 판정 수단이 없는 게이트는 "통과"가 아니라 **미측정**이다 — 링크 검사를 만들자마자 걸렸다

병합 조건이 문서 변경마다 *"링크와 앵커를 프래그먼트까지 검사해 0건 깨짐"* 을 요구했는데
**그 검사가 저장소에 없었다**([findings 34](tracking/findings.md)). 실물은 0건이었지만 그것은
사람이 손으로 확인한 값이고, 다음 변경이 깨뜨려도 스위트는 초록이었다.

검사기(`scripts/check_links.py`)를 세우고 `pytest` 에 물자 **그 세션 안에서 바로 실제 깨짐이
잡혔다** — findings 24 를 닫으며 제목에 "닫혔다" 를 붙인 순간 다른 문서가 걸어 둔 앵커가
어긋났고, 사람은 그것을 못 봤다. 게이트가 서기 전과 선 뒤의 차이가 그 한 건이다.

**만들 때 밟은 함정 셋.**

1. **자기 링크(`[x](#anchor)`)의 빈 경로를 정규화해라.** 경로가 비면 대상은 자기 파일이다.
   `Path("")` 을 그대로 두고 대조하면 앵커가 통째로 거짓 **양성**으로 뜬다 — 이 저장소가
   실제로 한 번 그렇게 읽었다.
2. **코드 펜스 안은 링크로도 헤딩으로도 세지 마라.** 펜스 안의 `# 주석` 이 헤딩이 되면 없는
   앵커가 생기고, 예시 경로가 깨진 링크가 된다. 줄 번호는 보존해야 하니 지우지 말고 **비운다**.
3. **슬러그는 GitHub 규칙을 그대로 따라야 한다.** 서식을 벗기고 소문자로 내린 뒤 낱말 문자·
   하이픈·공백 아닌 것을 지우고 공백을 하이픈으로 바꾼다. 지문은 **공백에 둘러싸인 em dash**
   자리에 하이픈이 **둘** 남는 것이다(`…적혀-있다--닫혔다-…`). 중복 헤딩은 `-1`·`-2` 다.

**검사기를 만들면 일부러 깨뜨린 입력으로 음성 대조를 함께 돌린다.** 없는 파일·없는 앵커·
마크다운 아닌 대상의 앵커가 잡히는가, 그리고 **정상 자기 앵커가 안 잡히는가**를 양쪽으로 잰다.

## 문서가 문서를 검증하던 자리 — 검증 건수는 이제 코드가 센다

검증 건수 인용이 실측과 갈린 사고를 **네 번** 겪었다. 원인은 하나다 — 저장소에서 그 숫자를
아는 코드가 0줄이라 정본이 **"마지막에 손으로 다시 센 사람"** 이었고, 테스트 하나만 늘어도
인용 네 곳이 동시에 틀리면서 스위트는 초록이었다.

`tests/test_documented_counts.py` 가 그 규율을 검사로 바꾼다. 세우면서 정한 것 셋.

- **모집단을 규칙으로 정한다.** 자리를 손으로 열거하면 그 목록이 다시 사람이 관리하는 상수가
  된다. 문서 전수를 훑고 **날짜가 붙은 `실행값` 문단만** 뺀다 — 그 줄은 그날 돌린 출력의
  사본이고, 나중에 참이 되도록 고치는 것이 오히려 거짓말이다.
- **줄이 아니라 문단이 단위다.** 기록의 수치는 다음 줄로 넘어가는 일이 흔해서(`… 실행값**
  (2026-08-21): ruff check 0 · ruff format --check` ⏎ `182 파일 · …`), 줄 단위로 걸러내면
  넘어간 절반이 "지금 상태 주장"으로 잘못 읽힌다. 실제로 그렇게 읽혀 과거 기록 세 문단이
  어긋남으로 잡혔다.
- **실행값은 도구를 실제로 돌린 출력만 쓴다.** 통과 건수와 `db` 마커 건수는 pytest 세션에서
  직접 세고(`session.items`), 파일 수는 `ruff format --check .`·`mypy` 를 그 자리에서 돌려
  읽는다. 재구현하면 도구가 무엇을 세는지에 대한 **두 번째 의견**이 생긴다.
- **부분 실행에서는 대조하지 않는다.** 경로·`-k`·`-m` 을 주면 세션이 스위트가 아니므로
  **사유를 담아 skip** 한다 — 거짓 빨강은 검사를 끄게 만든다.

`ruff format --check .` 이 무엇을 세는지도 여기 적어 둔다: **`.py` 와 `.md` 를 함께 센다.**
"파이썬 파일 수"로 읽으면 인용이 어긋난다(그 오해가 183↔184 사고의 내용이었다).

**그리고 이 검사가 커밋 순서 규칙을 뒤집었다.** 예전 규율은 *"코드 커밋이 전부 끝난 뒤에
건수를 적어라"* 였고 근거는 건수를 아는 코드가 0줄이라는 것이었다. 이제 스위트가 인용을
대조하므로 **건수를 나중 커밋으로 미루면 그 사이 커밋이 RED 다.** 건수를 움직이는 변경과 그
인용은 **한 커밋에 함께 간다.**

## 비밀은 **담는 것**과 **평문으로 내놓는 것**이 다른 문제다

접속 문자열(`postgresql://user:password@host/db`)은 비밀번호를 **담을 수밖에 없다** — 담지
않으면 DB 에 접속할 수 없다. 그래서 오래 "의도적으로 열린 경로"로 남아 있었다
([findings 24](tracking/findings.md)). 그런데 저울질하던 두 방향이 전부 **비밀번호를 어디에
두느냐**를 바꾸는 것이었다: 키워드 인자로 넘기면 프레임에 남고, `PGPASSWORD` 로 옮기면 프로세스
환경으로 옮겨갈 뿐이다. 어느 쪽도 공짜가 아니라서 계속 미뤄졌다.

**셋째 길은 두는 자리를 그대로 두고 내놓는 타입만 바꾸는 것이다.** 조립 결과를 비밀 전용
타입으로 감싸면 문자열은 그대로인데 표시·덤프가 필드와 같은 자격으로 닫히고, 평문이 되는
지점이 **드라이버에 넘기는 한 줄**로 좁아진다. 앞의 두 방향이 지불하던 대가가 없고 호출
형태도 안 바뀐다 — `pytest -m db` 가 실제 접속으로 그것을 확인한다.

**규율 하나가 함께 남는다: 규칙을 좁히지 말고 예외를 등재해라.** 자격 증명 필드를 이름으로
훑는 규칙에서 `judge_max_output_tokens` 오탐을 피하려고 `token` 을 **규칙에서 뺐던** 적이
있다. 그러면 지금 있는 넷은 잡히지만 앞으로 추가될 `*_token`·`*_credential` 형 비밀이 "전수"
검사 밖으로 조용히 나간다 — **규칙 축소는 미래의 필드를 함께 지운다.** 넓게 잡고 비밀이 아닌
이름만 사유와 함께 예외로 등재하면 새 필드는 자동으로 걸린다. 예외 목록에는 **죽은 예외
검사**를 함께 건다(그 이름이 실제 필드인가 · 규칙에 실제로 걸리는가).
