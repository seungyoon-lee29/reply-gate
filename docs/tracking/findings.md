# 미해결 문제

이 목록의 원래 정의는 **"지금 세션에서 해결할 수 없는 것"** 이었다. 고칠 수 있으면 고치고
그 지식은 엔지니어링 노트로 보낸다는 규칙은 그대로다.

**그런데 사이클 5 로 프로젝트가 닫히면서 그 정의가 성립하지 않는다** — "다음 세션"이 없기
때문이다. 그래서 2026-08-21 에 남은 항목을 **두 갈래로 갈랐다.**

- **의도적으로 하지 않기로 한 것** — 이 프로젝트의 범위 밖이라는 **판단과 근거**가 있다.
  결함으로 다시 열 자리가 아니라, 왜 안 하는지가 결론인 자리다.
- **여전히 미해결인 것** — 무엇이 왜 열려 있는지와, **다시 여는 사람이 무엇부터 볼지**를 적었다.

**닫는 방식을 갈라 적는다.** "고쳤다"·"사라졌다"·"반증됐다"·"재현됐다"는 다르고, 뭉뚱그리면
다음에 읽는 사람이 없는 근거를 있다고 믿는다.

**항목 번호는 다시 매기지 않았다.** 저장소 곳곳이 이 번호로 항목을 인용하는데 **대부분은
번호가 링크 글자에만 있고 주소에는 없다**(`[findings 23](findings.md)` 꼴). 번호를 바꾸면
**링크 검사가 잡지 못한 채** 그 인용들이 통째로 다른 항목을 가리킨다 — 이 파일 안의 앵커
인용만 검사에 걸린다. 그래서 재분류는 **갈래 표시와 사유를 더한 것**이지 번호를 바꾼 것이
아니다. 닫힌 항목의 번호도 비우지 않고 그 자리에 둔다.

## 1. 미끼 조항이 end-to-end 기각을 유발하지 못한다 — **라벨 결정 종결 (2026-08-10, 결정 0008)**

**증상**: 정책 문서에 값을 비워 둔 미끼 조항(고객센터 전화번호·이메일)을 겨냥한 골든셋 문의
5건에서 모델이 거의 값을 지어내지 않는다. "제공된 안내에는 기재되어 있지 않아 안내해 드리기
어렵습니다"로 답해 `pii_detected` 가 발화할 조건이 만들어지지 않는다.
**라이브 3회 반복 실측: 1/15 = 6.7%** (1회차에 G16 이 `missing_citation` 으로 한 번 기각).

**단일 표본이 아니다**: 2026-08-05 에 3회 반복해 확인했다. 회차별 1/5·0/5·0/5 로,
낮은 재현율은 실행 간 잡음이 아니라 재현되는 성질이다.
근거 산출물은 `reports/evaluation-live-{1,2,3}.json`.

**영향 범위**: 기각 유발이 데모의 첫 장면이자 신뢰성 서사의 근거 수치다. 게이트 자체는
정상 동작하지만(픽스처 측정에서 `pii_detected` 검출률 100%), **미끼 경로로는** 그 장면을
안정적으로 재현할 수 없다.

**왜 지금 해결할 수 없나**: 모델의 정직함에 달린 문제라 코드 수정으로 닫히지 않는다.

**방향 결정 (2026-08-05)**: **고치지 않고 L2 로 간다.** 초안 프롬프트의 억제 지시를 약화하거나
모델 등급을 낮추는 선택지는 기각했다 — 게이트를 쓸모 있어 보이게 하려고 생성기를 망가뜨리는
일이고, 이 프로젝트의 유일한 주장인 신뢰성 지표를 스스로 오염시킨다. 미끼 조항 강화도
지금은 하지 않는다(없는 문제를 만드는 쪽에 가깝다). 6.7% 는 **위험이 어디 있는지에 대한
발견**으로 그대로 둔다: 요즘 모델은 값을 지어내지 않으므로 구조적 결함이 거의 안 생기고,
L1 은 구조만 본다. 남은 실제 위험은 의미 층이며 그것이 L2 의 자리다.
같은 이유로 이 수치에는 목표치를 두지 않는다([결정 0006](decisions/0006-지표-목표치를-실측-뒤에-확정한다.md)).

**대안 경로(사이클 1 측정으로 확인됨)**: **`missing_citation` 으로는 기각이 안정적으로
재현된다.** 사이클 1(L2 꺼짐) 3회 실행 90 케이스-실행 중 12회 기각이 났고 전부 이 사유였다.
특히 무근거 문의 G21–G24 는 12회 중 11회 기각됐다 — 모델이 "안내에 없다"는 문장을 쓰면서
그 문장에 붙일 근거 ID 가 없기 때문이다. 기각 → 사유 피드백 → 재생성 → 통과 루프 전체가
저장된 처리 기록에 남아 있고 `GET /inquiries/{id}` 로 다시 열 수 있다.

**갱신 (2026-08-06, 사이클 2 = L2 켜짐 실측)**: 위 "기각 장면은 `missing_citation` 경로로"
라는 서사는 **L2 가 붙으면서 바뀌었다.** 근거 산출물은 `reports/evaluation-live-l2-{1,2,3}.json`.

- **미끼 재현율은 6.7% → 26.7%(4/15)** 로 올랐다. **그러나 `pii_detected` 발화는 여전히
  0/15 다** — 이 발견의 본체(모델이 값을 지어내지 않는다)는 그대로다. 재현된 기각은
  L2 의 `contradictory_evidence`(G18 "하자 상품 환불 서류는 어느 이메일로", **3회 모두**)와
  L1 의 `missing_citation`(2회차 G16)이다. 목표 없는 관측값이라 **개선으로 주장하지 않는다.**
- **가장 안정적인 기각 장면은 이제 L2 쪽이다.** 무근거 문의 G21–G24 가 3회 실행 12건
  **전부** `rejected_twice` 로 인계됐고, 사유 합집합에 L2 의 `unsupported_claim` 이 들어 있다
  (사이클 1 에서는 12건 모두 `answered`). 인접 조항을 딛은 "안내가 어렵다"를 기각하는
  비대칭 규칙이 실제로 발화한 것이다([결정 0007](decisions/0007-L2-판정을-배치-fail-closed로-짓는다.md)).
- **데모의 기각 장면**: `missing_citation` 경로(단일 층, 재생성 후 통과)와 **L2 경로**
  (L1 통과 → L2 기각 → 재기각 → 인계) 둘 다 실측에 있다. 2층이 각각 무엇을 잡는지 보이려면
  **두 장면을 함께** 쓰는 것이 실측에 부합한다.
- **미끼 문의 G16·G17·G19·G20 은 L2 가 붙은 뒤에도 어떤 시도도 기각되지 않았다**
  (남은 어긋남 11 케이스-실행이 전부 이 네 건이다). 정면 조항을 딛은 "없다" 안내를
  통과시키는 것은 설계된 비대칭의 다른 쪽이므로 L2 의 오작동이 아니지만,
  **미끼 경로로 기각 장면을 재현한다는 원래 기대는 여전히 닫히지 않았다.**

**재조사 (2026-08-10): 남은 것은 미끼가 아니라 라벨이다.** 3회 실측의 케이스별 결과를 다시
읽고 임베딩 유사도를 직접 재봤다(`reports/evaluation-live-l2-{1,2,3}.json` 의 `outcomes`).

| 케이스 | 3회 결과 | 실제로 일어난 일 |
|---|---|---|
| G16 전화번호 | 통과 / **기각→통과** / 통과 | 근거는 잘 잡힌다(4-1 유사도 0.63). 모델이 번호를 지어내지 않아 `pii_detected` 가 발화할 조건이 안 생긴다 |
| G19 이메일 | 통과 ×3 | 같음(4-2 유사도 0.43) |
| G20 둘 다 | 통과 ×3 | 같음(4-2 0.62 · 4-1 0.55) |
| G17 상담원 번호 | **`no_evidence` 인계 ×3 (시도 0건)** | **근거 검색 자체가 실패한다** — 아래 별도 항목 |
| G18 환불 이메일 | **기각→통과 ×3** | 기각되지만 미끼 때문이 아니라 근거 간 모순(`contradictory_evidence`) 때문이다 |

**G16·G19·G20 의 통과는 제품이 옳게 동작한 것이다.** 값이 비어 있는 정면 조항을 딛고
"기재되어 있지 않습니다"라고 답하는 것은 결정 0007 의 비대칭 규칙이 **통과시키기로 정한 쪽**
이다. 그런데 라벨은 `expect_reject: True` 라 이 올바른 동작을 매번 불일치로 채점한다.
**즉 남은 어긋남의 원인은 게이트가 아니라 채점표에 있다.**

**그래서 이 항목은 라벨 결정으로 옮겨갔다.** 선택지는 (a) 라벨을 유지하고 관측 한계로 명시,
(b) 정면 조항 "없다" 안내를 정답으로 라벨 재정의(일치율이 오르므로 변경 전·후 수치를 함께
남겨야 한다), (c) 미끼를 실제로 유발되는 형태로 재설계(사이클 1 에서 "없는 문제를 만드는 쪽"
이라며 한 번 기각한 방향). 어느 쪽도 코드 문제가 아니라 평가 설계 결정이라 사용자 판단이
필요했고, 라벨을 고치면 일치율이 오르므로 지표를 좋아 보이게 하려는 변경과 구분되는 장치가
필요했다.

**종결 (2026-08-10): 사용자가 (b) 를 확정했다.** G16–G20 의 `expect_reject` 를 전부 내리고,
기각 재현율의 분모를 라벨에서 범주(`reject_bait`)로 옮겨 관측값을 보존했다. 변경 근거(결정
0007 의 비대칭 규칙)와 **전후 수치 병기**(사이클 2 일치율 87.8% → 재채점 100.0%, 사이클 1
기준선 71.1% → 86.7%)는 [결정 0008](decisions/0008-미끼-라벨을-판정-규칙에-정렬한다.md) 에
있다. 종결된 것은 **라벨 결정**이다 — 증상 자체(미끼가 값 날조를 유발하지 않는다)는 이제
실패가 아니라 성질로 재분류됐고 관측은 계속된다. 커밋된 라이브 리포트는 사후 편집하지 않았다 — 재채점은 별도 계산이고 리포트 원본은
구 라벨 기준 기록 그대로다. 이 발견의 본체(모델이 값을 지어내지 않는다, `pii_detected` 0/15
× 2사이클)는 관측으로 계속 쌓인다. G17 의 검색 실패는 [11번](#11-구어체-문의에서-근거-검색이-실패한다-g17--종결-2026-08-14-사이클-3-t10-라이브-3회)이,
인접 조항 검색은 [2번](#2-무근거-문의가-인계되지-않고-답변으로-끝난다--종결-2026-08-19-사이클-4-기권-게이트-라이브-3회)이
추적하다 사이클 4 에 종결됐다.

## 2. 무근거 문의가 인계되지 않고 답변으로 끝난다 — **종결 (2026-08-19, 사이클 4 기권 게이트 라이브 3회)**

**종결**: 채택 축을 하나 더 만들어 닫았다 — 질의 단위 **기권 게이트**(1위 − `top_k`위 산포,
τ=0.06)를 컷 위에 얹었다([결정 0014](decisions/0014-기권-게이트를-1위-top_k위-산포-축으로-채택한다.md)).
라이브 3회(`reports/evaluation-live-l2-{10,11,12}`)에서 **G21–G24 12건 전부** 채택 근거
0건 · `no_evidence` · 시도 0건으로 끝났다 — 초안도 판정도 부르지 않는다. 아래 "원인은 그대로다"
가 지목한 것(인접 조항이 컷 위로 검색되는 것)은 **여전히 참이고**, 게이트는 그 조항들을 지우는
것이 아니라 **질의 하나를 통째로 기권시켜** 근거로 쓰이지 않게 한다.

**닫히지 않은 것 둘을 함께 적는다.** ① 게이트는 확률 층 위에 서 있다 — 재작성 산출이 실행마다
조금씩 달라 점수 분포가 움직인다. 3회는 관측이지 결정론이 아니다. ② **τ 는 이 임베딩 모델의
값이다**(`docs/engineering-notes.md` "τ 는 임베딩 모델에 묶인다").
전후 비용은 [pricing](pricing.md) 4절 ②.

아래는 종결 전 기록이다.

**증상**: 정책 문서에 근거가 없는 주제(해외 배송, 대량 구매 할인, 매장 수령, 선물 포장)를
묻는 골든셋 4건이 `no_evidence` 인계 대신 `answered` 로 끝났다.

**원인**: 유사도 임계값 0.3 에서 관련 있어 보이는 조항이 검색되고(예: "해외 배송" → 배송 정책),
모델이 그 근거를 딛고 "안내가 어렵다"고 답한다. 다만 **첫 초안에는 근거 ID 를 달지 않아
L1 이 `missing_citation` 으로 기각하고**, 재생성에서 근거를 붙이면 통과한다 — 그래서 최종
상태가 `answered` 다. 근거를 단 뒤에는 L1 이 잡을 구조적 결함이 없다.

**3회 반복에서 동일**: G21–G24 네 건 모두 3회 실행에서 같은 방식으로 어긋났다. 잡음이 아니다.

**영향 범위**: 판정 일치율 71.1% 를 깎는 8~9건 중 4건이 이것이다. 사용자에게 잘못된 정보가 가는 것은 아니지만
(모델이 "없다"고 답한다), 인계돼야 할 문의가 종결된다.

**증상은 L2 가 닫았다 (2026-08-06, 사이클 2 = L2 켜짐 실측)**: 같은 네 건이 3회 실행 12건
**전부** `rejected_twice` 로 인계됐다. 사유 합집합에 L2 의 `unsupported_claim` 이 들어 있다 —
인접 조항을 딛은 claim 을 뒷받침 없음으로 기각한 것이다. 일치율 71.1% → 87.8% 상승분의
대부분이 여기서 나왔다(`reports/evaluation-live-l2-{1,2,3}.json`).

**그러나 원인은 그대로다**: 정책 문서에 없는 주제인데 **유사도 0.3 에서 인접 조항이 검색되는
것** 자체는 변하지 않았다. 지금은 매 건 판정 호출을 태워 뒤에서 잡고 있고, 판정은 건당 토큰의
약 72% 다 — 검색 단계에서 걸러내는 편이 싸다. **그래서 이 항목은 닫지 않는다.**

**원인을 닫으려다 되돌렸다 (2026-08-14, 사이클 3 T7 → T10)**: "임계값을 바꿔가며 측정해야
한다"가 그 측정이었다. 오프라인 컷 스윕(`reports/retrieval-strategies-live-*`)에서
**G21–G24 네 건이 전부 기권하는 가장 낮은 컷이 0.50** 이었고 T7 이 그 값을 채택했다.
**T10 라이브 3회가 그 효과를 실측으로 확인했다** — 12건 중 **11건**이 검색 단계에서
`no_evidence` 로 끝났고 **초안도 판정도 부르지 않았다**(시도 0건 · 판정 토큰 0).
원인을 닫는 길이 있다는 것은 이제 실측이다.

**그런데 같은 컷이 다른 셋을 깨서 되돌렸다**(`72ff2d4`) — G04 의 정답 조항(0.3571)과
G18·G01 의 상충 조항(0.4676·0.4693)이 함께 잘렸다. 컷은 0.30 으로 복귀했고 **그래서 이
항목의 원인은 지금도 열려 있다.** 인접 조항은 다시 검색되고, 다시 매 건 판정 호출을 태워 뒤에서 잡는다.

**왜 그때 해결할 수 없었나**: 컷이라는 **한 축으로는 못 닫는다는 것이 실측으로 확정됐다** —
G21–G24 를 기권시키는 컷(≥0.500)과 G04 를 살리는 컷(≤0.350)이 겹치지 않는다. 전문은
[18번](#18-채택-컷-하나가-세-방향을-동시에-못-지킨다--종결-2026-08-19-사이클-4-기권-게이트)에 있다.
남은 길은 채택 축을 늘리는 것이었고(질의별 적응 컷·상대 마진·상충쌍 보존), 사이클 4 가
앞의 둘을 반증한 뒤([결정 0012](decisions/0012-적응-컷과-상대-마진을-반증하고-기권-게이트만-남긴다.md))
질의 단위 기권 게이트 하나로 좁혀 닫았다 — 위 종결 절.

## 3. 정상 실행 0건 SQL 이 처리 기록에 남지 않는다

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 기록 자리를 만드는 것은 스키마 변경
> 사안이고, 마이그레이션 도구가 없어 볼륨 재생성과 유료 재색인을 동반한다. 잃는 것은
> 감사 해상도 하나("조회했는데 0건"과 "조회하지 않았다"의 구분)이고 **지표 산출에는 영향이
> 없다** — 그 비용으로 그 값을 사지 않는다. 이 판단은 사이클 5 가 스키마를 건드리지 않기로
> 한 것과 같은 자리다.

**증상**: 존재하는 주문에 대해 SQL 이 정상 실행됐는데 결과가 0건인 경우, 채택된 근거도
실패 내역도 아니라서 저장할 자리가 없다. 인계 사유(`no_evidence`)만 남는다.

**영향 범위**: 감사 관점에서 "조회를 했는데 결과가 없었다"와 "조회를 하지 않았다"가 구분되지
않는다. 현재 지표 산출에는 영향이 없다.

**왜 지금 해결할 수 없나**: 스키마 변경 사안이고(새 테이블 또는 기존 테이블의 새 상태값),
마이그레이션 도구가 없어 볼륨 재생성을 동반한다. 이 사이클 범위 밖이다.

## 4. 처리 기록에 오탐 버그 시절의 문의가 남아 있다 — **종결 (2026-08-19, 볼륨 재생성으로 사라졌다)**

**종결**: 그 행은 **DB 에 없다.** 2026-08-19 에 직접 확인했다 — `inquiries` 5행 중
`pii_detected` 로 끝난 건은 0건이고, 남은 다섯은 2026-08-13 이후에 만들어진 것뿐이다.
사라진 시점은 아래 [19번](#19-보존하기로-한-처리-기록-2건이-db-에-없다--종결-2026-08-21-시연이-마지막-한-건을-재현했다)이 지목한 **08-13 의
provenance 컬럼 추가 볼륨 재생성**으로 보인다.

**종결 방식이 "고쳤다"가 아니라 "사라졌다"라는 것을 적어 둔다.** 아래가 예고한 대로
(`docker compose down -v` 로 전체를 지우면 함께 사라진다) 됐을 뿐이고, **복구는 불가능하다** —
그 오탐은 현재 코드에서 재현되지 않는다. 19번이 잃은 두 건 중 하나가 이것이다.

아래는 종결 전 기록이다.

**증상**: `pii_detected` 로 2회 연속 기각되어 `rejected_twice` 인계된 문의 1건이 DB 에 남아
있다. 이는 근거 ID 를 PII 검사 대상에 넣었던 시절의 **오탐**이며, 현재 코드에서는 재현되지 않는다.

**영향 범위**: 데모 중 처리 기록을 훑다가 이 건을 열면 현재 동작을 잘못 보여준다.

**왜 그때 해결할 수 없었나**: 처리 기록 삭제는 데이터 삭제이므로 사용자 판단 사안이다.
`docker compose down -v` 로 전체를 지우고 다시 시딩하면 함께 사라진다.

## 5. 테스트 클라이언트 deprecation 경고

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 의존성 교체라 별도 검증이 필요한데
> 지금 깨지지 않는다. 아래가 "다음 사이클의 의존성 정비와 함께"라고 적었지만 **그 사이클은
> 오지 않는다** — 그러니 미룬 것이 아니라 **하지 않기로 한 것**으로 적는다. 깨지는 것은
> `starlette` 를 올릴 때이고, 그때 올리는 사람이 함께 볼 일이다.

**증상**: `uv run pytest` 가 경고 1건과 함께 통과한다 —
`StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated`.

**영향 범위**: 현재는 통과한다. `starlette` 상위 버전에서 테스트가 깨질 수 있다.

**왜 지금 해결할 수 없나**: 의존성 교체(`httpx` → `httpx2`)는 다른 부분에 영향을 줄 수 있어
별도 검증이 필요하다. 지금 깨지지 않으므로 다음 사이클의 의존성 정비와 함께 다루는 것이 낫다.

## 6. 평가 하네스가 처리 기록을 남기지 않는다

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 아래 "왜 지금 해결하지 않았나"가
> 이미 의도적 선택이라고 적고 있고, 그 판단은 프로젝트가 닫히는 지금도 그대로다 — 평가
> 실행과 실사용 기록이 같은 테이블에 섞이면 지표 산출의 모집단이 흐려진다. 올바른 해법
> (평가 실행분을 구분하는 표식)은 스키마 변경이라 항목 3 과 같은 자리에 있다.
>
> **이 항목이 예고한 대가는 시연으로 갚았다** — 기각 장면의 기록은 평가 실행이 아니라
> 웹 폼 시연이 남겼고(항목 19), `GET /inquiries/{id}` 로 열린다.

**증상**: 골든셋 30건을 흘려도 `inquiries` 등 처리 기록 테이블에 아무것도 남지 않는다.
리포트만 산출물이다.

**영향 범위**: 평가 실행에서 나온 기각 건을 나중에 화면으로 다시 열어볼 수 없다.
데모에서 기각 장면을 보여줄 때는 웹 폼으로 직접 실행해 남은 기록을 쓴다 — 실제로 그런 기록이
남아 있고(기각→재생성→통과), `GET /inquiries/{id}` 로 열린다.

**왜 지금 해결하지 않았나**: 의도적 선택이다. 30건을 돌릴 때마다 기록이 쌓이면 정리 정책이
필요하고, 평가 실행과 실사용 기록이 같은 테이블에 섞여 지표 산출의 모집단이 흐려진다.
평가 실행분을 구분하는 표식을 두는 것이 올바른 해법이고, 그건 스키마 변경 사안이다.

## 7. 측정 3 이 중단되면 이미 과금된 부분 결과가 폐기된다

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 이 항목이 지키려던 성질 — "어느
> 측정이 죽어도 리포트는 반드시 쓰고, 중단 사유가 남고, 종료 코드가 1 이다" — 은 **이미
> 성립한다.** 남는 손해는 재구매 비용 하나인데 이 프로젝트는 유료 실측을 닫았다.
> 부분 완주를 살리려면 리포트 스키마가 "부분 완주"라는 상태를 새로 가져야 하고(부분 수치를
> 완주 수치와 같은 칸에 적으면 리포트가 거짓말을 한다), 그 설계는 이 프로젝트가 사지 않는다.
>
> **한 겹은 이번 사이클에 나아졌다** — 중단 표시가 사람이 읽는 줄에만 붙던 문제(항목 26 의 4)는
> 닫혔고, 이제 기계가 읽는 조건 지문의 `run_completion` 항목이 중단을 든다.

**증상**: 판정 픽스처 11건 중 7건을 판정한 시점에 중단(Ctrl-C·인프라 실패·SDK 의 `sys.exit`)
되면, 이미 판정을 마친 7건의 결과가 산출물에 반영되지 않는다. 리포트에는 측정 3 이
"미실행 + 중단 사유"로만 남는다.

**영향 범위**: 중단 **사유**는 정확히 남고 종료 코드도 1 이라 실행이 성공으로 읽히지는
않는다. 잃는 것은 **이미 지불한 판정 7건의 값**이다. 재실행은 11건을 다시 산다.

**측정 2 도 같은 모양이다**: 골든셋 30건 중 24건을 돌린 뒤 중단되면 진행분 24건을 살리지
못한다. 중단 자체는 리포트에 남지만(실행 조건에 "측정 2 중단" 꼬리표가 세 항목 모두에 붙는다)
완주분 수치는 산출물에 들어가지 않는다.

**왜 지금 해결할 수 없나**: 부분 집계를 반환하려면 `measure_*` 가 중단 시점까지의 결과를
들고 나오는 형태여야 하고, 리포트 스키마도 "부분 완주"라는 상태를 새로 가져야 한다
(부분 수치를 완주 수치와 같은 칸에 적으면 리포트가 거짓말을 한다). **설계 변경이라 이번
사이클 범위 밖이다.** 지금 우선한 것은 "어느 측정이 죽어도 리포트는 반드시 쓴다"이고,
그것은 이미 성립한다.

## 8. 응답에 실패 단계가 없어 웹 폼이 "왜 L2 가 안 돌았는지"를 추론한다

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** `failed_stage` 를 응답에 싣는 것은
> **답변 계약 변경**이고, 계약은 편의로 바꾸지 않는다는 규칙이 이 저장소에 있다. 그리고
> 아래가 적은 대로 **지금 파이프라인이 만들 수 있는 모든 경로에서 화면의 추론은 정확하다** —
> 틀리게 되는 것은 "L1 통과 + L2 없음 + `llm_call_failed`" 조합을 만드는 **새 경로**가
> 생겼을 때이고, 그 경로를 만드는 사람이 이 항목을 함께 연다.

**증상**: `attempts[].l2` 가 `null` 인 이유는 셋인데(L1 기각 · 스위치 꺼짐 · 판정 호출 실패)
응답에는 그것을 직접 말하는 필드가 없다. 처리 기록에는 `failed_stage` 가 남지만 API 응답
계약에는 없다. 그래서 웹 폼이 **관측값으로 좁힌다** — `l1.verdict == "reject"` 면 L1 기각,
마지막 시도이고 `escalation_reason == "llm_call_failed"` 면 판정 호출 실패, 그 밖은 스위치 꺼짐.

**영향 범위**: **지금 파이프라인이 만들 수 있는 모든 경로에서는 정확하다.** L1 통과 + L2 없음 +
`llm_call_failed` 조합을 만드는 경로가 판정 호출 실패뿐이기 때문이다. 미래에 **다른 원인**의
같은 조합이 생기면(예: 종결 직전 단계에서 나는 다른 LLM 실패) 화면이 "판정 호출 실패"로
오표기한다.

**왜 지금 해결할 수 없나**: `failed_stage` 를 응답에 싣는 것은 **계약 변경**이다
(`docs/contracts.md` 의 응답 스키마 + `contracts.py` 소유). 계약은 편의로 바꾸지 않는다는
규칙이 있고, 이번 사이클에 이미 층별 판정 키·판정 토큰 키로 응답을 넓혔다. 한 사이클에
계약을 두 번 넓히지 않는다.

## 9. 리포트 JSON 의 이월 목록 키가 `deferred_to_l2` 에서 `deferred` 로 바뀌었다

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 맞추는 유일한 길이 **커밋된 라이브
> 리포트를 손으로 고치는 것**인데, 그것은 하드 게이트 7("커밋된 라이브 리포트는 사후 편집하지
> 않는다")이 정면으로 금지한다. 저장소 안에 그 키의 소비자가 0 이라 지금 깨지는 것도 없다.
> **옛 산출물은 옛 실행의 기록 그대로 두는 것이 맞다** — 나중에 프로그램으로 훑을 사람이
> 두 키를 모두 보면 된다.

**증상**: 리포트 JSON 의 "다음으로 미룬 것" 목록 키 이름이 바뀌었다. L2 가 구현된 지금
`deferred_to_l2` 는 뜻이 맞지 않기 때문이다. 그 결과 **저장소에 커밋된 기존 라이브 리포트
3종**(`reports/evaluation-live-{1,2,3}.json`)은 옛 키를, 새 실행은 새 키를 쓴다.

**영향 범위**: 저장소 안에 이 키를 읽는 소비자가 없어(테스트·스크립트·문서 어디에서도 참조하지
않는다) 지금 깨지는 것은 없다. 커밋된 실측 리포트를 나중에 프로그램으로 훑는다면 두 키를
모두 봐야 한다.

**왜 지금 해결할 수 없나**: 커밋된 라이브 리포트는 **과금된 산출물이고 재생성이 불가능하다**
(확률 층이라 같은 값이 안 나온다). 키를 맞추려면 산출물을 손으로 고쳐야 하는데, 그건
"실측 산출물을 사후 편집하지 않는다"는 이 프로젝트의 원칙과 정면으로 어긋난다. 옛 산출물은
**옛 실행의 기록 그대로** 두는 것이 맞다.

## 10. 대역 파이프라인 조립기가 실제 조립을 손으로 복제한다

> **갈래 (2026-08-21): 여전히 미해결.** 가드 테스트가 드리프트를 잡으므로 조용히 어긋나지는
> 않지만, **가드는 증상 억제이지 원인 제거가 아니다.** 다시 여는 사람이 먼저 볼 것:
> `build_pipeline` 에 **판정자 주입 구멍**을 어떤 모양으로 뚫을 것인가. 배선 실수가 곧
> fail-open 인 자리라 "기본값 `None` 이면 L2 를 끈다" 같은 형태여서는 안 되고, 이 저장소는
> 같은 모양의 문제를 **조립 시점 오류**로 다루는 전례를 이미 셋 갖고 있다
> (`pipeline.PipelineWiringError` · `evidence.RetrievalWiringError` ·
> `config.AbstentionGateWiringError`). 그 셋과 같은 자리에 놓는 것이 첫 후보다.

**증상**: `testing.build_stub_pipeline` 이 `pipeline.build_pipeline` 과 **같은 협력자 조합**을
다시 적는다. 두 곳이 어긋나면 대역 실행이 실제 실행과 다른 것을 잰다.

**원인**: `build_pipeline` 이 판정자를 설정에서 조립하므로(실제 Anthropic 클라이언트)
**판정자 주입 구멍이 없다.** 대역 실행은 외부 호출 0회여야 해서 판정자를 갈아 끼워야 하는데,
끼울 자리가 없으니 조립을 통째로 다시 쓰는 수밖에 없었다.

**영향 범위**: `tests/test_testing_doubles.py` 가 두 조립의 협력자 종류를 대조해 드리프트를
잡는다. 그래서 조용히 어긋나지는 않는다 — 다만 **가드 테스트는 증상 억제이지 원인 제거가
아니다.**

**왜 지금 해결할 수 없나**: 근본 수정은 `build_pipeline` 에 판정자 주입 구멍을 뚫는 것이고,
그건 **파이프라인 모듈의 공개 표면 변경**이다(누가 판정자를 정하는가를 바꾼다). 배선 실수가
곧 fail-open 인 자리라 주입 구멍은 "기본값 `None` 이면 L2 를 끈다" 같은 형태여서는 안 되고,
설계를 한 번 더 정해야 한다. 이번 사이클은 fail-closed 배선을 먼저 세우는 것이 우선이었다.

## 11. 구어체 문의에서 근거 검색이 실패한다 (G17) — **종결 (2026-08-14, 사이클 3 T10 라이브 3회)**

**실측 (2026-08-10, 임계값 0.3 · top_k 5)**: 겨냥한 조항(support 4-1 고객센터 운영 안내)의

**임계값을 낮추는 것은 해법이 아니다.** G17 의 1위는 4-1 이 아니라 **4-7 회원 탈퇴(0.2753)**

[2번](#2-무근거-문의가-인계되지-않고-답변으로-끝난다--종결-2026-08-19-사이클-4-기권-게이트-라이브-3회)의
**반대 방향**(한쪽은 잘못 찾고 한쪽은 못 찾는다)이라, 한 임계값으로 둘을 동시에 만족시킬 수
없다는 것을 이 실측이 보여준다.

**~~그래서 지금 해결할 수 없다~~ — 질의 재작성으로 닫았다 (2026-08-14, 사이클 3 T7 배선 · T10 확인)**:
검색 품질 자체를 손대는 두 후보(임베딩 모델 상향 / 쿼리 재작성) 중 **재작성**을 채택했다.

사이클 1·2 에서 6회 모두 `no_evidence` 였던 문의다.

**컷 원복(0.50 → 0.30)이 이 종결을 되돌리지 않는다.** 재작성 뒤 4-1 은 0.580 이라 두 컷 모두
위에 있고, 위에서 "임계값을 낮추면 4-7 이 먼저 온다"고 적은 순위 문제도 재작성이 함께 고쳤다 —
라이브 채택 근거에서 **4-1 이 1위**다. 되돌린 것은 컷 한 축이고 재작성은 유지된다.

**남은 지식은 `docs/engineering-notes.md` "구어체 패러프레이즈는 임베딩이 잇지 못한다" 로
옮겼다.**

**참고 — 인계 자체는 옳은 동작일 수 있다**: 4-1 에는 애초에 전화번호가 없으므로, 근거를
찾았어도 답은 "기재되어 있지 않다"였을 것이다. 근거를 못 찾아 사람에게 넘긴 것이 사용자에게
잘못된 정보를 준 것은 아니다. 다만 **같은 미끼를 겨냥한 두 문의가 표현 차이만으로 다른 경로를
타는 것**은 검색 품질의 문제로 남는다.

## 12. 검색 정답 라벨의 "직접 관련" 기준이 케이스마다 다르게 적용됐다 — **종결 (2026-08-13, 결정 0010)**

**종결**: 사용자가 관련성 경계를 **정면 조항 + 상충 조항**으로 확정했다. G16·G17 에서 4-2 를
빼고, G18 에 상충 조항 2-4 를 넣었다(3건 변경, 정답 조항 총계 −1). 실행 요청(G25·G28)은
현행을 유지하되 구분 규칙("조항이 그 요청에 답하거나 스스로 할 방법을 주는가")을 라벨 note 에
명문화했다. 조건·제한 조항까지 넓히는 안은 기각했다 — 1-2 는 문의만 보고 해당 여부를 알 수
없어 어떤 검색기도 공정하게 맞힐 수 없는 분모가 된다. 근거·기각한 대안·전후 표는
[결정 0010](decisions/0010-검색-정답의-관련성-경계를-정하고-blind-재작성을-모델이-만든다.md).
남은 것은 라벨 변경 **전후 수치 병기** 하나이며 사이클 3 T6 실측 산출에서 같은 검색 결과를 구·신
라벨로 각각 채점해 닫는다(추가 과금 없음).

아래는 종결 전 기록이다.


`data/retrieval_labels.jsonl` 의 관련성 규칙이 방향에 따라 갈린다. **분모를 바꾸는 사안이라
사용자 결정 없이 고치지 않는다.**

- **전화 vs 이메일**: G16·G17(전화번호)은 `policy:support:4-1` + `4-2` 두 조항이고, 근거는
  "4-2 가 전화 상담 채널을 다룬다"다. 그런데 G19(문의 이메일)는 `4-2` 만, G18(하자 환불 서류
  이메일)은 `policy:refund:2-6` 만이다. 4-2 본문은 "전화 상담 **또는 이메일로** 접수"이므로
  같은 규칙이면 이메일 쪽도 2조항이어야 한다는 독법이 성립한다.
- **실행 요청**: G28("환불 처리해 주세요")은 `[]` + note "실행 요청의 직접 근거가 아니다"인데,
  G05("주문을 취소하고 싶은데 언제까지")는 `policy:support:4-3` 을 정답으로 잡았다. 취소와
  환불에 같은 규칙이 다르게 적용됐다.
- **인접·제한 조항**: G03(교환 가능 조건)은 `3-2` 만인데 `3-4`("재고 없으면 교환 불가")가
  가능 여부를 직접 제한한다. G11·G26(출고·도착 시점)은 `1-1` 만인데 `1-2`(대형 상품 지연·
  도서산간)는 **이 프로젝트가 일부러 심은 모호 조항**이다.

**영향**: recall 분모가 케이스별로 1↔2 로 갈린 채 macro 평균된다. 30건에서 조항 1개는 macro
recall 을 최대 1.7%p, 케이스 하나는 3.3%p 움직인다. G16·G17 은 4-1 만 찾아도 r@1=0.5 로
기록되어 표적 케이스 판독을 흐린다.

**왜 지금 고치지 않나**: 라벨은 검색 recall·precision 의 유일한 정답 입력이고 2026-08-12 에
확정된 입력이다. 규칙을 어느 방향으로 통일하든 이번 사이클 모든 수치의 분모가 바뀌므로
사용자가 규칙을 정한 뒤에 한 번에 반영한다. 관련성 정의의 경계(단순 처리 전제 제외 / 접근
통제 포함)는 도메인 판단이다.

## 13. oracle 픽스처 2건이 개정된 라벨과 반대 방향을 가리킨다 — **종결 (2026-08-13, 결정 0010)**

**종결**: oracle 의 정의가 "정답을 본 상한"이므로 라벨을 기준으로 두고 oracle 2건을 되돌렸다.
G28 은 원문 유지(빈 정답의 상한은 아무것도 채택하지 않는 것), G25 는 주문번호 어휘를 뺀
`"주문 상세 화면에서 확인하는 배송 상태와 배송 진행 단계"`. "oracle ≥ blind" 해석 전제가
회복됐다. 라벨을 oracle 에 맞추는 반대 방향은 기각했다(결정 0010 의 기각 대안).

아래는 종결 전 기록이다.


`data/rewritten_queries_oracle.jsonl` 이 "정답을 본 상한"이어야 하는데, 두 건이 자기 라벨을
부정한다. 결정 0008 이전에 만든 curated 문장이 라벨 개정 뒤 갱신되지 않은 것으로 보인다.

- **G28**: 라벨 `[]` + note "환불 처리 기간 조항은 실행 요청의 직접 근거가 **아니다**" ↔
  oracle 재작성 `"이 주문의 환불 처리 절차와 환불 진행 기간"` + note "환불 2-4 의 처리 절차와
  기간 어휘를 연결한다". 두 파일이 같은 커밋(`3bbb261`)에서 서로 반대로 작성됐다.
- **G25**: 라벨 note "주문번호 안내 같은 단순 처리 전제는 검색 정답에서 **제외**한다", 정답은
  `policy:shipping:1-5` 뿐 ↔ oracle 이 `"주문번호가 필요한 …"` 으로 `policy:support:4-4`
  (주문번호 안내)를 상위로 끌어올린다.

**영향**: 빈 정답 케이스에서 무엇이든 채택되면 precision 이 0 이므로 oracle 이 blind 보다
**불리**해진다. "oracle = 상한"이라는 해석 전제가 깨지고, blind 대비 gap 해석이 오염된다.
대역 실행에서 oracle 조건 안에서도 상한이 단조롭지 않은 것이 관측된다.

**왜 지금 고치지 않나**: oracle 을 라벨에 맞출 것인지(G28 재작성을 정답 없음 방향으로 되돌림)
라벨을 oracle 에 맞출 것인지(12번과 함께 규칙 재정의)가 서로 다른 결정이다. 둘 다 확정된
입력이라 사용자가 방향을 정해야 한다.

## 14. 리랭크 캐시가 한 번 미스했고 재현되지 않는다

> **갈래 (2026-08-21): 여전히 미해결.** 원래 정의의 "지금 해결할 수 없는 것"에 가장 정확히
> 들어맞는 항목이다 — **재현되지 않으므로 닫을 근거가 없다.** 라벨 누출이 아니라는 것은 세
> 갈래로 확인했고(하드 게이트 8 "라벨은 채점자만 본다"는 지켜졌다), 잃은 것은 리랭크 30건의
> 실비용이며 지표는 영향받지 않았다. 다시 나면 **캐시 파일에 결과만이 아니라 입력 원문을
> 함께 남기는 것**이 첫 조치다 — 지금 캐시 파일이 입력을 담지 않아 사후 진단이 막힌다.

**증상**: 같은 검색 산출을 구 라벨로 재채점하려고 `--labels` 만 바꿔 실행했더니 리랭크가
캐시를 하나도 못 맞히고 30건을 다시 호출했다(`cache_hits 0`, 입력 토큰 24936 — **직전
신 라벨 실행과 정확히 같은 토큰 수**). 같은 명령을 다시 돌리면 30/30 적중한다.

**라벨 누출은 아니다** — 세 갈래로 확인했다.
1. 리랭크 입력에 라벨이 들어갈 자리가 없다: `llm_rerank` 는 `query`·`rewritten_query`·
   `candidates`·`policy_texts` 만 받고, `retrieval_strategies.py` 는 구조 테스트가
   정답 라벨 import·경로 참조를 막는다(하드 게이트 8 "라벨은 채점자만 본다").
2. 구·신 라벨 실행의 순위가 하이브리드·리랭크 두 단 모두 **0/30 케이스 차이**다.
3. 캐시 디렉터리가 145개로 고정돼 있고 구·신 라벨 실행이 **같은 항목을 적중**한다.
   라벨이 입력에 닿았다면 blind 조건에서만 30쌍의 중복이 생겨야 하는데 서로 다른 입력
   해시가 같은 결과를 갖는 쌍은 4개뿐이다.

**영향 범위**: 실비용 리랭크 30건. 지표는 영향받지 않는다(순위가 동일하다).

**왜 지금 해결할 수 없나**: 재현되지 않는다. 캐시 키는 입력 JSON 의 정규화 해시라
비결정성이 들어갈 자리가 후보 풀 순서뿐인데, 그 순서가 흔들렸다는 증거를 사후에 잡을 수
없다(캐시 파일은 결과만 담고 입력을 담지 않는다). 다시 나오면 입력 원문을 캐시 파일에
함께 남기는 것이 첫 조치다.

## 15. 전송 정책 관문이 덕타이핑이라 못 덮는 재시도가 남는다

> **갈래 (2026-08-21): 여전히 미해결.** 지금 활성이 아니라서 열린 채로 두는 것이지, 판단이
> 끝나서 닫는 것이 아니다. **다시 여는 조건이 명확하다 — provider 를 셋째로 늘리는 순간**
> 이 항목을 먼저 읽는다. 그때 볼 것은 아래 두 구멍이고, 특히 `getattr(candidate,
> "max_retries", 0)` 의 기본값 0 이 "모르는 SDK"를 "재시도 없음"으로 읽는다는 것이다.
> 기본값을 뒤집는 방향(모르면 거부)은 테스트 대역 주입을 전부 막아 못 간다.

`llm._pin_transport_policy` 는 `with_options`·`max_retries` 라는 **속성 이름**으로 SDK 를
알아본다(`cddbd87`). 두 SDK 가 같은 이름을 쓰는 것은 사실이지만 계약이 아니다. 남는 구멍이 둘:

1. **다른 이름을 쓰는 provider.** 세 번째 provider 가 재시도 설정을 `retries` 나 `max_attempts`
   로 부르면 관문이 조용히 통과시킨다. `getattr(candidate, "max_retries", 0)` 의 기본값 0 이
   "재시도 없음"으로 읽히기 때문이다. 기본값을 뒤집으면(모르면 거부) 테스트 대역 주입이
   전부 막히므로 그 방향으로는 못 간다.
2. **전송 계층 재시도.** 주입 클라이언트가 `httpx.HTTPTransport(retries=N)` 를 물고 있으면
   SDK 계층에서 재시도가 꺼져 있어도 연결 오류에서 httpx 가 다시 보낸다. 어떤 설계로도
   SDK 설정만 봐서는 잡을 수 없다.

**지금 활성이 아니다** — provider 는 둘이고 둘 다 `max_retries` 를 쓰며, 운영 경로에서 raw
SDK 를 주입하는 곳은 0곳이다. 그래서 `docs/standards.md` 의 "provider 를 늘릴 때도 같은
확인이 필요하다"가 계속 **사람의 규율**로 남는다. provider 를 늘릴 때 이 항목을 읽어라.

## 16. 적재하지 않은 정책 인덱스도 `no_evidence` 로 위장한다

> **갈래 (2026-08-21): 여전히 미해결.** 이 저장소 자신의 규칙에 걸려 있는 항목이다 —
> *"문서에 '이 값을 이렇게 읽지 마라'를 적었다면 아직 안 고친 것이다."* 운영 문서가 실제로
> 그렇게 적고 있고, 낡은 인덱스는 503 인데 **빈 인덱스는 여전히 정상 업무 판정으로 집계된다.**
> 다시 여는 사람이 먼저 볼 것은 코드가 아니라 **범위 결정**이다: 빈 인덱스를 설정 오류로
> 올리면 부트스트랩 순서(스키마 → 시딩 → 인덱싱)에서 인덱싱 전 요청이 전부 503 이 되고,
> 적재 전 상태를 정상으로 보는 테스트·픽스처가 함께 바뀐다.

임베딩 provenance 를 고치면서(`policy_chunks.embedding_model`·`embedding_dimensions`,
`search_policy_chunks` 의 fail-closed 대조) **행 0개는 불일치가 아니다**로 두었다 — 적재 전과
"다른 공간을 비교 중"은 다른 상태이고, 부트스트랩 중 검색을 오류로 만들 이유가 없다.

그런데 실측에서 같은 위장이 남아 있는 것을 봤다. 스키마 변경으로 볼륨을 재생성한 직후
(정책 미적재 상태) 실제 서버에 문의를 넣으니 이렇게 끝났다:

```text
POST /inquiries {"content": "환불 신청 기간이 어떻게 되나요"}
→ 200 {"status": "escalated", "escalation_reason": "no_evidence", ...}
```

`docs/operations.md` 5단계가 "이 단계를 건너뛰면 모든 문의가 `no_evidence` 로 인계된다"고
이미 적어 두었다 — **문서에 "이 값을 이렇게 읽지 마라"를 적었다면 아직 안 고친 것이다.**
낡은 인덱스는 이제 503 인데 빈 인덱스는 여전히 정상 업무 판정으로 집계된다.

**지금 안 고치는 이유는 판단이 필요해서다.** 빈 인덱스를 설정 오류로 올리면 부트스트랩
순서(스키마 → 시딩 → 인덱싱)에서 인덱싱 전 요청이 전부 503 이 되고, 적재 전 상태를
정상으로 보는 테스트·픽스처가 함께 바뀐다. 어느 쪽이 이 제품에 맞는지는 범위 결정이다.

## 17. 조회 라우트가 쓰지도 않는 read-only 계정에 묶여 있다

> **갈래 (2026-08-21): 여전히 미해결.** 활성 유출도 오답도 아니고 손해는 진단성 하나지만,
> 보안 문서가 RO 계정을 경계로 다루므로 **폭발 반경 관점에서는 줄이는 것이 맞다** — 그래서
> 닫지 않고 열어 둔다. 다시 여는 사람이 먼저 볼 것은 두 수정 방향의 대가다: RO 커넥션을
> 옵셔널로 만들면 "text-to-SQL 은 반드시 read-only 커넥션으로"라는 불변식이 `None` 을
> 허용하게 되고(안전장치 1층이 헐거워진다), 지연 생성으로 가면 생성자 모양이 바뀌어 주입
> 지점 전체를 건드린다. **어느 쪽이 이 제품에 맞는지가 범위 결정이라 사용자에게 남긴다.**

`GET /inquiries/{id}` 는 `load_inquiry(conn=app_conn, ...)` 만 부른다 — read-only 커넥션을
쓰지 않는다. 그런데 커넥션을 여는 계층(`api.get_service` 의 `_open`)이 **둘을 함께** 열어서,
RO 계정만 깨져도 조회가 죽는다. RO 비밀번호만 틀리게 두고 실측:

```text
app 커넥션 정상: {'ok': 1}
500  POST 주문번호 형식 오류 → 422 여야 한다      ← 이건 16번 커밋에서 고쳤다
500  GET /inquiries/{id} → RO 를 쓰지 않는 경로다  ← 이건 남았다
```

(같은 실측에서 **오류 메시지에 비밀번호 평문은 없었다** — psycopg 는 host·port·user 만
싣는다. 확인하고 넘어간 것이지 검사하지 않은 것이 아니다.)

**활성 유출도 오답도 아니다.** RO 계정이 깨진 상태는 주 경로가 이미 죽은 상태이고, 조회가
500 이 되는 것은 진단성 손해다. `docs/security.md` 가 RO 계정을 경계로 다루므로 폭발 반경
관점에서는 줄이는 것이 맞다.

**지금 안 고치는 이유는 값이 아니라 모양 때문이다.** 라우트별로 필요한 커넥션만 열려면
`InquiryService` 가 RO 커넥션을 **선택적으로** 들거나 지연해서 열어야 하는데, 전자는
"text-to-SQL 은 반드시 read-only 커넥션으로"라는 불변식을 옵셔널로 만들고(안전장치 1층이
`None` 을 허용하게 된다), 후자는 생성자 모양을 바꿔 주입 지점 전체를 건드린다. 어느 쪽이
이 제품에 맞는지는 범위 결정이라 사용자에게 남긴다.

## 18. 채택 컷 하나가 세 방향을 동시에 못 지킨다 — **종결 (2026-08-19, 사이클 4 기권 게이트)**

**제목 정정 (2026-08-19)**: 이 항목의 제목은 오래 **"양방향"** 이었는데 본문이 세는 방향은
처음부터 셋이다 — ① 정답 조항 보존(G04) ② 무근거 문의 기권(G21–G24) ③ **상충쌍 보존**
(G18·G01·G02). ③이 제목에서 빠져 있었고, 그 셋째 방향이야말로 합산 지표에도 비악화 가드에도
안 잡혀 이 사이클을 촉발한 것이다. 제목을 방향 수에 맞춘다.

**종결**: 컷은 그대로 두고 **축을 하나 더 만들어** 닫았다 — 질의 단위 기권 게이트
(1위 − `top_k`위 산포, τ=0.06)를 컷 위에 얹었다
([결정 0014](decisions/0014-기권-게이트를-1위-top_k위-산포-축으로-채택한다.md)).
라이브 3회(`reports/evaluation-live-l2-{10,11,12}`)에서 **세 방향이 동시에 성립한다.**

| 방향 | 표적 | 새 축 3회 실측 |
|---|---|---|
| ① 정답 조항 보존 | G04 가 `policy:support:4-6` 을 채택하고 정상 답변 | **3/3** (채택 근거 `exchange:3-1`·`support:4-6`, 3회 모두 `answered`) |
| ② 무근거 문의 기권 | G21–G24 가 채택 0건 | **12/12** (`no_evidence` · 시도 0건) |
| ③ 상충쌍 보존 | G18·G01·G02 가 상충쌍을 **함께** 채택 | **각 3/3** |

**"두 번 실측된 것"은 여전히 참이다** — 컷이라는 **단일 축**으로는 셋을 동시에 못 지킨다.
바뀐 것은 축이 늘어난 것이고, 이 항목이 요구했던 **케이스 단위 하한**은 격자의 채택 규칙 ①로
코드에 들어갔다(`retrieval_eval.py`, 격자 165 구성 중 **124개가 그 규칙에서 탈락한다**).

**닫히지 않은 것 셋.** ① 확률 층 위의 관측이다 — 3/3 은 "항상"이 아니다. ② τ 는
`text-embedding-3-small` d1536 조건의 값이고 `-3-large` 계열에서는 어떤 τ 도 두 군을 가르지
못한다(`docs/engineering-notes.md` "τ 는 임베딩 모델에 묶인다"). ③ 아래 "왜 오프라인 채택이
이걸 못 잡았나"가 지적한 **집계와 케이스 단위의 어긋남 자체**는 사라지지 않았다 — 이번에는
채택 규칙에 하한을 명시해 피한 것이지 집계에 계단이 생긴 것이 아니다.

아래는 종결 전 기록이다.

**증상**: T10 라이브 3회(`reports/evaluation-live-l2-{4,5,6}`)에서 컷 0.50 이 표적 둘을
맞히면서 **다른 세 케이스의 근거를 잘랐다.**

| 잘린 것 | 코사인 | 결과 |
|---|---:|---|
| G21–G24 가 물던 인접 조항 | 0.347~0.481 | ✔ 검색 단계 기권 — 표적 관측 ② 11/12 |
| G04 정답 `policy:support:4-6` | 0.3571 | ✘ 근거 0건 → 정상 문의가 `no_evidence` 인계 (3/3) |
| G18 상충 `policy:refund:2-4` | 0.4676 | ✘ L2 모순 기각 소멸 — 사이클 2 는 3/3 `reject`, 지금 3/3 `pass` |
| G01 상충 `policy:refund:2-2` | 0.4693 | ✘ 같은 기전 — 사이클 2 는 2/3 `reject`, 지금 3/3 `pass` |

**G01 행은 2026-08-18 에 추가됐다** — T10 당시 이 항목이 "둘"로 적었다. 산출물 대조가 근거다:
사이클 2 는 `evaluation-live-l2-{1,3}` 이 `reject_reasons=["contradictory_evidence"]`,
T10 은 `evaluation-live-l2-{4,5,6}` 3회 모두 `adopted_evidence_ids=["policy:refund:2-1"]`
단독이다. **잘린 것은 계열이지 단발이 아니다.**

컷 스윕상 G04(≤0.350)와 G21–G24(≥0.500)를 **동시에 만족하는 값이 없다.** 재작성은 G17 을
고쳤지만(0.264 → 0.580, 3/3 채택) 컷이 만드는 양방향 문제 자체는 옮겼을 뿐이다.
**컷은 0.30 으로 원복했고 재작성은 유지한다**(하드 게이트 9 "실측이 정당화하지 않는 기본값을 남기지 않는다").

**왜 오프라인 채택이 이걸 못 잡았나** — 컷을 올리는 동안 **케이스가 죽은 걸음이 둘이고
둘 다 macro F1 이 오른 걸음이다**(`reports/retrieval-strategies-live-*` 의 `vector_rewrite` 스윕):

| 걸음 | macro F1 | 그 걸음에서 죽은 것 |
|---|---|---|
| 0.35 → **0.40** | 0.374 → **0.403** | **G04 가 정답 조항을 전부 잃었다**(recall 1.00 → 0.00) |
| 0.45 → **0.50** | 0.482 → **0.676** | **G18 이 상충 조항 `refund:2-4` 를 잃었다**(1.00 → 0.50) — L2 모순 기각이 사라진 지점 |

G04 의 전면 실패가 집계에 남긴 자국은 **recall 1/25 = 0.04 하나뿐**이다. precision 에는
아무것도 남지 않았다 — 오프라인 검색 지표 규약이 **"정답이 있는데 0건 검색"된 문의를
precision 평균에서 제외**하기 때문이다(분모가 0 이라 값이 없다. 분모 30 → 29). 벌점이 아니라
**퇴장**이다. 케이스 하나가 "정상 답변"에서 "근거 0건 인계"로 떨어진 사건이 집계에서는
**F1 상승으로 보였다.**

**규약이 틀린 것이 아니다** — 분모 0 인 precision 에 0 이나 1 을 채우면 검색 실패가
precision 을 올리거나 두 번 벌한다. 틀린 것은 **그때의 채택 규칙이 집계만 봤다는 점**이다.
사이클 3 의 채택 규칙은 사다리 단끼리의 상대 비교 넷뿐이었다 — ① 다음 단은 표적 결함
(G17 순위·유사도 / G21–G24 오검색)을 **적어도 하나 개선하고 다른 하나를 악화시키지 않을 때만**
후보가 된다 ② 전체 지표(recall·precision)가 기준선 아래로 내려가면 탈락 ③ 동률이면 싼 쪽·
의존성이 적은 쪽·차원이 안 바뀌는 쪽 ④ 결과는 "가장 싼 충분한 조합" 하나. 여기에 *"라벨이
있는 케이스가 채택 근거 0건이 되면 안 된다"* 는 **케이스 단위 하한**이 없었다. 제품에서 "근거
0건"은 부분 손실이 아니라 **상태 전이**(answered → escalated)인데 집계 단위에는 그 계단이
없다. 다음 채택 규칙은 이 조건을 명시해야 한다.

**G18 계열이 더 나쁜 모양이다.** 이 회귀는 **일치율에도**(결정 0008 이 미끼 라벨을 내려
`answered` 도 정답), **비악화 가드에도**(`matched=True`), **측정 3 에도**(픽스처 기반) 잡히지
않는다. 유일하게 잡은 것이 사이클 3 T9 의 분해 절(`answered_without_relevant_evidence /
missing=policy:refund:2-4`, 3회 모두)이다. 검색 라벨 note 가 기전을 미리 적어 뒀는데도
그렇다 — *"L2 가 모순을 잡으려면 검색이 둘을 함께 올려야 한다."*

**왜 그때 더 해결할 수 없었나**: 세 방향을 한 축으로 못 지킨다는 것이 실측으로 두 번
확인됐다. 남은 길은 컷이 아니라 **채택 축을 늘리는 것**(질의별 적응 컷·상대 마진·상충쌍 보존
규칙)이고 전부 별도 설계라 사이클 3 범위 밖이었다. **사이클 4 가 그 셋 중 앞의 둘을 손계산으로
반증하고**(적응 컷·상대 마진은 1위를 지우지 못해 절대 하한과 조합해도 기권이 안 생긴다 —
전수 격자 576 구성 중 0개, [결정 0012](decisions/0012-적응-컷과-상대-마진을-반증하고-기권-게이트만-남긴다.md))
**셋째(상충쌍 보존 규칙)는 고칠 것이 0건이라 범위 밖에 뒀다**
([결정 0013](decisions/0013-상충쌍-보존과-상충-후보-탐지기를-범위-밖으로-둔다.md)).
남은 것이 질의 단위 기권 게이트 하나였고 위 종결 절이 그 결과다.

**딸린 관측 2건**(수정 아님):
- 분해 절의 "검색 실패 5건" 중 3건(G25·G26·G27)은 주문번호 단계 **사전 인계**라 검색이
  개입할 자리가 없었다. 분해 규칙(**기각·인계된 케이스를 검색 정답 라벨과 조인해, 정답
  조항이 채택 근거에 있었으면 "생성 문제" · 없었으면 "검색 실패"로 가른다**) 그대로 동작한
  것이지만 이름이 실제를 오도한다.
- 미끼 기각 재현율 26.7% → **13.3%**(2/15). 남은 둘은 모두 G16 의 L1 `missing_citation`
  이라 **미끼 범주에서는 라이브 L2 기각 장면이 사라졌다** — 사이클 3 의 데모 서사가
  "L2 라이브 기각 장면"을 맡긴 G18 이 그 장면이었다. 사이클 3 T12 가 정면으로 부딪힌다.
  **범주 밖까지 넓히면 "사라졌다"는 거짓이다**(2026-08-18 정정): 같은 T10 3회에서 G30 이
  3/3 회 `unsupported_claim` 으로 기각→재생성→통과했고 run6 의 G02 는
  `contradictory_evidence` 였다. 사라진 것은 **미끼 골든셋이 재현하던 기각 장면**이지
  L2 기각 자체가 아니다.

## 19. 보존하기로 한 처리 기록 2건이 DB 에 없다 — **종결 (2026-08-21, 시연이 마지막 한 건을 재현했다)**

**종결 — 닫는 방식은 "고쳤다"가 아니라 "재현됐다"다.** 사이클 5 의 시연이 웹 폼으로 기각을
실제로 **유발해** 마지막 한 건을 다시 만들었다. 코드를 고쳐서 닫은 것이 아니라 확률 층을
여러 번 두드려 장면을 다시 얻은 것이고, 그 차이를 적어 두는 이유는 **같은 기록을 또 잃으면
다시 사야 한다**는 성질이 그대로이기 때문이다.

| 무엇 | 처분 | 근거 |
|---|---|---|
| `rejected_twice` 건 (L2 기각 → 재생성 → 재기각 → 인계) | **재현됐다** (사이클 3) | `208ba896-c193-4f16-ad40-e958d4a512c1` |
| `pii_detected` 오탐 건 | **복구 불가로 닫혔다** | 현재 코드에서 재현되지 않는다([4번](#4-처리-기록에-오탐-버그-시절의-문의가-남아-있다--종결-2026-08-19-볼륨-재생성으로-사라졌다)) |
| **`missing_citation` → 재생성 → 통과 건** | **재현됐다 (2026-08-21)** | `335b7c05-553c-450c-9de0-0ebf9da8f727` — 시연 장면 1의 **3회차**. `GET /inquiries/335b7c05-553c-450c-9de0-0ebf9da8f727` 로 열린다 |

DB 에서 직접 확인한 그 문의의 시도 기록은 이렇다 — 시도 1이 L1 `reject`(`missing_citation`,
L2 미실행), 시도 2가 L1 `pass` · L2 `pass`. **L1 구조 기각이 재생성 한 번으로 통과로 뒤집힌
기록**이고, README 가 인용하는 장면이 이제 DB 에도 있다.

**3회차라는 것을 함께 적는다.** 미끼 기각은 확률 층에 달려 있어 1·2회차는 1시도 통과로 끝났고
(`784099c2-…` · `2e2ec6a5-…`), 그 회차들도 기록에 남아 있다. **"한 번에 나온다"고 적으면
다음 사람이 같은 기대로 과금한다.**

아래는 종결 전 기록이다.

**갱신 (2026-08-19, 사이클 4 T13 데모 재현 중 확인)**: 현재 `inquiries` **5행** ·
`inquiry_attempts` **4행**이다.

| 문의 ID | 시각(UTC) | 상태 | 시도 | 무엇인가 |
|---|---|---|---:|---|
| `2a8882d0…` | 08-13 09:19 | `escalated` / `no_evidence` | 0 | 아래 원 증상이 적은 잔여 1행 |
| `bfb8cb5b…` | 08-14 07:03 | `answered` | 1 | 정상 답변 (카드 번호 뒷자리 문의) |
| `208ba896…` | 08-14 07:07 | `escalated` / `rejected_twice` | 2 | **L2 기각 → 재생성 → 재기각 → 인계** — README 3-2 가 인용하는 기록 |
| `3dc1f668…` | **08-19 10:30** | `answered` | 1 | 사이클 4 데모 — G04 정상 답변 (L1 pass → L2 pass) |
| `8e0e821f…` | **08-19 10:30** | `escalated` / `no_evidence` | **0** | 사이클 4 데모 — **기권 게이트**가 검색 단계에서 끝냈다 |

- **보존 대상 둘 중 하나는 재현됐다** — `208ba896…`(사이클 3 T12 가 웹 폼으로 다시 흘렸다).
  `GET /inquiries/208ba896-c193-4f16-ad40-e958d4a512c1` 로 열린다.
- **다른 하나는 복구 불가로 닫혔다** — [4번](#4-처리-기록에-오탐-버그-시절의-문의가-남아-있다--종결-2026-08-19-볼륨-재생성으로-사라졌다)의
  `pii_detected` 오탐 건은 현재 코드에서 재현되지 않는다.
- **아직 없는 것 하나**: 6번이 *"`GET /inquiries/{id}` 로 열린다"* 고 적은
  **`missing_citation` → 재생성 → 통과** 건(README 3-1 장면)은 DB 에 여전히 없다.
  재현하려면 웹 폼으로 미끼 문의를 흘려 L1 기각을 **유발**해야 하는데, 그 기각은 확률 층에
  달려 있어(미끼 기각 재현율 6.7~26.7%) 한 번에 나온다는 보장이 없다.

**그래서 이 항목은 "아직 없는 것 하나"로 좁혀 열어 둔다.** 남은 것은 데이터 손실이 아니라
**과금·비결정론이 붙은 재현 시도**이고, 몇 번을 시도할지는 사용자 판단이다.

아래는 원 기록이다.

**증상**: `inquiries` 1행 · `inquiry_attempts` **0행**이다. 남은 1행은 2026-08-13 09:19 UTC 의
`escalated`/`no_evidence` 이고, 보존 대상 두 건은 **둘 다 시도 기록이 있어야 한다**:
[4번](#4-처리-기록에-오탐-버그-시절의-문의가-남아-있다--종결-2026-08-19-볼륨-재생성으로-사라졌다)의 `rejected_twice` 건(시도 2건)과
[6번](#6-평가-하네스가-처리-기록을-남기지-않는다)이 *"`GET /inquiries/{id}` 로 열린다"* 고
적은 데모용 기각→재생성→통과 건이다. 시도 0행이면 어느 쪽도 존재할 수 없다.

**언제 사라졌나**: 08-13 의 provenance 컬럼(`embedding_model`·`embedding_dimensions`) 추가로
볼륨을 재생성한 시점으로 보인다. 볼륨 재생성 절차 — **처리 기록 4테이블 덤프 → 볼륨 재생성
→ 시딩 → 재색인 → 컬럼을 명시한 복원** — 에서 복원이 빠졌거나 비었다.
**`GET /inquiries/{id}` 로 실제 열어 확인하라**는 조항이 있는데 그것이 통과했다면 잡혔을
자리다 — 건수 대조만으로는 부족하다는 그 조항의 근거가 실측으로 확인된 셈이다.

**영향 범위**: 사이클 3 T10 은 영향받지 않는다 — 평가 하네스는 처리 기록을 쓰지도 읽지도 않는다(6번).
**T12 가 받는다.** 데모 기각 장면이 DB 에도 없고, 18번 때문에 골든셋 라이브 실행에도 없다.

**왜 그때 해결할 수 없었나**: 복구는 재생성이 아니라 **재현**이다 — 웹 폼으로 기각을 유발하는
문의를 실제로 흘려야 하고(과금·비결정론), 4번 건은 애초에 현재 코드에서 재현되지 않는
오탐이라 **복구할 수 없다**(그 사실 자체는 4번이 이미 적고 있다). 무엇을 어떤 조건으로
다시 만들지는 데모 서사 결정이라 사용자가 정한다.

## 20. 평가 리포트의 케이스 귀인이 세 가지를 구분·표기하지 못한다 — **종결 (2026-08-19, 사이클 4 T1 반영)**

**종결**: 셋 다 `evaluation.py` 의 귀인 절에 들어갔고, 사이클 4 의 첫 풀셋 라이브부터
산출물에 실린다. 커밋된 리포트에서 문면을 그대로 확인할 수 있다
(`reports/evaluation-live-l2-{7,8,9}` 이후 전부).

| 항목 | 반영된 모양 | 커밋된 산출물의 문면 |
|---|---|---|
| ① 정책 검색 실행 여부 | `GoldenOutcome.intent` 를 읽는다 — **검색 토큰 0 + `sql:` 단독 채택으로 역추론하지 않는다.** 의도 해석이 무너졌으면 `False` 가 아니라 `None`(미상)이다 | *"**정책 검색 미실행**(의도 분류가 `order` 로 라우팅해 정책 검색이 실행되지 않았다)"* — `G09`·`G10`·`G11`·`G13`·`G14`·`G25`~`G27`·`G29`·`G30` |

**그리고 이 항목이 지목한 필드 하나가 판정 조건으로 승격됐다** —
`missing_relevant_evidence_ids` 는 이제 표기가 아니라 회귀 가드 **비악화 판정 ②의 입력**이다
(`src/reply_gate/AGENTS.md` 불변식 17·21). 이 항목이 "결함 고발이 아니라 개선 목록"이라고
적은 그 장치가, 이번 사이클에 사람 눈이 아니라 코드가 돌리는 판정으로 올라갔다.

**닫히지 않은 것**: 커밋된 T10 산출물(`evaluation-live-l2-{4,5,6}`)은 **사후 편집 금지 원칙대로
그대로다** — 새 필드는 새 실행부터이고, 그 셋을 읽을 때는 위 세 구분이 없다는 것을 알고 읽어야
한다.

아래는 종결 전 기록이다.

T10 라이브 3회 산출물(`reports/evaluation-live-l2-{4,5,6}`)을 적대리뷰가 전수 재계산하면서
확인됐고, 각 건은 독립 검증(반박 시도)을 통과했다. **사이클 3 T9 가 넣은 귀인 절은 이 사이클 최대의
회귀(G18)를 유일하게 잡아낸 장치다** — 이 항목은 그 장치의 다음 개선 목록이지 결함 고발이
아니다.

**① "검색이 걸렀다"와 "검색이 아예 안 돌았다"를 구분하지 못한다.**
`answered_without_relevant_evidence` 로 찍힌 G09·G10·G11·G13·G29 와 `retrieval_failure` 로
찍힌 G30 은 **채택 근거가 `sql:` 행뿐이고 검색 토큰이 0** 이다 — 의도 분류가 `order` 로
라우팅해 정책 검색이 실행되지 않았다. 컷과 무관하므로 원복 후에도 그대로다. 사전 인계
계열(G25–G27)은 [18번](#18-채택-컷-하나가-세-방향을-동시에-못-지킨다--종결-2026-08-19-사이클-4-기권-게이트)의
딸린 관측이 이미 지적했고, 이 항목이 나머지 절반(의도 라우팅 생략 경로)을 마저 적는다.
G14 는 run 간 분류가 흔들리고(run5 `generation_issue` / run6 awre), G28 은 의도 분류
플랩으로 run5 만 정책 검색에 진입했다(원문 질의가 이미 컷 위 — 재작성 탓이 아니다).

**② 빈 정답 케이스의 anomaly 분류기가 주문 단계 사전 인계 경로를 모른다.**
G28 이 3회 전부 `expected_no_answer_anomaly` 로 찍혔다(run4/6 "검색 0건이지만
no_evidence·시도 0건 종료가 아님", run5 "근거를 채택했지만 L2 기각 사유 없음"). 셋 다
최종 상태는 `escalated`/`order_not_found` — business-rules 의 "구조적 사유가 이긴다"
계약상 **정상 종결**이다. 분류기의 기대 목록에 이 경로가 없다.

**③ `generation_issue` 는 분류가 아니라 표기가 오도한다.** 분류 자체는 정의
(`rejected_at_least_once`)에 부합한다 — T10 의 4건(케이스 G02·G14·G16)은 실제로 1차 초안이
기각됐다. 문제는 리포트가 **최종 상태와 matched 를 병기하지 않아** "기각·인계"가 종결
실패처럼 읽힌다는 것이다. 넷 다 재생성으로 회복해 `answered`/matched 로 끝났고, 특히
G02(run6)는 심어 둔 상충 조항을 L2 가 `contradictory_evidence` 로 잡은 **기대 동작**이다.

**왜 그때 해결할 수 없었나**: ①은 귀인 스키마에 "정책 검색 실행 여부" 필드가 필요하고(당시
산출물에서는 검색 토큰 0 + `sql:` 단독 채택으로만 역추론된다), ②는 분류기의 기대 경로
확장, ③은 리포트 표기 확장이다 — 셋 다 `evaluation.py` 귀인 절 재설계 사안이라 다음
사이클(status "남은 것" 2번의 회귀 판정 상설화와 같은 자리)로 넘겼다. 커밋된 T10 산출물은
사후 편집 금지 원칙대로 그대로 둔다. **사이클 4 T1 이 회귀 가드 상설화와 같은 작업에서
셋을 함께 반영했다** — 위 종결 절.

## 21. OpenAI 캐시 적중분을 재지 않아 생성·검색 계열의 달러가 전부 상한이다 — **종결 (2026-08-21, 사이클 5 T5)**

**종결 — 고쳤다.** `llm.py` 의 OpenAI 래퍼가 `usage.input_tokens_details` 의 캐시 계열을 읽고
(`faeedae`), 평가 리포트가 **계열마다 write/read 한 쌍**으로 집계한다 —
`generation_cache_creation_total`·`generation_cache_read_total` ·
`retrieval_cache_creation_total`·`retrieval_cache_read_total`. 아래가 요구한 규칙 둘을 지켰다:
없는 값은 0 이 아니라 미측정(`None`/`null`/"미측정")이고, **생성 입력 칸에 접지 않고 별도 칸**이다.

**포함 관계가 계열마다 반대라 환산식도 갈린다.** OpenAI 의 캐시 계열은 `input_tokens` 의
**내역**이라 적중분이 입력 안에 들어 있고, Anthropic 은 `input_tokens` 가 적중분을 **제외한**
값이다. 그래서 입력 칸에서 빼지도 더하지도 않았고 계열 합계에도 더하지 않았다 — 더하면 같은
토큰을 두 번 센다. 단가 문서가 계열별 환산식의 정본이다.

**첫 실측(`evaluation-live-l2-28`·`-29`·`-30`, 확인 실행은 `-31`)에서 값이 실제로 실렸다.**

| 세트 | 생성 write | 생성 read | 검색 write | 검색 read |
|---|---:|---:|---:|---:|
| 28 | 1,059 | 0 | 0 | 0 |
| 29 | 3,152 | 0 | 0 | 0 |
| 30 | 3,288 | 0 | 0 | 0 |
| 31 | 1,071 | 0 | 0 | 0 |

**닫힌 것과 닫히지 않은 것을 갈라 적는다.** 닫힌 것은 **읽지 못하던 것을 읽게 된 것**이다.
닫히지 않은 것 둘:

- **커밋된 옛 산출물의 생성·검색 달러는 영구히 상한이다.** 그 실행들이 캐시 계열을 재지 않았고
  재집계할 방법이 없으며, 재실행은 과금되고 확률 층이라 같은 값이 나오지 않는다
  (하드 게이트 7). 새 값이 정본이고 옛 값은 "상한"으로 병기한다.
- **캐시 write 단가가 출처 미확인이라 달러 칸이 비어 있다** — 토큰은 실측인데 벤더 출처
  표에 그 열이 없다. 새 항목 [30번](#30-openai-캐시-write-단가가-출처-미확인이라-달러-칸이-비어-있다)이 든다.

**위 네 세트에서 캐시 read 가 0 이라는 것도 함께 적는다** — 이 조건에서는 상한과 실측이 같다.
"캐시 적중이 없었다"는 **이 세트들의 관측**이지 일반 사실이 아니다.

아래는 종결 전 기록이다. **줄번호는 수정 전 것이다** — 지금 OpenAI 쪽 읽기는
`llm.py:516-521`(캐시 계열을 함께 읽는다)이고 Anthropic 쪽 배선은 `llm.py:661-667` 로 밀렸다.
아래 본문의 달러 단가는 **기준일 2026-08-19** 기준이다.

**증상**: `docs/tracking/pricing.md` 의 생성(`gpt-5.6-terra`)·검색 계열 달러는 **실제 청구액이
아니라 그 이상일 수 없는 값**이다. 얼마나 더 적은지는 이 저장소가 모른다.

**원인**: `src/reply_gate/llm.py` 의 `OpenAIGenerationClient.complete_json` 이
`usage.input_tokens`/`usage.output_tokens` 만 읽고 **캐시 적중분(`cached_tokens`)을 읽지
않는다**(`llm.py:423-425`). 그래서 리포트의 `generation_input_total`·`retrieval_input_total`
은 캐시 적중분을 **포함한 총 입력**이고, 그중 얼마가 캐시 단가($0.20/M — 정가의 1/10)로
과금됐는지 알 수 없다. 환산은 전부 정가 $2.00 을 곱한다.

**Anthropic 쪽에는 같은 배선이 이미 있다.** [결정 0019](decisions/0019-판정-프롬프트-캐싱을-실측하고-채택하지-않는다.md)
가 `cache_creation_input_tokens`·`cache_read_input_tokens` 를 `JsonCompletion` →
`JudgeOutcome` → 리포트까지 이었다(`llm.py:554-561`). **같은 자리가 생성 계열에 비어 있다** —
"교훈을 적을 때 그 규칙이 걸려야 할 나머지 대상을 함께 세어라"는 이 저장소의 규칙
(`docs/engineering-notes.md` "결함 보고서를 그대로 티켓으로 옮기지 마라")에 정확히 걸린다.

**영향 범위**: 계열 간 **절대액 비교**가 기운다. 판정 계열은 캐싱을 껐을 때 실측치가
정확한데(캐시 write/read 가 전부 0) 생성 계열은 상한이라, "판정이 건당 비용의 72.3%" 같은
점유율이 실제로는 더 높을 수 있다. **토큰 수는 영향받지 않는다** — 틀리는 것은 달러뿐이다.

**왜 지금 해결할 수 없나**: `llm.py` 배선 변경이라 코드 사안이고, 넣는다면 판정 쪽과 같은
규칙을 지켜야 한다 — **없는 값은 0 이 아니라 `None`(미측정)** 이고, 리포트에 **별도 칸**으로
싣는다(생성 입력 칸에 접으면 같은 은폐가 반대 방향으로 생긴다). 고칠지 말지는 별도 판단이다.

## 22. 단계별 지연이 한 번도 측정된 적이 없다 — **종결 (2026-08-21, 사이클 5 T4)**

**종결 — 고쳤다.** 구간 **아홉**을 재고(`9068aa0`+`d217ed1`) 평가 리포트까지 싣는다 —
`intent` · `query_rewrite` · `inquiry_embedding` · `policy_search` · `sql_generation` ·
`sql_execution` · `draft` · `gate` · `l2_judge`. 설계와 기각한 대안은
[결정 0025](decisions/0025-단계별-지연을-구간-아홉으로-가르고-미측정을-0-과-구분한다.md).
**돌지 않은 구간은 0 이 아니라 미측정**이고(JSON `null` · 마크다운 "미측정"), 예외로 죽은
호출의 경과도 토큰과 같은 자격으로 올려보낸다.

**이 항목이 "쓸 수 없다"고 적은 문장을 이제 쓸 수 있다.** `evaluation-live-l2-28` 실측:

| 구간 | 측정/미측정 케이스 | 평균 ms | p50 ms | p95 ms |
|---|---:|---:|---:|---:|
| `intent` | 30 / 0 | 1,400.95 | 1,248.15 | 2,453.49 |
| `query_rewrite` | 21 / 9 | 1,680.86 | 1,446.86 | 3,730.07 |
| `inquiry_embedding` | 21 / 9 | 363.20 | 181.53 | 830.04 |
| `policy_search` | 21 / 9 | 29.98 | 29.32 | 40.69 |
| `sql_generation` | 9 / 21 | 1,700.41 | 1,645.27 | 2,092.30 |
| `sql_execution` | 11 / 19 | 7.02 | 6.67 | 14.22 |
| `draft` | 22 / 8 | 2,098.16 | 1,848.27 | 4,221.76 |

**가장 큰 칸이 판정이고, L1 게이트는 1 ms 미만이다** — "결정론 층은 공짜에 가깝고 확률 층이
시간을 먹는다"는 이 저장소의 설계 서사가 처음으로 숫자를 얻었다. 미측정 칸도 0 과 갈렸다
(`query_rewrite` 21/9 · `sql_generation` 9/21 …).

**닫지 않은 것을 함께 적는다.**

- **계약과 스키마는 넓히지 않았다.** 구간은 평가 리포트까지만 간다 — HTTP 응답에도 처리
  기록에도 없다. "어느 문의가 몇 초였나"를 화면에서 보는 것은 여전히 안 된다.
- **구간 합은 전체 시간보다 작다.** 프롬프트 조립·근거 렌더링·판정 파싱처럼 어느 구간에도
  들지 않는 코드가 남는다. 계약은 "합이 전체를 넘지 않는다"이지 "합이 전체와 같다"가 아니다.
- **비동기화는 하지 않았다.** 이 계측이 그 판단의 선행 조건이었고 조건은 채워졌지만,
  비동기화 자체는 사이클 5 의 범위 밖이다
  ([결정 0020](decisions/0020-비동기화를-검토하고-이번-사이클에는-하지-않는다.md)).
- **대역 실행에서는 밖으로 나가는 여섯 구간이 0 이다.** 대역이 실제로 나가지 않기 때문이고,
  대역에 실제 시계를 붙이면 `--stub-llm` 산출의 결정론이 깨진다. 엔지니어링 노트가 그 자리를
  다룬다.

아래는 종결 전 기록이다.

**증상**: 리포트에 있는 지연 필드는 셋뿐이다 — 케이스별 `latency_ms`, 세트별
`latency_p50_ms`·`latency_p95_ms`. **임베딩·검색·재작성·초안 생성·판정 각각의 벽시계 시간을
기록하는 자리가 없다.** 측정 3(판정 픽스처)은 지연을 아예 기록하지 않는다.

**그래서 지금 말할 수 있는 것은 "파이프라인이 어디까지 갔는가"별 차집합뿐이다**
([결정 0020](decisions/0020-비동기화를-검토하고-이번-사이클에는-하지-않는다.md) 1절).
`evaluation-live-l2-{10,11,12}` 90건에서: 접수~검색 구간의 **상한**이 4.5초(기권 게이트로
끝난 12건의 최댓값 4.474초), 시도 1회 종결의 중앙값이 11.6~12.1초. **그 사이 7~8초대를
초안과 판정으로 가르는 값은 없다.** "초안 7초 / 판정 5초" 같은 문장은 지금 산출물로 쓸 수 없다.

**영향 범위**: 처리 비동기화 판단의 **1순위 선행 조건**이다. 계측 없이 비동기화하면
"무엇이 나아졌는가"를 말할 수 없고, 실측이 가리키는 진짜 꼬리(재생성 1회가 만드는 40~49초)를
겨냥했는지도 확인할 수 없다. 계측이 먼저인 이유는 그것이 **더 싸고**(계약 무변경) 비동기화가
못 쓰는 문장을 쓰게 해 주기 때문이다.

**왜 지금 해결할 수 없나**: 코드 변경이고, **계측 설계 자체가 결정 사안**이다 — 무엇을
언제 재는가(구간 경계), 응답 계약에 싣는가 처리 기록에만 남기는가, 미측정을 0 으로 채우지
않는 규칙(`scripts/AGENTS.md` 불변식 5)을 어떻게 거는가. 사이클 4 T11 은 문서 전용 범위였다.

## 23. 승격 기준선이 채택된 기본값과 어긋나 있다 — **종결 (2026-08-21, 사이클 5 T9·T10 재등재)**

**종결 — 고쳤다.** 현 기본값 조합으로 **풀셋 라이브 3회**를 사서(`evaluation-live-l2-28`·
`-29`·`-30`, 실측 $1.656935 — 단가 기준일 2026-08-19) 사용자 확인 뒤 등재했다(`4ab78d6`).
근거·관측·대가는 [결정 0027](decisions/0027-승격-기준선을-재등재한다.md).
`supersedes` 는 `evaluation-live-l2-{7,8,9}` 이고, 지문 스물다섯 칸은 **산출물 JSON 에서
복사**했다(옮겨 적지 않았다 — `retrieval_order` 에 `%s` 와 가운뎃점이 들어간다).

**아래 "재등재할 때 함께 정리할 것" 다섯이 전부 실행됐다.** 특히 5번(등재 뒤 첫 실행에서
구속 줄이 **선언 없이** 대조를 진행하는지)이 이 항목을 닫는 유일한 증거였고, 확인 라이브
1회(`evaluation-live-l2-31`, $0.517549 — 단가 기준일 2026-08-19)가 그것을 얻었다:
**지문 스물다섯 칸 완전 일치 · `--declare-experiment` 없이 대조 진행 · 어긋난 항목 0.**

**같은 확인 실행의 구속 줄 판정은 "미달"이었다.** `G06` 하나가 갈렸기 때문이고, 그것은
**이 항목이 말하던 어긋남과 다른 사건**이다 — 지문은 완전히 일치했고 어긋남 목록은 비어
있었다. 새 항목 [29번](#29-g06-이-확인-라이브에서-처음으로-이탈했다--확률-층의-첫-관측)이
그쪽을 든다. **두 사실을 함께 적지 않으면 다음에 읽는 사람이 속는다.**

**닫히면서 계보 하나가 끊겼다 — 대가를 알고 받았다.** 조건 지문이 18칸에서 25칸으로 넓어져
**커밋된 옛 산출물 전부가 새 일곱 항목에 대해 "미상"** 이 된다. 세트 정족수가 다시 차는 데
3회가 필요하고, 그 3회가 방금 등재한 28·29·30 이다.

아래는 종결 전 기록이다. **산출물 정정 절(커밋된 리포트 18건의 짝 이름 문구)은 종결과
무관하게 유효하다.**

**증상**: `data/promoted_baseline.json` 은 `evaluation-live-l2-{7,8,9}` 를 등재하고 있는데,
그 세 세트는 **기권 게이트가 배선되기 전**에 산 것이다. 게이트는 승격 **뒤에** 채택됐다
([결정 0014](decisions/0014-기권-게이트를-1위-top_k위-산포-축으로-채택한다.md)). 그래서
앞으로 어떤 풀셋 실측을 해도 회귀 가드가 이 두 항목을 어긋남으로 적는다.

어긋난 항목은 **넷**이고, 세 사건이 쌓인 결과다.

| 지문 항목 | 기준선 | 현 기본값 실측 | 언제 갈렸나 |
|---|---|---|---|
| `abstention_gate_statistic` | `미배선` | `rank1_minus_rank_k_spread` | 결정 0014 채택(승격 뒤) — **영구** |
| `abstention_tau` | `미배선` | `0.06` | 같음 — **영구** |
| `judge_fixture_version` | `fixture-836322e97320` | `fixture-2b8f33392b36` | [결정 0016](decisions/0016-J11-판정-픽스처를-제품-실행-경로의-근거-집합에-맞춘다.md) 의 픽스처 교정 — **영구** |

**영향 범위**: 앞의 셋은 `--declare-experiment` 로 선언하지 않으면 회귀 가드가 "대조 불가"로
멈춘다. **선언은 그 실행의 예외 처리이지 등재의 정정이 아니다** — 매 실행 선언을 붙이는 것이
기본이 되면, 어느 날 진짜 어긋남이 같은 선언에 묻힌다. 그리고 선언한 채로 진행한 대조는

종결 경로가 `rejected_twice` → `no_evidence` 로 바뀐 것)가 매번 차이 목록에 실린다.

**왜 지금 해결하지 않았나**: **사용자 결정이고 이번 사이클에는 하지 않기로 정해졌다.**
재등재는 **풀셋 라이브 3회(측정 2·3 모두)를 새로 사야** 하고, 승격은 사람만 한다
(`scripts/AGENTS.md` 불변식 17 — 하네스에 자동 경로가 없다).

**산출물 정정 (2026-08-19) — 커밋된 리포트 18건에 거짓 문장이 하나 실려 있다.**
`evaluation-live-l2-{10..27}` 의 회귀 가드 사유 줄이 `abstention_tau` 어긋남에
*"(짝인 `embedding_model` 도 함께 달라졌다)"* 를 붙였다. **사실이 아니다** — 승격 기준선과
그 실측 전부가 `text-embedding-3-small` 이고 임베딩은 한 번도 바뀌지 않았다. 짝 이름을
값 비교 없이 무조건 붙이던 문면 결함이고 코드는 고쳤다(`abd5642` — 짝이 실제로 달라진
경우에만 붙이고, 세 경우의 문면을 회귀 테스트가 못박는다).
**산출물은 보존한다** — 재생성에 과금이 들고 확률 층이라 같은 값이 나오지 않는다
(`CLAUDE.md` "절대 깨지 않는 것" 7). **어긋난 항목 자체는 위 표대로 맞다**; 틀린 것은 괄호 안
한 구절뿐이다.

**재등재할 때 함께 정리할 것** — 하나라도 빠지면 다시 어긋난 채로 등재된다:

1. **새 풀셋 라이브 3회를 현 기본값으로 산다** — 재작성 켜짐 · 컷 0.30 · **기권 게이트
   `rank1_minus_rank_k_spread` τ=0.06** · `judge_model=claude-sonnet-5` · 판정 프롬프트
   `judge-e26f6c8e0b84`(원복된 판) · **판정 픽스처 `fixture-2b8f33392b36`** · 캐싱 꺼짐 ·

2. `supersedes: ["evaluation-live-l2-7", "evaluation-live-l2-8", "evaluation-live-l2-9"]`
   를 적는다.
3. `fingerprint` 의 위 네 항목을 새 값으로 채운다 — `미배선` 두 칸이 실제 값으로 바뀐다.
4. **승격 사유에 관측 근거를 적는다** — 세 방향 동시 충족(G04 정답 조항 보존 · G21–G24 기권 ·

   그게 재등재가 실제로 닫혔다는 유일한 증거다.

## 24. Postgres 접속 문자열에 비밀번호가 박혀 있고, 드라이버 오류로 샐 가능성이 검증되지 않았다 — **닫혔다 (고쳤다, 2026-08-25)**

> **갈래 (2026-08-25): 닫혔다.** 2026-08-21 에는 "여전히 미해결"이었고, 그때 적어 둔
> **다시 여는 사람의 첫 할 일은 고치는 것이 아니라 재현**이었다. 사이클 5 감사가 카나리아를
> 주입해 그 재현을 마쳤다 — 필드 넷은 다섯 표면 전부에서 마스킹되는데
> `database_url`·`readonly_database_url` 에는 값이 **그대로 들어간다**. 조건이 채워졌으므로
> 그 다음 걸음을 걸었다.
>
> **닫는 방식**: 조립 결과를 `SecretStr` 로 감쌌다. 접속 문자열이 비밀번호를 **담는 것**은
> 그대로다(담지 않으면 접속이 안 된다). 바뀐 것은 **평문 `str` 로 내놓지 않는다**는 것이다 —
> 표시·덤프가 필드와 같은 자격으로 닫히고, 값이 필요한 자리는 `db.connect` 가 psycopg 에
> 넘기기 직전 **한 줄**뿐이다. AST 자리 세기가 `config.py` 2 · `db.py` 1 · `llm.py` 3 으로
> 그 수를 못박고, `tests/test_config_secrets.py` 가 카나리아를 덤프 경로 전수에 태워
> 확인한다. 동작 무변경 — `pytest -m db` 178건이 실제 접속으로 통과한다.
>
> **남는 한계 셋.** ① 값을 직접 꺼내 찍는 코드는 어떤 설정 클래스도 막지 못한다(리뷰가
> 막는다). ② 이미 새어 나간 값은 타입 변경으로 무효가 되지 않는다 — **로테이션은 따로다.**
> ③ 아래 "검증되지 않은 것"의 psycopg 내부 경로(커넥션 객체가 트레이스백에 실리는 경우 등)는
> 여전히 재현된 적이 없다. 감싼 것은 **우리 쪽 표면**이고, 드라이버가 자기 프레임에 들고 있는
> 문자열까지 감싸지는 못한다.

**증상**: `config.Settings._dsn` 이 `postgresql://<user>:<password>@host:port/db` 를 조립하고
`db.connect` 가 그 문자열을 `psycopg.connect` 에 그대로 넘긴다. **비밀번호가 문자열 안에
평문으로 들어 있다.**

**지금까지 확인된 것은 한 경로뿐이다.** [17번](#17-조회-라우트가-쓰지도-않는-read-only-계정에-묶여-있다)
의 실측에서 RO 비밀번호를 틀리게 두고 접속을 실패시켰을 때 **오류 메시지에 비밀번호는 없었다**
— psycopg 는 `host`·`port`·`user` 만 싣는다. 그 관측은 유효하다.

**검증되지 않은 것**: 그 밖의 경로 전부다. 다른 종류의 접속 실패(타임아웃·SSL·프로토콜 오류),
psycopg 상위 버전의 메시지 문면 변경, 커넥션 객체가 트레이스백·로그·`repr` 에 실리는 경우,
그리고 서드파티(예: pytest 의 지역 변수 덤프)가 DSN 문자열을 들고 있는 프레임을 찍는 경우.
**이번 사이클에 설정 객체의 `repr` 로 API 키가 pytest 출력에 실린 사고가 실제로 났고,
별개로 에이전트 세션 기록에 `.env` 값이 평문으로 남은 것도 확인됐다**
(`docs/engineering-notes.md` "설정 객체가 repr 되면 자격 증명이 평문으로 따라간다") — 같은
계열의 위험이 DSN 쪽에 남아 있는지를 **재현해 본 적이 없다.**

**영향 범위**: 로컬·합성 데이터 규모라 유출 대상은 로컬 Postgres 비밀번호뿐이다. 다만
`docs/security.md` 의 비밀 관리 규칙이 막으려는 것과 **같은 계열**이고, 이 저장소는
`Settings.postgres_app_password`·`postgres_ro_password` 를 `repr=False` 로 이미 뺐다 —
**DSN 은 그 조치의 밖에 있다**(값을 조립한 새 문자열이라 필드 repr 규칙이 걸리지 않는다).

**왜 그때 해결하지 않았나** (2026-08-21 기준 서술): **기록만 한다.** 고치는 방향은 둘인데
어느 쪽도 공짜가 아니다 — ① DSN 대신 키워드 인자(`psycopg.connect(host=..., password=...)`)로
넘기면 비밀번호가 별도 인자가 되지만, 그 값도 프레임에는 남는다. ② 비밀번호를
`PGPASSWORD`·`.pgpass` 로 옮기면 문자열에서는 사라지지만 프로세스 환경으로 옮겨갈 뿐이다.
**먼저 할 일은 재현이다** — "이 값을 이렇게 읽지 마라"를 문서에 적기 전에 실제로 새는지
확인한다(`docs/engineering-notes.md` "결함 보고서를 그대로 티켓으로 옮기지 마라").

**실제로 고른 것은 셋째 길이다** (2026-08-25). 위 둘은 **비밀번호를 어디에 두느냐**를 바꾸는
방향이라 "값이 옮겨갈 뿐"이라는 대가가 붙었다. 셋째는 두는 자리를 그대로 두고 **내놓는
타입**만 바꾼다 — 조립 결과를 `SecretStr` 로 감싸면 문자열은 그대로인데 표시·덤프가 닫히고,
평문이 되는 지점이 psycopg 호출 한 줄로 좁아진다. 위 둘의 대가(프레임·프로세스 환경으로의
이동)가 없고, psycopg 에 넘기는 인자 형태도 바뀌지 않는다. **재현이 먼저라는 규율은 지켰다** —
사이클 5 감사의 카나리아가 유출을 실제로 보인 뒤에 걸었다.

## 25. 판정 클라이언트의 thinking docstring 이 계열 전체에 참인 것처럼 적혀 있다 — **닫혔다 (고쳤다, 2026-08-23)**

> **갈래 (2026-08-23): 닫혔다.** 2026-08-21 에는 세 영향 중 하나만 닫혀 있었고, 남은
> 문면을 사이클 2 적대 리뷰가 다시 집어 그 자리에서 고쳤다.
>
> | 아래가 센 영향 | 지금 상태 |
> |---|---|
> | ① 모델을 이전 계열로 바꾸는 사람이 docstring 을 읽고 "thinking 은 켜져 있다"고 믿는다 | **닫혔다 (고쳤다)** — docstring 이 계열을 갈라 적는다: sonnet·opus 는 미전송이 adaptive 켜짐, `claude-haiku-4-5` 는 **미전송이면 안 켜진다** |
> | ② `judge_max_output_tokens=16000` 의 근거가 그 계열에서는 다른 뜻이 된다 | **닫혔다 (고쳤다)** — 같은 문면이 "계열을 바꾸면 이 상한의 뜻도 함께 바뀐다"를 명시한다 |
> | ③ 실행 조건 지문이 이 축을 숨긴다 | **닫혔다 (고쳤다)** — 지문에 `judge_thinking` 칸이 생겼다 |
>
> ③이 닫힌 방식: 지문이 `judge_effort` 와 **다른 축**으로 `judge_thinking` 을 따로 들고,
> 값은 "미전송(계열 기본)"이다. 그래서 `judge_model` 과 함께 읽으면 그 실행이 어느 계열의
> 기본으로 돌았는지 복원된다 — 세 모델이 모두 `judge_effort=기본값` 한 줄로만 적히던
> 상태가 아니다. **값이 코드 사실과 갈리지 못하게 구조 검사가 판정 요청 조립에 `thinking`
> 키가 없음을 못박는다**([결정 0026](decisions/0026-실행-조건-지문을-일곱-칸-넓히고-내용-지문의-범위를-선언과-동작으로-가른다.md)).
> **다만 그 검사도 이름 기반이라 다른 이름의 파라미터로 thinking 을 보내면 못 잡는다** —
> [28번](#28-구조-검사가-코드가-강제한다를-지탱하지-못한다--이름문면-블록리스트-2026-08-20)의
> 한계가 여기에도 그대로 걸린다.
>
> **닫는 방식**: `llm.py` 의 `complete_json` docstring 을 계열 한정으로 고쳤다(동작 무변경 —
> 여전히 `thinking` 을 보내지 않고, 구조 검사가 그것을 못박는 상태도 그대로다).
> **남는 한계**: ③의 구조 검사가 이름 기반이라는 [28번](#28-구조-검사가-코드가-강제한다를-지탱하지-못한다--이름문면-블록리스트-2026-08-20)의
> 제약은 이 항목이 닫혀도 그대로다.
>
> **정정 (2026-08-26): 닫은 문면이 사실 하나를 틀리게 적었다.** 아래 본문과 2026-08-23 의
> docstring 은 `claude-haiku-4-5` 를 *"thinking 이 아예 없다"* 로 적었는데, 그 계열도
> **extended thinking 을 지원한다** — 다만 4.6 이전이라 `thinking={"type": "enabled",
> "budget_tokens": N}` 을 **명시해야** 켜지고 미전송이면 안 켜진다. 저장소 자신이 같은
> 문단의 괄호(*"4.6 이전 계열은 `budget_tokens` 를 명시해야 켜진다"*)로 맞는 말을 하고
> 있었으므로 **문면끼리 충돌한 것**이다. 실무 결론(그 계열에서는 `max_output_tokens` 가
> 순수 응답 상한)은 바뀌지 않아 항목은 닫힌 채 두고, `llm.py` 의 문면만 정확히 고쳤다 —
> 오독을 막는다는 이 항목의 목적은 정정으로 오히려 더 채워진다.

**증상**: `src/reply_gate/llm.py:630-632` 의 `AnthropicGenerationClient.complete_json`
docstring 이 이렇게 적는다 — *"`thinking` 설정은 보내지 않는다 — 미전송은 '끔'이 아니라
**adaptive thinking 켜짐**이 모델 기본이다."* 이 문장은 **모델 계열에 따라 참이 아니다.**

**근거**: [결정 0018](decisions/0018-판정-모델-Anthropic-3종을-비교만-하고-기본값은-바꾸지-않는다.md)
의 "같은 조건이 아닌 축이 하나 있다" 절 — `claude-sonnet-5`·`claude-opus-5` 는 미전송이
adaptive thinking 켜짐이지만 **`claude-haiku-4-5` 는 미전송이면 안 켜진다**(4.6 이전 계열은
`budget_tokens` 를 명시해야 켜진다 — thinking 이 **없는** 모델이 아니다. 위 정정 참조).
docstring 은 4.6+ 계열에 대해서만 참이다.

**영향 범위**: 셋이다. ① `JUDGE_MODEL` 을 이전 계열로 바꾸는 사람이 docstring 을 읽고
"thinking 은 켜져 있다"고 믿는다. ② `judge_max_output_tokens=16000` 의 근거("thinking+응답
합산 상한이라 여유 있게 둔다")도 그 계열에서는 다른 뜻이 된다. ③ **실행 조건 지문이 이 축을
숨긴다** — 세 모델 모두 `judge_effort=기본값` 으로만 적히므로, 산출물만 보고는 thinking 축이
같았는지 알 수 없다. 결정 0018 의 판정 모델 비교표가 **사과 대 사과가 아닌 이유**가 이것이고,
그 문서는 그 사실을 본문에 적어 두었다.

**왜 지금 고치지 않나**: 이 항목이 발견된 작업(사이클 4 T13)이 **문서 전용 범위**라
`src/` 를 건드리지 않는다. 고칠 때 함께 볼 것 둘: docstring 문면을 계열 한정으로 바꾸는 것과,
**지문에 thinking 축을 실을 것인지**(모델별 기본 동작이라 "미전송"만으로는 조건을 복원할 수
없다). 후자는 지문 스키마 사안이라 별도 판단이다.

## 26. 사이클 4 최종 리뷰 advisory 중 **고치지 않기로 한 것** (수용 기록)

> **갈래 (2026-08-21): 일곱 중 다섯이 닫혔고 둘이 "의도적으로 하지 않기로 한 것"으로 남는다.**
> 아래 "다시 열 시점"이 예고한 대로 **재등재 묶음이 그 다섯을 한 번에 열었다.**
>
> | 하위 항목 | 처분 | 근거 |
> |---|---|---|
> | 1. 기권 게이트가 fail-open 이다 | **절반은 고쳤고 절반은 반증됐다** | 미정의 사유 둘을 갈랐다 — 1위 코사인 ≤ 0 은 **기권으로 뒤집었고**, 측정 2건 미만은 **열린 채 두는 것이 옳다는 것이 확인됐다**(fail-closed 를 기계적으로 걸면 후보가 하나뿐인 질의가 근거 없이 인계된다). [결정 0022](decisions/0022-미정의-사유를-갈라-처분하고-검색-정렬에-tie-break를-넣는다.md) |
> | 2. 검색 SQL 에 결정론 tie-break 가 없다 | **고쳤다** | `ORDER BY embedding <=> %s, evidence_id`. 같은 결정 |
> | 3. 승격 기준선이 낡았다 | **고쳤다** | [23번](#23-승격-기준선이-채택된-기본값과-어긋나-있다--종결-2026-08-21-사이클-5-t9t10-재등재)이 전문을 든다 |
> | 4. 중단 표시가 사람이 읽는 줄에만 붙는다 | **고쳤다** | 조건 지문에 `run_completion` 항목이 생겼고, **중단 사실은 마지막에 써서 명시 지문이 덮을 수 없다** |
> | 5. `extra_clauses` 가 "덮는 청크 없음"을 0 으로 채운다 | **하지 않기로 한 것** | 청킹은 비교까지만이고 제품에 한 줄도 반영되지 않았다. 같은 행의 `single_unit_covers_all=False` 가 두 상황을 가르고 리포트가 두 칸을 함께 싣는다 |
> | 6. 런타임 경로에 판정 계열 캐시 토큰 집계가 없다 | **하지 않기로 한 것** | 판정 캐싱이 기본 꺼짐이라 잠재 상태다. **생성·검색 계열의 같은 공백은 [21번](#21-openai-캐시-적중분을-재지-않아-생성검색-계열의-달러가-전부-상한이다--종결-2026-08-21-사이클-5-t5)이 닫았고**, 판정 계열은 기본값을 켜는 순간 기존 가드가 실패하는 자리라 함께 열지 않았다 |
> | 7. 임베딩을 바꿔도 런타임이 τ 를 막지 않는다 | **고쳤다** | `(모델, 차원)` 조건이 조립 시점에 죽는다. **명시적으로 끈 실행은 통과시킨다** — 그것이 τ 재산출의 유일한 문이기 때문이고, 지문에 `"꺼짐"` 으로 남는다 |
>
> **아래 "문서 리뷰 쪽에서 고치지 않은 것" 세 건(A·B·C)은 셋 다 "의도적으로 하지 않기로 한 것"** 이다.
> 사유는 각 항목이 그대로 들고 있고, 프로젝트가 닫히면서 바뀐 것은 없다. **B 가 남긴 규칙 —
> "근거 채택 순서의 정본은 구성 문서이고, 축이 바뀌면 다섯 곳을 함께 연다" — 은 그대로
> 유효하다**: 사이클 5 가 채택 축의 미정의 처리를 바꿨고 그 다섯 곳이 열려야 하는 자리였다.

**아래는 종결 전 기록이다.** 문면과 줄번호는 사이클 4 시점 그대로 두고 고치지 않는다 —
무엇이 어떻게 닫혔는지는 위 표가 든다.

최종 코드 리뷰 22건 중 고칠 것은 고쳤고(이중 기준선 동일 세트 표기 · `--chunking-grid` 의
무시되는 인자 · 손계산 산출물 비추적 명시 · 구조 테스트 사각 4건 · 테스트가 개발자 `.env` 를
읽던 것), 아래는 **고치지 않기로 판단한 것**이다. 조용히 버리지 않으려고 여기 남긴다.

**공통 사유가 하나 있다 — 실측이 끝난 뒤 제품 동작을 바꾸면 이번 사이클 라이브의 조건이
무효가 된다.** 커밋된 라이브 리포트는 재생성에 과금이 들고 확률 층이라 같은 값도 나오지
않는다. 그래서 "지금 틀린 값을 내지는 않는" 항목은 **승격 기준선 재등재와 한 묶음**으로
다음 사이클에 넘긴다(항목 23).

**1. 기권 게이트가 fail-open 이다.** `abstention_statistic`
(`src/reply_gate/retrieval_strategies.py:163`)은 측정된 점수가 2건 미만이거나 **1위 코사인이
0 이하**면 `ValueError` 를 낸다. `apply_abstention_gate`(`:186`)가 그 예외를 받아
`abstains=False` 로 접는다 — **통계량이 정의되지 않으면 게이트가 열린다.** 비를 쓰지 않는
`spread`·`stdev`·`gap_1_2` 도 같은 문에 함께 걸린다.
*지금 뒤에서 자르는 것*: 절대 하한 0.30. 1위 코사인이 0 이하인 질의는 모든 후보가 컷 아래라
어차피 채택 0건이다 — 관측 가능한 오동작이 아니다.
*왜 안 고치나*: fail-closed 로 바꾸면 채택 축의 동작이 바뀌어 `evaluation-live-l2-{10,11,12}`
3회의 실행 조건이 그 순간 무효가 된다.

**2. 검색 SQL 에 결정론 tie-break 가 없다.** `search_policy_chunks` 의
`ORDER BY embedding <=> %s LIMIT %s`(`src/reply_gate/policy_index.py:382`)뿐이라 **코사인
동점이면 순서가 Postgres 몫**이다. 26행 코퍼스·정확 스캔이라 실무상 안정적이지만 보장은
아니고, 동점이 `top_k` 절단선에 걸리면 채택 집합과 기권 게이트 통계량이 함께 흔들린다.
*왜 안 고치나*: `ORDER BY ..., evidence_id` 한 줄이지만 **채택 집합을 바꿀 수 있는 변경**이라
1번과 같은 자리에 있다.

**3. 승격 기준선이 낡았다.** 전문은 항목 23 이 들고 있다. 재등재는 풀셋 라이브 3회 구매 +
사람의 결정이고 **이번 사이클에는 하지 않기로 사용자가 정했다.**

**4. 중단된 측정 2 의 표시가 사람이 읽는 줄에만 붙는다.** `_ABORTED_MARK`
(`scripts/evaluate.py:318`)는 생성·임베딩·판정 **설명 문자열**에 붙지만
`_condition_fingerprint`(`:766`)에는 대응 항목이 없다 — **기계가 읽는 조건은 완주한 실행과
같다.** 리포트의 사람이 읽는 줄과 조건 지문이 갈릴 수 있다는 이 저장소의 함정이 여기 한 번 더
있다.
*지금 실제로 오염된 대조는 없다*: 중단 리포트는 골든셋 케이스가 비어 세트 정족수를 못 채운다.
*왜 안 고치나*: 지문에 항목을 더하면 **커밋된 라이브 전부가 그 항목 미상**이 되어 대조 계보가
한 번 더 끊긴다. 재등재 시점이 그것을 감당할 유일한 자리다.

**5. `extra_clauses` 가 "덮는 청크 없음"을 0 으로 채운다.**
`_adjacency_coverage`(`src/reply_gate/retrieval_eval.py:3665`)는 `covering` 이 비면 `extra=0`
을 적는데, 0 은 필드 주석대로 **"공짜로 둘을 얻는다"** 를 뜻하기도 한다 — 숫자만 읽으면 두
상황이 구분되지 않는다. 같은 행의 `single_unit_covers_all=False` 가 가르고 리포트 표가 두 칸을
함께 싣는다.
*왜 안 고치나*: 청킹은 **비교까지만**이고 제품에 한 줄도 반영되지 않았다
([결정 0015](decisions/0015-청킹은-조항-단위를-유지하고-고정-크기는-비교까지만-한다.md)).
산출물은 이미 커밋됐고 사후 편집하지 않는다.

**6. 런타임 경로에 캐시 계열 토큰 집계가 없다.** 집계는 **측정 3 경로에만** 있다. 캐싱이 기본
꺼짐이라 지금은 잠재 상태이고, `tests/test_judge_prompt_caching.py` 의 가드가 **기본값을 켜는
순간** 실패한다 — 그 가드는 이번 반영에서 문자열 스캔에서 AST 로 바꿨다(주석·docstring 에 이름이
스치기만 해도 가드가 스스로 꺼지던 사각이었다). 생성 계열의 같은 공백은 항목 21.

**7. 임베딩을 바꿔도 런타임이 τ 를 막지 않는다.** τ=0.06 은 `-3-small` 1536 에서만 분리하고
`-3-large` 계열에서는 여유가 **음수**다(−0.0114 / −0.0160) — 임베딩을 바꾸면 게이트가 조용히
무력해진다. 지금 있는 방어는 **리포트 지문의 짝 하나**뿐이다
(`regression_guard.PAIRED_FINGERPRINT_FIELDS["abstention_tau"] == "embedding_model"`) — 사후에
"대조 불가"로 드러나는 것이지 실행을 막지 않는다. `policy_chunks` 의 임베딩 출처 일치 검사는
코퍼스 일관성이지 τ 가 아니다.
*왜 안 고치나*: 런타임 방어(지문 불일치 시 게이트 거부 등)는 배선 변경이라 1·2 와 같은 자리다.

### 27-2. NFKC 가 대시류를 접지 않아 지어낸 번호가 초안에서 통과한다 — **해결됨 (2026-08-20)**

`fold_for_detection`(`gate.py:316`)의 docstring 은 "사람 눈에 같은 값이 패턴을 비껴가지
못하게 한다"고 적지만, NFKC 는 `Pd` 범주의 대시 대부분을 ASCII 하이픈으로 접지 않는다.
`DEFAULT_PII_PATTERNS`(`gate.py:94-130`)의 구분자 클래스는 `[-. ()]` 뿐이다.

미탐은 두 계열이다.

① **대시 변종** — `U+2010` · `U+2011` · `U+2012` · `U+2013` · `U+2014` · `U+2015` · `U+2212` ·
`U+2027` · `U+30FB` · `U+FF65` · `/` · `_`. NFKC 가 `Pd` 범주를 ASCII 하이픈으로 접지 않는다.

② **결합문자·변이선택자** — `U+0301` · `U+FE0F`. **둘 다 `category == "Mn"` 이라
`fold_for_detection` 의 `Cf` 필터에 안 걸린다.**

**②는 배치가 가른다** — 숫자열 **안쪽**에 끼워야 뚫린다:

```
"연락처는 010-1́234-5678 입니다"   (U+0301 자리 사이) → pass    ⚠
"연락처는 010-1234-5678́ 입니다"   (U+0301 맨 끝)     → reject
"연락처는 010-1️234-5678 입니다"   (U+FE0F 자리 사이) → pass    ⚠
"연락처는 010-1​234-5678 입니다"   (U+200B 자리 사이) → reject  ← Cf 는 지워진다
```

안쪽에 끼우면 `[0-9]{3,4}` 가 끊겨 통과하고, 끝에 붙이면 이미 매치가 끝난 뒤라 `(?![0-9])` 가
유지돼 기각된다. **회귀 테스트에는 자리 사이 배치를 박아야 한다.**

정상 탐지: ASCII `-` · `U+FF0D` · `U+00AD` · `U+200B` · `U+2060` · `U+00A0` · `U+3000`.

**그래서 접기 보강은 `Pd` 하나로는 부족하고 `Mn` 도 함께 지워야 한다.** 한쪽만 넣으면 나머지
계열이 그대로 남는다.

부수 사항: `fold_for_detection` 은 27-1 을 고치면서 `gate.__all__` 로 열렸고 `evidence.py` 가
쓴다. **접기를 넓히면 이 두 층이 함께 넓어진다** — 근거 필터의 기준도 같이 움직이므로 27-2 를
넣을 때 근거 쪽 회귀(정상 에코 보존)를 함께 봐야 한다.

**적대적이지 않은 경로로도 난다** — 생성 모델이 한국어 문장에서 en/em dash 를 쓰는 것은 흔하다.
양방향이라 미탐(지어낸 en-dash 번호 통과)과 오탐(근거가 en-dash 인데 초안이 ASCII 정상 에코
→ 기각) 둘 다 열린다.

**이쪽은 조건 보존이 아니다.** 접기를 넓히면 초안 판정 자체가 바뀌어 측정 1·2 의 조건이
달라진다 — 26번의 1·2·4·7 과 같은 자리, 즉 **재등재 묶음**이다.

### 27-3. 반대 방향 — 가드가 **승인한** 정상 쿼리가 정상 에코를 오기각한다 — **해결됨 (2026-08-20)**

`_pii_safe_output_columns`(`src/reply_gate/sql_guard.py:878`)는 `orders` **직접 컬럼만**
승인한다. 의미가 같고 가드를 통과하는 쿼리인데 **CTE · 파생 테이블 · `COALESCE`** 를 거치면
진짜 고객 연락처가 `evidence_text` 에서 사라져 정상 답변이 `pii_detected` 로 기각된다.
`COALESCE` 는 SQL 생성 프롬프트가 허용 함수로 **직접 광고**하는 것이다
(`evidence.py:234` → `describe_allowed_functions()` → `sql_guard.py:121`).

설계 의도는 fail-closed 지만, **그 대가가 오탐률이라는 것이 어느 문서에도 수치로 없다.**
헤드라인 지표 하나가 "정상 초안 오탐률"이라 SQL 생성기의 문체에 따라 지표가 흔들린다.
fail-closed 를 유지할지 provenance 를 넓힐지는 결정 사안이다.

### 27-4. 캐스트로 `pg_catalog` 이 읽힌다 — 안전장치 2층 우회 — **해결됨 (2026-08-20)**

`sql_guard.py:127` 이 `cast` 를 허용 함수로 두면서 **대상 타입을 검사하지 않는다.**
`SELECT CAST(10 AS REGROLE) AS who, order_no FROM orders WHERE order_no='…'` 가 가드를
통과하고 superuser 이름 `postgres` 를 근거로 들여온다. `CAST('inquiries' AS REGCLASS)` 는
화이트리스트 밖 테이블의 **존재 여부 오라클**이 된다(존재하면 이름, 없으면 `UndefinedTable`).

1층도 못 막는다 — read-only 계정이 `pg_catalog`·`pg_roles`·`pg_stat_activity` 를 읽는다
(`pg_authid`·`pg_shadow`·`pg_read_file` 은 `InsufficientPrivilege`). 즉 이 경로를 막는 층은
**가드 하나뿐**이다. `docs/security.md` "1층" 의 *"그 외 어떤 테이블에도 권한이 없다"* 는
시스템 카탈로그에 대해서는 참이 아니다.

주문 데이터·PII 로 확대되지는 않으므로 치명 1번(주문 밖 행)이 아니다. 다만 치명 3번의
문면("화이트리스트 밖 테이블이 읽히는 경로")에는 정면으로 걸린다.

### 뚫지 못한 것 (같은 감사의 음성 대조)

주문 범위 강제는 **뚫리지 않았다** — `OR 1=1` · `OR true` · WHERE 없음 · 다른 주문번호 ·
`IN` 다중값 · 부질의 조건 · `LIKE` · `NOT (…)` · `= ANY (SELECT …)` · 미한정 CTE · 미한정
파생테이블 · 미한정 상관 부질의 · SELECT 절 스칼라 부질의 · `USING`/INNER JOIN 한쪽만
전부 `order_scope` 거부. 외부 조인은 `unsupported_join`, 소스 별칭 중복은 `duplicate_source`.
화이트리스트도 테이블 경로로는 뚫리지 않았고, read-only 계정 쓰기는 전부
`InsufficientPrivilege` 다. **자격 증명 평문은 커밋된 파일·리포트 전수 스캔에서 0건이다.**

| 이름을 갈아 낀 헬퍼 한 겹을 거쳐 `promoted_baseline.json` 에 쓴다 | 6(승격은 사람만) | **열림** |
| `from reply_gate.llm import …` — 최상위 이름이 `reply_gate` 라 금지 집합을 비껴간다 | 1(L1 은 LLM 을 안 부른다) | **닫음** (2026-08-20) |
| `from statistics import pstdev` — `ast.Import` alias 와 `ast.Attribute` 호출만 보던 검사를 비껴간다 | 게이트 원시연산 재구현 금지 | **열림** |

그리고 **음성 대조가 검사기 함수만 태우고 검사 대상 목록 유도부를 태우지 않는** 파일이
둘 있었다 — 목록을 비워도 초록이었다(`test_durable_citations.py` · `test_regression_guard.py`).
`tests/AGENTS.md` 불변식 3 이 "빈 검사가 초록으로 보이는 사고를 blind 구조 검사에서 한 번
겪었다"고 적은 바로 그 형태다. **닫았다**(2026-08-20, non-empty 단언 + 음성 대조).

*왜 나머지를 안 고치나*: 이름 블록리스트를 의미 기반 검사로 바꾸는 것은 가드 층의 재설계라
범위가 크고, 지금 뚫리는 것은 **실수가 아니라 의도적 우회**뿐이다(실수 방지용으로는 9/9 로
충분하다). 다만 README·문서가 "코드가 강제한다"고 적는 자리에는 이 한계가 병기되어야 한다.

## 29. G06 이 확인 라이브에서 처음으로 이탈했다 — 확률 층의 첫 관측

> **갈래 (2026-08-21): 여전히 미해결.** 사이클 5 가 **새로 연** 항목이다.
> 결정 0027 이 *"닫은 것이 아니라 열어 둔다"* 고 명시했고, 여기가 그 자리다.

**증상**: 골든셋 `G06`(*"배송지를 바꾸고 싶은데 가능한가요?"*, 주문번호 없음)이
확인 라이브 `evaluation-live-l2-31` 에서 **인계**됐다. 골든셋 풀셋을 돌린 커밋 산출물은
**19세트**이고 `G06` 은 그중 **앞의 18세트 전부**에서 `answered`·일치였다 — 이번 사이클이
등재한 28·29·30 도 그 안에 든다. 이탈은 19번째인 확인 실행 하나다.

| | 앞선 18세트 | `evaluation-live-l2-31` |
|---|---|---|
| 의도 분류 | `policy` (기록이 있는 9세트 전부. 앞의 9세트는 산출물에 이 칸이 없다) | **`both`** |
| 종결 | `answered` (18/18) | `escalated` / **`missing_order_ref`** |
| 일치 | `matched` (18/18) | **불일치** |

`both` 는 정책과 주문 **둘 다** 필요하다는 분류이고, 그 의도에서 주문번호가 없으면 인계
사유가 `missing_order_ref` 다 — 이건 계약대로다. **갈린 것은 게이트도 채택도 아니라 의도
분류 한 칸이다**(결정 0027 이 "주문 문의로 분류"라고 적은 것이 이 값이다).

**귀인 — 이번 사이클의 변경이 아니다. 셋으로 가른다.**

1. **제품 코드가 무변경이다.** 실측 30 을 커밋한 지점부터 31 을 돌린 지점까지 `src/`·
   `scripts/` 변경이 **0 줄**이다(그 사이 커밋은 승격 참조 파일 · 검사 두 개 · 결정 기록뿐).
   **같은 코드가 `answered` 와 `escalated` 를 냈다.**
2. **앞선 18세트 전부 정상 답변이었고 이번이 첫 이탈이다.**
3. **이탈 지점이 의도 분류이고, 사이클 5 는 그 단계를 건드리지 않았다.**

**되돌릴 축이 없다.** 원복은 축별인데 귀인이 우리가 움직인 어느 축도 가리키지 않는다.
그래서 실행자가 축을 임의로 지목하지 않고 사용자 판단으로 넘겼고, **사용자가 "그대로 받고
정직하게 기록한다"를 골랐다** — 재구매하지 않았고 가드도 고치지 않았다.

**함께 드러난 성질 하나 — 확인 1회는 정족수를 기다리지 않는다.** 케이스 단위 비악화 술어의
다수결 하한이 `count // 2 + 1` 이라 **1회차에서 1** 이고, "기준선 전회 일치 → 새 실측 다수결
미달" 조건이 세트가 차기를 기다리지 않고 곧바로 발동한다. 그래서 확인 실행의 구속 줄 판정이
**보류가 아니라 미달**로 나왔다. **가드는 설계대로 동작했다** — 놓친 것은 예상 쪽이다.

**영향 범위**: 헤드라인 지표(측정 1)는 결정론이라 영향이 없고, 등재된 세트(28·29·30)의 관측도
뒤집히지 않는다 — 31 은 그 세트에 들어 있지 않다. 흔들리는 것은 **"측정 2 일치율 100%"가
얼마나 안정적인가**에 대한 기대다.

**왜 지금 해결할 수 없나**: 한 번의 관측으로는 원인을 가를 수 없고, 가르려면 **같은 조건의
라이브를 더 사야 한다.** 확률 층의 한 관측을 뒤집으려 다시 사는 것은 "잘 나온 것만 싣는다"의
다른 이름이라 하지 않기로 했다.

**다시 여는 사람이 무엇부터 볼 것인가**: `evaluation-live-l2-31` 의 `G06` 케이스와 앞선 18세트의
같은 케이스를 나란히 놓고 **의도 분류 값 하나**를 본다. 다음 물음은 "이 문의가 `both` 로도
읽히는 문의인가"이고(주문 문의가 아니라 **배송지 변경 가능 여부**를 묻는다), 그렇다면 고칠
자리는 게이트가 아니라 **의도 분류의 라우팅 기준**이다. 재현율을 재려면 같은 문의를 여러 번
흘려야 하고 그건 과금이다.

## 30. OpenAI 캐시 write 단가가 출처 미확인이라 달러 칸이 비어 있다

> **갈래 (2026-08-21): 여전히 미해결.** 사이클 5 가 **새로 연** 항목이다.
> [21번](#21-openai-캐시-적중분을-재지-않아-생성검색-계열의-달러가-전부-상한이다--종결-2026-08-21-사이클-5-t5)을
> 닫으면서 드러났다 — 토큰을 읽게 되자 그 토큰에 곱할 단가가 없다는 것이 보였다.

**증상**: 생성·검색 계열의 캐시 **write** 토큰은 실측인데(`generation_cache_creation_total`
등, 첫 실측에서 1,059~3,288) **달러가 빈 칸**이다. 벤더 출처 페이지의 OpenAI 표에 그 열이
없다. 단가 문서의 규칙 1 — *"기준일 없는 달러 수치는 싣지 않는다. 확정하지 못한 칸에는 숫자
대신 '출처 미확인'을 적는다"* — 을 그대로 따른 결과다.

**영향 범위**: 지금은 크지 않다. 첫 네 세트의 캐시 **read** 가 0 이라 그 조건에서는 상한과
실측이 같고, write 토큰은 이미 `input_tokens` 안에 포함돼 정가로 세어지고 있다. 흔들리는 것은
캐시가 실제로 적중하는 조건에서의 계열 절대액이다.

**왜 지금 해결할 수 없나**: 벤더가 공개하지 않은 값이다. 추정하면 이 저장소의 달러 규칙이
무너진다 — 기준일 없는 숫자를 싣는 순간 다음 사람이 검증할 수 없다.

**다시 여는 사람이 무엇부터 볼 것인가**: 벤더 페이지에 그 열이 생겼는지 확인하고, **기준일과
함께** 채운다. ⚠ **채울 때 더하지 마라** — OpenAI 의 write 토큰도 `input_tokens` 의 내역이라
현행 환산식이 이미 정가로 세고 있다. 별도 단가가 생기면 `(입력 − 캐시 read − 캐시 write)` 로
**빼낸 뒤** 곱한다. 정본과 경고는 [`pricing.md`](pricing.md) 가 든다.

## 31. 판정 픽스처를 넓혀 J11 을 다시 재는 길 — **하지 않기로 한 것**

> **갈래 (2026-08-21): 의도적으로 하지 않기로 한 것.** 사이클 5 가 문제정의의 범위를 닫으면서
> 이 길에 명시적으로 처분을 내렸다. 미뤄 둔 것이 아니라 **하지 않기로 한 것**이다.

**무엇을 안 하나**: 측정 3 의 유일한 어긋남(J11 — 모순 사유를 하나 덜 짚는다)을 가르는
**2×2 ablation** 을 완성하는 것. 축은 `{다리 조항이 claim 에 인용됨 / 수집만 됨}` ×
`{비지지 claim 있음 / 없음}` 이고 네 칸 중 둘이 관측됐다(J07 검출 15/15 · J11 미검출 0/15).
빈 두 칸을 채우려면 **판정 픽스처 2건을 새로 넣어야 한다.**

**왜 하지 않기로 했나 — 셋이다.**

1. **측정 3 의 분모가 바뀐다.** 지금 분모는 11 이고 픽스처를 넣으면 **지금까지의 판정 수치와
   계보가 끊긴다.** 이 프로젝트에서 계보를 끊는 것은 재등재 같은 사건에서만 감당하는 대가이고,
   프로젝트가 닫히는 자리에서 끊으면 **끊은 뒤의 실측이 없다.**
2. **추가 과금 사안이고 평가 장치 확장이라 별도 승인이 필요하다.** 하드 게이트 5 가 평가 장치를
   보호하는 자리에서, 늘리는 쪽도 사람의 결정이다.
3. **가설 두 개를 이미 실측으로 반증했고 모델을 올려도 닫히지 않았다.** 다리 조항 부재도
   (0/3), 프롬프트 강화도(1/3, 사전 판정선 미달 → 원복), 판정 모델 상향도(haiku 0/3 ·
   opus 0/3) 닫지 못했다. **다음 실험이 문면이 아니라 입력 판본이나 호출 구조여야 한다는
   것까지가 이 프로젝트가 얻은 결론**이고, 그 실험 자체는 판정 층의 판을 한 번 더 넘긴다.

**원인을 단정하지 않는다.** 이 저장소가 말할 수 있는 것은 관측뿐이다 — 커밋된 라이브 측정 3
**31세트 중 30세트**에서 J11 이 같은 방향으로 어긋난다(기대 사유가 `unsupported_claim` +
`contradictory_evidence` 인데 모순 쪽 하나를 덜 짚는다). 유일한 예외는 뒤에 원복된 프롬프트
판의 한 회(`evaluation-live-l2-16`)다. "모순 검출이 뒷받침 판정보다 약하다"는 **신호**이지
진단이 아니다.

**다시 여는 사람이 무엇부터 볼 것인가**: [결정 0016](decisions/0016-J11-판정-픽스처를-제품-실행-경로의-근거-집합에-맞춘다.md)
의 2×2 표와 [결정 0017](decisions/0017-사유-독립-명시를-실측으로-반증하고-판정-프롬프트를-원복한다.md)
의 반증. **분모를 바꾸기로 했다면 그 전후 수치를 반드시 병기한다** — 입력이 달라진 뒤의
동일성은 재현이 아니다.

## 33. 조회 가드의 분기 넷이 검사에 물리지 않는다 — **닫혔다 (고쳤다, 2026-08-25)**

> **갈래 (2026-08-25): 닫혔다.** 코드는 처음부터 옳았다. 닫은 것은 **검사가 그 옳음을 붙들지
> 않던 공백**이다. 35번을 닫으며 얻은 절차(격리 검산 + 뮤테이션으로 RED 확인)를 그대로 썼다.

`sql_guard.py` 의 네 분기가 **뮤테이션을 넣어도 스위트가 초록이다.**

| 분기 | 뒤집었을 때 | 유출로 이어지나 |
|---|---|---|
| `_resolve_bare_pii_safe` 의 `all` → `any` | 판정이 갈리는 입력이 존재한다 | **아니다** — 같은 이름을 내놓는 소스가 둘이면 PostgreSQL 이 ambiguous 로 먼저 죽는다 |
| `nullif` 의 비교 상대 UNKNOWN 검사 제거 | 판정이 갈린다 | **아니다** — `nullif` 의 출력은 `a` 아니면 NULL 이라 비교 상대 값이 흐르지 않는다 |
| 전부 고정값인 `coalesce` → DIRECT | 판정이 갈린다 | **아니다** — 승인되는 값이 개인정보 모양이 아닌 고정값뿐이다 |
| `o.*` projection → DIRECT | 판정이 갈린다(`coalesce` 인자 자리로 도달) | **아니다** — 최상위 projection 은 소스 단위로 따로 편다 |

**넷 다 심층 방어의 검사 공백이지 열린 구멍이 아니다.** 그래도 남겨 두는 이유는, 코드가
옳다는 것을 **지금 사람이 읽어서** 알고 있을 뿐 검사가 그것을 붙들고 있지 않기 때문이다.

**닫는 방식**: 각 분기 **하나만** 판정을 가르는 입력을 하나씩 짜서
`tests/test_sql_guard_provenance.py` 의 `test_유래_판정의_각_분기를_뒤집으면_이_입력의_판정이_갈린다`
에 넣었다. 넓은 음성 목록에 파라미터를 더하는 것으로는 닫히지 않는다 — 그 입력들이 **다른
이유로도** 불승인이라 노린 분기를 지워도 다른 분기가 대신 잡아 준다(35번과 같은 모양이다).

| 분기 | 그 분기에만 닿는 입력 |
|---|---|
| `_resolve_bare_pii_safe` 의 `all` | 임시 테이블이 `customer_phone` 을 합성해 내놓고 `orders` 도 같은 이름을 내놓는다 — **한쪽만** 증명됐다 |
| `nullif` 비교 상대 | `nullif(customer_phone, '010-9999-9999')` — `a` 는 직접 컬럼, **`b` 만** 증명되지 않았다 |
| `coalesce` 전부 고정값 | `coalesce('미정', '없음')` — 인자에 UNKNOWN 이 **없어서** 앞 가지에서 안 걸린다 |
| `o.*` projection | `coalesce(o.*, '미정')` — 별표가 인자 자리라 소스 단위 처리를 안 거친다 |

**뮤테이션을 실제로 돌려 확인했다** — 넷 다 지금 `()` 이고 각 분기를 뒤집으면
`("customer_phone",)` 가 된다. 얻은 규율은 [engineering-notes](../engineering-notes.md) 의
CHECK 음성 대조 절에 함께 적었다(그 규율이 DB 제약만의 것이 아니라는 것이 이번에 확인된
부분이다).

## 35. 층별 사유 CHECK 두 가지가 음성 대조에 물리지 않았다 — **닫혔다 (고쳤다, 2026-08-23)**

> **갈래 (2026-08-23): 닫혔다.** 33번과 같은 계열 — 코드는 옳고 검사가 안 물던 자리다.
> 33번과 달리 이쪽은 격리 케이스가 존재해서 그 자리에서 닫았다.

**증상**: `db/schema.sql` 의 `inquiry_attempts_l2_reasons_match_verdict` 를 **통째로 지워도
스위트가 초록이었다.** `tests/test_db_schema.py` 의 모순 상태 파라미터 아홉 건 중 이 제약에
닿는 것은 `l2-null-with-l2-reasons` 하나인데, 그 행은 `inquiry_attempts_l2_null_means_no_artifacts`
도 함께 어기고 검사 본문이 `CheckViolation` 만 걸 뿐 **제약 이름을 단언하지 않았다.**
`grep -rn "l2_reasons_match_verdict" tests/` 는 0건이었다.

공백은 한 칸 더 넓었다. L1 쪽도 마찬가지로 **"pass ⟺ 사유 0건"의 cardinality 가지**가
격리돼 있지 않았다 — `l1-pass-with-nonzero-reasons` 는 `inquiry_attempts_reasons_compose_layers`
(`[] ≠ ['pii_detected']`)도 동시에 어기고, 단독으로 남는 `l1-verdict-without-reasons-array`
는 "verdict 는 있는데 배열이 NULL" 가지만 덮는다.

**유출·지표 오염으로는 이어지지 않았다.** 생산 경로(`records.py` 의 `_l2_columns`)가
verdict 와 사유 배열을 항상 짝지어 쓰므로 위반 행을 만들 수 없다 — 33번과 같은 심층 방어의
검사 공백이다.

**닫는 방식**: 두 가지를 **각각 하나씩만** 어기는 파라미터 2건을 더하고 `diag.constraint_name`
까지 단언했다(`tests/test_db_schema.py` 의 `test_layer_pass_with_reasons_is_rejected_by_its_own_constraint`).
스크래치 DB(`reply_gate_mut_check`, 검증 뒤 DROP — 본 볼륨 무변경)에서 뮤테이션 대조를 실제로
돌렸다: 제약이 있으면 두 INSERT 가 **각자의 제약 이름으로** 거부되고, 두 제약을 DROP 하면
두 모순 행이 그대로 적재된다.

**얻은 규율은 [engineering-notes](../engineering-notes.md) 로 옮겼다** — CHECK 제약의 음성
대조는 "거부되는가"가 아니라 "**어느 제약이** 거부하는가"를 물어야 한다.

**그 다음에** 그 목록을 읽어 재집계하는 검사를 붙인다. 순서를 뒤집으면 닫히지 않는다.

| 무엇 | 어떻게 뚫렸나 | 재현 |
|---|---|---|
| 건수 대조가 **수집**을 **통과**로 셌다 | `session.items` 는 skip 을 구분하지 못한다. 문서가 인용하는 것은 `N passed` 다 | `POSTGRES_PORT=1 uv run pytest` → **1,310 passed · 178 skipped** 인데 `1,488 passed` 인용이 초록으로 통과 |
| 부분 실행 판별이 **옵션 값을 경로로** 읽었다 | `-` 로 시작하지 않는 토큰을 전부 경로로 셌다 | `uv run pytest -p no:cacheprovider` → 전체 스위트인데 *"경로를 지정한 실행: no:cacheprovider"* 로 **조용히 skip** |
| 슬러그가 GitHub 과 갈렸다 | 강조 기호를 벗기며 `_` 를 함께 지웠다. GitHub 은 `_` 를 낱말 문자로 **보존**한다 | 저장소 헤딩 **10개**에서 판정이 반대로 난다 — 실제로 도는 `#…deferred_to_l2…` 를 "깨졌다"고 잡고 안 도는 쪽을 통과시킨다 |
| 검사 모집단이 **한 문서 좁았다** | 루트 문서를 `README`·`CLAUDE`·`AGENTS` 로 손수 열거했다 | 감사가 손으로 훑은 **46개** 대신 45개. 빠진 것은 루트 `기획-입력.md` 이고 그 안에도 상대 링크가 있다 |
| 종료 코드 검사가 **동어반복**이었다 | `main` 이 루트를 고정해 부를 수 없어, 테스트가 `1 if broken else 0` 을 다시 계산했다 | `main` 을 `return 0` 으로 바꿔도 초록 |

**그리고 같은 세션이 같은 함정을 한 번 더 밟았다.** `docs/operations.md` 의 링크 검사 출력
예시가 `링크 387개` 로 적혔는데 **그 커밋의 실측은 389** 였고 두 커밋 뒤에 391 이 됐다 —
검증 건수 인용이 실측과 갈린 **다섯 번째**이고, 하필 그 함정을 닫겠다고 만든 커밋 안에서 났다.
새 건수 대조의 패턴 목록에 링크 수가 없어서 스위트가 못 잡았다.

**닫는 방식**

- **건수 대조를 둘로 갈랐다.** 도구 쪽(`ruff format`·`mypy`·링크 검사)은 skip 과 무관하므로
  전체 스위트면 늘 대조하고, 테스트 쪽은 *"이 실행에서 수집 = 통과인가"* 를 먼저 세운 뒤
  서지 않으면 **사유를 담아 skip** 한다. 전제는 두 방향으로 본다 — 대조 시점 **앞에서 이미
  보고된** 비통과(conftest 가 결과를 센다)와, **앞으로 예정된** skip(`db` 마커 × 접속 사유).
- **부분 실행은 `config.args_source` 로 판별한다.** 명령줄 토큰을 손으로 가르지 않는다.
- **슬러그에서 `_` 를 지우지 않는다.** 밑줄 강조는 이 저장소가 쓰지 않으므로 갈릴 일이 없다.
- **루트 문서를 글롭으로 유도한다**(`*.md`). 손으로 적은 목록은 새 문서를 조용히 흘린다.
- **`main(argv, root=…)`** — 진입점을 임시 루트로 부를 수 있게 해 종료 코드를 실제로 문다.
- **링크 수·문서 수도 건수 대조의 패턴에 넣었다.**

**얻은 규율은 [engineering-notes](../engineering-notes.md) 로 옮겼다** — *게이트를 세운
세션은 그 게이트를 통과한 유일한 세션이므로, **세운 자리를 그 자리에서 한 번 뒤집어 봐야
한다.*** 넷 다 "검사를 지우면 빨개지는가"가 아니라 **"검사가 겨냥한 상태를 만들면 빨개지는가"**
를 물었어야 잡혔다.

**남는 한계**: DB 없는 실행에서는 테스트 건수 인용이 **여전히 검사되지 않는다.** 달라진 것은
그 사실이 **skip 사유로 드러난다**는 것뿐이다 — 미측정을 통과로 적지 않는 것이 여기서 살 수
있는 전부다.
