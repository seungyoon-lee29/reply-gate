# 0019. 판정 프롬프트 캐싱을 실측하고 채택하지 않는다 — 캐시 계열 토큰 배선은 남긴다

날짜 2026-08-19. 판정 호출의 **고정 프리픽스**(판정 지침)에 Anthropic 프롬프트 캐싱을 걸고
전후를 실측한 기록이다. 채택 규칙은 **실측 전에** 확정했고, 결과는 **조건 ① 미달**이라
처분은 **미채택**(스위치를 꺼진 채로 남긴다)이다. **캐시 계열 토큰 수집 배선은 남긴다** —
그건 채택 여부와 무관하게 리포트가 참말을 하기 위한 장치다.

## 왜 배선이 먼저였나 — 이것이 절감 주장의 전제다

캐싱을 켜면 Anthropic 의 `usage.input_tokens` 는 **캐시 적중분을 제외한** 값이 된다.
`src/reply_gate/llm.py` 는 그전까지 `input_tokens`/`output_tokens` 만 읽었으므로, 그대로
캐싱을 켰다면 리포트의 판정 입력 토큰이 30,042 → 6,832 로 **77% 줄어든 것처럼** 찍혔을
것이다. 실제로 줄어든 것은 **단가**이지 토큰이 아니다(총 프롬프트 토큰은 뒤 표대로 30,042 로
같다). 그건 절감이 아니라 **조용한 토큰 은폐**다.

그래서 `usage.cache_creation_input_tokens`(캐시 write)·`usage.cache_read_input_tokens`
(캐시 read)를 수집해 평가 리포트까지 잇는 것을 **먼저** 했다.

### 무엇을 수집하게 됐는가

| 자리 | 더한 것 |
|---|---|
| `llm.JsonCompletion` | `cache_creation_input_tokens` · `cache_read_input_tokens` (`int \| None`) |
| `llm.LLMCallError` · `llm.LLMFormatError` | 같은 두 값 — **실행됐으나 실패한 호출의 캐시 write 도 실비용**이다 |
| `judge.JudgeOutcome` | 형식 재시도까지 누적한 두 값 |
| `evaluation.L2Outcome` · `evaluation.JudgeAccuracy` | 픽스처별·세트별 두 값 |
| 리포트(마크다운·JSON) | 판정 토큰과 **별도 칸**. JSON 은 `tokens.cache_creation_total` · `tokens.cache_read_total` 과 픽스처별 두 키 |

**없는 값은 0 이 아니라 `None`(해당 없음/미측정)이다.** `llm.accumulate_optional_tokens` 가
그 규칙을 코드로 들고 있고(`None + 0 ≠ 0`), 리포트는 재지 않은 실행을 "미측정"으로 적는다.
0 으로 채우면 "캐시가 0 토큰 적중했다"(측정했고 0)와 "캐시를 잰 적이 없다"(미측정)가 같은
값이 되어, 재지도 않은 축을 잰 것처럼 신고하게 된다 — `scripts/AGENTS.md` 불변식 5 와 같은
자리다. 생성 계열(OpenAI 래퍼)은 이 축을 재지 않으므로 항상 `None` 이다.

**분리 표기의 자리는 평가 리포트뿐이다.** API 응답·처리 기록의 판정 토큰 키·스키마·정의는
무변경이다(이번 사이클 계약 확장 0).

## 결정 1 — 캐싱은 호출 구성이지 지침 변경이 아니다

`judge.JUDGE_SYSTEM_PROMPT` 는 **한 글자도 바뀌지 않았다**(`judge_prompt_version` 이
`judge-e26f6c8e0b84` 로 전후 동일한 것이 그 증거다). 바뀐 것은 `AnthropicGenerationClient`
가 `system` 을 보내는 **모양**뿐이다:

- 꺼짐: `system="<판정 지침>"` (문자열 그대로 — 기준선 실측과 요청 모양이 같다)
- 켜짐: `system=[{"type": "text", "text": "<판정 지침>", "cache_control": {"type": "ephemeral"}}]`

브레이크포인트를 질의(user) 쪽에 두지 않는다 — 질의는 픽스처마다 달라져 매 호출이 새
프리픽스가 되고 적중이 0 이 된다.

스위치는 `config.Settings.judge_prompt_caching_enabled` 이고 **기본값은 꺼짐**이다.
`pipeline._LazyJudgeClient` 가 그 값을 판정 클라이언트에 그대로 넘기고, 실행 조건 지문의
`judge_prompt_caching` 이 같은 값을 읽는다(전에는 `"off"` 하드코딩이라, 캐싱을 켜도 지문이
거짓말을 했다).

### 최소 캐시 가능 토큰 — 걸렸다

`claude-sonnet-5` 의 최소 캐시 가능 프리픽스는 **1,024 토큰**이다. 판정 고정 프리픽스는
**2,110 토큰**으로 측정됐다(판정 지침 + 구조화 출력 스키마). 하한을 넘으므로 캐싱이 실제로
걸렸고, 아래 실측이 그것을 보여 준다 — "최소 길이 미달로 걸리지 않았다"는 경우가 아니다.

## 결정 2 — 라이브 3회를 사서 사전 판정선에 대고 잰다

  에서 원복됨)으로 돈 세트라 조건이 다르다.
- **"후" = `evaluation-live-l2-25`·`-26`·`-27`.** 지문에서 `judge_prompt_caching=on` 을
  확인했고, 나머지 지문 항목은 전 세트와 같다. 측정 2 는 세 세트 모두 `executed=false` +
  사유 문자열이고 0 채움이 아니다.

## 채택 판정 — 사전 확정한 두 조건 (회차끼리 짝짓지 않았다)

| 조건 | 기준 | 실측 | 판정 |

### ①이 갈린 지점은 J04 한 건, 그것도 한 회차다

전후 33칸(11 픽스처 × 3회) 중 달라진 것은 **`-25` 의 J04 하나**다(기대 `pass` → 실제

**J04 는 원래 흔들리던 픽스처다** — [결정 0016](0016-J11-판정-픽스처를-제품-실행-경로의-근거-집합에-맞춘다.md)
이 12세트에서 산발적으로 흔들린다고 적었다. 그러니 이 차이가 **캐싱 때문이라고 말할 수
없다.** 하지만 **캐싱 때문이 아니라고도 말할 수 없다** — 3회로는 확률 층의 잡음과 구분되지

선을 옮기면 사전 확정의 의미가 사라진다. 그래서 **미채택**이다.

②는 충족이다 — 다수결 층에서는 J04 도 `pass` 2/3 으로 전과 같은 판정을 유지했다.

### 토큰 4종 분리 — 뭉뚱그리지 않는다

캐시 write 는 일반 입력보다 비싸고(약 1.25배) read 는 싸다(약 0.1배). 단가가 다른 값을 한
칸에 넣으면 그 자체로 규칙 위반이므로 네 칸으로 갈라 적는다.

| 토큰 계열 | 전 (회당) | 후 (회당) | 전 (3회 합) | 후 (3회 합) |
|---|---:|---:|---:|---:|
| 일반 입력 (비캐시) | 30,042 | **6,832** | 90,126 | **20,496** |
| 캐시 write | **미측정** (배선 전) | **0** | 미측정 | **0** |
| 캐시 read | **미측정** (배선 전) | **23,210** | 미측정 | **69,630** |
| 출력 | 5,813 (5,463–6,122) | 5,932 (5,488–6,509) | 17,439 | 17,796 |
| **총 프롬프트 토큰** (일반+write+read) | **30,042** | **30,042** | 90,126 | 90,126 |

**총 프롬프트 토큰이 전후 정확히 같다** — 30,042 로 한 토큰도 다르지 않다. 캐싱이 한 일은
그중 **23,210 토큰(77.3%)을 정가 입력에서 캐시 read 단가로 옮긴 것**이지 토큰을 줄인 것이
아니다. 배선 없이 켰다면 리포트에 "판정 입력 토큰 30,042 → 6,832" 만 남았을 것이고, 그 한
줄이 이 사이클에서 가장 위험한 거짓말이었다.

#### 달러 환산 — 캐시 write/read 단가를 분리한 채로

단가와 기준일은 [단가 표와 비용 분해](../pricing.md) 1절 — **기준일 2026-08-19**, 출처
<https://platform.claude.com/docs/en/about-claude/pricing>. `claude-sonnet-5` 100만 토큰당
입력 $2.00 · 출력 $10.00 · **5분 캐시 write $2.50** · **캐시 read $0.20** 다(같은 페이지가
정의하는 배수 1.25× / 0.1× 와 일치한다). **네 단가를 한 칸으로 합치지 않는다** — 그러면 이
표가 존재하는 이유가 사라진다.

| 토큰 계열 | 단가 | 전 (3회 합) | 전 달러 | 후 (3회 합) | 후 달러 |
|---|---:|---:|---:|---:|---:|
| 일반 입력 | $2.00 | 90,126 | $0.180252 | 20,496 | $0.040992 |
| 캐시 write (5분) | $2.50 | 미측정 | — | 0 | $0.000000 |
| 캐시 read | $0.20 | 미측정 | — | 69,630 | $0.013926 |
| **프롬프트 소계** | | **90,126** | **$0.180252** | **90,126** | **$0.054918** |
| 출력 | $10.00 | 17,439 | $0.174390 | 17,796 | $0.177960 |
| **총계** | | | **$0.354642** | | **$0.232878** |

**프롬프트 비용 −69.5%, 총 판정 비용 −34.3%** (회당 프롬프트 $0.060084 → $0.018306).
총계가 덜 줄어드는 것은 출력이 캐싱과 무관하기 때문이다 — 오히려 확률 층의 흔들림으로 조금
늘었다(17,439 → 17,796).

**총 프롬프트 토큰은 전후 같은데 프롬프트 달러는 69.5% 줄었다.** 이 한 줄이 이 절의 전부다 —
캐싱이 옮긴 것은 **단가**이지 토큰이 아니다.

**이 −69.5% 는 캐시 write 0 조건의 수치다.** 아래 절이 그 조건을 적고, 콜드 write 를 포함한
환산은 그 뒤에 있다.

#### 캐시 write 가 0 인 이유 — 이 세 세트는 write 비용을 치르지 않았다

세 세트 전부 `cache_creation_total = 0` 이고 11건 모두 read 2,110 이다. 캐시 엔트리를 쓴
것은 이 세 세트가 **아니라**, 요청 형태를 확인하려고 세트 실행 **전에** 보낸 프로브 호출
2회다. 그 프로브에서 실측한 값은 다음과 같다(같은 프리픽스, 연속 2회):

| 프로브 | 일반 입력 | 캐시 write | 캐시 read | 출력 |
|---|---:|---:|---:|---:|
| 1회차 (콜드) | 175 | **2,110** | 0 | 204 |
| 2회차 (웜) | 175 | 0 | **2,110** | 270 |

즉 **콜드 write 비용은 프리픽스당 2,110 토큰 × 1회**이고, 이후 호출은 전부 read 다. 세 세트가
연속으로 돌아 5분 TTL 안에서 엔트리가 계속 살아 있었기 때문에 세트 경계에서도 write 가 다시
일어나지 않았다. **간격이 5분을 넘는 산발 실행에서는 write 가 세트마다 한 번씩 붙는다** —
위 표의 "후" 열은 그 조건을 재지 않았다. 이 한계를 지우고 "write 0" 을 일반화하면 안 된다.

**콜드 write 를 포함한 환산.** 산발 실행이면 세트마다 첫 호출이 write 가 되므로 3회 합으로
write 2,110×3 = 6,330 토큰, read 는 그만큼 줄어 63,300 토큰이다(총 프롬프트 토큰 90,126 은
그대로다). 두 조건을 나란히:

| 조건 | 일반 입력 | 캐시 write | 캐시 read | 프롬프트 달러 | 전 대비 |
|---|---:|---:|---:|---:|---:|
| **후 (관측 — 연속 실행, 5분 TTL 안)** | $0.040992 (20,496) | $0.000000 (0) | $0.013926 (69,630) | **$0.054918** | **−69.5%** |
| **후 (산발 실행 — 콜드 write 3회 포함)** | $0.040992 (20,496) | $0.015825 (6,330) | $0.012660 (63,300) | **$0.069477** | **−61.5%** |
| 전 (캐싱 꺼짐) | $0.180252 (90,126) | — | — | $0.180252 | — |

회당 프롬프트 비용으로는 $0.060084 → $0.018306(연속) / $0.023159(산발)이다.
**"−69.5%" 를 조건 없이 인용하면 거짓이 된다.**

### 지연 — 부차 관측 (주장하지 않는다)

**측정 3 은 호출 지연을 기록하지 않는다**(리포트의 지연 필드는 측정 2 전용이다). 그래서
전후를 같은 자로 잴 수 없었고, 아래는 성격이 다른 두 관측이다.

| 세트 | 관측 | 값 |
|---|---|---|
| 후 (`-25`·`-26`·`-27`) | 실행 시작 → 리포트 파일 기록 (프로세스 기동 포함) | 67.6s · 80.9s · 70.1s (평균 72.9s) |
| 전 (`-13`·`-14`·`-15`) | 연속 실행의 **시작 시각 간격** (직전 실행 시간 + 다음 프로세스 기동의 상한) | 94s · 84s |

방향은 짧아지는 쪽이지만 **두 값은 같은 양이 아니다** — 전 세트의 리포트 파일 mtime 은
워크트리 체크아웃 시각이라 같은 방식으로 잴 수 없었다. 지연 개선을 주장하지 않는다.

## 처분 — 미채택, 스위치는 꺼진 채로

- `Settings.judge_prompt_caching_enabled` 의 기본값은 **`False`** 그대로다.
- 캐시 계열 토큰 수집 배선(`llm.py` → `judge.py` → `evaluation.py` → 리포트)은 **남긴다.**
  채택 여부와 무관하게, 이 배선이 없으면 다음에 누가 캐싱을 켤 때 같은 은폐가 재발한다.
- 프롬프트 문면·API 응답 스키마·판정 토큰 키 정의는 무변경이다(계약 확장 0).
- 실측 리포트 3건은 커밋해 남긴다 — 과금 산출물이고 이 결정의 근거가 그 안에 있다.
  미채택은 코드에 대한 처분이지 관측에 대한 처분이 아니다.

캐싱 켜짐/꺼짐 **양쪽에서** 판정 산출 검증(fail-closed)과 사유 2종 판정이 그대로인 것은
`tests/test_judge_prompt_caching.py` 가 매개변수화 테스트로 고정한다. 캐시 계열 토큰이 실제로
수집돼 리포트까지 가는 것, 그리고 필드 없는 응답이 0 이 아니라 미측정으로 남는 것도 같은
파일이 지킨다 — 그 테스트가 없으면 절감 주장이 근거를 잃는다.

## 판정 층이 또 바뀐다 — 그 파급

`judge_prompt_caching` 이 실행 조건 지문 항목이므로, 켜고 돈 세 실행은 승격 기준선
(`data/promoted_baseline.json`)과 어긋나는 항목이 하나 늘어난 상태다. 미채택으로 스위치가
꺼졌으므로 **앞으로의 실행은 다시 `-13`…`-15` 와 같은 판**이고, 어긋남은 `-25`…`-27` 세
리포트에만 남는다.

**재등재는 이번 사이클에 하지 않기로 사용자가 정했다.** 재등재할 때 함께 정리해야 할 항목은
[결정 0017](0017-사유-독립-명시를-실측으로-반증하고-판정-프롬프트를-원복한다.md) 이 적은 것과
같고, **기권 게이트 축은 승격 뒤에 채택돼(결정 0014) 이미 어긋나 있다**:

- `judge_fixture_version`: 기준선 `fixture-836322e97320` → 실측 `fixture-2b8f33392b36`
  (결정 0016 의 대가, `--declare-experiment` 로 선언해 진행)
- `abstention_gate_statistic`: 기준선 `미배선` → 실측 `rank1_minus_rank_k_spread`
- `abstention_tau`: 기준선 `미배선` → 실측 `0.06`
- `measurement_scope`: 기준선 `full` → 실측 `measurement_1_3_only`

이번 세 실행의 회귀 가드도 위 셋(`abstention_*` · `measurement_scope`)을 "선언되지 않은 조건
불일치"로 그대로 적었다. 재등재는 풀셋 라이브 3회를 새로 사서 사람이 하는 일이다
(`scripts/AGENTS.md` 불변식 17 — 하네스에 자동 경로는 없다).

## 문서 부채 인계 — 이 작업의 범위 밖

`docs/contracts.md` 의 "토큰 집계 경계" 절에 **서술**이 필요하다(키 추가가 아니다):

> 캐싱 켜짐 조건에서 `metrics.tokens.judge_input` 이 담는 값은 **비캐시 입력**이고,
> 캐시 계열(write/read)은 응답이 아니라 **평가 리포트에서 본다**.

지금 그 절은 "L2 판정 모델 토큰"이라고만 적고 있어, 캐싱이 켜진 조건에서 그 키를 총 입력으로
읽게 된다. **키·스키마·정의는 바뀌지 않는다** — 서술만 더한다.

## 고려했지만 택하지 않은 것

- **판정선을 "다수결만 본다"로 낮춘다** — ②만 보면 채택이다. 실측 뒤에 선을 옮기는 것이고,
  사전 확정의 의미가 사라진다(결정 0017 이 같은 유혹을 같은 이유로 거절했다).
- **J04 를 예외로 두고 나머지 10건으로 집계한다** — 흔들리는 픽스처를 실측 뒤에 분모에서
  빼는 것이다. 그렇게 하면 어떤 축이든 원하는 결과를 만들 수 있다.
- **3회를 더 사서 6회로 본다** — 미달을 확인한 뒤 표본을 늘리는 것은 표본 확대가 아니라
  원하는 답이 나올 때까지 반복하는 것이다. 늘리려면 **먼저** 정한다.
- **캐시 적중을 "판정 입력 토큰 감소"로 적는다** — 이 문서가 존재하는 이유의 반대편이다.
- **`ttl: "1h"` 로 write 비용을 아낀다** — write 단가가 2배가 되고, 지금 조건(연속 3세트,
  간격 1분 미만)에서는 5분 TTL 로 이미 전부 적중한다. 재지 않은 조건의 기본값을 만들지 않는다.
- **달러 절감액을 미채택의 반증으로 쓴다** — 절감은 성립했다(프롬프트 −69.5%, 위 표). 미달인
  것은 집계 지표 조건 ①이고, 비용이 좋다고 사전 확정한 판정선을 옮기면 사전 확정의 의미가
  사라진다. **달러는 관측이지 처분의 근거가 아니다.**

## 결과

- **얻은 것**: ① 캐시 계열 토큰이 리포트까지 가는 배선 — 이제 캐싱을 켠 실행이 판정 입력
  토큰을 조용히 줄여 보고할 수 없다. ② **총 프롬프트 토큰이 전후 정확히 같다**(30,042)는
  실측 — 캐싱이 옮기는 것은 단가이지 토큰이 아니라는 사실이 숫자로 남았다. ③ 고정 프리픽스가
  2,110 토큰으로 `claude-sonnet-5` 의 최소 캐시 길이(1,024)를 넘는다는 확인.
- **잃은 것**: 라이브 3회분의 과금과, 측정 3 계열에 `judge_prompt_caching=on` 판이 하나 더
  생긴 것. 스위치는 원복(꺼짐)했지만 리포트에 남은 판 표기는 회수되지 않는다.
- **위험 — 절감 경로가 닫힌 것은 아니다**: 조건 ①의 차이는 J04 한 칸이고, 그것이 캐싱 때문
  인지 확률 층의 잡음인지 **이 실측으로는 가를 수 없다**. 다시 시도한다면 판정선을 **먼저**
  정하고(예: 회차 수를 늘린 사전 설계), J04 의 흔들림을 먼저 닫는 편이 순서다.
