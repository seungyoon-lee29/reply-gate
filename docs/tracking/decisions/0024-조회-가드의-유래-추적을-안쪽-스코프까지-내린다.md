## 문제

조회 가드에 방향이 반대인 구멍이 둘 있었다. 하나는 **과차단**, 하나는 **과통과**다.

### ① 승인한 정상 조회가 정상 답변을 기각했다

PII 허용 출처(`ValidatedQuery.pii_safe_output_columns`)의 승인 조건이 "최상위 projection 이
**기저 테이블의 직접 컬럼**인가" 하나였다. 그래서 의미가 같고 가드의 다른 검사를 전부
통과하는 조회인데도 아래 셋을 거치면 허용 출처가 **하나도** 나오지 않았다.

```sql
WITH t AS (SELECT customer_phone, order_no FROM orders WHERE order_no = '…') SELECT customer_phone FROM t
SELECT d.customer_phone FROM (SELECT customer_phone, order_no FROM orders WHERE order_no = '…') d
SELECT coalesce(customer_phone, '미정') AS customer_phone FROM orders WHERE order_no = '…'
```

허용 출처가 아니면 근거 렌더가 그 값을 패턴형 PII 로 보고 `evidence_text` 에서 버린다. 그러면
**진짜 고객 연락처를 그대로 옮겨 적은 정상 답변이 `pii_detected` 로 기각**되고, 재생성은 같은
근거를 쓰므로 반드시 다시 실패해 `rejected_twice` 인계가 된다. 이 프로젝트의 헤드라인 지표가
"정상 초안 오탐률"이라 오탐 경로는 곧 지표 오염이다.

세 번째 형태가 특히 나쁘다. 빈칸 채우기(`coalesce`)는 **SQL 생성 안내가 허용 함수로 직접
광고**하는 것이고, 허용한 이유가 주석에 그대로 적혀 있다 — *"미배송 주문의 빈 컬럼을 근거
문장에 그대로 싣지 않기 위해"*. 안내가 권한 관용구가 정상 답변을 죽이는 상태였다.

### ② 형변환 대상 타입을 한 번도 읽지 않았다

캐스트가 허용 함수인데 **무엇으로 변환하는지**는 검사하지 않았다. 그래서 이 한 줄이 통과했다.

```sql
SELECT cast('inquiries' AS regclass) AS x, order_no FROM orders WHERE order_no = '…'
```

시스템 카탈로그 참조 타입은 화이트리스트 밖 테이블의 **이름과 존재 여부**를 결과 컬럼으로
돌려준다 — 존재하면 이름이 나오고 없으면 오류가 그 사실을 알려주므로 양방향으로 훑을 수 있다.
`oid`·`regtype`·`regproc`·`regnamespace` 도 같은 계열이다.

**1층(read-only 계정)이 이 경로를 막지 못한다.** `pg_catalog` 은 PostgreSQL 이 PUBLIC 에
SELECT 를 주므로 `reply_gate_ro` 로도 읽힌다 — 실측으로 확인했다(`SELECT count(*) FROM
pg_class` → 455, `cast('inquiries' AS regclass)` → `inquiries`). 보안 문서 1층 서술의
*"그 외 어떤 테이블에도 권한이 없다"* 는 시스템 카탈로그에 대해 참이 아니었고, 이 결정과 함께
고쳤다. **막는 층이 가드 하나뿐**이라는 것이 이 항목의 요점이다.

## 고른 것

### ① 유래를 스코프를 타고 증명한다 — 표현식 거부 목록이 아니라

승인 판정을 "직접 컬럼인가"에서 **"값이 `orders` 직접 컬럼에서 왔음을 증명할 수 있는가"** 로
바꾼다. 증명되는 것은 셋뿐이고 나머지는 전부 불승인이다.

1. **직접 컬럼** — 유래 추적의 바닥.
2. **임시 테이블(CTE)·파생 테이블을 거친 직접 컬럼** — 안쪽 스코프가 같은 방식으로 증명했으면
   유래가 이어진다. 스코프마다 "내놓는 이름"과 "그중 증명된 이름"을 함께 들고 나온다.
3. **빈칸 채우기 관용구** — `coalesce(직접컬럼, '미정')` · `nullif(직접컬럼, '')`. 고정값이
   **패턴형 개인정보 모양이면 불승인**이다.

**허용을 늘리는 방식이지 거부 목록을 두는 방식이 아니다.** 검증기가 해석하지 못한 표현식은
자동으로 불승인이라, 새 SQL 문법이 생겨도 조용히 승인되지 않는다(fail-closed 유지).

### 이어 붙이기 계열에는 고정값이 들어갈 자리를 두지 않는다

`concat`·`||` 는 승인 대상에 넣지 않는다. **조각 하나하나는 개인정보 모양이 아닌데 합치면
번호가 되기 때문이다** — `'01' || '0-9999-9999'` 은 두 조각 모두 어떤 패턴에도 걸리지 않는다.
빈칸 채우기가 안전한 것은 출력이 인자 중 **하나 그대로**여서 가능한 값이 전부
(진짜 컬럼 값 | 개인정보가 아닌 고정값) 이기 때문이고, 이어 붙이기는 그 성질이 없다.

같은 이유로 `nullif(a, b)` 는 `a` 만 유래로 센다 — 출력은 `a` 아니면 NULL 이고 `b` 는 비교
상대일 뿐이라, `b` 자리의 직접 컬럼을 유래로 세면 **값이 흐르지 않는 자리로 승인이 난다.**
조건 분기(`CASE`)도 넣지 않았다: 넓히는 근거가 "생성 안내가 빈칸 채우기를 광고한다"는 것이고
조건 분기는 그 근거에 해당하지 않는다.

### "개인정보 모양"을 조회 가드가 정의하지 않는다

이 판정에는 "고정값이 개인정보 모양인가"가 필요한데, 조회 가드에는 개인정보 정규식이 한 줄도
없었고 앞으로도 없다. [결정 0021](0021-접기를-번호-계열-안에서만-넓힌다.md) 이 L1 게이트를
패턴 집합의 **단독 소유자**로 못박았고, 조회 가드는 그것을 **가져다 쓴다**(`gate.pii_shaped`).
그래서 두 층의 판정이 같은 집합 위에 선다 — 층마다 자기 정의를 두면 한쪽만 넓혀져 기준이
갈리고, 접기가 층마다 달라 실제로 그렇게 뚫린 적이 있다.

이 결정으로 그 소비자가 셋이 됐다: 게이트(소유자) · 근거 렌더의 개인정보 필터 · 조회 가드.
`tests/test_pii_pattern_ownership.py` 가 세 형태(자기 패턴 생성 · 정본 이름 재정의 ·
`unicodedata` import)를 AST 로 막는다.

부수 효과가 하나 있다: 이스케이프 문자열(`E'…'`·`U&'…'`·`$$…$$`·`N'…'`)은 sqlglot 이
`Literal` 이 아닌 별도 노드로 만들어 **고정값으로 인정되지 않는다.** 이 모듈이 이스케이프를
풀어 값을 계산하지 않으므로 그 편이 옳다 — 풀지 않은 문면으로 개인정보 판정을 하면
`E'010\0559999\0559999'` 가 "개인정보 모양이 아님"으로 통과한다.

### ② 형변환 대상 타입을 허용 목록으로 판정한다

목록은 SQL 생성 안내가 광고하는 용도에 맞춘다 — **숫자 · 일자 · 문자열**:

```
text, varchar, char, int, bigint, smallint, numeric, real, double precision,
date, timestamp, timestamptz, time
```

목록 밖은 거부(`unsupported_cast_type`)이고, 거부 사유가 그 목록 문면을 들고 나가 SQL 생성
1회 재시도의 피드백이 된다. 카탈로그 참조 타입(`oid`·`reg*`)은 sqlglot 이 `ObjectIdentifier`
로, 확장 타입은 `USERDEFINED` 로 만들어 **허용 집합에 들 수 없으므로 자동으로 거부**된다 —
새 타입 표기가 생겨도 목록을 따라잡을 필요가 없다.

### 목록의 소유자는 가드이고 안내는 그 문면을 그대로 싣는다

**가드와 안내가 갈리면 그 차이가 그대로 평가 수치가 된다** — 생성기가 목록 밖 타입을 쓸
때마다 거부 → 재시도 1회 → `sql_failed` 인계이고, 그 인계는 이번 사이클이 사는 기준선의
수치에 남는다. 그래서 목록을 두 곳에 적지 않는다: SQL 생성 프롬프트의 `[허용 함수]` 절이
이미 가드 소유의 문자열(`describe_allowed_functions()`)을 그대로 싣고 있었으므로, 캐스트
목록을 그 문면에 실어 **근거 수집 모듈을 한 줄도 건드리지 않았다.**

구조 검사(`tests/test_sql_cast_allowlist.py`)가 두 방향을 지킨다: ① 생성 안내에 실린 타입
집합이 가드의 목록과 같다(목록에서 **유도**하고, 낱말 경계로 본다 — 맨 부분 문자열로 찾으면
`bigint` 가 `int` 를 대신 켜 준다), ② 가드 밖 어떤 모듈도 같은 이름의 목록을 다시 정의하지
않는다(AST, 앞의 밑줄을 벗겨서 본다). 음성 대조를 같은 파일에 뒀다.

## 버린 것

- **이어 붙이기 계열도 "컬럼만 있으면" 승인한다.** `concat(quantity, unit_price_krw)` 처럼
  개인정보가 아닌 컬럼들만으로도 새 숫자열을 만들 수 있어, 승인 근거가 "값의 유래"에서
  "재료의 유래"로 미끄러진다. 정상 조회를 깨지 않는 쪽(계산 결과는 실행되고 `evidence_text`
  에도 남되 allowlist 출처가 아닐 뿐)이라 과차단 비용이 작다.
- **조건 분기(`CASE`)까지 넓힌다.** 넓히는 근거가 없고, 분기마다 유래가 달라 증명 규칙이
  빈칸 채우기보다 복잡해진다. 필요해지면 그때 근거와 함께 넓힌다.
- **카탈로그 참조 타입만 거부 목록으로 막는다.** PostgreSQL 의 타입을 우리가 따라잡아야 하고,
  이 저장소가 화이트리스트를 택한 이유와 정면으로 어긋난다.
- **`REVOKE ... FROM PUBLIC` 으로 카탈로그 접근을 권한에서 닫는다.** psql 메타명령과 드라이버
  내부 조회가 함께 깨지고, 앱 계정까지 영향을 받는다. 이 경로는 가드가 막는 것이 맞다.
- **컬럼 별칭 목록(`t(a, b)`)의 유래를 자리로 대응시킨다.** 어느 안쪽 projection 이 어느
  이름이 되는지 증명하려면 자리 계산이 필요한데, 별표 확장과 섞이면 조용히 어긋난다.
  **유래를 하나도 넘기지 않는다**(fail-closed).

## 대가

- **실제 모델의 조회문에서 무엇이 바뀔지는 프로브가 답하지 못한다.** ①은 지금까지 오기각이
  났을 조회를 살리는 방향이고 ②는 거부를 늘리는 방향이라, 라이브에서 `sql_failed` 가 늘면
  ②를, `pii_detected` 오탐이 줄면 ①을 먼저 본다.
- **캐스트 허용 목록이 과차단을 만들 수 있다.** `boolean`·`interval`·`jsonb` 로 캐스트하는
  정상 조회는 이제 거부된다(재시도 1회로 흡수되지만 그 1회를 태운다). 광고하는 용도 밖이라
  의도한 과차단이고, 실제로 생성기가 그 타입을 쓰면 목록을 넓히는 것이 답이다.
- **유래 규칙이 표현식마다 다르다는 사실 자체가 비용이다.** 함수를 허용 목록에 새로 넣는
  사람이 "그 함수가 유래를 잇는가"를 따로 판단해야 한다 — 기본값은 **잇지 않는다**이다.

## 무엇이 이 결정을 뒤집나

- 이어 붙이기·조건 분기를 거친 정상 조회가 실제 생성물에서 반복해 나타나고, 조각 합성을 열지
  않는 증명 규칙을 만들 수 있을 때.
- 캐스트 허용 목록 밖 타입이 라이브에서 `sql_failed` 를 실제로 만들 때 — 그때는 목록을 넓히고
  안내를 함께 갱신한다(정의는 계속 한 곳이다).
- 카탈로그 접근을 권한 층에서 닫는 방법이 앱 계정·드라이버를 깨지 않고 성립할 때. 그때도
