# 0005. 생성된 SQL 의 조회 범위를 프롬프트가 아니라 코드가 강제한다

## 맥락

text-to-SQL 안전장치는 처음에 세 층으로 설계됐다: read-only 계정, 스키마 화이트리스트,
쿼리 검증(단일 SELECT·다중문·주석·행 수 상한). "주어진 주문 1건만 조회한다"는 규칙은
SQL 생성 프롬프트에 문구로 들어갔다.

검증 과정에서 이 문구만으로는 아무것도 막지 못한다는 것이 드러났다. 조건 없는
`SELECT ... FROM orders LIMIT 3` 이 세 층을 전부 통과해 실행됐고, 그 결과 행이 근거가 되어
무관한 고객 50명(= 행 수 상한)의 연락처가 PII allowlist 에 올랐다. 문의 본문이 SQL 생성
프롬프트에 그대로 들어가므로 프롬프트 인젝션으로도 도달 가능했다.

## 결정

**조회 범위를 코드가 AST 로 강제한다.** 검증 단계에서 다음을 확인하고, 어기면 기존
`거부 → 1회 재시도 → sql_failed` 경로를 탄다.

- `orders.order_no` 에 대한 동등 비교가 있고 리터럴이 **선검사를 통과한 값과 일치**할 것
- `OR`·`IN` 다중값·부질의로 우회하지 않을 것
- 바인딩으로 인정하는 자리는 **WHERE 절과 INNER/CROSS 조인의 ON 절**뿐일 것
- **외부 조인(LEFT/RIGHT/FULL)은 거부**할 것 — 외부 조인의 ON 절은 보존측을 필터하지 않아
  조인 한 줄로 범위 제한이 무력화된다
- 기저 테이블을 하나도 해석하지 못했으면 **통과가 아니라 거부**할 것(fail-closed)

함수 허용 목록과 read-only 커넥션의 `statement_timeout` 도 같은 이유로 함께 넣었다 —
검증되지 않은 함수 호출이 워커를 몇 분씩 묶을 수 있었다.

## 고려했지만 택하지 않은 것

- **프롬프트 강화** — "반드시 WHERE 에 주문번호를 넣어라"를 더 강하게 쓴다. 기각했다:
  프롬프트는 확률적이고, 인젝션으로 덮어쓸 수 있다. 데이터 접근을 코드가 통제한다는 원칙과
  정면으로 어긋난다.
- **SQL 생성을 없애고 고정 쿼리만 사용** — 안전하지만 text-to-SQL 자체가 이 포트폴리오의
  전시 항목이라 제거할 수 없다.
- **read-only 계정의 행 수준 보안(RLS)** — 문의자 개념이 없어(인증 없음) 정책을 쓸 기준이 없다.

## 결과

- **얻은 것**: 실행되는 쿼리가 선검사를 통과한 그 주문 1건으로 묶인다는 것을 코드가 보장한다.
  실제 공격으로 확인했다 — 우회 8종이 전부 거부되고, INNER JOIN 대조군은 계속 통과한다.
- **대가(의도적 과차단)**: 외부 조인을 쓰는 정상 쿼리, 바깥 스코프가 부질의로만 좁혀지는 형태,
  `lower(order_no) = ...` 처럼 컬럼이 함수로 감싸인 형태, 허용 목록 밖 함수(`age`·`round`·
  `left`·윈도 함수)가 전부 거부된다. 재작성 비용은 재시도 1회로 흡수되지만, 단 1회뿐인
  재시도를 태울 수 있다. 현실 CS 조회 30건 검증에서는 과차단 0건이었다.
- **불가능해진 것**: 여러 주문을 한 번에 조회하는 기능. 필요해지면 범위 강제 규칙 자체를
  다시 설계해야 한다 — 조건을 느슨하게 푸는 것으로는 안 된다.
- **프롬프트는 남긴다**: 규칙을 프롬프트에도 적는다. 안전장치로서가 아니라 **재시도 예산을
  아끼는 장치**로서다.
