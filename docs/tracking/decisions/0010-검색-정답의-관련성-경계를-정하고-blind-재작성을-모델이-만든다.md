# 0010. 검색 정답의 관련성 경계를 정하고, blind 재작성을 모델이 만든다

- 날짜: 2026-08-13
- 상태: 확정 (사용자 결정)
- 관련: [0008](0008-미끼-라벨을-판정-규칙에-정렬한다.md) · [0009](0009-채택-판정을-절대-축으로-통일한다.md) ·
  [findings 12·13](../findings.md)

## 문제

유료 검색 비교(T6) 앞에서 입력 3종을 점검하다 두 가지가 걸렸다.

**(1) 라벨의 "직접 관련" 기준이 케이스마다 다른 수준으로 적용돼 있었다.** 30건이 세 수준에
흩어져 있었다 — G01·G02 는 정면 조항 + 상충 조항, G03·G11·G18·G26 은 정면 조항만,
G16·G17 은 정면 조항 + 채널 안내 조항. 라벨은 검색 recall·precision 의 유일한 정답 입력이라
기준이 흔들리면 케이스마다 다른 분모를 macro 평균하게 된다.

**(2) blind 재작성 픽스처가 사람이 손으로 쓴 문장이었다.** 블라인드 적대 리뷰 4회 중 3명이
"정답 조항의 표제어가 일부 들어와 있다"고 지적했고 1명은 아니라고 판단했다. 정답 자체의
누출(근거 ID·조항 번호·정책 고유 수치)은 4명 모두 0건으로 일치했으므로, 갈린 것은
"구어체 → 조항 표제어 정규화를 누출로 볼 것인가"였다. 사람이 쓰는 한 그 경계도 사람이
판정해야 하고, 그 판정이 blind 조건의 이득에 그대로 실린다.

## 결정

### 관련성 경계는 두 겹이다

**정답 = ① 문의에 정면으로 답하는 조항 + ② 그 조항과 같은 사안을 다르게 정한 상충 조항.**
조건·제한 조항(3-4 재고 소진, 1-2 대형 상품 지연)과 채널·전제 조항(4-2 접수 채널,
4-4 주문번호 안내)은 정답에 넣지 않는다.

바뀐 것은 3건이다.

| 케이스 | 전 | 후 | 이유 |
|---|---|---|---|
| G16 고객센터 전화번호 | 4-1, 4-2 | **4-1** | 4-2 는 이메일을 포함한 접수 채널 안내다. 전화만 묻는 문의의 정면 근거가 아니다 |
| G17 상담원 몇 번으로 | 4-1, 4-2 | **4-1** | 표현만 다른 같은 질문이므로 G16 과 같은 정답이어야 한다 |
| G18 하자 환불 서류 이메일 | 2-6 | **2-6, 2-4** | 2-6 "검수 절차 없이 즉시 환불" 과 2-4 "검수 완료 후 3영업일" 이 같은 상황을 다르게 정한다 |

G20(전화·이메일을 **둘 다** 묻는다)이 두 조항인 것은 규칙에 맞으므로 그대로 둔다.

### 실행 요청의 정답 유무는 "실행 요청인가"로 가르지 않는다

**정책 조항이 그 요청에 직접 답하거나 고객이 스스로 할 방법을 주는가**로 가른다.
G25("배송 상태 좀 확인해 주세요")는 1-5 가 주문 상세 화면에서 확인하는 방법을 정면으로
주므로 정답이 있다. G28("환불 처리해 주세요")은 2-4 가 반품 상품 입고·검수 **뒤**의 처리
기간이라 "환불해 달라"에 답하지 않으므로 빈 정답이다. 둘 다 현행을 유지하고 규칙만 라벨
note 에 적었다.

### oracle 픽스처는 라벨을 따른다

oracle 의 정의가 "정답을 본 상한"이므로 라벨이 기준이다. 2건을 라벨 쪽으로 되돌렸다.

- **G28**: `"이 주문의 환불 처리 절차와 환불 진행 기간"` → 원문 유지. 정답이 빈 케이스의
  상한은 아무것도 채택하지 않는 것이다.
- **G25**: `"주문번호가 필요한 …"` → `"주문 상세 화면에서 확인하는 배송 상태와 배송 진행 단계"`.
  4-4(주문번호 안내)를 끌어올리던 어휘를 뺐다 — 라벨 note 가 단순 처리 전제를 제외한다고
  명시하는데 oracle 이 그것을 상위로 올리고 있었다.

### blind 재작성은 생성 모델이 만든다

런타임 의도 해석과 같은 모델(`generation_model`)에 **문의 원문만** 주고 30건을 생성해
픽스처를 교체했다. 생성기는 `scripts/generate_blind_rewrites.py` 이고, blind 조건은
그 스크립트의 입력 목록이 지킨다 — 구조 테스트가 생성기가 정답 라벨·정책 문서·oracle
픽스처를 import 하거나 경로로 참조하지 못하게 막는다(미사용 import 도 잡는다).

## 왜 이렇게 골랐나

**라벨을 좁히는 쪽과 넓히는 쪽이 한 케이스씩이다.** G16·G17 은 좁아지고 G18 은 넓어진다.
한 방향으로만 움직였다면 지표를 좋아 보이게 하는 변경과 구분되지 않는다.

**G18 을 넓힌 것은 채점표가 제품이 원하는 동작을 벌하고 있었기 때문이다.** L2 가 모순을
잡으려면 검색이 2-6 과 2-4 를 함께 올려야 하는데, 라벨이 2-6 만이면 2-4 를 함께 가져온
검색기가 precision 에서 깎인다. G18 의 `contradictory_evidence` 기각은 사이클 2 라이브
3회 모두 재현된 장면이다(`reports/evaluation-live-l2-{1,2,3}.json`).

**G16·G17 을 좁힌 것은 표적 케이스 판독 때문이다.** G17 은 이 사이클이 겨냥한 검색 실패
사례인데(findings 11), 정답이 2조항이면 4-1 을 정확히 찾아도 r@1 이 0.5 로 기록돼 성공과
실패가 같은 숫자 대역에 들어간다.

**blind 를 모델에 넘긴 것은 리뷰어 분쟁을 사람의 판정으로 닫지 않기 위해서다.** 결과는
직관과 반대였다 — 모델 재작성이 curated 보다 정답 조항 어휘를 **더 많이** 들여온다.

| 픽스처 | 유입 케이스 | 유입 2-gram |
|---|---:|---:|
| 구 blind (사람) | 7 / 25 | 16 |
| 신 blind (모델) | **18 / 25** | **33** |
| oracle | 25 / 25 | 144 |

(원문에 없고 정답 조항에 있는 문자 2-gram 을 센 값. 정답이 있는 25건 기준, 개정 라벨 적용.)

정책 코퍼스를 입력으로 받은 적이 없는 모델이 같은 어휘를 재현한다는 것은, 그 겹침이
누출이 아니라 **구어체를 문서체로 옮기면 자연히 생기는 것**이라는 뜻이다. 리뷰어 3명이
본 현상은 실재하지만 그 원인 진단이 틀렸다. 그리고 blind·oracle 의 세 자릿수 격차는
그대로여서 두 조건의 분리는 유지된다.

## 기각한 대안

- **관련성을 조건·제한 조항까지 넓히기**: 1-2(대형 상품 지연)는 문의만 보고는 해당 여부를
  알 수 없다. 어떤 검색기도 공정하게 맞힐 수 없는 분모가 된다.
- **G28 에 2-4 를 넣어 G25 와 맞추기**: oracle 과 자동 정합해 findings 13 이 함께 닫히지만,
  기권이 정답인 케이스가 5→4 로 줄고 recall 이 오르는 방향이라 "지표를 좋게 만든 라벨 변경"
  과 구분되지 않는다.
- **G25 를 빈 정답으로 만들기**: 1-5 가 배송 상태 조회를 문자 그대로 서술하는데 버리게 되고,
  같은 주제의 G09·G10·G27 은 1-5 를 유지하므로 새 비대칭이 생긴다.
- **blind 재작성에서 표제어만 손으로 되돌리기**: 무과금이지만 "어디까지가 정규화인가"를
  계속 사람이 판정한다 — 리뷰어들이 갈린 바로 그 지점을 그대로 남긴다.
- **blind 를 상위 모델(`bulk_generation_model`)로 생성하기**: 배포 가능한 이득이 아니라
  또 하나의 상한을 재게 된다. 런타임이 실제로 부를 모델과 같아야 오프라인 비교가 라이브를
  예측한다.

## 받아들인 비용

- **8/12 에 확정된 입력 3종이 모두 바뀌었다.** 확정 뒤 변경이므로 이 문서가 근거를 들고 있고,
  구 fixture 는 git 이력에 남는다.
- **blind 픽스처가 확률적 산출이다.** 커밋된 순간 고정되지만, 재생성하면 다른 문장이 나온다.
  픽스처의 note 가 생성 모델을 기록하고, 구조 테스트가 G17 문장을 못박아 조용한 재생성을
  막는다.
