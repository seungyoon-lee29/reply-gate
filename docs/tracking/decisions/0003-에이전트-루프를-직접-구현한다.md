# 0003. 에이전트 루프를 프레임워크 없이 직접 구현한다

## 맥락

의도 해석 → 근거 수집 → 초안 생성 → 게이트 → 종결이라는 흐름은 에이전트 프레임워크가
그리라고 만들어진 모양이다. 노드·엣지·조건부 분기·상태·체크포인트가 그대로 대응한다.
프레임워크를 쓰면 재시도·상태 관리·시각화를 얻는다.

동시에 이 프로젝트는 채용 포트폴리오이고, 핵심 주장이 **"루프 종료·데이터 접근·권한은 항상
코드가 통제한다"** 이다. 프레임워크가 그 통제를 대신하면 무엇을 어디서 강제하는지 설명하기
어려워진다.

## 결정

루프를 직접 구현한다. 프레임워크는 쓰지 않는다.

- 재생성 상한은 `for` 문의 범위가 강제하고, DB `CHECK (attempt_no BETWEEN 1 AND 2)` 가
  같은 상한을 중복으로 건다.
- 분기는 평범한 `if` 다 — 어떤 조건에서 어느 인계 사유가 나오는지 코드에서 바로 읽힌다.
- 상태는 처리 기록 4테이블이다. 별도 체크포인트 저장소가 없다.

프레임워크 이해도는 README 의 비교 문서로 확보한다 — 자체 루프의 어느 부분이 프레임워크의
무엇에 대응하는지, 프레임워크가 유리했을 지점은 어디인지를 함께 적는다.

## 고려했지만 택하지 않은 것

- **그래프 기반 에이전트 프레임워크 채택** — 재시도·체크포인트·시각화를 얻는다. 기각했다:
  상한과 분기가 프레임워크 설정으로 들어가면 "코드가 통제한다"를 코드로 보일 수 없고,
  이 프로젝트에서 그것이 곧 제품 주장이다.
- **프레임워크를 쓰되 게이트만 밖에 두기** — 절충안. 기각했다: 노드가 5개뿐이고 분기도 단순해
  프레임워크가 주는 이득이 설명 비용을 넘지 않는다.

## 결과

- **얻은 것**: 재생성이 왜 2회를 넘지 않는지 `for` 문 한 줄로 보인다. 상한을 3으로 바꾸면
  테스트 3개가 깨지는 것으로 강제가 실재함을 증명할 수 있다.
- **잃은 것**: 장기 실행·중단 후 재개·병렬 노드가 필요해지면 직접 만들어야 한다. 현재 파이프라인은
  요청 단위 동기 처리라 필요 없다.
- **되돌리지 않기로 한 것**: 실행 중 "프레임워크를 쓰면 더 쉬운데"라는 판단이 들어도 되돌리지
  않는다. 이 결정은 편의가 아니라 전시 전략이다.
