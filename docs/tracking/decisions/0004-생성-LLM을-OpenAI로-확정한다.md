# 0004. 생성 LLM 을 OpenAI 로 확정하고 상위 검증은 다른 계열로 남긴다

## 맥락

생성(의도 해석·SQL 생성·초안 생성)과 임베딩을 어느 provider 로 할지 결정해야 했다.
임베딩은 처음부터 OpenAI 였고, 생성은 다른 계열도 후보였다.

동시에 다음 사이클의 의미 수준 검증(judge)을 어느 계열로 할지가 함께 걸린 문제였다.
생성과 판정이 **같은 계열**이면 self-judging bias 가 생기고, 두 모델의 blind spot 이
겹쳐 검출률 지표가 낙관적으로 오염된다.

## 결정

- **생성·임베딩 모두 OpenAI.** 이번 사이클 API 키는 1개다. 생성 모델 기본값은
  `gpt-5.6-terra` 이며 **모델 등급은 조정 가능 기본값**이다.
- **상위 검증(judge)은 OpenAI 가 아닌 다른 계열로 남긴다.** 계열은 미정이다.
- 합성 데이터 제작에만 상위 모델을 1회 쓰고, 그 산출물은 픽스처로 커밋해 시딩 경로에서
  LLM 을 뺀다.

## 고려했지만 택하지 않은 것

- **생성과 판정을 같은 계열로** — 키 관리가 단순하고 프롬프트 노하우가 재사용된다. 기각했다:
  검출률이 이 프로젝트의 헤드라인 지표인데, self-judging bias 로 그 수치가 오염되면 지표가
  주장의 근거 역할을 못 한다.
- **생성을 다른 계열로** — 임베딩이 OpenAI 이므로 키가 2개가 된다. 데모 규모에서 관리 비용만
  늘고 얻는 것이 없다.

## 결과

- **얻은 것**: 키 1개. 판정 계열을 다르게 가져가는 근거가 문서로 남아, 다음 사이클에
  "왜 굳이 다른 계열인가"를 다시 논의하지 않아도 된다.
- **제약**: 코드가 provider 중립이 아니다 — 래퍼가 OpenAI Responses API 의 구조화 출력
  형태에 맞춰져 있다. 계열을 바꾸려면 래퍼를 고쳐야 한다. 다만 호출부는 `GenerationClient`
  프로토콜에만 의존하므로 교체 지점이 한 곳으로 모여 있다.
- **재현성에 미친 영향**: 샘플링 파라미터로 결정론을 보장하지 않기로 했다(모델 계열에 따라
  파라미터를 받지 않는다). 대신 게이트 정확도는 결정론 층으로 재고, end-to-end 라벨은
  허용 결과 집합으로 정의해 비결정성을 평가 설계로 흡수한다.
