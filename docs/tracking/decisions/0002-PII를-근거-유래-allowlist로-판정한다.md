# 0002. PII 를 전면 차단이 아니라 근거 유래 allowlist 로 판정한다

## 맥락

답변에 전화번호·이메일이 실리는 것을 막는 가장 단순한 방법은 패턴이 잡히면 무조건 기각하는
것이다. 구현이 짧고 오탐 걱정이 없다.

그런데 주문 문의의 **정당한** 답변은 SQL 결과에서 온 연락처를 포함한다. "제 주문에 등록된
연락처가 뭔가요"에 답하려면 그 값을 말해야 한다. 전면 차단은 정상 답변을 전부 막는다.

## 결정

탐지된 패턴형 PII 를 **정규화한 뒤 이번 문의의 수집 근거와 대조**해, 근거에 있으면 허용하고
없으면 기각한다.

- 전화번호는 구분자·공백·괄호를 지우고 한국 국가번호(`+82`/`0082`)를 국내 `0` 표기로 바꾼다.
  주민등록번호는 구분자를 지우고, 이메일은 국제화 도메인까지 탐지해 소문자화한다.
- 근거 텍스트에도 **같은 패턴·같은 정규화**를 적용해 값 집합을 뽑고 **완전 일치**로 대조한다.
- SQL 근거 텍스트에서 실행 SQL은 제외한다. 비PII 계산값은 L2용으로 유지하되 계산된 패턴형
  PII는 제외하고, 가드가 `orders` 직접 컬럼으로 증명한 값만 PII 출처로 승인한다.
- 검사 대상은 답변 텍스트뿐이다 — `citation_ids` 는 제외한다.

결과적으로 지어낸 전화번호는 기각되고, 근거에 있는 값의 정상 에코는 표기 형식이 달라도 통과한다.

## 고려했지만 택하지 않은 것

- **패턴 전면 차단** — 정상 주문 답변을 전부 막는다. 기각.
- **부분 문자열 대조** — 정규화한 숫자열을 근거 원문에서 부분 문자열로 찾는 방식. 구현이 더
  짧지만, 근거에 긴 숫자(주문번호 등)가 있을 때 지어낸 번호가 그 안에 우연히 포함되어
  통과한다 — 즉 유출이다. 기각.
- **비패턴형까지 커버(이름·주소)** — 정규식으로 잡을 수 없다. 의미 수준 검증의 몫으로 이월.

## 결과

- **얻은 것**: 게이트가 "PII 인가"가 아니라 "근거에서 왔는가"를 본다. 지어낸 연락처와 다른
  고객의 연락처는 기각되고 정당한 에코는 통과한다.
- **부수 효과**: allowlist 가 **수집된 근거로부터** 만들어지므로, 근거에 무관한 고객 데이터가
  섞이면 그 데이터가 자동으로 허용된다. SQL 조회 범위를 코드가 강제해야 하는 이유가 여기 있다
  ([0005](0005-SQL-조회-범위를-코드가-강제한다.md)).
- **대가**: 위에서 정규화하지 않는 표기는 정상 에코도 기각될 수 있다. 보수적 방향이라 유출은
  없지만 오기각이 생긴다.
- **불가능해진 것**: 이름·주소를 잡는다고 말할 수 없다. 커버리지가 패턴형뿐이라는 한계를
  축소하지 않고 그대로 서술하는 것이 이 결정의 일부다.
