# 0022. 미정의 사유를 갈라 처분하고 검색 정렬에 tie-break 를 넣는다

## 맥락

채택 축에 **보장이 없는 자리**가 둘 있었다. 둘 다 지금 틀린 값을 내지는 않아서 오래 살아
남았다 — 사이클 4 는 "실측이 끝난 뒤 제품 동작을 바꾸면 그 사이클 라이브의 조건이 무효가
된다"는 이유로 둘 다 다음 사이클로 넘겼다.

**① 통계량이 정의되지 않으면 게이트가 열렸다.** 기권 게이트의 통계량은 두 경우에 정의되지
않는다 — 측정된 점수가 2건 미만이거나, 1위 코사인이 0 이하거나. 순수 판정 연산이 두 경우를
한 예외로 묶어 던졌고 호출자가 그것을 받아 **하나로 접었다**(둘 다 "발동하지 않음").

**② 검색 결과 순서에 결정론 tie-break 가 없었다.** 정책 검색 SQL 이 코사인으로만 정렬해
**동점이면 순서가 Postgres 몫**이었다. 26조항 정확 스캔이라 실무상 안정적이지만 그것은
관측이지 보장이 아니고, 동점이 `top_k` 절단선에 걸리면 채택 집합과 기권 게이트 통계량이
함께 흔들린다.

## 결정

### 미정의 사유를 갈라 처분한다 — 하나로 접지 않는다

| 미정의 사유 | 처분 | 근거 |
|---|---|---|
| 측정된 점수가 **2건 미만** | **기권하지 않는다** | 미정의를 0 으로 채우거나 fail-closed 로 접으면 모든 양수 τ 에서 기권이 되어, 후보가 하나뿐인 질의가 근거 없이 인계된다. 항목 축(절대 하한)이 그 자리를 맡는다 |
| **1위 코사인이 0 이하** | **기권한다** | 모든 후보가 절대 하한 아래라 채택 집합은 어차피 비므로 결과가 달라지지 않고, 통계량을 신뢰할 수 없었다는 사실이 판정에 드러난다 |

**두 번째 줄은 결함이 아니라 계약이다.** 근거 채택 함수의 설명이 이미 못박고 있었다 —
*"통계량이 미정의면(측정된 후보 2건 미만) 게이트는 열린 채로 남는다. … 여기서 뒤집지
않는다."* **fail-closed 를 기계적으로 적용하면 이 층에서는 정상 케이스가 죽는다.**
fail-closed 가 지키는 것은 "검증하지 못한 답변을 내보내지 않는다"이고, 근거 수집은 검증이
아니라 재료 수집이다.

### 미정의 사유를 밖으로 내보낸다

사유는 **이미** 판정 값 안에 실려 있었다. 문제는 그 다음 칸이었다 — 근거 채택 함수가 판정에서
"기권했나" 한 칸만 읽고 나머지를 버려서, 사유가 근거 묶음에도 처리 결과에도 평가 리포트에도
없었다. 그래서 채택 결과를 **묶음**(`evidence.PolicyAdoption`)으로 바꿔 판정을 함께 들고
나오게 하고, 근거 수집 결과(`EvidenceCollection.abstention_undefined_reason`)가 그 사유를
그대로 싣는다. 조용한 폴백을 금지하는 것과 같은 규칙이다 — 처분만 남기면 어느 사유였는지
산출물에서 복원할 수 없다.

거기서 평가 리포트로 잇는 것은 리포트 층을 소유하는 뒤 태스크의 몫이다(사이클 5 T3 → T6).
두 자리 사이의 계약은 **"근거 묶음이 기권 사유를 들고 있다"** 하나다.

### 검색 정렬을 유사도 → 근거 ID 전순서로 만든다

고친 자리는 **DB 질의의 정렬 한 곳**이다. 파이썬 쪽 합집합 병합은 **이미** 유사도 → 근거 ID
로 정렬하고 기본값(재작성 켜짐) 경로가 그 병합을 지난다 — 남아 있던 비결정은 **DB 가 상위
`top_k` 를 자를 때 어느 행이 살아남는가** 하나였다. 근거 ID 는 유일 제약이 걸려 있어
전순서를 만든다.

## 전수 대조 — 조건 보존

유료 실측 앞에 무과금 대조를 뒀다(`uv run python -m scripts.contrast_adoption_axes`).
모집단은 커밋된 검색 산출물 6개와 전략 4종과 골든셋 케이스 30건의 곱이다. **자유 모집단이
있는 축이라 프로브가 아니라 전수다.**

| 축 | 모집단 | 결과 |
|---|---|---|
| 미정의 ① 측정 2건 미만 | 점수열 720건 | **0건** |
| 미정의 ② 1위 코사인 0 이하 | 점수열 720건 | **0건** |
| 코사인 동점 | 코사인 순서 행 360건 | **0건** |
| 절단선 동점 | 코사인 순서 행 360건 | **0건** |
| 순위 변화 | 코사인 순서 행 360건 | **0건** |

관측된 최소 여유: **1위 코사인 최솟값 0.2287** · **절단선 간격 최솟값 0.0002**
(둘 다 기본 조건 `text-embedding-3-small`/1536). 1위 코사인이 0 에서 멀어 분기 ②는 이
코퍼스에서 탈 수 없고, 절단선 간격이 0 이 아니라 동점도 없다.

**두 분기 모두 0건이므로 이 변경은 커밋된 조건을 보존한다.** 라이브 관측의 사전 예측은
"채택 집합·기권 판정 무변화"다.

대조의 모집단이 두 축에서 다른 것에 이유가 있다. 미정의 축은 전략 4종을 전부 세지만, 정렬
축은 **적힌 순서가 실제로 코사인 내림차순인 행만** 센다 — 융합·리랭크 단의 순서는 코사인이
아니라 RRF·리랭크가 정하므로 그 행을 코사인으로 다시 세우면 대조가 엉뚱한 것을 잰다. 대상
여부는 손으로 정하지 않고 행마다 확인해서 가른다.

또 하나: **대조는 커밋된 산출물의 상위 `top_k` 가 아니라 조항 26개 전체 점수열을 읽는다.**
잘린 상위 `top_k` 만으로는 절단선 바로 아래가 무엇이었는지가 사라져 **절단선의 동점을 볼 수
없다.**

## 손계산 쌍둥이의 처분 — 갈리는 것을 받아들인다

같은 미정의 두 조건이 채택 축 **손계산** 모듈(`reply_gate.adoption_axis`)에 같은 문면으로 한
벌 더 있다. τ=0.06 을 정당화한 격자(`retrieval_eval`)는 런타임 원시연산을 import 하므로 이
변경을 따라 움직이지만, 손계산 쪽은 따라오지 않는다.

**함께 바꾸지 않는다.** 이유가 셋이다.

1. **손계산은 게이트가 아니다.** 커밋된 산출물을 읽어 분리 여유를 계산하는 **채점자**라
   "게이트를 열지 닫을지"라는 처분 자체가 없다. 미정의 입력은 처분이 아니라 즉시 실패가
   맞다 — 채점 입력이 잘못된 것이기 때문이다.
2. **두 구현이 독립이어야 교차 대조가 의미를 가진다.** 손계산을 런타임 원시연산으로 갈아
   끼우면 "두 구현이 같은 수를 낸다"는 검사가 자기 자신을 대조하게 된다.
3. **두 분기 모두 0건이라 격자의 결론이 그대로다.** 손계산이 실제로 계산하는 30개 케이스에
   미정의 입력이 하나도 없으므로, 처분이 갈려도 분리 여유도 τ 도 움직이지 않는다.

**갈림을 검사로 못박았다** — `tests/test_adoption_determinism.py` 가 "값은 같고 미정의 사유는
가르지 않는다"를 단언한다. 받아들인 갈림을 아무도 지키지 않으면 다음에 조용히 벌어진다.

## 대안과 기각 사유

- **미정의를 0 으로 채운다** — 모든 양수 τ 에서 기권이 되어 후보가 하나뿐인 질의가 근거 없이
  인계된다. 결정 0014 가 이미 기각했다.
- **두 사유를 다 fail-closed 로 접는다** — 위와 같은 결과다. fail-closed 가 지키는 것은
  "검증하지 못한 답변을 내보내지 않는다"이지 "재료가 적으면 답하지 않는다"가 아니다.
- **두 사유를 다 열어 둔다(현상 유지)** — 지금 값은 틀리지 않지만, 컷이 낮아지거나 임베딩이
  바뀌어 1위 코사인이 0 이하인 질의가 생기는 순간 게이트가 조용히 무력해진다.
- **파이썬에서 정렬을 다시 한다** — 병합 경로는 이미 그렇게 한다. 남은 비결정은 DB 가 상위
  `top_k` 를 **자르는** 시점에 있어서, 파이썬으로 되돌린 뒤에는 이미 잘려 나간 행을 되살릴 수
  없다.

## 받아들인 비용

- **동점 재현 검사는 DB 가 있어야 돈다**(`db` 마커). 파이썬 층에서 쓴 동점 검사는 수정 전에도
  통과하므로 구속력이 없다 — 실제 DB 에 동점을 심어 절단선에 걸리게 해야 한다.
  그리고 **정본 순서(근거 ID 오름차순)와 반대로 심어야 한다**: 갓 삽입된 행은 물리 순서가
  삽입 순서라, 근거 ID 순으로 심으면 tie-break 가 없는 코드도 우연히 정본 순서를 돌려줘
  음성 대조가 초록으로 태어난다.
- **정렬 키가 하나 늘었다.** 26행 정확 스캔이라 비용은 사실상 0 이지만, 코퍼스가 커지면
  정렬 비용이 유일 컬럼 비교만큼 늘어난다. 근사 인덱스를 두지 않는다는 결정과 같은 자리에서
  다시 볼 값이다.
