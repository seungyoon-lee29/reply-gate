# 도메인 규칙

## 엔티티와 관계

- **문의** — `order_no`(선택) + `content`(필수). 최종 상태는 `answered` | `escalated` 둘뿐이고
  둘 다 종결 상태다. 역방향 전이는 없다.
- **시도(attempt)** — 초안 1개 + 그에 대한 **층별 판정**(L1, 그리고 L1 을 통과했고 L2 가
  켜져 있으면 L2). **문의당 최대 2건**(최초 + 재생성 1회).
  DB 가 `CHECK (attempt_no BETWEEN 1 AND 2)` 로 같은 상한을 강제한다.
  시도의 **종합 판정**은 두 층의 결합이다: 종합 pass ⟺ L1 pass 이고 L2 가 실행됐다면
  L2 도 pass. 종합 기각 사유는 두 층 사유의 합집합이며 순서는 고정이다(L1 4종 먼저, L2 2종 뒤).
  **L2 미실행은 pass 로 치지 않고 판정에서 빠진다** — 사유 3종은 `docs/contracts.md`
  "층별 판정 키" 절에 있다.
- **초안** — `{"claims": [{"text": <문장 1개>, "citation_ids": [<근거 ID>...]}]}`.
  사용자에게 보이는 답변은 claims 의 text 를 순서대로 이은 것이다.
- **근거** — 정책 조항 청크(`policy:<문서 slug>:<조항 번호>`) 또는 SQL 결과 스냅샷
  (`sql:<문의 ID>:<실행 순번>`). **한 답변에 두 종류가 공존할 수 있다** — 이것이 이 도메인의
  구조적 특징이고, citation 무결성 검사가 두 출처를 하나의 집합으로 다루는 이유다.
- **주문** — 주문번호가 식별자. 형식은 `ORD-YYYYMMDD-NNNN` 이며 날짜는 실재하는 달력 날짜,
  순번은 `0001`~`9999`. 문의는 존재하지 않는 주문번호도 받는다(그래야 `order_not_found`
  경로가 기록에 남는다) — 그래서 문의 테이블에 주문 FK 를 두지 않는다.

## 상태 전이

```
접수 ──▶ (근거 수집)
          ├─ 구조적 실패/근거 0건 ──▶ escalated (초안 전 인계)
          └─ 근거 있음 ──▶ 초안 ──▶ L1 ──┬─ reject ─────────────────────┐
                                          └─ pass ──▶ L2*               │
                                                       ├─ pass ──▶ answered
                                                       ├─ reject ───────┤
                                                       └─ 호출 실패 ──▶ escalated (llm_call_failed)
                                                                        │
                          ┌─────────────────────────────────────────────┘
                          ▼
                  재생성(1회) ──▶ L1 ──┬─ reject ─────────▶ escalated (rejected_twice)
                                        └─ pass ──▶ L2*
                                                     ├─ pass ──▶ answered
                                                     ├─ reject ─▶ escalated (rejected_twice)
                                                     └─ 호출 실패 ──▶ escalated (llm_call_failed)

* L2 스위치가 꺼져 있으면 이 단계를 건너뛴다 — L1 pass 가 곧 answered 다(사이클 1 동작).
```

**"pass → answered" 에는 예외가 하나 있다.** L2 **호출이 실패한** 시도는 층 결합 정의상
종합 verdict 가 `pass` 인데 문의는 `escalated`(`llm_call_failed`)로 끝난다 — 검증하지 못한
답변을 내보내지 않는 fail-closed 가 스펙이 정한 동작이고, 그 시도의 진실은 **인계 사유와
실패 단계**(`l2_judge`)가 들고 있다. 종합 verdict 만 보고 통과로 읽으면 안 된다.
판정 호출 실패는 **재생성 사유가 아니다** — 인프라 실패는 초안을 고쳐서 나아지지 않으므로
루프를 더 돌리지 않는다.

일어날 수 없는 전이: `answered`/`escalated` 에서 나가는 전이, 3번째 시도, 재생성 시 근거 재수집,
초안 전 인계 뒤의 초안 생성, L1 기각분에 대한 L2 실행.

## 인계 사유 6종 — 각각이 구분되는 이유

| 사유 | 발생 조건 | 이 사유가 따로 있는 이유 |
|---|---|---|
| `no_evidence` | 필요한 모든 소스에서 근거가 비었거나 임계값 미달 | 검색이 아무것도 못 찾은 것 — 검색 품질 문제 |
| `missing_order_ref` | 의도가 `order`/`both` 인데 주문번호가 없음 | 사용자 입력 부족 — 되물으면 해결된다 |
| `order_not_found` | 형식은 맞지만 존재성 선검사에서 주문이 없음 | 주문이 실재하지 않음. **이 판정 주체는 선검사뿐이다** |
| `sql_failed` | text-to-SQL 이 재시도 후에도 실패 | 조회 자체가 불가 — 안전장치 거부/실행 오류/생성 실패 |
| `llm_call_failed` | LLM 전송 오류·형식 불일치가 재시도 후에도 지속. **L2 판정 호출 실패도 여기다**(실패 단계 `l2_judge`) | 외부 장애. 실패한 단계 이름을 함께 기록한다 |
| `rejected_twice` | 초안이 **2회 연속 기각(층 무관)** — L1 기각 2회, L2 기각 2회, L1 기각 후 L2 기각이 모두 여기로 온다 | 게이트가 일한 결과 — 위 다섯과 달리 초안이 실제로 만들어졌다 |

**사유를 뭉치면 지표가 죽는다.** `no_evidence` 와 `order_not_found` 를 한 사유로 묶으면
"검색이 약한 것"과 "주문이 없는 것"을 구분할 수 없어, 다음 사이클에 무엇을 고쳐야 할지 알 수 없다.

## 근거 부족 판정 — `both` 의도의 우선순위

의도가 `both`(정책+주문 둘 다 필요)인데 한쪽만 근거가 있을 때:

- **구조적 사유가 이긴다.** 주문 측이 `missing_order_ref`·`order_not_found`·`sql_failed` 중
  하나면, 정책 근거가 있어도 **인계**한다. 구조적 실패를 정책 근거로 덮으면 사용자는 주문
  질문에 답을 못 받은 채 정책 안내만 받게 된다.
- **SQL 이 정상 실행되고 0건인 것은 구조적 실패가 아니다.** 주문의 존재는 선검사가 이미
  확인했으므로 `order_not_found` 가 아니다. 이때는 **주문 소스 근거 0건**으로 다룬다:
  `order` 단독 의도면 `no_evidence` 인계, `both` 면 정책 근거만으로 초안을 진행한다.
  (주문 정보를 근거 없이 지어낸 문장은 L1 citation 규칙이 잡는다.)

## L1 게이트 판정 규칙

기각 사유는 아래 4종이 전부다. **하나를 잡고 멈추지 않고 전부 수집한다** — 한 번의 재생성으로
모든 문제를 고칠 기회를 주기 위해서다.

| 사유 | 규칙 |
|---|---|
| `schema_violation` | 답변 계약 구조 위반 — 필수 키 누락, 타입 오류, `claims` 비어 있음, claim `text` 가 빈 문자열·공백뿐임 |
| `missing_citation` | `citation_ids` 가 빈 claim 이 존재 |
| `invalid_citation` | 이번 문의에서 수집된 근거 집합에 없는 ID 를 참조 |
| `pii_detected` | 초안 텍스트에 **근거에 없는** 패턴형 PII 가 존재 |

**스키마 검사는 구조까지만 본다.** "citation_ids 1개 이상"을 스키마 검사에 넣으면
`missing_citation` 이 영원히 발화하지 않아 사유 분리가 무너진다.

**원시 초안은 무엇이든 들어올 수 있다.** 초안 생성이 형식 불일치 시 모델 응답 원문 문자열을
그대로 넘기기 때문이다. 문자열·`None`·리스트가 와도 예외를 던지지 않고 `schema_violation` 으로
판정한다.

## PII 규칙 — 근거 유래 허용(allowlist)

주문 문의의 정당한 답변은 SQL 결과에서 온 연락처를 포함할 수 있다. 그래서 무조건 차단이 아니라
**근거에서 왔는지**를 본다.

1. 초안 텍스트에서 패턴형 PII(휴대전화·일반전화·15xx~18xx 대표번호·이메일·주민등록번호)를 탐지한다.
2. 탐지값을 **정규화**한다 — 전화번호는 구분자·공백·괄호를 지우고 한국 국가번호
   (`+82`/`0082`)를 국내 `0` 표기로 바꾸며, 주민등록번호는 구분자를 지우고 이메일은
   소문자화한다. 이메일 도메인은 비ASCII 국제화 표기도 탐지한다.
3. 이번 문의의 근거 원문(`evidence_text`)에 같은 정규화를 적용해 값 집합을 뽑고 **완전 일치**로
   대조한다. SQL 근거의 `evidence_text` 는 실행 SQL 원문을 제외하고 결과 행만 담는다. 비PII
   계산값은 L2용으로 유지하되 계산된 패턴형 PII는 제외하며, `orders` 직접 컬럼 값은 보존한다.
4. 근거에 있으면 허용, 없으면 `pii_detected`.

결과: **지어낸 전화번호는 기각되고, 근거에 있는 값의 정상 에코는 표기 형식이 달라도 통과한다**
(근거 `010-1234-5678` ↔ 초안 `01012345678` 은 통과).

**검사 대상은 답변 텍스트뿐이다** — 구체적으로 **claim 의 `text`**, 즉 답변으로 연결되어 나가는
문자열이다. `citation_ids` 는 검사하지 않는다(근거 ID 는 답변 문장이 아니라 식별자이고,
`sql:<UUID>:<순번>` 의 UUID 16진 숫자가 전화번호 패턴에 우연히 걸린다). **스키마 밖 키도
검사하지 않는다** — 초안 최상위의 `debug` 든 claim 안의 `note` 든 답변에 실리지 않으므로,
검사하면 답변에 없는 값으로 정상 초안을 기각하게 된다. 답변 후보 텍스트를 하나도 식별할 수
없는 초안(원문 문자열이 통째로 넘어온 경우)만 전체를 검사한다 — 그 초안은 어차피
`schema_violation` 이다.

**커버리지 한계**: 이름·주소 등 비패턴형 개인정보는 정규식으로 잡을 수 없어 **L1 의 검사 대상이
아니다**. 이 한계는 축소해서 말하지 않는다.

## 게이트 2층 구조

- **L1 — 결정론 층.** citation 존재·참조 무결성·스키마·패턴형 PII. **LLM 호출 0회**의
  코드 검사이고 100% 재현된다. 기각 사유 4종.
- **L2 — 확률 층.** L1 을 통과한 초안만 claim 단위로 근거와 대조하는 의미 수준 검증.
  답변 계약(claim + citation_ids)과 근거 스냅샷이 그대로 입력이다. 기각 사유 2종.
  판정 계열은 생성과 **다른 provider** 로 고정한다(self-judging bias 차단 —
  `docs/tracking/decisions/0004`).

**L2 는 스위치(`L2_ENABLED`, 기본 켜짐)로 통째로 끌 수 있고, 끄면 L1 단독으로 동작한다**
(사이클 1 동작과 완전히 같다). 그러나 **켜진 채로 판정이 실패하면 통과시키지 않는다** —
실패 정책은 fail-closed 이고, 검증하지 못한 답변은 내보내지 않고 인계한다. 스위치를 끄는 것은
"검증을 안 하기로 명시하는 것"이고, 판정이 실패하는 것은 "검증하려 했는데 못 한 것"이라
같은 결과로 접지 않는다. 같은 이유로 **스위치 켜짐 + 판정자 미배선은 조립 시점 오류**다 —
조용히 건너뛰는 경로를 두면 fail-closed 가 배선 실수 하나로 무너진다.

L1 이 판정하지 **않는** 것: 근거끼리 모순인지, 근거를 오독했는지, 내용이 사실인지.
정책 문서에 일부러 심어 둔 모호·상충 조항이 L1 을 그대로 통과하는 이유가 이것이고,
**그 통과분을 받는 것이 L2 다.**

## L2 판정 규칙

L2 는 **초안을 고쳐 쓰지 않는다.** 두 가지만 판정하고, 시도(초안)당 **1회 배치 호출**이다 —
모순 감지가 claim·근거 교차 시야를 요구해 claim 별 호출로 쪼갤 수 없다.

판정 범위 **밖**인 것: 문의와 답변의 관련성, 답변의 품질·톤, 외부 지식과의 사실 대조.
보는 것은 **근거와 claim 사이의 정합**뿐이다.

### 기각 사유 2종 — 이것이 전부다

| 사유 | 규칙 |
|---|---|
| `unsupported_claim` | 어떤 claim 이 **자신이 인용한 근거**로 뒷받침되지 않는다. reject 인 claim 이 하나라도 있으면 발화하고, 없으면 발화하지 않는다 |
| `contradictory_evidence` | 수집 근거에 서로 모순되는 쌍이 있고, 초안이 그 모순을 명시하지 않은 채 그 근거를 딛고 답한다 |

### 뒷받침 판정 — claim 단위

- 입력은 **각 claim 의 text + 그 claim 이 인용한 근거의 원문**이다. 인용하지 않은 근거는
  뒷받침 판정에 넣지 않는다.
- 근거 내용을 그대로 옮기거나 왜곡 없이 요약·환언한 claim 은 pass.
- **주제 인접 인용은 기각한다.** 인용한 조항이 claim 의 주제를 실제로 다루지 않으면 reject 다.
  예: 해외 배송을 묻는 문의에 **국내** 배송 조항만 인용해 "안내가 어렵다"고 쓴 claim —
  국내 배송 조항은 해외 배송이라는 주제를 다루지 않으므로 뒷받침이 아니다.
- **정면 조항의 "없다" 안내는 통과시킨다.** 인용한 조항이 claim 의 주제를 **정면으로**
  다루면서 해당 값만 비어 있으면, "기재되어 있지 않다"는 claim 을 그 조항이 뒷받침한다.
- **"없다" 안내의 의미 정책은 비대칭이다**: 같은 문장이라도 인접 조항을 딛고 있으면 기각,
  정면 조항을 딛고 있으면 통과다. 근거로 삼은 조항이 그 주제를 다루는가가 갈림길이고,
  이 비대칭이 미끼 경로에서 L1 이 잡지 못하는 실패를 잡는 자리다
  (`docs/tracking/decisions/0007`).
- claim 판정은 **뒷받침 여부만** 본다. 근거 사이의 모순은 claim 판정에 반영하지 않고
  모순 기록에만 남긴다.

### 모순 판정 — 근거쌍 단위

- 대상은 **이번 문의의 수집 근거 전체**다(초안이 인용했는지 무관). 상충 쌍이 한쪽만
  인용됐거나 아예 인용되지 않아도 검출돼야 하기 때문이다.
- 모순은 **근거쌍 단위로 기록**한다 — 특정 claim 에 귀속되지 않을 수 있어 claim 판정 배열과
  별도다. 기록에는 근거 ID 두 개와 설명이 남는다.
- **기록됐다고 곧 기각은 아니다.** 초안이 그 모순을 명시하고 **두 기준을 모두 안내**했다면
  기각 사유가 아니다 — 모순 쌍은 기록하되 `contradictory_evidence` 를 넣지 않는다.
  모순을 명시하지 않은 채 어느 한쪽이라도 딛고 답하면 기각이다.

### 산출 정합 — 해석하지 못한 판정은 통과가 아니라 거부다

판정 산출은 fail-closed 로 다시 검증한다. 사유 2종 밖의 값, 판정값 밖의 값, 수집 근거에
없는 ID 의 모순 쌍, claim 판정이 초안의 claim 과 1:1 로 대응하지 않는 산출, verdict·사유·
세부 배열이 서로 어긋나는 산출은 **전부 형식 불일치**로 취급해 1회 재시도하고, 재실패하면
`llm_call_failed` 인계다. 어긋난 판정이 그대로 기록되면 헤드라인 지표가 오염된다.

### 재생성 피드백

기각 사유는 **전부**(L1 4종 + L2 2종) 다음 재생성의 피드백이 된다. L2 기각이면 **claim 단위
상세**("어느 문장이 왜")까지 함께 간다 — 사유 코드만으로는 고칠 지점을 알 수 없기 때문이다.
재생성도 **같은 근거**로 한다.

## 평가용 데이터의 지위

- **정책 문서의 미끼·모호·상충 조항** — 게이트가 일하는 모습을 만들기 위한 원재료다.
  "테스트 데이터 정리" 명목으로 제거하면 기각 장면이 재현되지 않아 제품 서사가 무너진다.
- **골든셋 라벨은 허용 결과 집합**이다 — 초안이 확률적이라 단일 정답이 없기 때문이다.
  기대 최종 상태 집합 + 허용 인계 사유 집합 + 기각 기대 여부 + 금지 기각 사유로 기술한다.
- **L1 픽스처**는 고정된 (초안, 근거) 쌍이다. LLM 을 부르지 않으므로 100% 재현된다.
- **L2 판정 픽스처**(`data/judge_fixtures.jsonl`)는 고정된 (claims, 근거, 기대 판정) 쌍이다.
  판정 모델을 실제로 부르므로 100% 재현되지는 않지만, **측정 3 의 유일한 입력**이라
  다른 평가 장치와 같은 지위로 보호한다(`standards.md` 하드 게이트 5).
