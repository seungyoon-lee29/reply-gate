# Reply-Gate 스펙 — 사이클 1: Gate L1 동작까지

## 목표와 동기

**Reply-Gate**는 근거 없는 답변을 스스로 reject하는 이커머스 CS 답변 에이전트다. "초안 생성"이
아니라 **"틀린 초안을 걸러내는 것"이 제품의 존재 이유**다. 이번 사이클의 목표는 결정론적 게이트
**L1이 실제로 동작하는 데까지**: 문의를 받아 근거를 수집하고, 초안을 생성하고, L1이 기계 검사로
통과/기각을 판정하며, 기각·인계가 눈에 보이는 파이프라인 전체를 완성한다.

데모의 첫 3초는 **답변이 기각되는 순간**이어야 한다. "CS 챗봇"으로 포지셔닝하지 않는다 — 리드는
항상 "근거 없는 답변을 기각하는 에이전트".

## 범위

**포함**: 자체 에이전트 루프(의도 해석 → 근거 수집 → 초안 생성 → L1 게이트 → 확정/재시도/인계),
정책 문서 RAG(벡터 검색 단독), 주문 DB text-to-SQL + 안전장치, L1 게이트 전체, FastAPI API +
최소 웹 폼 1장, 합성 데이터(주문 500건 + 정책 문서), 골든셋 30건 + L1 픽스처 셋 평가 하네스, README(노드/엣지
다이어그램 + 확률/결정 경계 + "LangGraph로 짰다면" 비교 1페이지).

**제외 (이번 사이클)**: L2(claim 단위 LLM judge), Next.js 등 대시보드, n8n, MCP 서버,
RAG 심화(하이브리드 검색·리랭킹·청킹 전략 실험), 배포. 프로젝트 전체 범위는 handoff의
Project Foundation 참조.

**영구 제외**: 파인튜닝·자체 임베딩 학습, 카카오·이메일 등 채널 연동(웹 폼 + 웹훅까지만),
"CS 챗봇" 포지셔닝.

## 파이프라인 행위 (노드별 확률론/결정론 경계 명시)

문의 1건은 아래 순서로 처리된다. 각 노드의 **[LLM]**/**[코드]** 표기는 제품의 구조적 특징이며
README 다이어그램에도 그대로 실린다. 권한·데이터 접근·루프 종료 조건은 항상 코드가 통제한다.

1. **접수 [코드]** — 웹 폼/API로 문의 수신. 입력 필드: `order_no`(주문번호, 선택),
   `content`(문의 내용, 필수). 주문번호 형식 검증은 코드가 한다. LLM이 자유 텍스트에서
   주문번호를 추출하지 않는다. 주문번호 형식의 정의는 코드 한 곳에 두고 데이터 시딩과
   접수 검증이 같은 정의를 공유한다.
2. **의도 해석 [LLM]** — 문의를 읽고 필요한 근거 소스를 분류한다: `policy`(정책만) /
   `order`(주문만) / `both`. 분류 결과는 구조화 출력으로 받는다. 호출 실패는 아래
   "LLM 호출 공통 실패 정책"을 따른다.
3. **근거 수집 [코드]** — 분류 결과에 따라 코드가 조회를 실행한다(조회 실행 주체는 항상 코드).
   - **정책 벡터 검색**: 문의 임베딩 → pgvector 유사도 검색 → 상위 k개 조항 청크.
     유사도 점수가 임계값 미만인 결과는 버린다(임계값·k는 조정 가능 기본값).
   - **주문 존재성 선검사**: 의도가 `order`/`both`이고 주문번호가 있으면, text-to-SQL 이전에
     코드가 고정 파라미터 쿼리로 해당 주문의 존재를 확인한다. 없으면 `order_not_found` 인계
     (text-to-SQL 미진입). 선검사는 존재 확인에만 쓰며 그 결과를 근거로 쓰지 않는다 — 주문
     근거는 text-to-SQL 경로로만 수집한다. `order_not_found` 판정 주체는 이 선검사뿐이다.
   - **주문 SQL**: 선검사를 통과한 주문에 대해 text-to-SQL(LLM이 SQL 생성 [LLM], 실행·검증은
     코드)로 조회. 안전장치는 아래 별도 절.
4. **초안 생성 [LLM]** — 수집된 근거만을 컨텍스트로 초안을 생성한다. 산출물은 아래
   "답변 계약"의 구조화 JSON — 문장(claim) 단위로 쪼개고 각 claim에 citation ID를 매핑한다.
5. **L1 게이트 [코드]** — LLM 호출 0회, 100% 재현 가능한 기계 검사. 검사 규칙은 아래 별도 절.
   기각 사유는 하나만 잡고 멈추지 않고 **전부 수집**한다.
6. **종결 [코드]** — 통과 시 답변 확정. 기각 시 기각 사유 전체를 피드백으로 붙여 초안을
   **1회만 재생성**(4번으로 복귀, 근거는 재수집하지 않고 동일 근거 재사용)하고, 재기각 시
   상담원 인계로 종료한다. 루프 상한(재생성 1회)은 코드가 강제한다.

### 초안 전 인계 (초안 생성 없이 즉시 상담원 인계)

LLM이 근거 없이 지어낼 기회 자체를 차단하기 위해, 다음 경우 초안 생성 단계에 진입하지 않고
바로 인계한다. 각각 구분되는 인계 사유 코드를 남긴다.

| 상황 | 인계 사유 코드 |
|---|---|
| 필요한 모든 소스에서 근거가 비었거나 임계값 미달 | `no_evidence` |
| 의도 분류가 `order`/`both`인데 주문번호가 없음 | `missing_order_ref` |
| 주문번호 형식은 맞으나 존재성 선검사에서 해당 주문이 없음 | `order_not_found` |
| text-to-SQL이 재시도 후에도 실패 (아래 SQL 실패 경로) | `sql_failed` |
| LLM 호출 전송 오류가 재시도 후에도 지속 (아래 LLM 호출 공통 실패 정책 — 초안 생성 단계에서 발생해도 동일 사유) | `llm_call_failed` |

의도 분류가 `both`인데 한쪽 소스만 근거가 있는 경우: 확보된 근거만으로 초안을 진행한다 —
단, 주문 측이 위 표의 구조적 사유(`missing_order_ref`·`order_not_found`·`sql_failed`)에
해당하면 인계가 우선한다. 존재성 선검사를 통과한 주문에 대해 SQL이 정상 실행되고 0건인 것은
구조적 실패가 아니라 **주문 소스 근거 0건**이다: `order` 단독 의도면 `no_evidence` 인계,
`both`면 정책 근거만으로 진행한다(주문 정보를 근거 없이 지어낸 문장은 L1 citation 규칙이
잡는다).

## 답변 계약 (초안 JSON 스키마 — L1 기계 검사의 대상)

초안 생성 LLM의 산출물은 아래 형태의 구조화 JSON이다. 이 스키마가 L1 검사의 전제이자
다음 사이클 L2(claim 단위 대조)가 그대로 이어받는 계약이다.

```json
{
  "claims": [
    { "text": "<답변 문장 1개>", "citation_ids": ["<근거 ID>", "..."] }
  ]
}
```

- `claims`: 1개 이상. 각 claim은 답변의 문장 1개.
- `citation_ids`: 각 claim이 딛고 선 근거 ID 목록. **모든 claim에 1개 이상** 있어야 한다.
  이 규칙의 위반 판정은 L1 `missing_citation`이 전담한다(스키마 검사 대상이 아님 — L1 절 참조).
- 최종 사용자에게 보여줄 답변 텍스트는 claims의 text를 순서대로 이은 것이다.

### 근거(citation) ID 체계

| 근거 종류 | ID 형식 | 안정성 |
|---|---|---|
| 정책 조항 청크 | `policy:<문서 slug>:<조항 번호>` | 문서 기반 안정 식별자 |
| SQL 조회 결과 | `sql:<문의 ID>:<실행 순번>` | 요청별 생성, 스냅샷 영속화 |

SQL 근거는 **정상 실행되어 근거로 채택된 쿼리 1건당 ID 1개**를 부여하고, 실행된 쿼리문과
결과 행 전체를 처리 기록에 스냅샷으로 영속화한다 — 감사·재현·차기 L2 claim 대조가 모두 이
스냅샷 위에 선다. 실행 순번은 채택된 쿼리에만 매긴다: 안전장치에 거부되거나 실행에 실패한
쿼리는 근거 ID 없이 처리 기록에 실패 내역(쿼리문·오류)만 남기고, 존재성 선검사 쿼리는 근거가
아니므로 ID를 받지 않는다.

## L1 게이트 검사 규칙

모두 코드로 검사한다(LLM 호출 0회). 기각 사유 코드는 아래 enum이 전부다.

| 사유 코드 | 규칙 |
|---|---|
| `schema_violation` | 초안이 답변 계약 JSON 스키마에 맞지 않음 (필수 키 누락, 타입 오류, claims 비어 있음 포함) |
| `missing_citation` | citation_ids가 빈 claim이 존재 |
| `invalid_citation` | citation_ids에 이번 문의에서 실제 수집된 근거 집합에 없는 ID가 존재 (참조 무결성) |
| `pii_detected` | 초안 텍스트에 **근거에 없는 PII**가 존재 (아래 PII 정책) |

`schema_violation`의 스키마 검사는 구조(필수 키·타입·claims 비어 있음)까지만 본다.
"citation_ids 1개 이상"은 `missing_citation`이 전담하므로 **스키마 검사기에 최소 개수 제약을
넣지 않는다** — 넣으면 missing_citation이 영원히 발화하지 않아 사유 분리가 무너진다.

### PII 정책 — 패턴형 PII, 근거 유래 허용 (allowlist)

주문 문의의 정당한 답변은 SQL 결과에서 온 연락처 등 개인정보를 포함할 수 있다. 따라서:

- 초안 텍스트에서 **패턴형 PII**(전화번호, 이메일, 주민등록번호 등 — 패턴 집합은 조정 가능
  기본값)를 정규식으로 탐지한다. 이름·주소 등 비패턴형 개인정보는 정규식으로 잡을 수 없으므로
  **L1의 검사 대상이 아니며**, L2 사이클의 claim 단위 근거 대조로 이월한다. README·데모 서술도
  이 한계를 그대로 말한다(과장 금지 — 과장이 오히려 면접 역공 지점).
- 탐지된 값은 **정규화 후** 이번 문의의 수집 근거(정책 청크 텍스트 + SQL 결과 스냅샷)와
  비교한다 — 숫자형 PII는 구분자·공백을 제거한 숫자열로, 이메일은 소문자화해 비교한다(정규화
  규칙은 조정 가능 기본값). 근거에 존재하면 허용, 존재하지 않으면 `pii_detected`로 기각한다.
- 이 설계가 게이트의 정교함을 보여주는 지점이다: 지어낸 전화번호·다른 고객의 연락처는
  기각되고, 근거에 있는 값의 정상 에코는 표기 형식이 달라도 통과한다.

## text-to-SQL 안전장치 (스펙 필수 — 빼면 면접 역공 대상)

1. **read-only DB 계정** — SQL 실행은 SELECT 권한만 가진 별도 계정으로만 한다.
2. **스키마 화이트리스트** — 조회 가능한 테이블·컬럼 목록을 코드에 명시하고, 생성된 SQL이
   화이트리스트 밖을 참조하면 실행 전에 거부한다.
3. **쿼리 검증** — 실행 전 코드가 SQL을 파싱·검증한다: SELECT 단일문만 허용, DML/DDL/다중문/
   주석 우회 거부, 결과 행 수 상한(조정 가능 기본값).

### SQL 실패 경로 (검색 결과 0건과 구분되는 상황)

안전장치의 쿼리 거부, 실행 오류, LLM의 유효 SQL 생성 실패 시: 오류 내용을 피드백으로
**SQL 생성만 1회 재시도**한다. 재실패하면 상담원 인계(사유 `sql_failed`). 쿼리가 정상 실행되고
결과가 0건인 것은 실패가 아니라 **주문 소스 근거 0건**이다 — 주문의 존재는 선검사가 이미
확인했으므로 `order_not_found`가 아니며, "초안 전 인계" 절의 근거 0건 규칙을 따른다.

### LLM 호출 공통 실패 정책

- **전송 오류**(타임아웃·API 오류로 응답 자체가 없음): 의도 해석·초안 생성·SQL 생성·임베딩
  호출 공통 — 해당 호출을 1회 재시도하고, 재실패하면 상담원 인계한다(사유 `llm_call_failed`,
  실패한 단계를 처리 기록에 남긴다).
- **구조화 출력 형식 불일치**: 의도 해석은 1회 재시도 후 재실패 시 `llm_call_failed` 인계.
  초안 생성은 재시도하지 않는다 — 산출을 그대로 L1에 넘겨 `schema_violation`으로 판정하고
  기존 재생성 루프가 처리한다. SQL 생성은 위 "SQL 실패 경로"(`sql_failed`)가 우선한다.

## 판정·상태 모델

- 문의의 최종 상태: `answered`(L1 통과, 답변 확정) | `escalated`(상담원 인계).
- 인계 사유: `no_evidence` | `missing_order_ref` | `order_not_found` | `sql_failed` |
  `llm_call_failed` | `rejected_twice`(초안 2회 연속 L1 기각).
- 시도(attempt)별 L1 결과: `pass` | `reject`(+ 사유 코드 목록). 시도 기록은 최대 2건
  (초안 + 재생성 1회).

## API 표면

| 메서드/경로 | 행위 |
|---|---|
| `POST /inquiries` | 문의 접수 + 동기 처리. 요청: `{order_no?: string, content: string}`. 응답: 아래 응답 스키마 |
| `GET /inquiries/{id}` | 처리 기록 조회 (시도 이력·근거 스냅샷·판정 포함) |
| `GET /` | 최소 웹 폼 1장 (FastAPI가 서빙하는 템플릿/정적 페이지, 대시보드 아님) |
| `GET /health` | 헬스 체크 |

응답 스키마 (`POST /inquiries`, `GET /inquiries/{id}` 공통 골격):

```json
{
  "inquiry_id": "<ID>",
  "status": "answered | escalated",
  "answer": "<확정 답변 텍스트, answered일 때만>",
  "claims": [ { "text": "...", "citation_ids": ["..."] } ],
  "citations": [ { "id": "...", "source": "policy | sql", "content": "<청크 텍스트 또는 쿼리+결과 요약>" } ],
  "attempts": [ { "verdict": "pass | reject", "reject_reasons": ["..."] } ],
  "escalation_reason": "<escalated일 때만>",
  "metrics": { "latency_ms": 0, "tokens": { "input": 0, "output": 0 } }
}
```

모든 키는 항상 존재한다: `answer`·`escalation_reason`은 해당 없을 때 null, `claims`·`citations`·
`attempts`는 해당 없을 때 빈 배열. 초안 전 인계라도 그 시점까지 수집된 근거는 `citations`에
기록한다(감사 목적). `metrics.tokens`는 생성 계열(Claude) 호출의 합산이며, 임베딩 토큰은
처리 기록에 별도 필드로 남겨 건당 비용 산출에 반영한다.

웹 폼은 이 응답을 그대로 보여준다 — 특히 **기각·인계 순간(attempts의 reject와 사유)이 화면에서
바로 보이는 것**이 데모 요구사항이다.

  케이스를 포함하고 LLM 호출 없이 돌므로 100% 재현된다(규모는 조정 가능 기본값).

## 저장

- **Postgres + pgvector, 로컬 Docker 1개** — 주문 테이블, 정책 청크 + 벡터 인덱스,
  처리 기록(문의·시도·근거 스냅샷·판정·지연·토큰)이 한 DB에 산다.

  기록한다.

## 기술 결정

- **백엔드**: Python / FastAPI (확정 — 카드 A가 TS를 이미 증명하므로 여기는 Python).
- **생성 LLM**: Claude API, `claude-opus-5` (의도 해석·초안 생성·SQL 생성 공통. 추후 L2 judge도
  동일 계열 전제).
- **임베딩**: OpenAI `text-embedding-3-small` (Anthropic은 임베딩 API가 없음. 한국어 무난).
  API 키 2개(Anthropic, OpenAI)는 환경 변수로 관리하고 코드·문서에 평문 금지.
- **에이전트 루프**: 자체 구현, LangGraph 미사용. README에 노드/엣지 다이어그램 +
  "LangGraph로 짰다면" 비교 1페이지를 넣어 키워드는 문서에 등장시킨다.

  산출 비결정성은 평가 설계로 흡수한다: 게이트 정확도는 L1 픽스처(결정론 층)로 측정하고,
  end-to-end 라벨은 허용 결과 집합으로 정의한다(평가 절).
- **동시성/일관성**: N/A — 단일 개발자 데모, 요청 단위 무상태 처리, 주문 데이터는 read-only.
  공유 가변 상태 없음.

## 평가 (이번 사이클 정의)

L1은 citation 존재·무결성·스키마·PII만 검사하므로, 이번 사이클 지표는 **L1이 잡을 수 있는
범위로 측정**하고 나머지는 명시적으로 이월한다. 측정은 결정론 층과 확률 층을 분리한다 —
LLM 비결정성이 게이트 자체의 정확도 수치를 흔들지 못하게 하기 위해서다.

- **측정 1 — L1 게이트 단위 정확도 (결정론)**: L1 픽스처 셋(고정 초안+근거, LLM 호출 없음)에
  대해 구조적 오류 검출률 / 정상 초안 오탐률. 100% 재현 가능 — 신뢰성 서사의 헤드라인 수치.
- **측정 2 — 파이프라인 판정 일치율 (end-to-end)**: 골든셋 30건을 전체 파이프라인에 흘려 —
  - 허용 결과 집합 대비 일치율 (초안 전 인계 경로 포함 — L1 판정만의 지표가 아님을 리포트에 명시)
  - 기각 유발 문의의 기각 재현율 (데모 신뢰성의 근거 수치)
  - p50/p95 지연, 문의 1건당 토큰 비용 (생성·임베딩 구분 기록, 합산 보고)
- **이월 (L2 사이클)**: 내용상 hallucination율, L1 필터링에 의한 L2 호출 감소율,
  RAG 검색 품질 단계별 개선표.
- **목표치**: 첫 측정값을 보고 확정한다(조정 가능으로 기록). 지표 목표치를 지금 박지 않는 것은
  결정이며, 평가 하네스가 수치를 산출하는 것까지가 이번 사이클 완료 조건이다.

## 완료 검증 게이트

이 저장소에는 기존 검증 명령이 없으므로 이번 사이클이 게이트를 신설한다. "완료" 선언 전 모두
통과해야 한다:

1. `uv run pytest` — 전체 테스트 녹색 (L1 규칙·안전장치·인계 경로는 단위 테스트 필수.
   DB 통합 테스트는 docker compose로 DB를 띄운 상태에서 실행 — 이 전제를 README에 명시)
2. `uv run ruff check` (+ `ruff format --check`) — 린트 통과
3. `uv run mypy` — 타입체크 통과
4. 골든셋 평가 하네스 실행이 끝까지 돌고 지표 리포트가 산출됨
5. 실제 동작 확인: 웹 폼에서 (a) 정상 답변 1건, (b) L1 기각→재생성 1건, (c) 인계 1건이
   재현됨. (b)는 골든셋에서 기각 재현율이 검증된 기각 유발 문의로 시연한다 — 라이브 유발이
   실패하면 골든셋 실행에서 기록된 실제 기각 건의 처리 기록 화면(`GET /inquiries/{id}`)으로
   대체할 수 있다.
