# 사이클 3 스펙 — 검색 품질 (RAG 심화)

이 문서가 이번 사이클의 **ground truth** 다. plan 과 어긋나면 spec 이 이긴다.
spec 의 오류는 사용자 승인으로만 고친다.

---

## 1. 목표와 동기

**게이트 앞의 검색을 측정 가능하게 만들고, 측정으로 이긴 구성만 제품에 반영한다.**

두 사이클의 실측이 문제를 게이트 층 **밖**으로 밀어냈다. 지금 남은 결함은 전부 검색이다:

- **못 찾는다** — G17("상담원과 통화하고 싶은데 몇 번으로 걸면 되나요?")이 겨냥한 조항
  `policy:support:4-1` 의 유사도는 **0.2637**로 임계값 0.3 아래다. 같은 조항을 겨냥한
  G16("고객센터 전화번호 알려주세요")은 **0.6289**로 통과한다. 구어체 패러프레이즈를
  임베딩이 잇지 못한다([findings 11](../docs/tracking/findings.md)).
- **잘못 찾는다** — 정책에 없는 주제(G21–G24)에서도 임계값 위로 인접 조항이 검색된다.
  사이클 2 의 L2 가 이 건들을 `unsupported_claim` 으로 잡아 인계하지만, **원인은 검색에
  그대로 남아 있고**([findings 2](../docs/tracking/findings.md)) 그 뒤처리에 판정 호출이
  들어간다 — 판정은 건당 토큰의 **약 72%** 다.
- **임계값 하나로는 양방향을 못 막는다.** 낮추면 G17 이 엉뚱한 조항을 먼저 물고, 올리면
  정상 문의의 근거가 잘린다. 실측으로 확정된 사실이다.

동시에 [기획 입력](../기획-입력.md) 확정사항 4("RAG 는 여기서 심화한다")는 **유일하게 비어
있는 확정사항**이다. 별도 RAG 프로젝트를 만들지 않기로 했으므로 검색 품질을 측정·개선한
이력이 이 저장소 안에 있어야 하고, 기본값 `text-embedding-3-small` 을 고른 근거가 "싸서"가
아니라 **"측정해보니 충분해서"** 여야 한다.

이번 사이클은 그 근거를 만든다.

## 3. 검색 정답 라벨 (`data/retrieval_labels.jsonl`)

검색 품질을 재려면 "무엇이 정답 조항인가"가 저장소 안에 있어야 한다. 지금은 없다.

### 3-1. 형태

골든셋 30건과 **1:1**로 대응하는 JSONL. 키는 세 개다.

- `id` — 골든셋 케이스 ID. 골든셋에 없는 ID, 골든셋에 있는데 라벨에 없는 ID는 **로드 시
  예외**다. 라벨이 조용히 비면 recall 분모가 소멸하고 지표가 사라진다(골든셋 범주 검증과
  같은 이유).
- `relevant_evidence_ids` — 정답 조항의 `evidence_id` 배열. **순서는 의미를 갖지 않는다.**
  존재하지 않는 `evidence_id` 는 로드 시 예외다(정책 문서 26개 조항과 대조).
- `note` — 왜 그 조항인지 한 줄.

검색 관련성은 **문의에 답하거나 안전하게 제한하는 데 직접 필요한 모든 정책 조항**이다.
주문번호 안내처럼 단순한 처리 전제·입력 안내는 제외하고, 상세 정보 공개를 제한하는 접근
통제는 포함한다. 따라서 G16·G17은 4-1과 4-2를 모두 포함하고, G25는 1-5만,
G29·G30은 공개 제한 근거인 4-5를 포함한다.

**빈 배열은 유효한 라벨이고 이 사이클의 핵심이다.** 근거가 없는 것이 정답인 문의
(G21–G24: 해외 배송·B2B 할인·매장 픽업·선물 포장, G28: 직접 처리 정책이 없는 환불 실행
요청)는 `relevant_evidence_ids: []` 로 적는다. 이 다섯 건은 recall 의 분모에서 빠지고
**precision 쪽에만** 들어간다 — "아무것도 검색되지 않아야 한다"가 정답이기 때문이다.

미끼 문의(G16–G20)의 정답은 **정면 조항 전체**다(예: G16·G17 →
`policy:support:4-1`, `policy:support:4-2`).
값이 비어 있다는 사실 자체가 그 조항이 답하는 내용이라는 것이 결정 0007 의 비대칭이고
결정 0008 이 라벨을 거기 정렬했다.

### 3-2. 출처와 검수

골든셋의 `note` 필드가 이미 조항 번호를 적고 있다(예: G01 "환불 기간 조항(2-1)").
초안은 거기서 뽑되 **정책 문서 원문과 대조해 확정하고, 30건 전부를 사용자에게 제시해
1회 검수받는다**(§12 의 중간 체크포인트). 라벨이 이번 사이클 모든 수치의 분모다.

### 3-3. 평가 장치 등록

이 파일은 **평가용으로 심은 장치**다. `CLAUDE.md`·`AGENTS.md` 의 "제거하지 않는다" 목록에
`data/judge_fixtures.jsonl` 과 같은 자격으로 올린다.

## 4. 오프라인 비교 하네스 — 지표 정의

### 4-1. 실행 형태

**DB 를 거치지 않는다.** 조항 26개와 문의 30건을 메모리에 올려 코사인 유사도를 직접
계산한다. 이유는 셋이다: (i) 임베딩 모델 비교는 차원이 다른 벡터를 나란히 놓는 일인데
`policy_chunks.embedding` 은 `vector(1536)` 고정이라 스키마를 건드리지 않고는 담을 수 없다,
(ii) 26×30 규모라 인메모리가 자명하게 충분하다, (iii) 비교 때문에 DB 를 재생성하면
보존하기로 한 처리 기록이 비교 실험마다 날아간다.

**DB 에 들어가는 것은 채택된 구성 하나뿐이다**(§8).

### 4-2. 임베딩 캐시

구성별 벡터를 파일로 캐시해 비교 재실행이 무과금·동일 결과가 되게 한다. 캐시는
gitignore 한다(재생성 비용 $0.01 미만). 캐시 키는 (모델, 차원, 대상 텍스트의 해시)다 —
정책 문서가 바뀌면 자동으로 무효가 되어야 한다.

### 4-3. 지표 — **두 벌을 함께 낸다**

| 벌 | 무엇을 재나 | 왜 |
|---|---|---|
| **순위 품질** | 임계값을 **무시**하고 recall@1 / recall@3 / recall@5 | 임계값은 이번 사이클의 조정 대상이다. 임계값에 종속된 수치만 재면 전략 비교가 임계값 튜닝에 오염된다 |
| **채택분 품질** | 임계값 **적용 후** precision / recall | 제품이 실제로 근거로 삼는 것은 임계값을 통과한 것뿐이다 |

- **recall** = 정답 조항 중 검색된 비율. 분모는 `relevant_evidence_ids` 가 비지 않은
  문의만이다.
- **precision** = 검색된 조항 중 정답인 비율. **`relevant_evidence_ids` 가 빈 문의는
  여기 포함된다** — 한 건이라도 검색되면 그 문의의 precision 은 0 이다.
- **아무것도 검색되지 않은 문의(0건)의 precision 규약** — 이 사이클의 목표 상태가 바로
  이것이라 규약이 없으면 채택 결과가 뒤집힌다:
  - 정답이 **빈 배열**인데 0건이 검색됐다 → **precision = 1.0**. 이것이 정답이다.
  - 정답이 **있는데** 0건이 검색됐다 → precision 은 **평균에서 제외**한다(분모가 0이라
    값이 없다). 이 실패는 **recall = 0** 으로 이미 계상된다. 제외하지 않고 0 이나 1 로
    채우면 검색 실패가 precision 을 올리거나 두 번 벌준다.
- 두 지표 모두 **문의 단위로 먼저 계산하고 평균낸다**(macro). 조항 수가 많은 문의가
  평균을 끌고 가면 30건 규모에서 한 건이 지표를 흔든다.
- **채택 컷(임계값)은 구성의 일부이고, 무엇에 거는지도 구성이 정한다.** 지금은 코사인
  유사도 하나뿐이지만 사다리를 올라가면 최종 순위를 만드는 것이 바뀐다. 구성별로 다음을
  명시한다 — 이 정의가 없으면 "검색 단계에서 걸러졌다"(성공 판정 ②)가 판정 불가다:
  | 구성 | 컷을 거는 대상 |
  |---|---|
  | 벡터 단독 · 질의 재작성 | **코사인 유사도** (현행 그대로). 재작성은 원문·재작성 각각의 유사도 중 큰 값 |
  | 하이브리드(RRF) | **RRF 점수**. 코사인 스케일이 없으므로 스윕 범위가 다르다 |
  | 리랭킹 | **리랭커가 매긴 순위의 상한(상위 n)**. 리랭커는 점수를 내지 않는다. 리랭커에 들어가기 **전** 후보 선별은 직전 단의 컷을 그대로 쓴다 |
- **임계값 스윕**: 구성마다 컷을 훑어 최적점을 함께 낸다. 임베딩이 바뀌면 유사도 스케일이
  달라지고 RRF·순위는 아예 다른 축이므로, 기존 0.3 을 고정한 비교는 불공정하다.
  코사인 구성의 스윕 범위·간격은 조정 가능 기본값(0.10~0.70, 0.05 간격)이고, RRF·순위
  구성의 범위는 그 축에 맞게 하네스가 정한다(조정 가능).
- `top_k` 는 현행 5 를 기본으로 두되 구성 인자로 노출한다(조정 가능 기본값).
  **순위 품질은 항상 recall@1/3/5 로 낸다** — `top_k` 가 5 보다 작은 구성에서도 순위
  자체는 그 아래까지 계산해 낸다(컷과 순위 품질은 다른 축이다).

### 4-4. 표적 케이스는 개별로도 보인다

집계 수치와 **별도로** 리포트가 케이스별 행을 싣는다. 최소한 다음이 한눈에 보여야 한다:
G17 이 `policy:support:4-1` 을 몇 위로·어떤 유사도로 물었는가, G21–G24 가 임계값 위로
무엇을 물었는가. 이번 사이클의 성공 판정(§10)이 그 두 줄이다.

## 5. 전략 사다리

네 단이고, **각 단은 직전 단을 대체하지 않고 얹힌다**. 비교 하네스는 어떤 조합이든
구성으로 받아 돌릴 수 있어야 한다.

### 5-1. 벡터 단독 (현행, 기준선)

문의 원문 임베딩 → 코사인 상위 k → 임계값 필터. 지금 제품이 하는 것 그대로다.

### 5-2. 질의 재작성

LLM 이 문의를 검색용 질의로 바꾼다. G17 처럼 구어체·완곡 표현이 조항 어휘와 겹치지 않는
경우를 겨냥한다. 원문 질의와 재작성 질의를 **둘 다** 검색해 결과를 합집합으로 모으는 것이
기본이다 — 재작성이 주제를 옮기면 원문이 안전망이 된다.

**재작성을 만드는 자리는 두 가지고, 둘 다 비교 대상이다:**

- **(A) 별도 호출** — 검색 전용 LLM 호출을 하나 더 둔다.
- **(B) 의도 해석 호출에 얹기** — 파이프라인은 이미 문의마다 의도 분류를 부른다. 그
  구조화 출력에 "검색용 질의" 필드를 하나 더해 **추가 호출 0회**로 얻는다
  ([findings 11](../docs/tracking/findings.md) 이 이미 적어 둔 대안이다).

**(B) 가 §7-3 의 "싼 쪽"에서 이긴다** — 호출이 늘지 않고, 폴백도 단순해진다(의도 해석이
실패하면 어차피 `llm_call_failed` 인계라 새 실패 경로가 생기지 않는다). 다만 의도 분류의
구조화 출력 스키마를 넓히는 것이므로 **(A) 와 나란히 재고 채택 시점에 고른다.**
비교 자체는 재작성 **문자열**의 검색 성능을 보는 것이라 두 자리가 같은 하네스를 쓴다.

**오프라인 비교에서는 커밋된 픽스처를 쓴다.** 재작성이 확률 층이면 비교표의 입력이
실행마다 흔들려 채택 근거가 되지 못한다. 기본 입력 `data/rewritten_queries.jsonl` 은
정책·라벨을 보지 않고 원문만으로 요청 유형·대상·단정 강도를 보존한 **blind/deployable**
조건이다. 정책의 답·전제·제약을 새로 넣지 않는다. 기존의 정책·라벨 기반 curated 문장은
`data/rewritten_queries_oracle.jsonl` 로 별도 보존하고 **oracle upper bound**로만 표시한다.
oracle 결과는 배포 가능한 재작성 전략의 개선폭으로 주장할 수 없다. 두 조건 모두 사용자가
검수한다(§12 체크포인트).

픽스처 계약은 라벨(§3-1)과 같은 엄격도다:

- 골든셋과 **1:1**. 어긋난 ID는 양쪽 어느 방향이든 로드 시 예외.
- 키는 `id` · `original`(골든셋 `content` 와 일치해야 한다 — 다르면 예외) ·
  `rewritten` · `note`(어떤 어휘를 겨냥했는가).
- `rewritten` 은 비어 있을 수 없다. 재작성이 필요 없다고 판단한 문의는 원문과 같은
  문자열을 명시적으로 적는다 — 빈 값과 "재작성 안 함"이 구별돼야 한다.

**런타임 경로는 두 픽스처를 절대 읽지 않는다.** 읽으면 골든셋 30건 전용 치트가 되고,
그 순간 측정 2 의 수치가 무의미해진다. **런타임이 픽스처 경로에 닿지 않는 것을 테스트가
구조로 검사한다**(게이트의 LLM import 금지를 AST 로 검사하는 것과 같은 자격의 하드 게이트).

### 5-3. 하이브리드 (BM25 + 벡터)

- **BM25 는 파이썬 측에서 조항 전체(현재 26개)를 읽어 계산한다.** Postgres 전문 검색을
  쓰지 않는다 — 한국어 형태소 설정을 DB 에 들이는 것은 이 규모에 맞지 않는 무게고,
  조항이 26개라 전량 인메모리 계산이 자명하게 싸다.
- **런타임 코퍼스의 출처는 `policy_chunks` 테이블이다** — `data/policies/*.md` 파일이
  아니다. 적재가 멱등이고 사라진 조항을 삭제하는 규칙 때문에 **런타임의 진실은 DB** 고,
  파일을 직접 읽으면 재색인하지 않은 문서 수정이 검색에 반영되는 이중 진실이 생긴다.
  문의마다 전량 SELECT 가 붙지만 26행이라 비용이 문제가 아니다(프로세스 수명 캐시는
  조정 가능한 최적화이지 계약이 아니다). **오프라인 비교 하네스는 §4-1 대로 파일에서
  읽는다** — DB 를 거치지 않는 것이 그쪽의 설계다.
- **토큰화는 문자 2-gram 이 기본값(조정 가능)**이다. 한국어는 조사가 붙어 공백 분리
  토큰이 잘 맞지 않고, 형태소 분석기를 넣으면 의존성이 또 하나 늘어난다.
- 두 순위의 결합은 **RRF(reciprocal rank fusion)** 를 기본값으로 한다 — 점수 스케일이
  다른 두 순위를 정규화 없이 합칠 수 있고, 상수 하나만 조정 가능 기본값으로 남는다.

### 5-4. 리랭킹

- **LLM 리랭크**다. 기존 OpenAI 키로 저가 모델(`gpt-5.6-luna` 급, 조정 가능 기본값)이
  후보 조항을 재정렬한다. 의존성·키 추가가 0 이다.
- **판정 계열 분리 규칙(결정 0004)의 적용 대상이 아니다.** 리랭크는 판정이 아니라 **재료
  정렬**이다 — 자기 출력을 평가하는 self-judging 이 아니라 문서를 고르는 일이고, 그 뒤에
  L1·L2 두 층이 그대로 서 있다. 다만 "생성기와 같은 계열이 재료를 고른다"는 편향 가능성은
  **비교표에 기록으로 남긴다**(리랭크 없는 구성이 함께 재어지므로 그 차이가 곧 관측이다).
- 로컬 크로스인코더와 전용 리랭크 API 는 검토 후 제외했다 — 전자는 추론 무게를 서빙
  경로에 들이고, 후자는 제3 provider·키·과금 계정을 늘린다.

## 6. 임베딩 모델 축

| 구성 | 차원 | 비고 |
|---|---|---|
| `text-embedding-3-small` | 1536 | 현행 기본값 |
| `text-embedding-3-large` (절단) | 1536 | 스키마 무변경으로 채택 가능한 경로 |
| `text-embedding-3-large` (네이티브) | 3072 | 채택 시 **스키마 변경 → 볼륨 재생성**(§8-4) |
| BGE-M3 (로컬) | 1024 | 선택적 의존성. 채택 시 스키마 변경 |

- **BGE-M3 는 선택적 의존성 그룹**(예: `rag-local`)으로만 들어간다. 기본 설치에 torch
  계열 2~3GB 를 들이지 않는다. 비교 스크립트가 미설치를 감지하면 그 행만 **"미측정 —
  로컬 의존성 미설치"** 로 적고 나머지 결과는 그대로 낸다. 측정 하나가 없다고 리포트가
  죽거나 0 으로 채워지지 않는다(리포트 불변식 그대로).
- 채택 후보에서 차원 변경 조합을 **제외하지 않는다.** 이기면 쓴다 — 대신 §8-4 의 절차를
  탄다.

## 7. 채택 규칙

**절대 목표선을 긋지 않는다.** 결정 0006 의 논리("측정 전에 목표를 적으면 숫자를 맞추러
간다")가 그대로 적용된다. 대신 **비교 규칙**을 쓴다:

1. **사다리는 표적 결함을 개선할 때만 올라간다.** 다음 단(5-2 → 5-3 → 5-4)은 직전 단
   대비 ① G17 의 정답 조항 순위·유사도 ② G21–G24 의 오검색 건수 중 **적어도 하나를
   개선하고 다른 하나를 악화시키지 않을 때만** 채택 후보가 된다.
2. **전체 지표가 악화하면 그 단은 탈락한다** — recall(순위 품질)이나 precision(채택분)
   어느 쪽도 기준선 아래로 내려가면 안 된다.
3. **동률이면 싼 쪽·의존성이 적은 쪽·차원이 안 바뀌는 쪽**을 고른다. 이 순서다.
4. 결과는 **"가장 싼 충분한 조합" 하나**다. 여러 구성을 켤 수 있게 남겨 두지 않는다 —
   기본값이 하나여야 실측이 그 기본값의 근거가 된다.

이 규칙은 실측 **전에** 정해도 숫자를 맞추러 가지 않는다. 넘어야 할 경계선이 없고
직전 단과의 상대 비교뿐이기 때문이다.

채택 결과와 근거는 **결정 0009** 로 남긴다 — 비교표, 탈락한 단과 그 이유, 차원 변경
여부, 그리고 채택하지 **않은** 것들(청킹·크로스인코더·전용 리랭크 API)까지.

## 8. 제품 경로 반영 계약

채택된 구성만 반영한다. 반영하지 않은 전략의 코드는 비교 하네스 쪽에 남고 실행 경로에
들어가지 않는다.

### 8-1. 검색 단계의 생성 호출 — 실패 시 폴백

질의 재작성·LLM 리랭크는 **실행 경로에 확률 층을 하나 더 얹는다.** 실패 처리 규칙:

- **런타임 호출 실패는 폴백이다.** 재작성이 실패하면 원문 질의로, 리랭크가 실패하면
  벡터 순위 그대로 검색을 계속한다. 폴백 결과는 사이클 2 까지의 제품 동작과 정확히
  같고, 그 뒤에 L1·L2 두 층이 그대로 서 있다.
- **fail-closed 원칙과 충돌하지 않는다.** 그 원칙이 지키는 것은 **"검증하지 못한 답변을
  내보내지 않는다"** 이다. 검색은 검증이 아니라 재료 수집이고, 재료가 덜 좋아진 것은
  검증 없이 내보내는 것과 다르다. L2 호출 실패가 인계인 것은 변함없다.
- **조용한 폴백은 금지한다.** 폴백은 (i) 처리 기록에 남고 (ii) 평가 리포트에 "검색
  단계 폴백 n건"으로 집계된다. 실패한 호출이 쓴 토큰도 실비용이므로 그대로 센다
  (판정 토큰 규칙과 같다).
- **배선 누락은 폴백이 아니라 조립 시점 오류다.** 전략이 켜져 있는데 클라이언트가
  배선되지 않은 조립은 명시적으로 죽는다 — L2 의 `PipelineWiringError` 와 같은 자격이다.
  기본값·`None` 이 조용히 전략을 끄는 fail-open 배선을 두지 않는다.

### 8-2. 토큰 집계 — 검색 계열을 분리한다

검색 단계에서 생성 호출을 쓰는 구성이 채택되면, 그 토큰을 **생성 토큰에 합산하지
않는다.** 새 계열로 분리한다.

근거는 정직성이다. 성공 판정 ②는 "G21–G24 가 검색 단계에서 걸러져 **초안 생성·판정
호출 없이** 끝난다"인데, 리랭크 토큰이 생성 토큰 칸에 들어가면 초안을 만들지도 않은
문의가 초안 생성 토큰을 쓴 것으로 찍힌다 — 리포트가 거짓말을 한다. 판정 토큰을 분리한
것과 같은 이유다(패키지 불변식 12).

**주의 — 생성 토큰은 원래 0 이 되지 않는다.** `input_tokens`/`output_tokens` 는
"의도 해석 + SQL 생성 + 초안 생성" 합산이고(`docs/contracts.md`), 의도 해석은 검색보다
**먼저·무조건** 돈다. 커밋된 실측이 이를 보인다: `evaluation-live-l2-1.json` 의 G17 은
이미 `no_evidence` 인계인데 `input_tokens 216 / output_tokens 12` 다. 그래서 성공 판정은
"생성 토큰 0"이 아니라 **"시도(초안) 0건 + 판정 토큰 0"** 으로 적는다(§10-2).
**의도 해석 토큰을 새 검색 계열로 옮기지 않는다** — 그것은 §8-5 가 무변경으로 못박은
계약을 건드리는 일이고, 이번 사이클의 범위가 아니다.

계약 확장 범위: `ProcessedInquiry` · 처리 기록 스키마 · `GET /inquiries/{id}` 응답 ·
평가 리포트 집계. 임베딩 토큰과도 분리한다(단가가 다르다).

**이 확장은 채택 구성이 검색 단계에서 생성 호출을 쓸 때만 한다.** 쓰지 않는 구성이
이기면 항상 0 인 컬럼을 만들지 않는다.

### 8-3. 검색 구성이 리포트 실행 조건에 실린다

라이브 리포트의 실행 조건에 **검색 구성 요약**(임베딩 모델·차원·전략 조합·임계값·top_k)을
필수 필드로 싣는다. 리포트 마크다운 머리에도 표시한다.

**리포트 파일 이름 계열은 늘리지 않는다.** L2 도입 때 이름을 갈랐던 것은 지표의 정의
자체가 달라지는 층 도입이었기 때문이고, 검색 구성은 **같은 지표를 다른 설정으로 잰
것**이라 실행 조건 필드가 맞는 자리다. 구성마다 이름 계열을 늘리면 이름 가드가 조합
폭발한다. L2 켜짐 실측의 자동 넘버링(`evaluation-live-l2-<n>`)을 그대로 쓴다.

### 8-4. DB 반영과 처리 기록 보존

- **차원이 안 바뀌면**: 재색인(`scripts.index_policies`)만 한다. 볼륨은 그대로다.
- **차원이 바뀌거나 처리 기록 스키마가 넓어지면**: 볼륨 재생성이 필요하다(이 프로젝트에는
  마이그레이션 도구가 없고 DDL 이 전부 `CREATE TABLE IF NOT EXISTS` 다).
  - **실행 전 사용자 확인을 별도로 받는다.**
  - **처리 기록 4테이블을 덤프 → 볼륨 재생성 → 시딩 → 재색인 → 복원**한다. 복원은
    컬럼을 명시한 삽입이고, 새로 생긴 컬럼은 기본값을 받는다.
  - 보존 대상은 이번 세션에서 "그대로 둔다"로 결정된 두 가지다: 오탐 버그 시절 기록
    1건([findings 4](../docs/tracking/findings.md))과 데모용 기각→재생성→통과 기록.
  - 복원 후 `GET /inquiries/{id}` 로 실제 열어 확인한다. 건수 대조만으로는 부족하다.

### 8-5. 무엇이 안 바뀌는가

L1·L2 게이트의 동작, 답변 계약(`claims`/`citation_ids`), 근거 ID 체계
(`policy:<slug>:<조항>`), text-to-SQL 안전장치 3층, **재생성 1회 상한(문의당 시도 최대
2건)**, 인계 사유 6종, L2 판정 사유 2종, 그리고 **생성 토큰의 정의**("의도 해석 + SQL
생성 + 초안 생성" 합산) — 전부 무변경이다. 이번 사이클은 **게이트 앞**만 손댄다.

## 9. 평가 리포트 확장 — 검색 실패 / 생성 문제 분해

확정사항 4-④ 를 여기서 낸다.

- **`GoldenOutcome` 에 채택된 근거 ID 목록을 싣는다.** 지금은 없어서 "G17 이 4-1 을
  찾았는가"를 산출물만 보고 확인할 수 없다. 성공 판정 ①이 이 필드 위에 선다.
- **기각·인계된 케이스를 라벨과 조인해 둘로 가른다:**
  - 정답 조항이 채택 근거에 **있었는데도** 기각·인계됐다 → **생성 문제**
  - 정답 조항이 채택 근거에 **없었다** → **검색 실패**
  - 정답이 빈 배열인 문의(G21–G24)가 인계됐다 → **정상 동작**이며 어느 쪽도 아니다.
    검색 0건으로 끝났는지, 근거를 물고 L2 가 잡았는지를 함께 적는다 — 이 사이클의
    개선이 바로 여기서 보인다.
- 이 절은 라벨 파일이 있을 때만 산출된다. 없으면 "미산출 + 사유"다(0 으로 채우지 않는다).
- 측정 1·2·3 의 정의와 목표치 체계는 **건드리지 않는다.** 검색 지표는 측정 4 로 승격하지
  않는다 — 오프라인 격자 비교는 실행 주기(사이클 1회)와 산출 형태(전략×모델 격자)가
  달라 같은 리포트 골격에 들어가지 않고, 편입하면 매 평가 실행마다 임베딩 과금이 붙는다.

## 10. 라이브 재실측과 성공 판정

### 10-1. 실행

채택 구성으로 **라이브 3회 1세트**. 사이클 2 실측 기준 3회 합산 약 47만 토큰이다.
**실행 직전에 사용자 승인을 한 번 더 받는다**(§13 과금 통제).

### 10-2. 성공 판정 — 표적 관측 + 비악화 가드

**표적 관측** (둘 다 성립해야 한다):

1. **G17 이 `policy:support:4-1` 을 근거로 채택한다** — 라이브 3회 중 **3회 모두**.
   판정 근거는 리포트의 채택 근거 ID 필드(§9)다.
2. **G21–G24 가 검색 단계에서 걸러져 `no_evidence` 인계로 끝난다** — 3회 × 4건 = 12건 중
   **10건 이상**(≥ 3회 중 2회 재현). 판정 근거 세 가지가 **모두** 성립해야 한다:
   - `status == escalated` 이고 `escalation_reason == no_evidence`
   - **시도(초안) 0건** — `attempt_verdicts` 가 비어 있다. 초안 생성에 진입하지 않았다는 뜻이다
   - **판정 토큰 0** — L2 를 부르지 않았다는 뜻이다

   **생성 토큰 0 을 요구하지 않는다.** 의도 해석 호출이 검색보다 먼저 무조건 돌아
   수백 토큰이 남는다(§8-2 의 실측 인용). 비교는 절대값이 아니라 대비로 한다 — 사이클 2
   실측에서 G21 은 `input_tokens 2183 · judge_input_tokens 3472` 였다.

**비악화 가드 — 케이스 단위 회귀**:

- 기준선은 **결정 0008 의 새 라벨로 재채점한 사이클 2 실측: 90/90 = 100.0%** 다.
  (재채점은 커밋된 산출물의 재계산이고, 새 라벨 기준의 라이브 실행은 이번이 처음이다.)
- 판정: 사이클 2 에서 **3회 모두 일치했던 케이스**가 새 실측에서 **3회 중 2회 이상**
  일치해야 한다. 어느 케이스든 이를 못 채우면 **악화**다.
- 합산 일치율은 **병기하되 판정 기준이 아니다.** 90건 규모에서 잡음 1건이 1.1%p 라
  합산으로 판정하면 확률 층의 흔들림이 사이클 성패를 정한다.
- 측정 1(100%/0%)과 측정 3(검출률 100%·오탐 0%)은 **무변경이어야 한다.** 검색은 이 둘의
  입력이 아니므로 값이 움직이면 그 자체가 회귀 신호다.

### 10-3. 라이브가 오프라인 채택을 반증하면

표적 관측이나 비악화 가드가 미달이면 **원복이 기본이다.**

- 채택을 되돌려 기존 기본값(`3-small` · 벡터 단독 · 임계값 0.3 · top_k 5)으로 복구한다.
- 실측값과 원인을 **리포트와 `docs/tracking/findings.md` 에 그대로 남긴다.** 오프라인에서
  이겼는데 라이브에서 진 것 자체가 이 프로젝트가 말할 수 있는 관측이다.
- 재시도 여부는 그 시점에 사용자 판단으로 넘긴다. 상한 안에서 임의로 다시 사지 않는다.
- **실측이 정당화하지 않는 기본값을 저장소에 남기지 않는다.** 남기면 "측정해보니
  충분해서"라는 채택 근거 전체가 무너진다.

### 10-4. 목표치 재확정은 이번 사이클 실측 뒤다

새 라벨 기준으로는 L2 꺼짐 기준선(86.7%)도 측정 2 목표 75% 를 넘는다 — 목표치가 이미
현황 추인이 됐다([결정 0008](../docs/tracking/decisions/0008-미끼-라벨을-판정-규칙에-정렬한다.md) 위험 절).
재확정은 **이번 사이클의 라이브 실측이 나온 뒤** 결정 0006 갱신으로 한다. 지금 그으면
검색 개선의 목표선을 검색 개선 전에 긋는 것이 된다.

## 12. 중간 체크포인트 (사용자 1회)

비교 실행 **전에** 다음 두 가지를 함께 제시하고 확정받는다. 둘 다 이번 사이클 모든
수치의 입력이라 잘못되면 비교 전체를 다시 사야 한다.

1. **검색 정답 라벨 30건**(§3) — 케이스별 정답 조항과 근거 한 줄.
2. **blind 재작성 질의 픽스처 30건**(§5-2) — 원문과 재작성문을 나란히. oracle/curated
   upper-bound 세트는 별도 조건으로만 보존한다.

사용자 검토에서 관련성 정의와 oracle 누출을 지적한 경우 수정본을 다시 확정받기 전에는
오프라인 유료 비교를 실행하지 않는다.

## 13. 과금 통제

- **사전 승인 + 상한 $10.** 오프라인 비교·재색인·임베딩 캐시 생성은 상한 안에서 승인
  없이 실행한다. 오프라인 격자는 임베딩 호출 위주라 전부 합쳐 $0.01 미만이고, LLM
  리랭크 비교가 $0.1 미만이다.
- **라이브 재실측(§10-1)만 실행 직전에 한 번 더 확인받는다.** 여기가 유일하게 달러
  단위가 나가는 지점이다(3회 합산 약 47만 토큰).
- 상한을 넘길 상황이면 실행 전에 멈추고 보고한다.
- 비밀은 `.env` 에만 둔다. 로그·리포트·오류 메시지에 값이 남지 않는다.

## 14. 산출물 보존

- **오프라인 비교 리포트는 저장소가 추적한다.** 위치는 `reports/retrieval-*.md` 와
  `reports/retrieval-*.json`, `.gitignore` 에 되살림 패턴을 추가한다. 확정사항 4 가
  요구하는 "측정·개선 이력"이 이 파일이고, 결정 0009 가 이것을 인용한다.
  **`.gitignore` 는 중괄호 확장을 지원하지 않는다** — 확장자별로 두 줄로 적는다
  (기존 `evaluation-live-*` 패턴이 이미 그렇게 되어 있고, 그 자리의 주석이 바로 이
  종류의 사고를 경고한다).
- 추적되는 순간 **에이전트·사람의 사후 편집은 저장소의 PreToolUse 훅이 막는다** —
  "`reports/` 아래의 git 추적 파일"이 보호 대상이다.
- **훅이 막지 못하는 경로가 하나 남는다**: 비교 스크립트를 다시 돌리면 훅에 파일 경로가
  드러나지 않아 커밋된 비교 리포트를 조용히 덮어쓴다. 그래서 **비교 하네스가 스스로
  거부해야 한다** — 이미 존재하는 `retrieval-*` 산출물에는 쓰지 않고 이름을 올려 붙인다
  (`resolve_report_stem` 이 평가 리포트에 하는 것과 같은 규율이고, 그 가드를 확장하는
  것이 아니라 검색 하네스가 자기 몫으로 갖는다).
- 기존 라이브 실측 **6회분 12개 파일**(`evaluation-live-{1,2,3}` ·
  `evaluation-live-l2-{1,2,3}` 각각 `.md`·`.json`)은 **덮어쓰지도 지우지도 않는다.**
- 리포트 이름 가드(`resolve_report_stem`)는 `evaluation` 계열 전용이다. 검색 비교
  리포트는 그 계열에 들어가지 않으므로 가드를 확장하지 않는다.

## 15. 완료 검증

완료 게이트는 **셋**이다. 사이클 2 는 (a)(b) 둘로 갈랐지만 이번 사이클은 **제품 배선이
채택 결과에 종속**되므로 배선 검증을 과금 앞으로 당길 수 없다.

**(a) 과금 없이 성립하는 것 — 비교 준비 완료.** 여기가 무과금 경계다(T1–T5·T9).

1. `uv run ruff check .` · `uv run ruff format --check .` · `uv run mypy` 통과.
2. `uv run pytest` 전체 녹색 + `uv run pytest -m db` **skip 0**.
3. 라벨 로더의 음성·양성 대조: 골든셋과 어긋난 ID, 존재하지 않는 `evidence_id`, 빈 배열
   라벨이 각각 의도대로 동작한다. 재작성 픽스처 로더도 같은 수준(§5-2 계약).
4. **런타임 경로가 재작성 픽스처에 닿지 않는 것**을 구조 테스트가 검사한다.
   **그 테스트가 실제로 실패하는 것까지 확인한다.**
5. 비교 하네스를 대역 임베딩으로 완주해 리포트가 생성된다(과금 0). 전략 조합과 모델 축이
   전부 배선돼 있고, BGE-M3 미설치 행이 사유와 함께 미측정으로 찍힌다.
6. 평가 리포트의 검색/생성 분해가 3분류 픽스처로 재현되고, 라벨 부재 시 미산출 사유가
   찍힌다.

**(b) 채택과 제품 배선** — 오프라인 과금(상한 안)이 필요하다.

7. 오프라인 격자 비교 완주 + 비교표 산출 + 채택 결정(결정 0009 초안).
8. 채택 구성이 제품 경로에 배선되고, 1·2 의 검증 명령이 다시 전부 녹색이다.
9. **채택 구성이 검색 단계에서 생성 호출을 쓰는 경우에만**: 폴백(재작성 실패·리랭크
   실패·둘 다 중 채택 구성에 해당하는 것)이 인계가 아니라 폴백으로 끝나고 폴백 사실과
   토큰이 기록되는 것, 전략 켜짐 + 클라이언트 미배선이 조립 시점에 죽는 것을 테스트가
   확인한다. **생성 호출을 쓰지 않는 구성이 이기면 이 항목은 "해당 없음"으로 닫는다** —
   미달이 아니다.
10. DB 반영 완료. 볼륨을 재생성했다면 처리 기록 복원을 **API 로 실제 열어** 확인.

**(c) 실측과 판정** — 라이브 과금(별도 승인)이 필요하다.

11. 라이브 3회 재실측 + 성공 판정(§10-2). 미달이면 원복(§10-3)까지가 이 항목이다.
12. 문서 현행화 · 결정 0009 확정 · 목표치 재확정(§10-4) · 데모 서사 재구성(§16).

## 16. 데모 서사

검색 개선이 성공하면 **지금 가장 안정적인 L2 라이브 기각 장면이 사라진다.** 무근거 4건
(G21–G24)이 검색 단계에서 걸러지면 그 12/12 인계는 더 이상 L2 장면이 아니다.
기획 입력 확정사항 1 은 "데모 첫 3초는 답변이 기각되는 순간"이다.

- **새 서사로 재구성한다** — "검색이 먼저 거르고(비용 0), 남은 의미 결함은 L2 가 잡는다".
  개선된 제품을 그대로 말하는 쪽이다.
- **L2 라이브 기각 재현은 G18(모순 기각)이 맡는다** — 사이클 2 실측에서 3/3 재현됐다.
- **기각 장면을 살리려고 검색을 일부러 느슨하게 두지 않는다.** 그건 제품을 나쁘게 만들어
  데모를 지키는 것이다.
- README 는 검색 품질 단계별 개선표(확정사항 4)를 싣고 결정 0009·비교 리포트로 링크한다.
