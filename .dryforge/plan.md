# Reply-Gate 플랜 — 사이클 1 (잠정 청사진)

spec.md가 행위의 정본이다. 이 문서는 실행 순서와 작업 대상만 정한다.

## 단계 서사

스캐폴드(T0)가 웨이브 0에서 프로젝트 골격(pyproject·패키지 구조·LLM 클라이언트 래퍼)을 깐다.
그 위에서 데이터 기반(T1)이 바닥이 되고, 정책 문서·인덱싱(T2)이 서고, 근거 수집(T3)이 이 둘을
소비한다. 초안 생성(T4)과 L1 게이트(T5)는 spec의 답변 계약만 보고 독립적으로 만들 수 있으므로
T1과 같은 웨이브에서 병렬로 간다. 루프+API(T6)가 T3·T4·T5를 하나의 파이프라인으로 묶고,
그 위에서 평가(T7)와 README(T8)가 병렬로 마무리한다.

## 태스크

### T0 — 스캐폴드 (프로젝트 골격)
- **목표**: uv 프로젝트 초기화 — pyproject.toml(전체 의존성·ruff·mypy·pytest 설정 일괄 선언),
  src 패키지 골격과 tests 디렉토리, `.env.example`(키 이름만, 값 없음), LLM·임베딩 클라이언트
  공통 래퍼(spec "LLM 호출 공통 실패 정책"의 전송 오류 1회 재시도 구현 포함).
- **작업 대상**: pyproject.toml, 패키지·테스트 골격, 린트/타입/테스트 설정, .env.example,
  공통 LLM 클라이언트 모듈.
- **행위 계약**: 이후 태스크는 pyproject.toml을 수정하지 않는다(공유 쓰기 지침). 비밀 평문
  금지 — .env.example에는 키 이름만. 클라이언트 래퍼는 재시도 정책만 담고 프롬프트를 담지
  않는다(프롬프트는 T3·T4 소유). 주의 — Anthropic·OpenAI SDK는 기본적으로 전송 오류·429·5xx를
  2회 자동 재시도하므로 래퍼에서 `max_retries=0`을 명시해 재시도를 래퍼가 단독 통제한다
  (중첩되면 스펙의 "1회 재시도"가 실제로는 최대 6회 전송 시도가 되어 지연·처리 기록이 어긋난다).
- **검증 게이트**: 빈 골격에서 `uv run pytest`·`ruff check`·`mypy` 녹색, 래퍼 재시도 정책
  단위 테스트(목 사용) 녹색.

### T1 — 데이터 기반 (DB·스키마·합성 주문)
- **목표**: Docker Compose로 Postgres+pgvector 1개를 띄우고, 스키마(주문 테이블, 정책 청크+
  벡터 컬럼, 처리 기록: 문의·시도·근거 스냅샷)와 계정 2개(앱 계정, SELECT 전용 read-only
  계정)를 만들고, 합성 주문 500건을 시딩한다.
- **작업 대상**: docker compose 파일, 스키마 마이그레이션/DDL, 시딩 스크립트, DB 접속 설정.
- **행위 계약**: 시딩은 재실행 가능(멱등 또는 리셋 후 재시딩). read-only 계정으로 INSERT/
  UPDATE/DDL 시도 시 권한 오류가 나야 한다. 주문 필드는 text-to-SQL·PII 시연에 필요한 구성
  (spec "데이터" 절).
- **검증 게이트**: 시딩 후 주문 500건 카운트 테스트, read-only 계정 권한 거부 테스트 녹색.

### T2 — 정책 문서 작성 + 인덱싱 파이프라인
- **목표**: 한국어 이커머스 CS 정책 문서(배송·환불·교환 등)를 작성하되 모호·상충 조항과
  **미끼 조항**(패턴형 값을 일부러 뺀 조항 — spec "데이터" 절, 사이클 1 기각 유발 재료)을 심고
  (심은 위치는 문서 내 주석/메타데이터로 표시 — 모호·상충은 L2 검출 대상, 미끼는 골든셋 재료),
  조항 단위로 청킹해 OpenAI 임베딩으로 pgvector에 적재하는 파이프라인을 만든다.
- **작업 대상**: 정책 문서 원본(마크다운 등), 청킹·임베딩·적재 스크립트.
- **행위 계약**: 청크 ID는 `policy:<문서 slug>:<조항 번호>` 형식으로 안정적이어야 한다.
  파이프라인 재실행 시 중복 적재 없이 갱신된다.
- **검증 게이트**: 적재 후 청크 수·ID 형식 검증 테스트, 샘플 쿼리로 유사도 검색이 관련 조항을
  반환하는 스모크 테스트 녹색.

### T3 — 근거 수집 (의도 분류·벡터 검색·존재성 선검사·text-to-SQL)
- **목표**: 의도 분류(LLM, 구조화 출력: policy/order/both, 실패 시 공통 실패 정책) → 코드가
  조회 실행. 벡터 검색(임계값 필터), 주문 존재성 선검사(고정 파라미터 쿼리), text-to-SQL
  (LLM이 SQL 생성, 코드가 안전장치 3종으로 검증·실행, 실패 시 1회 재시도), 근거 ID 부여·
  스냅샷 구성까지.
- **작업 대상**: 근거 수집 모듈(의도 분류 클라이언트, 검색, 존재성 선검사, SQL 생성·검증·실행),
  스키마 화이트리스트 정의.
- **행위 계약**: spec의 "text-to-SQL 안전장치"·"SQL 실패 경로"·"LLM 호출 공통 실패 정책" 절이
  그대로 규칙이다. 화이트리스트 밖 참조·비SELECT·다중문은 실행 전에 거부. `order_not_found`
  판정 주체는 존재성 선검사뿐이고 선검사 결과는 근거가 아니다. SQL 정상 실행 0건은 "주문 소스
  근거 0건"으로 처리(spec 초안 전 인계 절). 채택된 쿼리 실행 1건당 근거 ID 1개
  (`sql:<문의 ID>:<순번>`) + 쿼리문·결과 스냅샷, 거부·실패 쿼리는 ID 없이 실패 내역만 기록.
  유사도 임계값 미달 결과 폐기.
- **검증 게이트**: 안전장치 거부 케이스(비SELECT, 화이트리스트 밖 테이블, 다중문), SQL 재시도
  경로, 존재성 선검사(존재/부재), SQL 정상 실행 0건 처리, 의도 분류 구조화 출력 파싱·재시도
  경로(LLM 목), 임계값 필터 단위 테스트 녹색.

### T4 — 초안 생성 (claim 매핑 구조화 출력)
- **목표**: 수집된 근거만 컨텍스트로 넣고 답변 계약 JSON(claims + citation_ids)을 생성하는
  모듈. 재생성 변형: L1 기각 사유 목록을 피드백으로 붙여 같은 근거로 다시 생성.
- **작업 대상**: 초안 생성 모듈(프롬프트, Claude 구조화 출력 호출, 재생성 프롬프트 변형).
- **행위 계약**: 산출은 spec "답변 계약" 스키마를 따른다(따르지 못하면 L1이 잡는 것이 정상 —
  생성 측에서 스키마 강제 수단이 있으면 쓰되, L1 검사를 대체하지 않는다). 근거 밖 지식을
  쓰지 말라는 지시를 프롬프트에 명시. 이 프롬프트의 품질이 기각 분포와 데모 품질을 좌우하는
  확률적 핵심이다 — 골든셋 실측(T7)을 보고 조정한다.
- **검증 게이트**: 파싱·매핑 로직 단위 테스트 녹색 (LLM 호출은 목/픽스처로).

### T5 — L1 게이트
- **목표**: spec "L1 게이트 검사 규칙"의 4개 사유(schema_violation, missing_citation,
  invalid_citation, pii_detected)를 코드로 구현. LLM 호출 0회. 사유는 전부 수집.
- **작업 대상**: L1 게이트 모듈(스키마 검사, citation 존재·무결성 검사, PII 정규식 +
  근거 유래 allowlist).
- **행위 계약**: 입력 = 초안 JSON + 이번 문의의 수집 근거 집합. 출력 = pass | reject +
  사유 코드 목록. PII는 정규화 후 근거 텍스트(정책 청크 + SQL 스냅샷)와 비교해 존재하면 허용
  (spec PII 정책). 스키마 검사는 구조까지만 — citation_ids 최소 개수 제약은 missing_citation
  전담이므로 스키마 검사기에 넣지 않는다(spec L1 절). 100% 결정론 — 같은 입력에 항상 같은 판정.
- **검증 게이트**: 사유 4종 각각의 양성·음성 케이스, PII allowlist 통과/기각 케이스,
  복수 사유 동시 수집 케이스 단위 테스트 녹색.

### T6 — 에이전트 루프 + API + 웹 폼
- **목표**: T3·T4·T5를 spec "파이프라인 행위" 순서로 묶는 자체 루프(재생성 1회 상한 코드
  강제, 인계 경로 전부 — spec 판정·상태 모델의 사유 6종, 종결 상태·사유 기록), FastAPI
  엔드포인트 4개, 최소 웹 폼 1장.
- **작업 대상**: 오케스트레이션 모듈, FastAPI 앱·라우트, 웹 폼 템플릿, 처리 기록 저장.
- **행위 계약**: spec의 "판정·상태 모델"과 "API 표면"이 그대로 계약이다. 웹 폼은 기각·인계
  순간(attempts의 reject 사유)이 바로 보이게 렌더링. 지연·토큰 사용량을 처리 기록에 남긴다.
- **검증 게이트**: 인계 사유 6종 각각의 시나리오 + 기각→재생성→확정 + 재기각→인계 시나리오
  테스트(LLM 목), API 응답 스키마 테스트(빈 배열·null 규칙 포함) 녹색.

### T7 — 골든셋 + L1 픽스처 + 평가 하네스
- **목표**: 허용 결과 집합 라벨이 붙은 골든셋 30건(정상·기각 유발·무근거·인계 유도 혼합)과
  L1 픽스처 셋(고정 초안+근거 쌍)을 만들고, 두 층을 분리 측정하는 하네스와 리포트를 만든다 —
  측정 1: L1 게이트 단위 정확도(픽스처, 결정론), 측정 2: 파이프라인 판정 일치율·기각 유발
  문의의 기각 재현율·p50/p95 지연·건당 토큰 비용(골든셋, end-to-end).
- **작업 대상**: 골든셋 데이터 파일, L1 픽스처 셋, 평가 실행 스크립트, 지표 리포트 산출물.
- **행위 계약**: spec "평가" 절의 이번 사이클 정의를 따른다. 골든셋 라벨은 허용 결과 집합으로
  기술한다. 측정값은 목표치 확정의 입력이 된다(목표치는 리포트에 "미확정, 측정 후 결정"으로
  명시).
- **검증 게이트**: 하네스가 픽스처 셋과 골든셋 30건 전체를 끝까지 처리하고 두 측정이 모두
  담긴 리포트 파일을 산출.

### T8 — README (전시 문서)
- **목표**: 노드/엣지 다이어그램 + 노드별 [LLM]/[코드] 경계 표기, "LangGraph로 짰다면" 비교
  1페이지, 데모 시나리오(기각 순간 첫 화면), 실행 방법, 신뢰성 지표 축 서술.
- **작업 대상**: README.md (+ 다이어그램 자산).
- **행위 계약**: 리드는 "근거 없는 답변을 기각하는 에이전트" — "CS 챗봇" 표현 금지.
  다이어그램은 실제 구현(T6)과 일치해야 한다. PII 게이트 서술은 패턴형 한정임을 명시하고
  비패턴형(이름·주소)은 L2 이월로 적는다 — 과장 금지. 실행 방법에는 검증 게이트의 전제
  (docker compose로 DB 기동)를 포함한다.
- **검증 게이트**: 문서-only — 링크·명령어 실효성 확인(README의 실행 명령이 실제로 동작).

## 공유 쓰기 지침 (프로즈 힌트)

- FastAPI 라우트 등록·패키지 `__init__`·설정 파일 등 공유 등록 지점은 T6이 단독으로 소유한다.
  T3·T4·T5는 자기 모듈 파일만 만들고 공유 등록 파일을 건드리지 않는다.
- pyproject.toml(의존성 선언)과 LLM 클라이언트 래퍼는 T0이 단독으로 소유한다 — 이후 태스크는
  수정하지 말고, 추가 의존성이 필요하면 태스크 노트로 남겨 오케스트레이터가 반영한다.
- 주문번호 형식 정의(정규식·생성 규칙)는 T1이 코드 한 곳에 두고 단독 소유한다 — T6의 접수
  검증은 그 정의를 import해서 쓰고 재정의하지 않는다.

## Execution Graph

```yaml
tasks:
  - id: T0
    depends: []
    risk: MECHANICAL
  - id: T1
    depends: [T0]
    risk: MECHANICAL
  - id: T2
    depends: [T1]
    risk: MECHANICAL
  - id: T3
    depends: [T1, T2]
    risk: RISKY
  - id: T4
    depends: [T0]
    risk: RISKY
  - id: T5
    depends: [T0]
    risk: RISKY
  - id: T6
    depends: [T1, T3, T4, T5]
    risk: RISKY
  - id: T7
    depends: [T1, T2, T6]
    risk: MECHANICAL
  - id: T8
    depends: [T6]
    risk: NONE
regen_barriers: []
```

(웨이브 도출: {T0} → {T1, T4, T5} → {T2} → {T3} → {T6} → {T7, T8}. T2→T1, T3→T2는 산출물 소비
엣지 — T2는 T1의 스키마·DB에 적재하고, T3의 검색은 T2의 적재된 인덱스를 통합 테스트에서
소비한다. T7→T2는 골든셋 문의가 T2의 정책 문서 내용(미끼 조항 포함)을, T7→T1은 합성 주문
데이터(주문번호·필드)를 전제로 작성되기 때문. T4는 초안 생성 프롬프트가 기각 분포를 좌우하는
확률적 핵심이라 RISKY로 상향. regen barrier 없음 — 태스크 산출물에서 재생성되는 코드가 없다.)
