# 사이클 3 플랜 — 검색 품질 (RAG 심화)

이 문서는 **잠정 청사진**이다. spec 과 어긋나면 spec 이 이긴다.
자유롭게 수정할 수 있지만, 수정이 spec 의 행동 계약을 바꾸는 것이라면 사용자 승인이 필요하다.

---

## 단계 서사

1. **재료를 만든다** — 정답 라벨이 없으면 아무것도 잴 수 없다(T1). 라벨이 서면 오프라인
   비교 하네스와 평가 리포트 확장이 **동시에** 갈라진다(T2·T9).
2. **사다리를 세운다** — 벡터 단독 위에 재작성·하이브리드·리랭크를 얹고(T3), 재작성
   질의를 픽스처로 고정하고(T4), 임베딩 축을 붙인다(T5). 셋은 같은 파일을 소유하므로
   **직렬**이다.
3. **잰다** — 격자를 돌려 비교표를 내고 규칙대로 하나를 고른다(T6). 여기서 처음 과금된다.
4. **반영한다** — 이긴 구성만 제품 경로에 배선하고(T7) DB 에 반영한다(T8).
5. **확인한다** — 라이브 3회로 표적 관측과 비악화를 판정한다(T10). 미달이면 원복이다.
6. **기록한다** — 문서·결정·데모 서사를 실제 동작에 맞춘다(T11·T12).

**과금선은 T6 앞에 있다.** T1–T5·T9 는 전부 무과금으로 완주할 수 있어야 한다.

## T1 — 검색 정답 라벨 세트

**목표**: 골든셋 30건 각각에 "정답 조항"을 붙여 검색 품질을 잴 수 있게 한다.

**작업 대상**
- 신규: `data/retrieval_labels.jsonl` (30행)
- 신규: `src/reply_gate/retrieval_labels.py` — 로더와 검증. **비교 하네스(T2)와 평가
  리포트(T9)가 함께 쓰므로 독립 모듈**이다. 어느 한쪽에 넣으면 다른 쪽이 그것을 import
  하며 경계가 무너진다.
- 수정: `CLAUDE.md` · `AGENTS.md` · `docs/standards.md`(하드 게이트의 평가 장치 목록)
  — 세 곳이 같은 목록을 들고 있다. 한 곳만 고치면 문서끼리 어긋난다
- 신규: 테스트

**행동 계약**
- 라벨은 골든셋과 **1:1**이다. 어긋난 ID(양쪽 어느 방향이든)는 로드 시 예외.
- `relevant_evidence_ids` 의 각 항목이 실제 정책 조항으로 존재해야 한다 — 정책 문서를
  파싱해 대조한다. 존재하지 않으면 예외.
- **빈 배열은 유효한 라벨이다.** G21–G24 가 그것이고, 빈 배열을 "라벨 누락"으로 다루면
  이 사이클의 precision 지표가 통째로 사라진다.
- 라벨 초안의 출처는 골든셋 `note` 지만 **정책 문서 원문과 대조해 확정한다.** note 는
  사람이 쓴 메모지 계약이 아니다.

**검증 게이트**: 음성 3종(골든셋에 없는 ID · 라벨에 빠진 ID · 없는 `evidence_id`)이 각각
예외로 죽고, 양성(30건 정상 로드 + 빈 배열 4건 보존)이 통과한다. 파일 diff.
**그리고 30건을 사용자에게 제시해 검수받은 뒤에 이 태스크가 닫힌다**(spec §3-2·§12) —
검수 없이 닫으면 T6 에서 라벨이 바뀌는 순간 격자 전체를 다시 사야 한다.

**함께 갱신할 것**: `src/reply_gate/AGENTS.md` 의 파일별 경계 표에 `retrieval_labels.py`
행을 추가한다. 새 모듈이 소유·금지 없이 들어오면 다음 사람이 경계를 모른다.

**thinking-base**: 라벨을 골든셋 파일 안에 필드로 넣지 않고 **별도 파일**로 뺐다. 골든셋은
"허용 결과 집합"이라는 판정 라벨이고 검색 라벨은 "정답 근거"라는 다른 축이다. 한 파일에
섞으면 골든셋 로더가 두 종류의 라벨 검증을 지게 되고, 검색 라벨이 없어도 측정 2 는 돌아야
한다는 관계가 흐려진다.

## T2 — 오프라인 비교 하네스 골격

**목표**: DB 를 거치지 않고 검색 구성 하나를 30건에 대해 채점하는 하네스를 만든다.
이 태스크는 **벡터 단독**까지만 담는다.

**작업 대상**
- 신규: `src/reply_gate/retrieval_eval.py` — 구성 정의, 채점, 집계
- 신규: `scripts/compare_retrieval.py` — 진입점(얇은 껍데기)
- 수정: `.gitignore` — `reports/retrieval-*.{md,json}` 되살림 + 임베딩 캐시 무시
- 수정: `pyproject.toml` — 하네스가 필요로 하는 의존성이 있으면 여기서 한 번에
- 신규: 테스트

**행동 계약**
- **DB 접속 없음.** 조항 26개는 `policy_index.load_policy_documents` 로, 문의 30건은
  골든셋 로더로 읽는다. 유사도는 인메모리 코사인이다.
- 지표는 **두 벌**이다(spec §4-3): 임계값 무시 recall@1/3/5, 임계값 적용 후
  precision/recall. 둘 다 **문의 단위 계산 후 평균**(macro)이다.
- 정답이 빈 배열인 문의는 **recall 분모에서 빠지고 precision 에는 들어간다.** 한 건이라도
  임계값을 넘으면 그 문의의 precision 은 0 이다.
- **임계값 스윕**: 구성마다 범위를 훑어 최적점을 함께 낸다. 범위·간격은 조정 가능
  기본값(0.10~0.70, 0.05).
- **임베딩 캐시**: (모델, 차원, 텍스트 해시)를 키로 파일 캐시. 정책 문서가 바뀌면 자동
  무효.
- **0-검색 문의의 precision 규약**(spec §4-3)을 그대로 구현한다 — 빈 라벨 + 0건 = 1.0,
  라벨 있음 + 0건 = 평균에서 제외(recall 0 으로 계상). 이 규약이 채택 결과를 뒤집는다.
- 리포트는 `reports/retrieval-<구성>.md` / `.json` 이고 **케이스별 행을 반드시 포함한다** —
  G17 의 정답 조항 순위·유사도, G21–G24 가 컷 위로 문 조항 목록(spec §4-4).
- **이미 존재하는 `retrieval-*` 산출물에 쓰지 않는다** — 이름을 올려 붙인다. 저장소의
  PreToolUse 훅은 스크립트 재실행 경로를 못 잡으므로 하네스가 자기 몫으로 거부한다
  (spec §14).
- `.gitignore` 되살림 패턴은 **확장자별 두 줄**이다. gitignore 는 중괄호 확장을 지원하지
  않는다 — 기존 `evaluation-live-*` 자리의 주석이 정확히 이 사고를 경고하고 있다.
- 대역 임베딩(`testing` 의 어휘 임베딩)으로도 완주해야 한다 — 배관 검증이 무과금이어야
  한다. 대역 수치에는 리포트가 경고를 단다(기존 규율 그대로). **대역은 배관만 검증한다** —
  어휘 임베딩 자체가 문자 n-gram 계열이라 BM25 와 신호가 겹쳐 전략 간 "차이"는 관측되지
  않는다. 대역 결과로 전략을 고르지 마라.

**검증 게이트**: 대역 임베딩으로 완주해 리포트 2종이 생성되고, 지표가 손계산한 소형
픽스처와 일치한다(빈 라벨 케이스 + 0-검색 케이스 포함). 기존 산출물 덮어쓰기 거부가
테스트된다. 파일 diff + 생성된 리포트.

**함께 갱신할 것**: `src/reply_gate/AGENTS.md`(`retrieval_eval.py` 행) ·
`scripts/AGENTS.md`(`compare_retrieval.py` 행 + 이 스크립트의 과금 성격).

**thinking-base**: 인메모리로 간 이유는 spec §4-1 에 있다 — 차원이 다른 벡터를
`vector(1536)` 컬럼에 담을 수 없고, 비교 때문에 볼륨을 재생성하면 보존하기로 한 처리
기록이 실험마다 날아간다. **비교를 DB 로 끌어들이지 마라.**

## T3 — 전략 사다리 3종

**목표**: 질의 재작성 · 하이브리드(BM25+벡터) · LLM 리랭크를 비교 하네스가 구성으로 받아
돌릴 수 있게 만든다.

**작업 대상**
- 수정: `src/reply_gate/retrieval_eval.py` (전략 정의와 조합)
- 신규 가능: 전략 구현 모듈 — 제품 경로가 나중에 같은 구현을 쓰므로 `retrieval_eval.py`
  안에 가두지 말고 재사용 가능한 자리에 둔다
- 신규: 테스트

**행동 계약**
- **각 단은 얹힌다** — 대체가 아니다. 구성은 조합으로 표현된다(예: 벡터+재작성+리랭크).
- **컷을 무엇에 거는지가 구성마다 다르다**(spec §4-3 표): 코사인 / RRF 점수 / 리랭커
  순위 상한. 하네스가 이 셋을 하나의 축으로 뭉뚱그리면 성공 판정 ②가 판정 불가가 된다.
- **질의 재작성**: 원문과 재작성문을 **둘 다** 검색해 합집합. 재작성이 주제를 옮겼을 때
  원문이 안전망이다. 컷은 두 유사도 중 **큰 값**에 건다.
  재작성을 만드는 자리 두 곳((A) 별도 호출 / (B) 의도 해석 호출에 얹기, spec §5-2)은
  **비교 하네스에서는 구분되지 않는다** — 비교 대상은 재작성 문자열의 검색 성능이다.
  자리 선택은 T6 의 채택 판단이고 T7 의 배선 대상이다.
- **BM25**: 파이썬 측에서 조항 전체를 대상으로 계산한다. Postgres 전문 검색을 쓰지
  않는다. 토큰화는 **문자 2-gram 기본값(조정 가능)** — 한국어 조사 때문에 공백 분리가
  잘 맞지 않는다. **코퍼스 출처는 오프라인이 파일, 런타임이 `policy_chunks`** 다
  (spec §5-3). 구현을 한쪽으로 통일해 런타임이 파일을 읽게 만들지 마라 — 이중 진실이
  생긴다.
- **결합은 RRF 기본값**. 상수 하나만 조정 가능 기본값으로 노출한다.
- **LLM 리랭크**: OpenAI 저가 모델(조정 가능 기본값)이 후보를 재정렬한다. 오프라인에서
  같은 입력에 대해 재실행 가능해야 하므로 호출 결과를 캐시한다.
- 어떤 전략도 **정답 라벨을 보지 않는다.** 라벨은 채점자만 본다. (하네스 안에서 둘이
  가까이 있으므로 실수로 새기 쉽다 — 테스트로 못박아라.)

**검증 게이트**: 전략별 단위 테스트(재작성 합집합, BM25 2-gram 점수, RRF 결합 순서,
리랭크 실패 시 원순위 유지) + 대역으로 조합 4종 완주. 파일 diff.

**thinking-base**: 리랭크를 LLM 으로 간 이유는 의존성·키 추가가 0 이라서다. 로컬
크로스인코더는 서빙 경로에 추론 무게를 들이고, 전용 리랭크 API 는 provider 를 늘린다.
**판정 계열 분리 규칙(결정 0004)은 여기 적용되지 않는다** — 리랭크는 판정이 아니라 재료
정렬이다(spec §5-4). 이 판단을 뒤집어 "일관성을 위해" 리랭커를 Anthropic 으로 옮기지 마라.

## T4 — 재작성 질의 픽스처 + 런타임 격리

**목표**: 오프라인 비교의 입력을 확률 층에서 떼어내고, 그 픽스처가 런타임으로 새지
못하게 막는다.

**작업 대상**
- 신규: `data/rewritten_queries.jsonl` (30행 — 1회 생성 후 커밋)
- 수정: `retrieval_eval.py` — 오프라인 경로는 픽스처를 읽는다
- 신규: 구조 테스트 (하드 게이트)
- 수정: `CLAUDE.md` · `AGENTS.md` — 평가 장치 목록에 추가

**행동 계약**
- 오프라인 비교의 재작성 질의는 **커밋된 픽스처**다. 비교표의 입력이 실행마다 흔들리면
  채택 근거가 되지 못한다.
- **로더는 라벨(T1)과 같은 엄격도다**(spec §5-2): 골든셋과 1:1, 키 4개
  (`id`·`original`·`rewritten`·`note`), `original` 이 골든셋 `content` 와 다르면 예외,
  `rewritten` 이 비면 예외(재작성 불필요는 원문과 같은 문자열을 **명시**한다).
- **런타임(파이프라인) 경로는 이 파일에 닿지 않는다.** 실행 경로에서 재작성은 매번 LLM
  이 만든다. 픽스처를 런타임이 읽으면 골든셋 30건 전용 치트가 되고 측정 2 가 무의미해진다.
- **구조 테스트로 못박는다** — 게이트의 LLM import 금지를 AST 로 검사하는 것과 같은
  자격이다. 실행 경로 모듈에서 이 픽스처 경로·로더로 가는 참조가 없음을 검사한다.
- 픽스처는 생성 직후 **사용자 검수 대상**이다(spec §12). 검수 전 값으로 비교를 돌리지
  않는다.

**검증 게이트**: 구조 테스트가 실제로 실패하는 것을 확인한다 — 실행 경로 모듈에 참조를
일부러 넣어 테스트가 빨개지는지 보고 되돌린다. 통과만 확인하면 아무것도 검사하지 않는
테스트를 못 잡는다. 파일 diff.

## T7 — 채택 구성 제품 배선

**목표**: 이긴 구성만 실행 경로에 넣는다.

**작업 대상**: `src/reply_gate/config.py` · `evidence.py` · `policy_index.py` ·
`pipeline.py`(토큰 계열) · `contracts.py`(계약 확장 시) · `api.py`(응답 키) ·
`records.py` + `db/schema.sql`(스키마 확장 시) · `evaluation.py`(실행 조건 필드) ·
**`testing.py`**(대역 조립기 — 아래) · 테스트

**행동 계약**
- **폴백 규칙**(spec §8-1): 런타임 호출 실패는 폴백이다 — 재작성 실패 → 원문 질의,
  리랭크 실패 → 벡터 순위. 인계가 아니다. L2 호출 실패가 인계인 것은 **변함없다.**
- **조용한 폴백 금지**: 폴백은 처리 기록에 남고 평가 리포트에 집계된다. 실패한 호출의
  토큰도 실비용이므로 센다.
- **배선 누락은 조립 시점 오류**다 — 전략 켜짐 + 클라이언트 미배선은 명시적으로 죽는다
  (`PipelineWiringError` 와 같은 자격). 기본값·`None` 이 조용히 전략을 끄지 않는다.
- **토큰 분리**(spec §8-2): 검색 단계 생성 호출의 토큰은 생성·임베딩·판정 어디에도
  합산하지 않는다. **이 확장은 채택 구성이 검색 단계에서 생성 호출을 쓸 때만 한다.**
- **실행 조건에 검색 구성 요약**을 필수 필드로 싣는다(spec §8-3). 리포트 이름 계열은
  늘리지 않는다.
- **재작성을 채택했다면 (A) 별도 호출 / (B) 의도 해석 호출에 얹기 중 T6 이 고른 자리로
  배선한다**(spec §5-2). (B) 를 골랐다면 의도 분류의 구조화 출력 스키마가 넓어진다 —
  그 파싱 실패는 기존 `llm_call_failed` 경로 그대로다.
- **대역 조립기(`testing.build_stub_pipeline`)를 함께 맞춘다.** 새 클라이언트가 파이프라인
  조립에 들어오면 대역 조립이 실제 조립과 어긋나 T2·T3 의 "대역 완주"가 다른 것을 잰다
  ([findings 10](../docs/tracking/findings.md) 이 추적하는 드리프트 면적이 넓어진다).
  **드리프트를 맞추는 것까지가 이 태스크이고, findings 10 의 근본 수정(판정자 주입 구멍)은
  범위 밖이다** — 그건 파이프라인 공개 표면 변경이다.
- 게이트 두 층·답변 계약·근거 ID 체계·SQL 안전장치·재생성 상한·인계 사유·**생성 토큰의
  정의**는 **무변경**이다.

**검증 게이트**: **채택 구성이 검색 단계에서 생성 호출을 쓰는 경우에만** — 해당 폴백이
인계가 아니라 폴백으로 끝나고 기록되는 것, 미배선이 조립에서 죽는 것, 토큰이 계열별로
분리되는 것을 테스트가 확인한다(spec §15-(b)9). 쓰지 않는 구성이 이기면 "해당 없음"이지
미달이 아니다. 어느 경우든 전체 스위트 녹색 + `pytest -m db` skip 0. 파일 diff.

**thinking-base**: 폴백으로 간 근거는 fail-closed 원칙의 **적용 범위**다 — 그 원칙이
지키는 것은 "검증하지 못한 답변을 내보내지 않는다"이고, 검색은 검증이 아니라 재료
수집이다. 재료가 덜 좋아진 것과 검증 없이 내보내는 것은 다르다. **이것을 "일관성"을 이유로
fail-closed(인계)로 바꾸지 마라** — 검색 층의 일시적 실패가 인계를 쏟아내면 제품이
사이클 2 보다 나빠진다.

## T8 — 채택 구성 DB 반영  ⚠️ 상태 변경 · 조건부 과금

**목표**: 채택 구성을 DB 에 실제로 반영하고, 보존하기로 한 처리 기록을 잃지 않는다.

**작업 대상**: 외부 상태(Postgres 볼륨·`policy_chunks`·처리 기록 4테이블) ·
`db/schema.sql`(차원·컬럼 변경 시) · `docs/operations.md`(절차)

**행동 계약**
- **차원이 안 바뀌면**: 재색인만. 볼륨은 그대로 둔다.
- **차원이 바뀌거나 처리 기록 스키마가 넓어지면**(spec §8-4):
  1. **실행 전 사용자 확인을 별도로 받는다.**
  2. 처리 기록 4테이블을 덤프한다 — 컬럼을 명시한 덤프다.
  3. `docker compose down -v` → 재생성 → 시딩 → 재색인.
  4. 복원. 새로 생긴 컬럼은 기본값을 받는다.
  5. **`GET /inquiries/{id}` 로 실제 열어 확인한다.** 건수 대조만으로는 부족하다 —
     복원이 형식만 맞고 내용이 깨진 경우를 못 잡는다.
- 보존 대상은 오탐 버그 시절 기록 1건(findings 4)과 데모용 기각→재생성→통과 기록이다.
  이 세션에서 "그대로 둔다"로 결정된 것이고, 그 결정이 이 절차의 존재 이유다.

**검증 게이트**: 재색인 후 `pytest -m db` skip 0. 볼륨을 재생성했다면 복원된 기록을
API 로 열어 응답을 캡처해 남긴다(외부 상태 작업이므로 파일 diff 가 아니라 캡처가 증거다).

## T10 — 라이브 3회 재실측과 성공 판정  ⚠️ 과금

- 표적 관측(spec §10-2): ① G17 이 `policy:support:4-1` 을 3회 모두 채택 ② G21–G24 12건
  중 10건 이상이 `no_evidence` 인계 + **시도(초안) 0건** + **판정 토큰 0**.
  **"생성 토큰 0"으로 재지 마라** — 의도 해석 호출이 검색보다 먼저 무조건 돌아 수백
  토큰이 남는다. 사이클 2 실측의 G17 이 이미 `no_evidence` 인데 `input_tokens 216` 이다.
- 비악화: 사이클 2 에서 3회 모두 일치한 케이스가 새 실측에서 3회 중 2회 이상 일치.

**검증 게이트**: 라이브 리포트 3종이 생성되고, 판정 근거(케이스별 채택 근거 ID·토큰·

- **`CLAUDE.md`/`AGENTS.md`** 는 T1·T4(평가 장치 목록)와 T11(불변식 개정)이 만진다.
  전부 다른 파도다.
- **`docs/`·`README.md`** 는 T11 → T12 순서로만 만진다.
- **`retrieval_eval.py` 는 T2 → T3 → T4 → T5 로 이어지는 단일 소유다.** 그래서 T4·T5 가
  `depends` 로 직렬화되어 있다 — 파도를 줄이려고 이 간선을 지우면 같은 파일에 병렬
  쓰기가 생긴다.
- **`src/reply_gate/AGENTS.md`** 는 T1(라벨 모듈) → T2(하네스·스크립트) → T3(전략 모듈)
  순서로만 만진다. 셋 다 다른 파도다.
- `evaluation.py` 는 T9(파도 2)와 T7(파도 7)이 만진다. 파도가 갈라져 있어 충돌하지
  않지만, T7 이 실행 조건 필드를 넣을 때 T9 가 넣은 절을 덮어쓰지 않도록 주의한다.

## 실행 그래프

```yaml
tasks:
  - id: T1
    depends: []
    risk: RISKY
  - id: T2
    depends: [T1]
    risk: RISKY
  - id: T3
    depends: [T2]
    risk: RISKY
  - id: T4
    depends: [T3]
    risk: RISKY
  - id: T5
    depends: [T4]
    risk: MECHANICAL
  - id: T6
    depends: [T5]
    risk: MECHANICAL
  - id: T7
    depends: [T6]
    risk: RISKY
  - id: T8
    depends: [T7]
    risk: RISKY
  - id: T9
    depends: [T1]
    risk: RISKY
  - id: T10
    depends: [T8, T9]
    risk: RISKY
  - id: T11
    depends: [T10]
    risk: NONE
  - id: T12
    depends: [T11]
    risk: NONE
regen_barriers: []
```

**파도는 11 개다**: T1 → {T2, T9} → T3 → T4 → T5 → T6 → T7 → T8 → T10 → T11 → T12.
T3·T4·T5 가 직렬인 것은 셋 다 `retrieval_eval.py` 를 쓰기 때문이고, T6 의 `depends` 가
`[T5]` 하나인 것은 T3·T4 가 그 사슬에 이미 들어 있어서다(간선을 늘리면 노이즈다).

**장벽이 비어 있는 이유**: 이 사이클의 유일한 재생성 대상은 DB 상태(재색인·볼륨
재생성)이고, 그것은 T8 이라는 **단일 쓰기 지점**으로 직렬화되어 있다. T10 이 T8 에
의존하므로 순서가 이미 보장된다. 파일을 재생성하는 단계는 없다.
